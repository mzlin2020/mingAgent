# `@xm/storage`

`EventStore` 与 `BlobStore` 端口的落地：**SQLite（WAL）+ 内容寻址的文件 blob**。

端口、七条不变量、以及那 12 条一致性用例都在 [`@xm/kernel`](../kernel/README.md)；
这里只有实现。选型理由（以及为什么不是 PostgreSQL）见 [ADR-0013](../../docs/adr/0013-存储引擎选型与EventStore端口.md)。

## 这个包负责什么

| 模块 | 职责 |
|---|---|
| `src/schema.ts` | 表结构 + 有序迁移 + 版本闸门 |
| `src/sqlite-event-store.ts` | `EventStore` 的 SQLite 实现（单写者租约、同事务投影、分页读） |
| `src/file-blob-store.ts` | `BlobStore` 的文件实现（sha256 寻址、写临时文件→fsync→rename） |
| `src/open-store.ts` | 按 `XmPaths` 打开全部存储。**落盘位置的唯一来源** |

## 不负责什么

- **electron**。原生模块的 ABI 差异由构建期的 `electron-rebuild` 处理，不是靠
  在代码里 import electron 解决（depcruise 强制）。
- 审计库。它是独立文件、记录的也不是 `XmEvent`，是否复用同一端口待定（ADR-0013 遗留）。
- blob 的引用计数与 GC。M2 随 checkpoint 一起做——没有引用计数的删除只会删掉还在用的东西。

## 四条容易被破坏的约束

**一、契约必须在文件库上也跑一遍。**
`tests/sqlite-event-store.test.ts` 跑两个工厂：`:memory:` 与临时文件库。
内存库是**连接私有**的，跨连接的排他标记在它上面根本测不到——只跑内存库等于漏掉不变量四整条。

这不是假设：`PROCESS_HANDLES` 从实例级改成进程级，就是被文件库那一轮当场逼出来的。
在那之前，同一进程里的第二个 store 会把别人的租约当成"自己上次崩溃的残留"接管掉。

**二、`append` 的原子性不能只靠"先校验后写入"。**
校验跑在任何一次插入之前，所以 seq 跳号那条用例即便把 `db.transaction(...)` 整个摘掉
也照样绿——2026-08-05 的反向演练当场演示过。真正需要事务的是**校验通过、插入中途失败**
（投影落后于事件时会发生），`校验通过但插入中途失败 → 整批回滚` 那条用例专门盯它。

摘要更新也必须在同一个事务里（ADR-0013 决策六）：分两次写，崩在中间就会留下
"事件在、会话列表里没有"的会话，用户再也找不到它。

**三、投影推进只用内核的 `applyToSummary()`，不许用 SQL 再写一遍。**
两边各写一遍必然分叉，而分叉的表现是"列表里的标题跟打开后看到的不一样"——
用户会发现、开发者查不出来的那类问题。`rebuildSummaries` 与增量维护走同一个函数，
所以那条等价性用例才是有意义的。

**四、`read()` 用分页，不用游标。**
better-sqlite3 全同步，游标要跨越 `yield` 一直开着，而消费方在两次 `yield` 之间
完全可能往同一个连接上写（UI 一边回放、一边有新事件进来就是这个形状）。
分页把它拆成一串独立的短查询，内存仍然有界，语义完全一样。

## 一条要说清楚的话：租约不是正确性保证

`write_leases` 是一个**早期的、友好的错误**。真正的保证是 `PRIMARY KEY(session_id, seq)`
（不变量三）：即便租约被误判、两个写者同时进来，第二个的插入也会当场冲突，
而不是写出一段错乱的历史。

租约在 PID 复用上有残余竞态，判定因此刻意保守——宁可报"会话被另一进程持有"
让用户看到一个可操作的错误，也不要静默双写。细节见 `#acquireLease` 的注释。

**把租约说成万无一失，比没有租约更危险**：那会让人觉得可以省掉主键。
