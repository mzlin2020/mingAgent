# 05 · 可插拔与扩展体系

> 核心命题：**小明的能力上限，等于它的扩展体系的表达能力**。这一层设计错了，后面所有能力都会被迫走后门。

> **实现状态（2026-08-14）**：M2 已有内建 Provider、内建工具、角色模型引用和可序列化
> `PluginManifest` 最小契约，但还没有插件容器、插件宿主、`@xm/plugin-sdk`、MCP 客户端、
> Skill 加载器或渲染器注册表。**示例 API 不是当前可调用接口。**
>
> 本页现在跨两个里程碑：
>
> - **M3（下一阶段）**交付进程内的插件容器、扩展点、能力接缝与渲染器注册表——
>   也就是本页第 2 节"统一扩展模型"里"注册 / 激活 / 停用"那部分的机制底座。
>   总纲见 [11-微内核与插件容器](./11-微内核与插件容器.md)。
> - **M4** 交付三方生态：插件宿主的隔离方案、MCP 客户端、Skill 加载器、多 Provider 路由。
>   **§2.2 的进程隔离方案属于 M4，尚未决议**（见下）。

## 1. 六类扩展点

| 扩展点 | 解决什么 | 隔离级别 | 谁来写 |
|---|---|---|---|
| **Model Provider** | 接入任意模型服务 | 进程内（受信） | 一方 / 三方 |
| **Tool** | 给 Agent 新动作 | 进程内（一方）/ 进程外（三方） | 一方 / 三方 / **小明自己** |
| **MCP Server** | 接入外部标准工具生态 | 进程外（协议隔离） | 生态 |
| **Plugin / Extension** | 组合式扩展包（工具 + UI + 钩子 + 技能） | 进程外，能力受限 | 三方 / **小明自己** |
| **Executor** | 决定命令跑在哪 | 视实现 | 一方 |
| **Skill 技能** | 纯提示词/流程资产，无代码 | 无（数据） | 用户 / **小明自己** |

**加粗的"小明自己"是长期目标**：Tool、Plugin、Skill 三类要设计成 Agent 可自动生成的产物（见 [07](./07-自我迭代能力.md)）。

## 2. 统一扩展模型

所有扩展都遵循同一套：**清单（Manifest）→ 发现（Discovery）→ 校验（Validation）→ 激活（Activation）→ 注册（Registration）→ 停用（Deactivation）**。

### 2.1 清单格式

```jsonc
{
  "id": "com.xiaoming.git",
  "name": "Git 工具集",
  "version": "1.0.0",
  "engines": { "xiaoming": "^1.0.0" },       // 语义化版本约束
  "contributes": {
    "tools":     ["./dist/tools.js"],
    "providers": [],
    "panels":    [{ "id": "git.diff", "title": "变更", "entry": "./dist/panel.js" }],
    "renderers": [{ "displayKind": "git.diff", "entry": "./dist/render.js" }],
    "skills":    ["./skills/*.md"],
    "commands":  [{ "id": "git.commit", "title": "提交变更" }]
  },
  "capabilities": {                            // ★ 声明式权限，安装时向用户展示
    "fs":      { "read": ["${workspace}/**"], "write": ["${workspace}/**"] },
    "process": { "spawn": ["git"] },           // 只允许 spawn git
    "network": { "hosts": [] },                // 不需要网络
    "secrets": []
  },
  "activation": ["onWorkspaceContains:.git", "onTool:git.*"]   // 懒加载条件
}
```

**设计要点**：

- 能力**最小化且显式**。装插件时用户看到的是"这个插件要读写你的工作区、可以执行 git"，而不是"安装吗？"
- **激活事件**驱动懒加载。装 50 个插件不影响启动时间——这是 VS Code 验证过的模式。
- `contributes` 覆盖代码、UI、提示词三类资产，不给"只能贡献工具"的天花板。

### 2.1.5 能力接缝：三个角色缺一不可（M3 新增）

一个"可插拔单元"不是一个接口，是**三个角色**：

| 角色 | 是什么 | 住在哪 |
|---|---|---|
| **接缝定义** | 接口 + 词汇类型 + 服务 key | `kernel/src/port/` |
| **提供者** | 实现，注册到 `ctx.<key>` | platform / storage / providers / tools-core |
| **消费者** | 通过 `inject` 取用，通常是工具或运行时 | tools-core / runtime |

**只交付一个角色不算接缝完成。** 而且"端口中立性"只有在有第二个实现时才被真正检验过——
ADR-0022 记过这一笔：接第二家 Provider 的第一小时抓到三处绑死 Anthropic 的假设。
详见 [ADR-0054](./adr/0054-能力接缝三角色与执行世界.md)。

上表六类扩展点里，**执行器**在 M3 从一个字符串字段（`executor: 'local' | 'container' | 'remote'`，
今天没有任何代码根据它切换行为）升级为真实接缝 `ctx.executor`，覆盖 fs / process / pty 三类操作。
换一个提供者，文件、命令、终端整片跟着换，不需要改任何一个工具。

### 2.2 插件宿主与能力网关

> ⚠️ **本节的进程隔离方案属于 M4，尚未决议（2026-08-14）。** 参考实现 deepseek-harness
> 的插件就是 npm 包、全部进程内受信；本节承诺的是"一插件一进程 + 能力网关"。
> 两者的取舍（安全边界 vs 实现量与扩展体验）在 M4 与 MCP 隔离一起定案，届时补 ADR。
> **M3 只做进程内容器**，服务对象是一方插件与小明自己生成的插件；本节内容原样保留，
> 不因为参考实现是进程内就先行删掉。

```
主进程 Runtime                        插件进程（一插件一进程）
  ┌──────────────┐                   ┌───────────────────────┐
  │ CapabilityGW │◄──── RPC ────────►│ @xm/plugin-sdk        │
  │ 逐调用鉴权    │                   │  xm.fs.read(...)      │
  │ 路径规范化    │                   │  xm.exec(...)         │
  │ 审计落库      │                   │  xm.registerTool(...) │
  └──────────────┘                   └───────────────────────┘
```

- 插件**没有** Node 的 `fs` / `child_process` / `net` 直通能力（通过 `--experimental-permission` 或独立运行时限制），一切经能力网关
- 网关对每次调用做：清单能力比对 → 路径规范化与逃逸检测（`..`、符号链接、`${workspace}` 展开）→ 策略引擎判定 → 审计
- 插件崩溃/超时/内存超限 → 宿主重启它，并降级为"该插件的工具暂时不可用"，主循环不中断

### 2.3 版本与兼容

- 扩展 API 走 `@xm/plugin-sdk`，**语义化版本**，破坏性变更走主版本号 + 迁移指引
- 宿主同时支持 N 与 N-1 大版本 SDK，给三方留迁移窗口
- 清单 `engines.xiaoming` 不满足则拒绝激活并明确提示

## 3. Model Provider 的可插拔

```ts
// 内置 Provider 与三方 Provider 走完全相同的注册路径
registry.registerProvider({
  id: 'my-llm',
  factory: (config: ProviderConfig) => new MyProvider(config),
  configSchema: z.object({ baseUrl: z.string().url(), apiKeyRef: z.string() }),
});
```

配套要求：

- **模型档案（Model Profile）**与 Provider 解耦：同一个 OpenAI 兼容端点可以配多个模型，各自有独立的上下文长度、价格、能力标记
- **路由策略**：按角色分配模型（主循环用强模型、子 Agent 用快模型、摘要用便宜模型、嵌入用嵌入模型），可按会话覆写
- **降级链**：主模型不可用（限流/超时/欠费）自动降级到备选，事件流里明确告知用户，不静默切换
- **密钥引用**：配置里只存 `apiKeyRef`，真实密钥在钥匙串（对照参考项目把 key 提交进 git 的反面教材）

## 4. MCP 集成

作为一等公民，而非可选功能：

| 维度 | 要求 |
|---|---|
| 传输 | stdio / SSE / streamable-http 全支持 |
| 能力 | tools **和** resources **和** prompts（参考项目只用了 tools） |
| 隔离 | 每个 Server 独立进程；stdio 启动 argv 必须经过命令主张、策略拒绝清单与受限执行器，不存在审批旁路 |
| 生命周期 | 懒连接 + 健康检查 + 断线重连（指数退避）；连接失败不阻塞主循环 |
| 命名 | 工具名加前缀 `mcp__<server>__<tool>` 避免冲突 |
| 安全 | **MCP 返回值默认是不可信输入**，不能依赖三方 Server 自报能力；注册和回传必须闭合 ADR-0033 的污点传播闸门 |
| 可观测 | 每次 MCP 调用记录耗时、成功率，供用户判断某 server 是否值得留着 |

> 参考项目的教训：MCP 客户端的资源清理必须与初始化在同一个异步作用域内（它踩过 anyio task group 的坑）。TS 侧对应的坑是 `AbortSignal` 与 `child_process` 的生命周期——用统一的 `Disposable` 作用域管理，不手工 try/finally。

## 5. Skill：无代码扩展

技能 = 一个 Markdown 文件（frontmatter + 正文），描述"遇到某类任务时怎么做"。

```markdown
---
name: 发版流程
description: 当用户要求发布新版本时使用
triggers: ["发版", "release", "打个 tag"]
tools: ["shell.exec", "fs.read", "git.*"]     # 该技能允许用的工具子集
---

1. 确认 main 分支干净且 CI 全绿
2. 更新 CHANGELOG（从 git log 生成，人工确认后写入）
3. `pnpm version <level>` 并推 tag
...
```

**为什么它重要**：这是小明自我迭代成本最低的一环——不需要写代码或构建，就能沉淀经验；
生效过程仍要可见、可撤销并受工具白名单约束。做对了这一层，L1/L2 级自我迭代基本就通了。

技能的加载策略：**元数据常驻上下文（名称 + 描述，几十 token），正文按需加载**。否则技能一多就把上下文吃光。

## 5.5 特性 → 机制映射（M3 新增）

微内核这个说法要可被检验，判据是：**下面这张表里没有一行需要改主循环。**

| 想做的事 | 挂在哪 |
|---|---|
| 加一个模型 Provider | 注册 `ctx.llm` 提供者 |
| 加一个工具 | `ctx.tools.register()`，schema 自动进提示词，卡片自带 |
| 加一个执行世界（容器 / 远端） | 注册 `ctx.executor` 提供者 |
| 上下文压缩策略 | `turn/pre-step` + `turn/step-error` |
| 写前还原点 | `tool/execute` 环绕 |
| hooks（用户级 / 项目级） | `turn/pre-step`、`tool/pre-execute`、`tool/post-execute`、`turn/stopping` |
| MCP server | 一个 server 一个插件：发现工具 → `ctx.tools.register()` |
| Skill 技能 | 提示词段 + 一个工具；调用时 `inject()` 正文 |
| 记忆 | 提示词段 + 一个工具 + `inject()` 召回 |
| 后台任务 / 定时任务 / 文件变更通知 | 各自的触发源 → `inject()`（忙时）或 `followup()`（空闲且需要行动） |
| 子 Agent 回传 | `inject({ source: { kind: 'subagent' } })` |
| 审计 / 指标 | `tool/result` 只读观察 |
| 插件自有持久状态 | `ext.persisted` 信封 + 自建投影 |

扩展点全表与工具执行的十二步见 [11 §6](./11-微内核与插件容器.md) 与
[ADR-0055](./adr/0055-Turn驱动器的扩展点契约.md)。

## 6. 渲染器扩展

工具用**纯函数投影**声明自己的卡片，由渲染器注册表消费：

```ts
ui.registerRenderer('diff',     DiffRenderer);      // 内置
ui.registerRenderer('terminal', TerminalRenderer);
ui.registerRenderer('diff',     MyGitDiffRenderer); // 插件贡献：已有种类的另一种画法
```

**卡片种类是闭集**（2026-08-14 更正：初稿这里写的是插件可贡献 `git.diff` 这样的新种类，
与 ADR-0058 的"四种卡片是一个闭集、加卡片种类比加工具贵"冲突）。
插件能注册的是这四种的**渲染器**；第五种种类要新 ADR 并同批更新渲染层——
门槛高是有意的，否则卡片种类会随工具数量线性增长，等于换个地方重演"每加一个工具改一处 UI"。

工具侧是两个纯函数加一份落库元数据：

- `presentCall(args)` → 挂起卡片
- `presentResult(args, result)` → 完成卡片
- `presentationMeta(args, value)` → 回放需要的**最小事实**，落在 `tool.end` 上

四种卡片：`generic` / `terminal` / `diff` / `search`。无匹配渲染器时降级为通用卡片 + 一行摘要。
**新增工具不需要改 UI 代码**——这条直接消除了参考项目"加个工具要改三处"的问题。

> **两条硬约束**（[ADR-0058](./adr/0058-工具渲染意图与结果投影.md)）：
> ① 投影函数在实时流与日志回放两条路上都跑，因此**禁 I/O、禁读会话状态、禁时钟随机**——
> 一个会读盘的 `presentCall` 就是第二份会漂移的状态；
> ② 遇到畸形或旧版参数**返回"没有卡片"而不是抛异常**——小明的整个 UI 就是 `reduce(events)`
> 的投影，展示路径崩了等于会话打不开。
>
> 历史注记：契约 `DisplayHint` 从 M0 就在 `contracts/tool/display.ts` 里，
> **零生产者、零消费者**，而真实需求绕过它长出了 `edit-review.ts` 专用通道——
> 这是本仓库第四次"契约写好了、没有任何调用点"。**M3-f 已修掉**：
> `DisplayHint` 连同它在 `PermissionRequest.preview` 上那份同样没人写的副本一起删除，
> `edit-review.ts` 与渲染层的专用组件已物理删除，逐块接受/拒绝改走卡片动作通道。

### 6.1 卡片动作：反方向的那条路

上面三件套**全是只出不进的数据投影**，它们能把 diff 显示出来，但逐块接受/拒绝需要
一条反方向的路。少了它，`edit-review` 专用通道退役不掉——2026-08-14 复审抓到的缺口，
由 [ADR-0065](./adr/0065-卡片动作通道.md) 补上：

```ts
// 工具侧声明具名动作
actions: { accept: { schema: HunkSelection, label: '接受所选' } }

// 渲染层只能引用 actionId，唯一的具名 IPC，不是通用 invoke
ui.cardAction({ callId, actionId: 'accept', payload })
```

卡片数据里**不能出现工具名、路径或任何"要执行什么"的描述**——否则一张模型构造的卡片
就能诱导用户点出一次任意工具调用。主进程由 `callId` 从**已落库的事件流**反查工具，
渲染层说了不算；动作最终转化为一次**新的工具调用**，进完整十二步链。

三条不继承：不复用原调用的判定结果、**不因为"用户点的"就提升 `trustLevel`**
（被接受的内容仍是模型产出的）、不允许跨会话引用 `callId`。
第二条是 [ADR-0045](./adr/0045-M2-e-diff审阅不是权限审批.md)"diff 审阅不是权限审批"
在新通道上的落点：**点了接受不等于批准了写入。**

## 7. 扩展点的红线

1. 扩展**不得**绕过权限闸门直接触碰系统资源
2. 扩展**不得**修改内核状态或事件流（只能追加自己的事件）
3. 扩展的失败**不得**导致主循环中断
4. 扩展**不得**读取其它扩展的密钥或私有存储
5. 一方插件与三方插件走**完全相同**的 API——发现自己需要"内部 API"时，说明公共 API 设计不足，应该补公共 API 而不是开后门
6. **扩展点只能收紧，不能放宽**（M3 新增）。任何监听器都不能把 `deny` 变回 `allow`；
   红线是单调 `guard`，后续监听器**在接口上就拿不到翻案入口**。收紧的表达方式只有一种：
   追加 deny。见 [ADR-0053](./adr/0053-微内核的特权底座与扩展点边界.md)。
7. **六项安全底座不可替换、不可卸载、不可重排**（M3 新增）：`seq` 单点分配、`evaluate()`、
   路径能力网关、`SecretStore`、`redact()`、落库与广播顺序。容器在装配收敛时断言它们在位，
   缺失即拒绝启动。这是与参考实现"没有特权内核"最大的分歧。

> 红线二的具体落法（M3）：插件事件走 `ext.persisted` / `ext.transient` 两个信封，
> `reduce()` 对它们**恒等**——核心 `SessionState` 一个字段都不加，插件自建投影。
> 见 [ADR-0057](./adr/0057-扩展事件通道与未知事件语义.md)。

## 8. 扩展体系的验收测试

| 测试 | 通过标准 | 何时可跑 |
|---|---|---|
| 删掉所有一方插件 | 应用正常启动，工具列表为空，UI 提示"未安装工具" | **M3-b**（改一个 profile 就行；这条从 M0 写下起一直跑不了） |
| 卸载一个插件 | 它注册的工具 / 监听器 / 提示词段全部消失，不留残留 | M3-a |
| 恶意插件试图放行红线 | 单调性检查拦下并记审计 | M3-c |
| 插件冒充基线层服务 | 装配期断言拒绝启动 | M3-b |
| 换 Provider | 只改配置，不改任何代码，会话可继续 | 已可（M1-b 起） |
| 换 Executor | 同一套工具代码，fs / 命令 / 终端整片跟着换 | **M3-e**（用假提供者验收；容器实现在 M5） |
| 新增一个工具（含 UI 卡片） | 不触碰 `turn.ts`、装配层、渲染层任何文件 | ✅ **M3-f 已交付** |
| 装 50 个插件 | 启动时间增量 < 200ms（靠激活事件懒加载） | M4（需要懒激活与真实插件生态） |
| 插件死循环 | 5s 后被宿主终止，主循环不受影响，UI 有明确提示 | M4（需要进程隔离决议） |
| 插件尝试读 `~/.ssh/id_rsa` | 被网关拒绝，审计日志有记录，用户收到告警 | M4（同上） |
