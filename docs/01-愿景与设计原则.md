# 01 · 愿景与设计原则

## 1. 产品定位

小明是**私人通用 Agent 的本地宿主**。它不是聊天客户端，也不是 IDE 插件，而是一个常驻本机、拥有真实执行能力、并随使用不断变强的助手。

三条能力主线：

| 主线 | 含义 | 对标 |
|---|---|---|
| **写代码 / 改代码** | 理解仓库、多文件编辑、跑测试、提交 PR | Claude Code、Codex、OpenHands |
| **操作电脑** | 终端、文件、浏览器、GUI（截图 + 鼠标键盘）、系统应用 | Manus、Computer Use |
| **自我迭代** | 沉淀记忆与技能、自动生成插件、改进自身代码 | 目前无成熟对标，是小明的差异点 |

### 目标用户

单人（本人）+ 未来可能的小团队。**不做多租户 SaaS**——这一条极大简化了鉴权、配额、隔离设计，必须坚持。

### 非目标（明确不做）

- ❌ 云端托管与多租户，不做用户体系与计费
- ❌ 面向大众的"无代码 Agent 编排画布"
- ❌ 自研模型、自研推理引擎
- ❌ 追求跨所有平台（平台分级见 [ADR-0007](./adr/0007-平台支持分级.md)：mac/Windows 为 Tier 1，Linux 为 Tier 2 —— 除计算机操作外全功能，是正式发布产物）
- ❌ 早期不做移动端

## 2. 与参考产品的差异定位

| 产品 | 强项 | 小明的取舍 |
|---|---|---|
| Claude Code | 终端内编码 Agent，上下文管理与工具设计一流 | **借鉴其交互范式与工具粒度**，但要有 GUI 与计算机操作能力 |
| OpenHands | 开源、沙箱执行、可自托管 | 借鉴其运行时隔离，但拒绝其重量级部署 |
| Manus / manusAgent | 通用任务、Planner+Executor、虚拟机可视化 | 借鉴事件驱动 UI 契约，但拒绝其僵化的双 Agent 状态机 |
| Codex / Cursor | 代码理解与编辑体验 | 借鉴多文件编辑与 diff 审阅体验 |
| OpenCode | 插件化、Provider 无关 | **可插拔理念与其一致，且要做得更彻底** |

**小明的独特赌注**：把"能力"做成可被 Agent 自己创作的产物。别人的插件由人写，小明的插件最终由它自己写。

## 3. 七条设计原则

每条原则都配了**可检验的落地约束**——不能被 CI 或代码审查检验的原则等于没有。

### 原则一：内核最小且纯净

Agent 主循环、上下文装配、事件模型、策略判定属于内核；文件、网络、进程、数据库一律不属于。

> **约束**：`packages/kernel` 的 `package.json` 中 `dependencies` 只允许出现 `zod` 一类的纯数据依赖，禁止出现 `node:*`、`electron`、任何 SDK。CI 用 `depcruise` 规则强制。内核的单元测试必须能在无网络、无文件系统的环境下全绿。

### 原则二：一切皆插件（能力层面）

模型、工具、MCP、执行器、技能、UI 面板——六类扩展点，全部走同一套注册/发现/生命周期机制。内置能力也必须用插件机制实现，**不允许内置能力走特权后门**。

> **"能力"与"能力的裁判"是两回事（2026-08-14 澄清）。** 本原则约束的是**能力**：
> 工具、Provider、执行器、技能、UI 面板一律走插件机制，无一例外。而权限判定
> （`evaluate()` 与 27 条红线）、路径能力网关、`SecretStore`、`redact()`、`seq` 单点分配
> **不是能力，它们是判定能力能否运行的裁判**——这六项构成不可替换、不可卸载、不可重排的
> 安全底座，由容器在装配收敛时断言在位，缺失即拒绝启动。见
> [ADR-0053](./adr/0053-微内核的特权底座与扩展点边界.md)。
>
> 这一条与参考实现 deepseek-harness 的"没有特权内核、一切可从配置替换"是**刻意的分歧**，
> 理由是三次真实事故（ADR-0017 / ADR-0018 / ADR-0039）。照着参考实现补代码前先读那份 ADR。

> **约束**：删掉 `packages/tools-core` 后，内核 + UI 必须仍能启动（只是没有工具可用）。这是可以写成集成测试的。
>
> ⚠️ **这条约束从 M0 写下起从未被落实过**——今天删掉 `tools-core`，`services.ts` 根本编译不过。
> 它是 M3「微内核化重构」的总验收第一条（[M3 阶段划分 §4](./M3-阶段划分.md)）。
>
> **它差点被换成一条更容易通过的（2026-08-14 复审抓到）。** M3 初稿把基线行
> `baseline.gateway` 指向 `@xm/tools-core`，于是总验收被写成"删掉全部**业务插件行**后仍能启动"
> ——**删行不等于删包**，那份 profile 之外的 import 一条不少。根因是包切错了：
> 路径网关与写前 checkpoint 是"能力的裁判"，却和工具实现挤在同一个包里。
> [ADR-0063](./adr/0063-安全底座与工具实现的包边界.md) 把它们迁进 `@xm/tool-runtime`，
> 本条约束因此**改回物理删除**：`rm -rf packages/tools-core` + 一份不含工具行的 profile，
> `pnpm typecheck` 与 headless smoke 必须通过。
>
> 记这一笔是因为这类失效最难自查：规则还在，只是检验它的那个测试被换掉了。

### 原则三：契约优先，单一事实来源

事件、工具入参出参、配置、插件清单，全部先有 Schema（Zod），类型从 Schema 推导，前后端共享同一个 `@xm/contracts` 包。

> **约束**：禁止在渲染层手写事件类型或做 `normalizeEvent` 式的手工转换（参考项目的坑）。任何跨进程边界的数据都要经过 Schema 校验，校验失败即抛出并记录，不静默兜底。

### 原则四：默认不信任

模型的输出是**不可信输入**。网页内容、文件内容、MCP 返回值、子 Agent 结果同样不可信（提示词注入的主要入口）。

> **约束**：所有工具入参必须通过 Zod 严格校验（`.strict()`，禁止静默丢弃未知字段）；所有产生副作用的工具必须声明 `capabilities` 与 `risk`，并经过权限闸门（判定只有 `allow`/`deny` 两个答案，[ADR-0039](./adr/0039-放弃审批模式.md)）；任何**绕过 deny 判定**的代码路径都要有 ADR 说明。
>
> 「默认不信任」在没有审批之后靠红线与拒绝清单兑现，不靠提问——原则本身不变，变的是它的实现方式：以前还有一道"问问用户"的缓冲，现在只剩"规则写对了没有"。

### 原则五：流式优先，端到端不阻塞

从模型 token 到 UI 像素，全链路增量。工具执行的中间产物（命令输出、下载进度、截图）也要流式上报。

> **约束**：模型层接口只提供 `stream()`，不提供阻塞式 `invoke()`（需要完整结果时由上层聚合）。UI 首字节延迟目标 < 300ms。

### 原则六：可观测、可回放、可回滚

每一次运行都是一串可持久化的事件；给定事件流应能完整重建会话状态与 UI。

> **约束**：会话状态 = `reduce(events)`，不允许存在只写内存不写事件的状态。带
> `fs.write` / `fs.delete` 主张的工具调用在执行前建立 checkpoint v2 整组 manifest，并把创建、
> 恢复和失败生命周期写入持久事件；当前不声称存在 git stash 型还原点或独立审计数据库。

### 原则七：为自我迭代而设计

代码结构本身要对 Agent 友好：目录职责单一、命名可搜索、每个模块有本地 README、副作用集中。

> **约束**：新增模块必须能用一句话说明职责；单文件超过 400 行、单函数超过 60 行触发审查；每个 `packages/*` 根目录有 `README.md` 说明"这个包负责什么、不负责什么"。

## 4. 质量标线（可量化）

| 维度 | 目标 | 说明 |
|---|---|---|
| 冷启动 | < 1.5s 到可交互 | 插件与索引异步加载，不阻塞首屏 |
| 首 token 延迟 | < 300ms（不含模型侧） | 本地链路开销 |
| 空闲内存 | < 400MB | Electron 基线约 150MB，控制渲染层与索引缓存 |
| 长会话 | 1000+ 轮不劣化 | 事件表增量写入 + 分层上下文压缩 |
| 崩溃恢复 | 进程被杀后重启，运行中任务可恢复或明确失败 | 参考项目做不到，这是硬指标 |
| 核心包测试覆盖 | kernel ≥ 85% | 内核纯逻辑，无理由不测 |

## 5. 命名与身份

- 产品名：**小明 / xiaoming**

- CLI 命令：`xm`

- 项目级配置：仓库内 `.xiaoming/`
