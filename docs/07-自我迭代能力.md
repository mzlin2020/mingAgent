# 07 · 自我迭代能力

> 这是小明与 Claude Code / Manus / OpenHands 的核心区别，也是最容易做成噱头的部分。
> 判定标准只有一条：**用了三个月之后，它是不是明显比第一天更好用**——且这个"更好"可被评测集量化，不是错觉。

## 1. 分级路线

| 级别 | 能力 | 风险 | 何时做 |
|---|---|---|---|
| **L0 记录** | 完整 trace：每次运行的输入、上下文、工具调用、结果、耗时、成本、用户是否满意 | 无 | M1（地基，必须先有） |
| **L1 记忆** | 沉淀用户偏好、项目事实、常用路径，自动召回 | 低 | M2 |
| **L2 技能** | 从成功的运行中提炼可复用的 Skill（Markdown），自动生成、自动改进 | 低 | M3 |
| **L3 工具/插件** | 自主编写、构建、测试、注册新工具与插件 | 中 | M4 |
| **L4 内核** | 修改自身核心代码，走完整 CI + 人工审批 | 高 | M5+ |

**顺序不可跳级**。没有 L0 的数据，L1 以上全是拍脑袋；没有 L2 的评测反馈，L3 的自动生成无法判定好坏。

## 2. 改进闭环

```
     ┌──────────────────────────────────────────────────────┐
     │                                                      │
     ▼                                                      │
  [运行]  用户的真实任务                                      │
     │  产出 trace（L0）                                      │
     ▼                                                      │
  [观测]  失败信号采集                                        │
     │  · 显式：用户打断 / 否决 / 重试 / 负反馈                 │
     │  · 隐式：工具报错率、循环、超预算、超时、上下文溢出        │
     ▼                                                      │
  [诊断]  离线分析（低峰期跑，用便宜模型批处理）                 │
     │  · 归因：提示词问题？工具缺失？工具描述不清？策略太严？     │
     │  · 聚类：把同类失败合并成一个"改进议题"                   │
     ▼                                                      │
  [提案]  生成候选改进                                        │
     │  L1 记忆条目 / L2 技能 / L3 工具 / L4 代码补丁            │
     ▼                                                      │
  [验证]  评测集回归 + A/B                                    │
     │  必须证明：目标指标改善 且 其它指标不劣化                  │
     ▼                                                      │
  [发布]  按级别决定闸门                                       │
        L1/L2 自动生效（可撤销）                               │
        L3 需用户确认                                          │
        L4 需人工审阅完整 diff ──────────────────────────────┘
```

## 3. 三类基础设施（必须先建）

### 3.1 Trace 记录（L0）

每次 Turn 落盘一份完整可回放的记录：

```jsonc
{
  "traceId": "...", "sessionId": "...", "ts": "...",
  "input": { "userMessage": "...", "cwd": "...", "attachments": [] },
  "context": { "systemPromptHash": "...", "skills": [], "memoriesUsed": [], "tokens": 12043 },
  "model": { "provider": "anthropic", "model": "...", "params": {} },
  "steps": [ { "kind": "tool", "name": "fs.read", "input": {}, "ok": true, "ms": 12 } ],
  "outcome": { "stopReason": "end_turn", "turns": 3, "costUsd": 0.043, "wallMs": 18200 },
  "feedback": { "explicit": null, "interrupted": false, "rejectedPermissions": 0, "retried": false }
}
```

要求：**可回放**（同样的输入 + 固定随机种子 + 录制的模型响应 = 同样的执行路径），这是评测与回归的前提。

### 3.2 评测集（Eval Suite）

`evals/` 目录，三类用例：

| 类型 | 内容 | 判定方式 |
|---|---|---|
| **单元级** | 单个工具、单个提示词片段的行为 | 断言式，确定性 |
| **任务级** | 真实任务（"给这个函数加测试并跑通"），带初始工作区快照 | 结果检查（文件状态/命令退出码）+ LLM 评判 |
| **回归级** | 历史上失败过的真实 case，修好后固化 | 同上 |

指标：成功率、平均轮数、平均成本、平均耗时、权限被拒次数、用户打断率。

> **纪律**：每修好一个真实失败，必须往 `evals/regression/` 加一个用例。这是防止小明"改好一个坏掉两个"的唯一手段。

### 3.3 提示词版本化

系统提示词、工具描述、技能，全部纳入版本管理，每个变更关联评测结果。禁止手改线上提示词而不跑评测——**提示词是代码**。

## 4. 各级别的具体做法

### L1 记忆

三种作用域：

| 作用域 | 内容 | 例子 |
|---|---|---|
| 全局（用户） | 长期偏好 | "提交信息用中文"、"不喜欢过度注释" |
| 项目 | 项目事实 | "这个仓库的测试用 vitest，跑 `pnpm test`" |
| 会话 | 临时上下文 | 本次任务的中间结论 |

- **写入**：显式（用户说"记住…"）+ 隐式（从 trace 中提炼，需用户确认后固化，避免记住错误的东西）
- **召回**：按当前意图检索 Top-K，而非全量塞入
- **治理**：可查看、可编辑、可删除的记忆面板；带来源与时间戳；**支持过期与冲突检测**（新旧偏好矛盾时提示用户裁决）

> 风险点：错误的记忆比没有记忆更糟，因为它会持续污染每一次运行。所以记忆必须可见、可删、可追溯来源。

### L2 技能自动生成

触发：某类任务重复出现（trace 聚类）且成功完成。

流程：从成功 trace 中提炼步骤 → 生成 Skill 草稿 → 在评测集上验证（用了技能是否更快/更省/成功率更高）→ 用户确认 → 入库。

技能带**效果统计**：使用次数、成功率、平均节省成本。表现差的技能自动标记待淘汰。

### L3 工具与插件自动生成

这是"自我迭代"最有实感的一级：小明发现自己缺一个工具，就写一个。

```
识别缺口（trace 中反复用 shell 拼凑同一件事）
  → 生成插件脚手架（清单 + 工具实现 + 测试）
  → 在 container 执行器中构建与测试（不污染本机）
  → 生成能力清单，向用户展示"这个工具要什么权限"
  → 用户确认 → 安装到插件目录 → 热加载注册
  → 后续 trace 追踪其实际效果，无用则建议卸载
```

安全约束：自动生成的插件**默认最小权限**，且首次使用时的每个能力都要 ask。

### L4 内核自修改

严格走 [06 文档第 8 节](./06-安全与权限模型.md)的安全闸。工作流：

```
改进议题 → 在 git worktree 开分支
  → 小明实现改动（它读的是本 docs/ 目录，所以文档质量直接决定改动质量）
  → 跑：类型检查 + lint + 架构守护规则 + 单测 + 集成测试 + 完整评测集
  → 生成变更报告：改了什么、为什么、评测指标前后对比、影响面
  → 人工审阅 diff → 批准 → 合并 → 构建新版本 → 重启生效
  → 保留回滚点
```

**红线**（硬编码在策略里，不可通过配置放开）：

- 不得修改 PolicyEngine / CapabilityGateway / 审计模块 而不经二次确认
- 不得删除或弱化任何测试用例来让 CI 变绿
- 不得修改评测集的判定标准来让指标变好（**评测集与被评测者必须分离**，评测集变更单独审阅）
- 不得关闭架构守护规则
- 不得修改自身的红线定义

> 最后一条是关键：**允许自我修改的系统必须有一组它自己改不动的约束**，否则所有安全设计都是自欺欺人。这组约束在代码里以显式清单形式存在，且其修改需要在应用外部（直接改源码 + 重新构建）完成。

## 5. 反脆弱设计

| 风险 | 对策 |
|---|---|
| 越改越差（指标漂移） | 每次改动必须跑全量评测；任一核心指标劣化即拒绝 |
| 局部最优 | 评测集持续加入新的真实任务，防止过拟合到老用例 |
| 记忆污染 | 记忆可见可删；带来源；冲突检测 |
| 技能膨胀 | 技能元数据常驻但正文懒加载；低效技能自动淘汰 |
| 插件泛滥 | 使用率统计，长期未用的建议卸载 |
| 自我迭代喧宾夺主 | 改进任务只在低峰期/空闲时跑，不占用用户交互时的资源与预算；有独立的成本预算上限 |

## 6. 阶段性验收

| 里程碑 | 可验证的标志 |
|---|---|
| L0 达成 | 任意一次历史运行可完整回放，产出相同的执行路径 |
| L1 达成 | 用户说过一次的偏好，一周后仍被正确应用，且能在记忆面板里看到出处 |
| L2 达成 | 至少 3 个自动生成的技能在评测集上证明有正向收益 |
| L3 达成 | 至少 1 个小明自主生成、通过测试并被用户接受的工具在日常使用 |
| L4 达成 | 至少 1 个小明自主提出、实现、通过全量评测并被合并的核心改动 |
