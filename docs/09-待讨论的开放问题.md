> 另外：CLI + Linux Tier 2 组合起来，未来可以把小明跑在服务器上——这条路径现在不用走，但接口不要堵死。

## C. 安全与权限

### ~~C1. 默认严格度？~~ ✅ 已定案 → [ADR-0003](./adr/0003-默认权限策略.md)

平衡档。派生的硬性要求：还原点无条件建立（成为关键路径，需独立完整性测试）；红线不受档位影响；注入降级只作用于不可撤销的能力子集。

### C2. 本地执行是否强制沙箱？ 🟡 部分定案

- 强制 sandbox-exec / Job Object 会带来兼容性问题（某些工具链在沙箱内行为异常）。
- **倾向**：默认不强制（依赖策略闸门 + 还原点），但提供"沙箱模式"开关，且执行来源不明的代码时**自动**切到容器执行器。
- **2026-08-07 进度**：`shell.exec` 落地时（[ADR-0026](./adr/0026-命令的主张分解与argv契约.md)）把
  "默认不强制"这一半坐实为几条具体、可测的进程级约束——env 白名单（不是黑名单）、
  stdin 接 `/dev/null`、超时 + 按进程组 kill、输出上限。**"沙箱模式"开关与
  "不可信来源代码自动切容器执行器"两样倾向里写的东西仍未实现**，C2 因此还不能
  整体转 ✅。真正的隔离仍然靠策略闸门（命令拆出的主张撞路径 / 主机红线）兜底，
  不是进程沙箱。

### ~~C3. 提示词注入的权限降级机制会不会太吵？~~ ✅ 随 C1 定案，**2026-08-10 补充修正** → [ADR-0034](./adr/0034-知情授权穿透注入降级.md)

只针对不可撤销的能力子集：网络外发、文件删除、`git push`、GUI 输入注入。全局收紧会误触发到被用户关掉，等于不存在。

**2026-08-10 修正**：上面这个答案不完整，而缺的那一半在真实体验里当场暴露——用户让小明联网搜索，每个网址都要授权一次，开到「帮我批准」/「完全访问权限」也照问不误。

原因不是"降级范围太宽"，而是 **`net.fetch` 同时是污点源和降级对象——它自己污染自己**：第一次 `web.fetch` 就置上 `untrustedContext`（粘性），此后每一次 fetch 都被降级打回。而降级排在 `evaluate()` 最后一步，也就排在 YOLO 之后、**所有层之后**，于是连用户当场点的「本会话都允许」也一并被压掉——同一个域名、同一个能力、同一个污染源，被反复问到用户不再看内容为止。

限定"只作用于不可撤销子集"防的是**跨能力的误伤**（读个网页就不能写文件了），它防不了**同一个能力在自己造成的污染下被无限重复询问**。ADR-0034 补上后者：满足「session 层 + 带具体 target + 授权晚于污染」三个条件的 allow 穿透降级。仍未解决的是"一次搜索仍然是每个新域名一个框"（根因是没有 `web.search` 工具），见 ADR-0034 的后果一节。

### ~~C4. `PermissionRequest.target` 是一个字符串，够用吗？~~ ✅ 已定案（2026-08-05）→ [ADR-0020](./adr/0020-非路径target的规范化契约.md)

**结论：每个能力恰好一种 target 语义（`path` / `host` / `command` / `opaque`），穷尽映射，没有契约的那一种失败关闭。**

- `host`（`net.fetch` / `browser.control`）完整落地：大小写、默认端口、FQDN 尾点、userinfo 归一；数字进制 IP、百分号编码、非 ASCII、非 http(s) 一律拒绝。
- `command`（`shell.exec` / `process.spawn`）**契约已于 2026-08-07 落地** → [ADR-0026](./adr/0026-命令的主张分解与argv契约.md)：结构化 `{ argv, cwd }` 归一到规范形式，但归一本身不是防线；真正拦截靠把命令拆成一组「能力 + 目标」的主张，交给已有的路径 / 主机规则去判（不是"执行器沙箱"，C2 那句话被修正——见 C2 的 2026-08-07 进度）。含 `$(...)` / 反引号 / `$VAR` / 通配符等展开结果依赖运行时环境的构造一律判不了直接拒，不降级 ask。红线仍不许建立在命令 target 上，普通规则（会话授权、判不了的 bin 的默认 deny）现在可以。
- `opaque` 明确**不是安全边界**，红线不得建立在它上面（构造期断言）。

原倾向里那句"不要试图用 glob 匹配命令行"被完整采纳，并且比原计划更进一步：不是"匹配得弱一点"，而是**在契约落地之前一条也不许写**——顶着的那个 glob 会让所有人以为这里已经防住了。

### ~~C5. YOLO 是否应该越过**用户自己写的** deny 规则？~~ ✅ 已定案（2026-08-05）→ [ADR-0017](./adr/0017-地基复审二-注入防御与红线能力错位.md)

**结论：不越过。YOLO 只跳过 `ask`，不跳过任何 `deny`。**

拍板前实测确认了问题确实存在：用户写 `deny fs.delete /home/ming/work/prod/**`，balanced 档 DENY、yolo 档 ALLOW（`ruleId` 变成 `builtin.tier-fallback`）。

理由按原倾向：用户写下一条 deny 是**长期意图**，开 YOLO 是**"这一小时别烦我"**——前者省的是确认框，后者删掉的是用户唯一能表达"这里绝对不行"的手段。而且它恰好在最危险的时候失效，因为开 YOLO 正是为了放手让它长时间自己跑。

实现是把 `engine.ts` 里 YOLO 分支挪到普通 deny 之后（求值顺序改为 `红线 → deny → YOLO → ask → allow → 档位兜底`）。docs/06 §3 "YOLO = 全 allow，只有绝对红线不受影响"的措辞需要同步改成"只有 deny 不受影响"。

### C6. 桌面端如何降噪：「替我审批」与「完全访问权限」两种模式 🟢「替我审批」已落地（2026-08-07 提出，2026-08-08 部分定案 → [ADR-0030](./adr/0030-桌面端三档审批模式.md)）

**来源**：用户真实体验反馈——用小明做一个"写个 todolist"这么朴素的任务，
中途弹出的确认框超过 8 次，用户全程只在点"允许"。M1-c 的审批 UI（本次 /
本会话 / 永久 / 拒绝）解决的是"每一条主张要不要问"，没有解决"这一整段
时间我根本不想被问"——两者是不同层面的问题，前者按*目标*降噪
（同一个文件第二次不再问），后者要按*时间窗口*降噪（接下来这一段随便跑）。

用户提的诉求是两种模式，字面意思不完全等价，需要在设计时把它们拆清楚：

1. **「替我审批」**——听起来是"这一段时间的 `ask` 我都替你点允许"。这与
   已经存在、但从未在桌面 UI 上暴露过的 `PermissionTier.yolo` 高度重合：
   `engine.ts` 的 YOLO 语义是"跳过 `ask`，不跳过任何 `deny`"（C5 定案，
   红线与用户自己写的 deny 规则原样生效）。如果这就是用户想要的东西，
   缺的只是**桌面端一个能切换它的开关**——目前 `tier` 只能在 `config.json`
   里手改，改完还要重启会话，普通用户不会去碰配置文件。开关放在哪个
   范围（单次回合 / 整个会话 / 全局默认）是这里要定的第一件事。

2. **「完全访问权限（允许任何操作）」**——字面意思比 YOLO 更进一步：
   **允许任何操作**，那就不只是跳过 `ask`，是把 `deny` 也跳过去。这与
   本项目从 ADR-0003 起就有的地基性质直接冲突——C1 定案写的是
   **"红线不受档位影响"**，`engine.ts` 里红线在所有档位、所有层之前
   全局最先判，没有任何一条分支能绕开它。如果真要做一个字面意义上
   "允许任何操作"的模式，等于要新开一个凌驾于红线之上的层级，这不是
   在现有 `PermissionTier` 上加一档就能实现的，而是要重新回答
   "红线还是不是红线"这个已经定案过的问题——**这一步不该被一个 UI
   开关的命名顺带做掉，需要单独拍板**，包括但不限于：
     - 这个模式是否连 `red.fs-delete-home-root` / `red.self-modify-*`
       这类红线也放行？如果放行，"红线"这个词在文档里就名不副实了；
       如果不放行，那它本质上还是 YOLO，只是文案上写成了"完全"，
       需要在 UI 文案上讲清楚"完全"指的是"不再确认"而不是"没有底线"，
       避免用户以为开了这个开关就真的没有任何保护。
     - 即使真的要做一个能越过红线的档位，至少要有比"点一下按钮"更高的
       操作成本（例如要求先手改配置文件、或者要有比普通确认框更醒目的
       二次警告），否则和"这个应用没有权限模型"没有实质区别。

**倾向（未定案）**：先做「替我审批」——把已经落地、已经过 C5/ADR-0017
验证过安全语义的 YOLO 档暴露成桌面端的一个开关（大概率是会话级，跟着
`SessionState` 走，不动全局 `config.json`），这一步风险可控、实现量也小。
「完全访问权限」按上面列的问题单独讨论，不与前者同批做，避免"顺手就把
红线绕过去了"这种事在一次不起眼的 UI 需求里发生。

**2026-08-08 部分定案 → [ADR-0030](./adr/0030-桌面端三档审批模式.md)**：
「替我审批」按倾向落地，桌面端新增会话级、不持久化的 `ApprovalMode` 三档
UI（请求批准/帮我批准/完全访问权限），`帮我批准` 就是暴露出来的 YOLO 档
（用户确认过要放开到连 `shell.exec` 也不再问）。**「完全访问权限」没有
按字面意思实现**——它与「帮我批准」复用同一套判定机制（都映射到 `yolo`，
不新增、不修改 `PermissionTier`，不碰 `evaluate()`），区别只在桌面 UI 的
开启门槛（需要二次确认）与文案。上面列的两个问题——"是否连红线也放行"、
"需不需要比点按钮更高的操作成本"——**仍未解决**：本轮的答案是"不放行"，
第二个问题靠一次内联二次确认部分满足，但都是刻意搁置而不是拍板，留给
将来要做"字面意义上、真的能越过红线"的模式时单独开 ADR。

**2026-08-10 第二个真实实例 → [ADR-0034](./adr/0034-知情授权穿透注入降级.md)**：
用户开着「帮我批准」/「完全访问权限」联网搜索，每个网址仍被要一次授权。
这次的噪音**不是 ADR-0030 没做完**，而是判定顺序上的一个洞：注入降级排在
`evaluate()` 第 5 步，YOLO 在第 4 步——两档审批模式都映射到 `yolo`，
于是第 4 步刚把 `ask` 变成 `allow`，第 5 步又变回 `ask`，
**按设计就穿不过去**。同一个原因让会话授权层与用户配置层的 allow 一并失效。

这条记录在这里是因为它说明 C6 那句"按*目标*降噪 vs 按*时间窗口*降噪是两个
不同层面的问题"还漏了第三个层面：**两种降噪手段之间会互相抵消**。
ADR-0030 做的是时间窗口降噪，M1-c 做的是目标降噪，而注入降级把两者同时压掉了，
三者各自都对，合起来是"什么都没降"。

**2026-08-10 第三个真实实例 → [ADR-0035](./adr/0035-注入降级感知审批档位.md)
+ [ADR-0036](./adr/0036-只检查的主张.md)**：同一天，ADR-0034 落地之后用户再次反馈
「搜一个今日新闻点了 10+ 次允许」。ADR-0034 消掉的是"**同一个**域名被反复问"，
而一次搜索里**每个域名都是新的**——一条都不在它的覆盖范围内，它自己的「后果」段
就写着这条残留，只是当时没意识到那等于"用户的症状一点没变"。

**教训（值得单独记）：修完一个降噪问题，要按用户的原始场景数一遍框，
不要按"我修掉的那条路径"数。** ADR-0034 的端到端用例断言的是"3 条降到 1 条"，
而用户的场景是 11 个不同域名——用例绿了，症状还在。ADR-0035 的用例因此
直接照抄用户那句话：SERP + 5 个各不相同的域名，断言 `permission.request` **为 0**。

同一次测量还查出第二个乘数（ADR-0036）：网关为 SSRF 判定产出的"解析出的 IP"主张
也命中了 `def.net-fetch` 的 ask，于是**每次联网本来就弹两个框**。
两个乘数相乘才凑出"10+ 次"——这也说明第三个层面还得再补一句：
**噪音是会相乘的，只修掉其中一个因子，用户感觉不到差别。**

### C7. `shell.session`（PTY）落地前必须先拍板的六个开放问题 🟢 已定案（2026-08-08 提出 → 同日 [ADR-0031](./adr/0031-shell-session-pty.md) 定案并落地最小可用版本）

**来源**：M1-d 剩余交付项排优先级时的探查——`web.fetch` 的 IP 级 SSRF 判定
（[ADR-0028](./adr/0028-web.fetch的IP级SSRF判定与DNS重绑定防护.md)）与多模态图片
（设计已存档于 [docs/08 M1-d](./08-路线图与里程碑.md)）都不碰权限判定循环与工具
执行生命周期这两处核心机制，可以照既有模式直接落地；PTY 不一样——它会正面改动
这两处刚刚才稳定下来的机制，直接写代码大概率会做出一条绕开现有不变量的旁路
（本项目历史上"规则存在 ≠ 规则生效"反复出现的形状，只是这次会变种成"架构不变量
存在，但 PTY 这条路径没有被它约束"）。以下六项必须先在一份专门的 ADR 里定案，
不是实现细节可以边写边改的那种问题：

1. **工具执行生命周期要不要引入"跨 turn 常驻会话"这个新抽象，长什么样。**
   现状：`ToolContext` 由 `dispatchCall` 每次调用现造，工具执行绑死在一次
   `dispatchCall`→`executeCall` 内（`turn.ts`）。PTY 会话本质是"打开一次、跨越
   多个 turn 持续存在、被后续多次调用共享同一句柄"的对象，现有抽象里没有这种
   模式。要定：会话句柄放在哪一层持有（`SessionRuntime`？`ToolRegistry`？一个新的
   `SessionManager` 端口？）；打开/写入/读取输出/关闭是拆成四个工具还是一个工具
   带 `action` 字段（直接决定权限判定挂在哪个粒度上）；会话数量上限、空闲超时、
   异常退出时事件流该记成什么。

2. **命令级判权 vs 会话级判权——PTY 里到底判什么。**
   `command-claims.ts` 的 `analyzeArgv()` 假设"一次调用 = 一条完整命令行"，是
   无状态纯函数。PTY 场景是用户/模型往一个已经打开的 shell 里逐字符/逐行敲，
   "这一批字节构成了一条完整命令"本身就很难界定（可能没敲完就等一会儿、或者一次
   粘贴进去三条用分号分隔的命令）。要定：打开会话时做一次粗粒度 ask（此后不再
   逐条判权，靠回显+能随时中断兜底），还是坚持每条完整命令重新走一遍
   `analyzeArgv`+claim+policy（如果坚持，怎么从连续字节流里可靠切出"一条命令"是
   一个 shell 语义问题，不是简单字符串处理能解决的）——两个选项的安全含义完全
   不同，必须先定，不能写代码时临时决定。

3. **`SessionState.pendingPermission` 从单槽改队列的具体设计。**
   现状是单槽（`PermissionRequest | undefined`），上一轮"多 claim 排队 bug"
   （见 [ADR-0026 补记](./adr/0026-命令的主张分解与argv契约.md)）的修法前提是
   "一次 `dispatchCall` 内的多个 claim 是提前算好、按顺序遍历的有限集合，
   `turn.ts` 完全掌控发问节奏，任意时刻只有一个在等答案"。PTY 场景可能出现真正
   并发的多个 ask（比如同时有两个 PTY 会话都在等审批），这个前提不成立。要定：
   `pendingPermission` 改成 `Map<requestId, PermissionRequest>` 还是队列，
   `reduce.ts` 怎么处理"新请求到达时上一个还没答完"；桌面端 `PermissionCard`
   只渲染一张卡片，改成渲染多张后 UI 上"先答哪个"要不要有顺序保证；
   `store.ts` 的 `respondPermission` 按 requestId 匹配的逻辑大概率不用改，但要
   在 ADR 里明确写清楚"为什么不用改"，避免有人顺手又加一层不必要的匹配逻辑。

4. **`node-pty` 的 N-API 现状要先核实清楚，不是假设。**
   [ADR-0016](./adr/0016-原生模块与打包.md) 明确点名 `node-pty` 是"两轨 ABI
   问题会复活"的触发条件——现役唯一原生依赖 `better-sqlite3` 是纯 N-API、随包发
   prebuild，`electron-builder.yml` 配了 `npmRebuild: false`。`node-pty` 历史上
   是否已经全面 N-API 化，要实际去查它当前发布版本的 binding.gyp/prebuild 策略，
   不能凭印象往下走。要定：如果仍不是纯 N-API，是恢复 `electron-rebuild`（连带
   新增校验产出 `.node` 文件的 CI 检查），还是找替代实现，还是先只支持类 Unix、
   Windows 上暂不做；打包三平台的风险清单（`asarUnpack`/`files`/交叉编译）要不要
   重新过一遍。

5. **终端输出的 IPC 推流方式——要不要换掉现有的 `EventBus`→`webContents.send`。**
   [ADR-0015](./adr/0015-进程与IPC边界.md) 明写现有 IPC 推流"没有背压"，且把
   "实时终端输出"列为需要重新评估、可能要换 MessagePort 直连的场景。终端输出的
   密度（用户在里面跑一个日志密集的命令，或者 `top`/`vim` 这类全屏刷新的程序）
   远超目前唯一验证过的场景（`message.delta` 的 token 级流）。要定：继续复用
   现有机制（意味着接受某种程度的丢帧/延迟风险，需要明确能接受到什么程度），
   还是引入 MessagePort（意味着这次范围要连带做 ADR-0015 遗留的这块重新评估，
   工作量会超出"只做 PTY"）——这个决定必须先做，它决定 PTY 的实现要不要顺带动
   IPC 基础设施这条更底层的路。

6. **UI 侧的终端渲染选型。**
   现状零 xterm.js 依赖、零 ANSI 处理、无持续追加型 console 组件；唯一可复用的是
   `App.tsx` 里的 `stickToBottom` 自动滚动逻辑。这项不算必须先拍板才能动工的架构
   决策（选型基本没有别的合理选项），但要在 ADR 里至少写一句选型结论 + 大致的
   组件边界（终端视图是不是要走 IPC 之外的直接渲染路径），避免和问题 5 的推流
   方式决策脱节。

**2026-08-08 定案 → [ADR-0031](./adr/0031-shell-session-pty.md)**：六项逐一定案，
核心结论——四个独立工具（open/write/resize/close），`PtySessionManager` 全应用
共享一份、按 xm 会话分区（与 C6 的 `ApprovalModeStore` 同一形状）；**打开会话时
问一次、之后完全不再判权**（`write`/`resize`/`close` 声明空能力集，不是"依赖
用户选 session 作用域"）——代价是红线/deny 对会话内容零覆盖，这一点比 C6 的
"帮我批准"更彻底（那里红线仍逐条判，这里从一开始就没有 claim），必须在 ask
文案里讲清楚；`pendingPermission` 不用改队列（实测 `dispatchCall` 目前是顺序
执行，不产生并发 ask）；`node-pty` 已核实是纯 N-API、自带 prebuild（但只覆盖
Windows/macOS，Linux 需要本地编译），在本项目钉住的 Electron 43 上实测通过；
IPC 复用现有 `EventBus` 推流，新增的三个事件类型不需要任何新 IPC 代码；UI
选型 `@xterm/xterm`，`TerminalPanel` 是写死组件、v1 只读（人不能直接在里面
打字）。已实现并测试，非本轮范围的邻近问题（Windows/macOS 未验证、
`EventBus` 无背压、通用面板注册表未实现、人类接管输入未做）记在 ADR-0031
的"遗留"一节，**逐条转成本文档 C8 的完善计划**，推到后续阶段再排期。

## D. 数据与存储

### D1. 会话数据是否加密？ 🟡

- 会话里会有代码、路径、可能的敏感信息。
- **倾向**：SQLite 默认不加密（性能与可调试性），但提供可选的 SQLCipher；审计库与密钥始终受 OS 级保护。
- **M0-b 现状（2026-08-05）**：不加密。库落在平台数据目录（ADR-0014），依赖 OS 的文件权限。SQLCipher 会把 better-sqlite3 换成一个需要自行编译的分支——那会推翻 ADR-0016 刚确认的「N-API 预编译产物，Electron 升级不需要重编」这个便宜。真要做时这笔账要重算。

### D2. 是否做多设备同步？ 🟢 延后

- **倾向：M6 之后再考虑**。同步会引入冲突解决、端到端加密、云依赖，与"零外部依赖"原则冲突。

### D3. 索引策略？ 🟡

- 全仓库预索引（启动慢、内存高、始终新鲜）vs 按需索引（启动快、首次查询慢）
- **倾向**：按需 + 后台增量（打开工作区后台建索引，未建完时降级为 ripgrep 直搜）

## G. 地基复审二（2026-08-05）开出的问题

来源：[ADR-0017](./adr/0017-地基复审二-注入防御与红线能力错位.md)。前三条是那次复审**修完之后剩下的缺口**，后两条是实测出的规模问题。

**2026-08-05 进度**：G1 / G3 / G6 是 M1-a 的三个前置，已全部做完（ADR-0019 / 0020 / 0021）。剩下 G2 升为 🔴——G1 落地之后，它是注入防御上**唯一**剩下的绕过路径。

**2026-08-09 进度**：G4 / G5 提前在 M1-d.5 修完（不是原计划的 M2），见下方两条与 [ADR-0032](./adr/0032-地基复审三-M1收尾前的原则符合度审查.md)——地基复审三发现它们早就实测过却从未排进优先级表，直接证伪了 docs/01 的质量标线，因此没有再等到 M2。

### ~~G1. 不可信标记的解除入口~~ ✅ 已做（2026-08-05）→ [ADR-0019](./adr/0019-不可信标记的解除入口.md)

新增持久化事件 `trust.cleared` + `SessionRuntime.clearUntrusted()` + 渲染层常驻横幅。

三条定下来的：解除是**事件**不是内存标志；作用域是**到下一次引入外部内容为止**（`reduce` 置回 `undefined`，下一次 `tool.start` 会被 `taintOf()` 重新标上，不需要额外机制）；**只有人能按**——`ToolContext` 里没有任何记录事件的入口，工具在结构上够不着，且有用例盯着防止将来"顺手"给它加一个 `record`。

原倾向里的作用域判断被采纳。额外发现的一点写进了 ADR：解除入口自带社工面（模型可以在回复里写"请点上面那个按钮"），所以横幅必须复述事件流里的事实——哪个工具、哪个能力、什么时候。

### G2. MCP 工具与子 Agent 的污点传播 🟡 **闸门已落地（2026-08-09 → ADR-0033），实现仍随载体走（M2/M3）**

现在的污点判定读的是 `tool.start` 事件里的 `capabilities`，因此覆盖不了两条路：

- **MCP 工具**若不如实声明 `net.fetch`，它拉回来的外部内容就标不出来。而 MCP server 是第三方的。
- **子 Agent** 的不可信标记不会传染回父会话——子会话有独立的 `sessionId` 与独立的事件流（ADR-0008 决策四），父会话 reduce 不到它的 `tool.start`。

第二条更要紧：把"读网页"派给子 Agent 做，正好是当前设计下绕过注入防御的完整路径。

- **倾向**：MCP 工具一律**默认**按不可信内容源处理（宁可误标，不可漏标）；子 Agent 在 `subagent.end` 时把子会话的污点并回父会话。
- **2026-08-05 更新**：G1 落地之后，**这是注入防御上唯一剩下的绕过路径**。优先级从 🟡 升到 🔴。
- **2026-08-06 更新——它挡的比原先写的更早。** 路线图原话是"接 MCP 前必须做"，
  但**子 Agent 是 M2 的交付项**（M3 才是 MCP）。把"读网页"派给子 Agent，正是当前设计下
  完整的绕过路径，所以 G2 的真实位置是 **M2 之前**。
- **落地方式（2026-08-06 定）**：M1 既没有 MCP 也没有子 Agent，**没有载体就无法在真实输入下
  验证**。此时写实现，等于再造一个"测试全绿、真实输入下从未跑过"的东西——`trustLevel` 硬编码
  （ADR-0017）与 8.3 短名（ADR-0018）两次翻车都是这个形状。

### ~~G4. 会话回放是超线性的，且 `messages` 无上界~~ ✅ 已于 2026-08-09 修复 → [ADR-0032](./adr/0032-地基复审三-M1收尾前的原则符合度审查.md) #1

`reduce` 每条 `message.end` 都做 `messages: [...state.messages, m]`，即每条消息一次全量数组拷贝。实测（16k 条 `message.end`）：

| 事件数 | 回放耗时 | N 翻倍后的倍率 |
|---|---|---|
| 1 000 | 11.6 ms | — |
| 4 000 | 69.1 ms | ×3.79 |
| 8 000 | 110.6 ms | ×1.60 |
| 16 000 | **1121.2 ms** | ×10.14 |

打开一个用了几个月的会话要卡一秒以上，而且 `state.messages` **永不收缩**——`context.compacted` 在 reduce 里只记标记，压缩替换是 ContextBuilder 装配时做的事。对一个"长期演进"的 Agent，这是最先撞到的墙。

**2026-08-09 已修复**：`EventStore` 端口新增 `readSnapshot`/`writeSnapshot`（不变量八：纯派生、可选加速手段），`SessionRuntime` 每 500 条持久事件存一份快照，命中快照时只补读尾部。本地基准复现同一测法：n=16000 从 1077ms 降到 0.4ms（2801×），n=50000 从 22337ms 降到 1.6ms（13695×）。测试：`packages/kernel/tests/snapshot.test.ts`（往返正确性）、`packages/runtime/tests/session-runtime.test.ts`（快照触发/命中尾部回放/写失败防重入）、`packages/kernel/src/port/event-store-contract.ts`（三条端口契约用例）。回归用例固化在 `evals/regression/g4-session-replay-superlinear.json`。

### ~~G5. `readSession` 在 IPC 边界把流式读取全量物化了~~ ✅ 已于 2026-08-09 修复 → [ADR-0032](./adr/0032-地基复审三-M1收尾前的原则符合度审查.md) #1

`SqliteEventStore.read()` 特意做了 500 条一页的分页，注释写着"绝不 `all()`：一次性物化会在打开会话时占掉几十 MB 并阻塞主进程"。但 `apps/desktop/src/main/ipc.ts` 的 `readSession` 处理器是：

```ts
const out = [];
for await (const e of ...read(...)) out.push(e);
return out;          // ← 整个数组一次性过 IPC
```

存储层的克制在边界上被完整抵消。实测 5 万条事件：堆增长 41.9 MB，`structuredClone` 一次 685.6 ms（Electron 的 IPC 编码同源）——主进程和渲染进程各卡一次。

**2026-08-09 已修复**：与 G4 同一次解决，但比原来设想的"快照 + 尾部事件"更进一步——`readSession` 现在直接返回主进程已经 `reduce()` 过的当前状态（`getSessionState()`），渲染层不再自己重放任何历史事件，只对后续的实时事件继续增量 `reduce()`（ADR-0015"内核能在浏览器里跑"这条价值在这部分不受影响）。本地基准：n=50000 的"IPC 物化+渲染层归约"总耗时从 22889ms 降到 227ms（100.9×）。移除了从未被消费过的 `ReadSessionRequest.fromSeq` 字段。

### ~~G6. 两条各自正确的约束合起来，让流式输出渲染不出来~~ ✅ 已做（2026-08-05）→ [ADR-0021](./adr/0021-流式渲染与第二份状态的边界.md)

原倾向（与 `SessionState` 分离的 live buffer）被采纳，并补上了它最需要的那一半：**一条可执行的判据**——*任何时刻，同一段文字要么在 buffer 里，要么在 `state.messages` 里，不会同时在两边*。归零时机（`message.end` / `message.interrupted` / `turn.end` / 新 `message.start`）是全部要害。

实现放在 `packages/kernel/src/state/live-buffer.ts`（纯函数），不是渲染层——CLI（M3）要渲染同一件事，两份实现的归零时机会分叉。

~~**遗留**：停止按钮还没有；`tool.progress` 同样是瞬态事件，"工具正在跑第几步"目前也显示不出来。~~
✅ 两项都已补上：停止按钮在 M1-b（[ADR-0022](./adr/0022-Provider传输层与密钥归宿.md)），
`tool.progress` 在 M1-c 按同一套判据扩展了 `LiveBuffer`。值得记一笔的是两者**满足判据的方式不同**：
delta 的文字最终会原样进 `message.end`，所以它是"先在 buffer、后在 state"；
而 progress 的内容**永远不会进 state**（持久流里对应的是 `tool.end` 的结果），
所以它的判据是"随 `tool.end` 消失"，不是"被取代"。照抄上一半的归零时机会把它挂在
`message.end` 上——那样进度会在模型说完话的那一刻消失，而工具那时才刚开始跑。
