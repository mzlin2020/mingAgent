# M3.5-f 收官记录 · 上下文占用环

- **日期**：2026-08-16
- **范围**：`ContextBuilder` 组装完请求后产出占用投影；发送键旁 14px 环；
  占用不是事件
- **决策**：无新 ADR。壳在 [ADR-0074](../../adr/0074-桌面端两栏让位链与右栏详情.md)
  的发送区，投影姿势抄 [ADR-0058](../../adr/0058-工具渲染意图与结果投影.md) 的卡片 sidecar，
  估算器沿用 [ADR-0048](../../adr/0048-M2-h上下文预算与持久摘要.md) 的 UTF-8 / 3
- **结果**：见门禁节。事件类型表未增行。headless 持久 180 / 总线 249 与 M3-h 一致。

---

## 一、交付了什么

| 层 | 落点 |
|---|---|
| 契约 | `ContextOccupancy`（`strictObject`：三段 + total + 路由容量） |
| Runtime | `projectContextOccupancy()`；`ContextBuilder.build()` 结束后 `runtime.noteOccupancy()` |
| 写入闸门 | 运行时不变量「占用投影不得进事件流」盯全部已知类型；`sample-events` 拒绝名字含 occupancy 的类型 |
| IPC | `PushedEvent.occupancy` 挂在 `message.start`；`ReadSessionResult.occupancy` |
| 渲染层 | `ContextMeter`：发送键旁 14px 环，点开系统提示词 / 工具 / 对话 |

sidecar 住在 `SessionRuntime`，**不是** `SessionState`：不进快照、不进 `reduce()`、
进程退出即丢，下次组装再算。渲染层切会话即清空，跟卡片同一条生命周期。

无 `provider.countTokens` 时，环上合计与压缩路径看到的 `estimateRequestTokens(request)`
一字不差。有精确计数时三段按估算比例摊到这个总数上。

## 二、验收

- 环的合计在无精确计数时等于本次组装请求的 `estimateRequestTokens`。
- 相对字节/4 的宽松估算，偏差方向稳定为高估（UTF-8 / 3）。
- 占用投影进不了模型请求：`projectContextOccupancy` 不改入参。
- `build()` 不因写占用而推进 `lastSeq`。
- 📌 **待补**：真机发送键旁的环与点开三段的截屏。与 a～e 同一笔欠账（当前环境没有桌面会话）。

## 三、反向演练，逐条看它红过一次

计划里是一条：「把占用投影塞进事件流」。实测拆成两条路，因为它们失效的形状不同。

| # | 构造 | 实际报错 | 闸门 |
|---|---|---|---|
| 1 | `parseStoredEvent({ type: 'context.occupancy', payload: { systemTokens, toolsTokens, conversationTokens, totalTokens, capacityTokens } })` | `未知事件类型 "context.occupancy"（seq=1）。多半是该会话由更新版本的小明写入。请升级后再打开。` | `parseStoredEvent` + 注册表 |
| 2 | `runtime.record({ type: 'notice.posted', payload: { …, systemTokens, toolsTokens, conversationTokens, capacityTokens } })` | `运行时不变量被破坏：· [@xm/runtime] 占用投影不得进事件流……事件 notice.posted 的 payload 携带了占用投影字段` | `record()` 上的不变量 |
| 2b | `ALL_EVENT_TYPES` 出现名字含 `occupancy` 的类型 | `占用投影不得登记为事件类型：…` | `sample-events()` 开场断言 |

第 1 条在加新类型之前就已经红：未知类型失败关闭。第 2 条是本段补上的——
payload 是 `looseObject`，不补这条，占用字段会静默躺进库里，`reduce()` 当没看见。
第 2b 条挡住「补一条样本就把新类型洗白」：缺样本检查会逼人把 occupancy 写进样本，
看起来像做完了契约，所以名字本身就被拒绝。

## 四、明确没做

- 打开会话时预演一次 `ContextBuilder`（会碰 Provider / 可能触发压缩）。环在本进程
  第一次组装请求之后出现；重启后要再发一轮才有读数。
- 把占用写进 `usage.recorded` 或任何持久 payload。
- 新 ADR：投影形状与卡片同源，估算器沿用 ADR-0048，没有新的跨包决策。

## 五、全程不变的确认

1. 消息仍来自 `reduce(events)`。占用是 sidecar，与卡片、`extRecords` 同类。
2. 渲染层不认识任何具体工具。
3. preload 未增通道；占用只出现在主进程 → 渲染层的事件推送与 `readSession`。
4. `ALLOWLIST` 未增行。`context-builder.ts` 396 行，`store.ts` 399 行。
5. 事件注册表未增类型。生成表：配置目录 14 个字段；`message.start` 消费者多了
   `desktop-host`（占用 sidecar 挂在这条上），没有 `context.occupancy` 这一行。
