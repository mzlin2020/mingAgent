## 这一批的共同形状：**接口做完了，最后一公里没有接上**

A1/A2/A3 那一批的形状是"规则写得对，指向的东西不在那儿"。这一批是它的近亲，
但更值得单独记一笔——**五处里有四处，机制、契约、用例全都在，只差最后一次接线**：

| # | 机制在不在 | 差的那一步 | 表现 |
|---|---|---|---|
| B1 | ADR-0023 的三层 + `tightenOnly()` 都在，用例全绿 | 装配把 `cwd` 传成了家目录 | 项目层**从未生效过一次** |
| B2 | ADR-0028 的 DNS pin 通道在，两侧代码都对 | 键的算法两侧各写了一份 | IPv6 字面量 / 带尾点 FQDN **从未成功过一次** |
| C1 | 入参 schema 全是 `.strict()` | 解码那一步 `catch { return {} }` | 坏 JSON 变成"没带参数"，工具**照常执行** |
| C2 | ADR-0069 的两条预算都在，`terminate()` 也真的调了 | 宿主侧的在途子调用没人管 | 程序"已终止"，它派发的命令继续跑完 |
| D1 | ADR-0005 的 `resources()` / `concurrency` 做进了每个工具 | 调度器从来没写 | 两个字段**没有任何代码读过** |

判据从这一批里长出来一条：

> **一个契约做完的标志不是"接口和实现都在"，是"有一条测试跑过从调用方到效果的整条路"。**
> 上面五处，每一处的单元测试都是绿的——因为单测喂的是**正确的调用方参数**。

## B1 · 项目层权限规则从未被加载

```ts
// apps/desktop/src/main/desktop-host.ts（旧）
const loaded = await loadConfig({ paths, cwd: app.getPath('home') });
```

`cwd` 是项目层的查找起点。传家目录 ⇒ "项目层"恒等于 `~/.xiaoming/config.json`，
而用户真正打开的那个仓库里的 `.xiaoming/config.json` 一次也没被读过。

根因是**时机**：`loadConfig()` 在启动时跑一次，那一刻一个会话都没有，
而工作目录是每个会话各自的。一个进程级的加载函数回答不了一个会话级的问题。

处置（ADR-0080）：`loadProjectPermissionRules(cwd)` + `apps/desktop/src/main/session-policy.ts`，
按会话算一次规则层并缓存，顺带把 ADR-0078 的 `extraSourceRoots` 也合进来
（两件事的触发条件都是"这个会话的 cwd 是什么"）。**配置分层从此分两半**：
`permission.rules` 按会话，其余按进程。

## B2 · `pinnedHosts` 的键，两侧各算一份

```
http://[::1]:8080/     网关写 [::1]        工具查 ::1            → 落空
http://example.com./   网关写 example.com  工具查 example.com.   → 落空
```

落空的表现是工具抛"内部错误：找不到已解析地址（pinnedHosts）"——一句看起来像内部 bug、
实际上是 SSRF 判定链接缝错位的话。处置：键收敛成 `pinnedHostKey(rawUrl)`（内核），
**网关与工具都调它**。与 ADR-0078 那道闸门坚持"用内核自己的 `globMatch`"是同一个教训。

## C1 · 坏掉的入参 JSON 静默变成 `{}`

三处各写了一份 `try { JSON.parse } catch { return {} }`。`argsJson` 是模型输出，
也就是不可信输入（不变量三：**不静默兜底**）。后果分两种，都很难自查：

- 入参**全可选**的工具（`fs.list`、`git.status`、`todo.write`…）**照常执行**，
  带着一整套默认值。模型以为让它读 `/a/b`，它读的是 cwd。
- 有必填字段的工具报"缺少字段 x"，而真正的原因是"你那段 JSON 断在半路"——
  模型于是去补一个它本来就给了的字段，同一个错反复重试。

最常见的成因不是模型犯傻，是 `max_tokens` 恰好落在一次工具调用的参数中间。

处置：`packages/runtime/src/turn-args.ts` 一份 `parseToolArgs()`，解不开就
`invalid_input` + 原文片段 + 一句"常见原因是被 max_tokens 截断，请整段重发"。
**空串仍然是"没有参数"**——多数 Provider 对零参数工具发的就是空串，那不是兜底。

## C2 · Code Mode 超时后，在途子调用仍会跑完

```
程序：xm.shell.exec({ argv: ['sleep', '10'] });

800ms   墙钟触发 → run_code 收尾 → 模型被告知"程序超时终止"
10s     sleep 才结束；它的 tool.code.dispatch 这时才想落库，会话已经关了 → 审计丢失
```

`terminate()` 只杀得掉客体域；宿主侧的子调用是个普通 Promise。处置（ADR-0081）：
`CodeRuntime.call(request, signal)` 多一个**运行域信号**，接缝把它与 `deps.signal`
取并集接到子调用的 `ToolContext.signal` 上；收尾时等在途调用最多 1 秒，为的是审计顺序。

## D1 · ADR-0005 的调度器从来没有被写出来

`resources()` 与 `concurrency` 一路做进了每个工具定义，而驱动器从 M0 起就是
`for (const call of calls) await dispatch(call)`。于是模型一次回复里发的 5 个 `fs.read`
串成 5 段执行——**小明省掉了模型往返，却把工具执行串了回去**，
而 ADR-0005 开头批评参考项目的正是这件事的另一半。

处置（ADR-0082）：切成顺序执行的批次、批内并发、上限 8。**只并行"无论怎么排都不会互相
影响"的调用**：`parallel` 且资源声明里没有 write / global / pty。

ADR-0005 想要的路径冲突检测**做不到**，而理由是当时没看见的一件事：
`resources(input)` 拿到的是**网关规范化之前**的入参，`./a.ts` 与 `/work/a.ts`
在排班这一层看不出是同一个文件。按 ADR-0005 自己写的那句判据——收益是省时间、
代价是数据损坏，两者不对称——只能收窄。
