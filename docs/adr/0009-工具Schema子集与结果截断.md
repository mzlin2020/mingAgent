# ADR-0009 · 工具契约：可序列化 Schema 子集 + 统一结果截断

- **状态**：🟢 Accepted
- **日期**：2026-08-04
- **相关**：[10-契约设计 §5](../10-契约设计.md)、[05-可插拔与扩展体系](../05-可插拔与扩展体系.md)、[02 §2.7 §2.12 §2.14](../02-参考项目评审-manusAgent.md)

## 背景

工具入参的 Zod schema 要同时满足三件事：

1. 严格校验模型给的参数（原则四）
2. 导出 JSON Schema 塞进模型请求
3. 跨进程传输（插件宿主、MCP、渲染层都要拿到）

Zod 的表达力远超 JSON Schema，很多构造做不到上述三件事的交集。如果不划定子集，问题会以最难查的方式暴露：某个插件工具用了 `z.lazy()`，导出的 JSON Schema 带 `$ref`，某些模型能处理某些不能，表现为"这个工具偶尔调不对"。

第二个问题是结果体积。`shell.exec("npm test")` 可能输出几 MB，`fs.read` 一个大文件同理。不加控制就会单次撑爆上下文。参考项目对此没有任何机制（2.12），且展示信息在编排层按工具名 if-else 填充（2.14），每加一个工具都要改内核。

## 选项

### 关于 Schema 子集

**A. 不限制，出问题再说** —— 问题会在三方插件接入后集中爆发，且报错点离原因很远。

**B. 只允许平坦对象（无嵌套）** —— 过于严苛，`edit` 工具的"多处替换"天然需要对象数组。

**C. 划定明确子集 + 注册时强制断言** —— 开发期就炸，报错点即原因点。

### 关于截断

**D. 由工具自己截断** —— 每个工具都要实现一遍，插件作者必然遗漏，且策略不一致。

**E. 由运行时统一截断，工具声明限额** —— 一处实现，所有工具受益，包括三方的。

## 决策

### 1. Schema 子集（选 C）

| 允许 | 禁止 | 禁止的原因 |
|---|---|---|
| `strictObject` / 基本类型 / `enum` / `literal` | `.transform()` | 输入输出类型不一致，`Tool<I>` 的 `I` 失去意义 |
| `array` / `optional` / `nullable` / `default` | `z.lazy()` / 递归 | JSON Schema 出 `$ref`，模型侧支持参差 |
| `discriminatedUnion`（成员均为 object） | 裸 `union` 混合类型 | 模型极难稳定产出 |
| `.describe()`（每个字段都应写） | `z.any()` / `z.unknown()` | 等于没有约束，模型必然乱填 |
| `.refine()`（约束需同步写进 description） | `z.function()` / `z.map()` / `z.set()` | 不可 JSON 序列化 |

`ToolRegistry.register()` 调用 `assertToolSchema(schema)`，违规直接抛出。内置工具在启动时就会炸，插件工具在加载时就会被拒绝并给出明确原因。

> **实测补充（2026-08-04 冒烟）**，两条必须写进实现：
>
> 1. **`z.toJSONSchema(s, { io: 'input' })` —— `io` 参数不可省。** 默认的 `io:'output'` 会把带 `.default()` 的字段全部塞进 `required`，模型将被迫每次填写可选参数。实测 `edits[].replaceAll`、`maxResults` 均中招。
> 2. **`assertToolSchema()` 必须自行遍历 Zod 结构判定，不能靠"导出是否抛错"。** 实测 `.transform()` 在 `io:'output'` 下抛错、但在我们实际使用的 `io:'input'` 下**静默通过**；`z.any()` 产出 `{}`；递归产出 `{"$ref":"#"}`——三者导出全都不报错，只有主动检测才拦得住。
>
> 其余已验证达标：合法子集导出无 `$ref`/`$defs`、`additionalProperties:false` 正确、`.describe()` 中文无损落到 `description`、`discriminatedUnion` 导出为 `oneOf` + `const`、`strictObject` 以 `unrecognized_keys` 拒绝幻觉字段。

**`.refine()` 的附加要求**：refine 表达的约束在 JSON Schema 里不可见，模型看不到。凡 refine 表达的约束，必须在 `.describe()` 里用自然语言重复。这条写进工具开发规范并在 code review 检查——无法自动化，但漏了的后果只是模型多试一次，可接受。

**入参用 `strictObject`（未知字段报错），与 [ADR-0008](./0008-事件持久化分层与演进.md) 里"事件 payload 用宽松 object"是刻意的不对称**，理由见该 ADR §4。

### 2. 统一截断（选 E）

工具声明 `resultLimits: { maxBytes, maxLines?, strategy }`，运行时统一执行：

- 全量结果写进 blob（内容寻址）
- 按策略截断后作为 `forModel` 喂给模型
- 截断处插入**对模型可见**的标记，含省略量与 blob 引用

```
[... 已省略 128,442 字节 / 3,102 行。完整内容: blob:sha256:ab3f… ，
     可用 result.expand 工具按行范围读取 ...]
```

三个要点：

- **标记必须可见**。悄悄截断是最坏的做法——模型会基于残缺内容自信地下结论，且没人知道它为什么错了。
- **默认策略 `middle`**（保留头尾）。命令输出的头部有上下文、尾部有错误信息，中间常是噪音。`head`/`tail` 留给信息分布明确的工具。
- **`result.expand` 工具 M2 补**。M0 只需在契约里留好 blob 引用位置。

### 3. 展示契约由工具自带

工具返回 `DisplayHint { renderer, summary, data, blobs? }`，编排层不认识具体工具。找不到对应渲染器时**降级为纯文本 `summary`**——降级路径必须存在，否则三方插件的工具会让 UI 白屏。

### 4. 描述符与接口分离

契约包只放可序列化的 `ToolDescriptor`；带 `execute()` 的 `interface Tool` 留在 `@xm/kernel`。跨进程传的是描述符，不是工具。这让内置工具、插件工具、MCP 工具在注册表里形状完全一致——"一切皆插件"（原则二）能否落地，就取决于这条边界划得干不干净。

## 后果

**正面**
- Schema 问题在注册时暴露，不在模型调用时暴露
- 上下文不会被单个工具结果撑爆，且模型知道内容被截断了、知道去哪取全文
- 新增工具零内核改动——这是与参考项目 2.14 的关键差异
- 三方插件与 MCP 工具自动获得截断保护，不依赖其作者的自觉

**负面**
- 子集限制会让某些工具的入参表达不够自然（例如递归的文件树筛选条件只能拍平）
- 全量结果都写 blob 带来存储增长，需要 GC（按 refcount + 保留期）
- `resultLimits` 的默认值（64KB）是拍脑袋的，不同工具的合理值差异大

**缓解措施**
- 子集不够用时，正确做法是把工具拆细而不是放宽子集——一个入参需要递归结构的工具，通常是职责过载
- blob GC 在 M2 随 checkpoint 机制一起做；M0/M1 数据量不构成问题
- `resultLimits` 按工具单独调，并在 M5 用真实 trace 统计截断率反过来校准默认值

**重新评估的触发条件**
- 出现合理但被子集挡住的工具设计，且无法通过拆分解决
- 截断率统计显示默认值系统性偏低（模型频繁需要 expand）→ 调默认值或改策略
