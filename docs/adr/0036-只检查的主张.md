# ADR-0036 · 只检查的主张：解析出的 IP 不该自己弹一个确认框

## 背景

排查 ADR-0035 时对真实网关做的测量，顺带查出**审批噪音的第二个来源**。

`resolveHost`（`packages/tools-core/src/gateway.ts`）给每个 URL 产出**两条**主张：

- **claim A**：可读域名，例如 `https://example.com/page`
- **claim B**：解析出的 IP，例如 `http://93.184.216.34/`

claim B 是 ADR-0028 加的，用途写在代码注释里：**让 SSRF 的 IP 段规则有东西可匹配**。
判定与建连必须看同一个地址，否则就是 DNS 重绑定的窗口。这个设计是对的。

问题是 claim B 除了匹配 SSRF 的 `ipRange` deny，**也匹配 `def.net-fetch` 的 `ask`**——
后者是一条不带 `match` 的规则，对该能力的一切目标生效。实测：

```
claim A  https://example.com/page   balanced / model  →  ask  def.net-fetch
claim B  http://93.184.216.34/      balanced / model  →  ask  def.net-fetch   ← 第二个框
```

于是**每一次 `web.fetch` 弹两个确认框**：一个写着域名，一个写着用户根本无从判断的裸 IP。
用户报的"搜一条新闻点了 10+ 次允许"，是这个乘数与 ADR-0035 那个问题相乘的结果。

第二个框不换来任何安全：用户能做的判断全在域名那一个框里，
针对 IP 的那次授权也不会泛化到任何别处。它唯一的作用是把确认框数量翻倍，
而 `turn.ts` 自己写着「审批噪音会直接转化成"下次顺手点允许"」。

## 决策

`PermissionClaim` 新增可选 `checkOnly?: boolean`，语义是
**这条主张只用来查 `deny`，不拿去问用户**：

- `deny` → 照旧拦（那才是它存在的理由），行为一个字没变
- `ask`  → 视为已满足，不进待问队列
- `allow`→ 与今天一样，直接通过

`resolveHost` 给 claim B 标上它。判定发生在 `turn.ts` 的第一遍循环里，
紧挨着既有的 deny 分支——**deny 那一半在它前面，没有被绕过的可能**。

### 为什么是在类型上标，而不是在规则里绕

试过的两条路都不行：

- **给 IP 字面量的 target 加一条内置 allow**：那会让模型直接 `web.fetch http://1.2.3.4/`
  也变成静默放行——claim A 和 claim B 在这种输入下是同一个字符串，分不开。
- **让 `turn.ts` 认出"这是一对主张里的第二条"**：`turn.ts` 拿到的是一个扁平数组，
  要它反推哪条是"检查用的"，就是把网关的内部约定藏进另一个文件里靠猜。

把"这条主张是检查用的"写进类型，是唯一让这个约定**说得出口、测得到**的做法。
它同时把 ADR-0028 当时的一个隐含假设显式化了：claim B 一直是靠"恰好也命中 ask"
才没被发现有问题，而那从来不是它的设计意图。

默认 `false`：只有明确知道自己是检查用的主张才配得上这个标记，
忘了标的后果是多问一次，不是少拦一次——落在保守的那一侧。

## 后果

- 正面：默认「请求批准」档下，每次联网的确认框从 **2 个降到 1 个**，
  而且那 1 个写的是用户看得懂的域名。
- 正面：SSRF 防线一个字没动。实测（`web-fetch-ssrf.test.ts`，走真实 `nodeToolGateway`）：
  解析到保留网段仍然被 `def.no-fetch-private-network` 拦下，且仍然零确认框。
- 中性：这是本仓库第一条"有语义的主张"。将来若再出现同类需求（例如"只用来
  匹配红线的探针主张"），应复用这个字段而不是再加一个 —— 两个近义标记必然分叉。
- 负面 / 已知代价：一个标错了 `checkOnly` 的网关可以让某条主张永远不问用户。
  但它**不能**让任何 deny 失效，所以最坏情况是"少问一次"，不是"绕过判权"。
  网关是内置代码、不是插件扩展点，这个面目前是封闭的；
  等 MCP / 插件能提供网关时要重新评估（与 ADR-0033 的污点传播是同一批前提）。

## 反向演练

- 临时停掉 `turn.ts` 里的 `if (claim.checkOnly === true) continue;` →
  `informed-grant-noise.test.ts` 的「每个 URL 只问一次，问的是域名，不是解析出的 IP」
  当场红，`asked` 里多出一条裸 IP 的 target，与实测到的症状一致。
- `web-fetch-ssrf.test.ts` 那一组（保留网段 deny、DNS 只解析一次、
  用户规则覆盖后真的能连通）全程绿，证明改动没有碰到 deny 那一半。

### 附：为什么这条的端到端用例用假网关

"只问一次"那条断言需要 DNS 指向一个**公网可连**的地址，否则用例会卡在真实建连上
（第一版就是这么超时的）。而"要不要问用户"这件事完全不依赖真的连上去。
所以那一半用假网关复刻两条主张来考，deny 那一半留在 `web-fetch-ssrf.test.ts` 里
用真网关守着——两个文件各自考它能诚实考到的那部分。
