# ADR-0060 · 运行时不变量注册表与文档图谱生成

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0011](./0011-契约与内核实现期的偏离.md) · [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md) · [ADR-0052](./0052-插件容器与效果模型.md) · [ADR-0054](./0054-能力接缝三角色与执行世界.md)

## 背景

`CLAUDE.md` 里有一条自陈：

> 本项目已经栽过八次"规则存在但从未生效"。

翻出其中几次，它们的形态出奇一致：

| 事故 | 规则在不在 | 生效没有 |
|---|---|---|
| depcruise 因未装 electron 而看不见 `import 'electron'` | 在 | 没有 |
| depcruise 因 exclude `dist/` 而看不见 135 条跨包边 | 在 | 没有 |
| `trustLevel` 硬编码成 `'model'` | 在（三条 `red.*-untrusted` 红线 + 整套注入降级） | **一次也没触发过** |
| `truncateResult` 实现与 12 条用例俱全 | 在 | `executeCall` 里一次也没调 |
| `checkpoint.created` 无人发出 | 在（ADR-0003 承诺无条件还原点） | 没有 |
| `DisplayHint` 契约完整 | 在 | 零生产者、零消费者（ADR-0058） |

**共同点：静态检查证明的是"东西存在"，而失效的永远是"它在真实运行里起没起作用"。**
单元测试对这类失效同样免疫——`truncateResult` 有 12 条用例，全绿，而它从没被调用过。

容器化之后这个风险会**变大**而不是变小：注册关系从 import 图挪到运行时（ADR-0052 的真损失），
"这个插件到底装上没有、它注册的监听器到底被派发到没有"，静态分析看不见。

参考实现对这件事有一个专门的答案：`ctx.invariants` 注册表，每个包发布一个 `./invariant`
伴生模块，**只断言自己拥有的、可观察的事件关系或可变数据**，明确禁止断言
"服务存在""方法存在""插件元数据""固定纯函数结果"——因为那些是类型、加载或单元测试的职责。
它同时从代码生成接缝图、事件生产消费表、工具目录、配置目录，并把生成器接进闸门。

## 选项

### 选项 A：继续靠"加护栏必须做反向演练"这条纪律

优点：零成本，且这条纪律确实有效——它抓出过 depcruise 两条核心规则静默失效。
缺点：它是**一次性**的。反向演练证明"规则在写下的那一刻是生效的"，不保证半年后重构之后
它还生效。上面六条里至少三条是在"当初演练过"之后被后来的改动弄失效的。

### 选项 B：只做文档图谱生成

优点：解决文档漂移，成本低。
缺点：不解决运行时失效。图谱能告诉你"谁注册了这个监听器"，不能告诉你"它被调用过没有"。

### 选项 C：不变量注册表 + 图谱生成，两件一起做

## 决策

**选择 C。** 两者解决的是同一个问题的两半：图谱管"结构上是不是接上了"，
不变量管"运行时是不是真的在跑"。

### 一、不变量注册表

`ctx.invariants.register(packageName, installer)`。每个包发布一个 `./invariant` 伴生入口，
在装配时注册自己的运行时不变量。

**可以断言的**（有拥有关系、可观察）：

- 事件流关系：`turn.start` 必有配对 `turn.end`（ADR-0008 包含性）；
  `tool.start` 与 `tool.end` 的 callId 一一对应；`seq` 严格递增无空洞。
- 可变数据关系：inbox 的 FIFO 守恒（ADR-0056）；工具注册表在插件卸载后确实为空。
- 判定路径关系：**每一次 `tool.end` 之前必有一次判定记录**——这一条如果早就存在，
  `trustLevel` 硬编码那次事故会在第一个真实会话里被照出来。

**明确禁止断言的**（脚本会拒收）：

- "某个服务存在""某个方法存在""某个插件装上了"——那是类型与加载期的事。
- 固定纯函数在固定输入上的结果——那是单元测试的事。
- 插件元数据、effect 的存在性。

**没有可断言关系时**，伴生模块写一个空 installer 加一句 `无运行时不变量：` 开头的理由
（纯工具包、薄适配器、组合包）。理由必须在这个包长出可变状态或事件协议时重新审视。
`pnpm verify` 新增一道 `check:invariants`，拒收：未发布伴生模块、无理由的空 installer、
注册名与包名不符、以及断言了上面禁止项的 installer。

**在哪跑**：dev 与 CI 装配下开启；生产装配可由 profile 关闭（它有运行时开销）。
断言失败抛 `InvariantError` 并落审计——不静默。

### 二、文档图谱生成

从代码生成，进 `pnpm verify`，文件头带"由脚本生成，请勿手改"：

| 生成物 | 回答什么问题 | 补的是哪个盲区 |
|---|---|---|
| 接缝图 | 谁定义 / 谁提供 / 谁消费每个 `ctx.<key>` | ADR-0052 的真损失（import 图看不见运行时依赖） |
| 事件生产消费表 | 每个事件类型谁发、谁听 | 今天靠全文搜索 |
| 扩展点挂载表 | 每个扩展点上挂了哪些插件、什么顺序 | ADR-0055 之后"一次调用经过了什么"的唯一答案 |
| 工具目录 | 全部工具的 schema、能力、风险、卡片种类 | 今天散在各处 |
| 配置目录 | 全部配置字段、默认值、层级 | 今天散在 schema 里 |

生成物与源码不一致时闸门变红。这条把"文档与代码同批提交"从纪律变成机制——
它拦不住所有漂移（散文部分仍靠人），但把最容易漂、也最有价值的那五张表拦住了。

### 三、不做的

- 不做覆盖率闸门的提高（参考实现要求 per-file 100%）。本仓库 kernel 85% 行门槛保持不变；
  上面六条事故没有一条是覆盖率不足造成的，提高覆盖率解决不了它们。
- 不做双语文档与 i18n 流水线。

## 后果

- **正面**：把"规则存在但从未生效"这类失效从**靠人记得演练**变成**持续断言**。
  这是本仓库历史上出现频率最高的一类缺陷，值得为它单独建机制。
- **正面**：生成的接缝图与扩展点挂载表，是容器化之后小明自己读自己架构的主要入口——
  比读 `turn.ts` 更能回答"这次调用经过了什么"。

- **负面**：不变量在 dev/CI 下有运行时开销，且写得不好会误报。误报比漏报更伤——
  一次误报会让人把整个机制关掉。缓解：伴生模块只断言**自己拥有**的关系，
  跨包关系归属给拥有那条事件流的包；宁可少断言，也不要断言一个自己控制不了的东西。
- **负面**：多两道闸门，`pnpm verify` 变慢。可接受。

- **代价与缓解**：五张生成表会让 `docs/` 里出现不能手改的文件，与"docs 是给人和小明共同读的"
  略有张力（生成物往往不好读）。缓解：生成物单独放 `docs/generated/`，
  手写文档链接过去，不混在一起。

- **必做的反向演练**：
  1. 手改一处生成的接缝图 → 闸门必须红。
  2. 写一个断言"`ctx.tools` 服务存在"的伪不变量 → `check:invariants` 必须拒收。
  3. 把 `trustLevel` 改回硬编码 `'model'` → 判定路径的不变量必须在第一个真实会话里红。
     **这一条是本 ADR 的立身之本**：它要能抓住一次已经真实发生过的事故。
  4. 卸载一个插件后不撤销它的工具注册 → 注册表守恒的不变量必须红。

- **重新评估条件**：如果不变量在半年内产生的误报多于真报，说明断言的粒度选错了——
  收缩到只保留事件流关系那几条，而不是关掉整个机制。

## 2026-08-15 实现定案（M3-g）

五处与初稿字面不同。前两处是**发现初稿写错了**，记下来比记"照做了"更要紧。

### 一、`tool.start` 与 `tool.end` 的"一一对应"是错的，改成单向

初稿把它列为可断言项。它在这个系统里不成立：**被闸门拒掉的调用只记 `tool.end`**
（`failCall`），连 `tool.start` 都不产生——那正是"闸门在执行之前"的可观察形态
（ADR-0065 §四）。照初稿写，第一次真实拒绝就会误报。

落地的是单向的那一半：**一次 `ok: true` 的结束必有开始**。它拦的是"有东西没走完整
十二步链就产出了结果"，而这恰恰是更值得拦的方向。

误报比漏报更伤——一次误报就会让人把整个机制关掉，本 ADR 的"负面"一节自己写着这句。
所以宁可只断言成立的那一半。

### 二、光靠抛出不够：违例必须同时进一份清单

初稿说"断言失败抛 `InvariantError` 并落审计"。实测抛不出去：`check()` 的调用点在
`SessionRuntime.record()` 里，而它的上游 `executeCall` 为了把工具失败翻译成一条
`tool.end`，**catch 掉了一切**——一次真实违例于是变成了"某个工具失败了"，安静地过去。

这是在 §「必做的反向演练」第 3 条（把 `trustLevel` 改回硬编码）的现场发现的：
事件流里既没有 `error.raised`，测试也照绿。

所以违例有两条出路：抛出（给没人 catch 的调用点）+ `registry.violations` 清单
（给闸门与用例）。清单不会被任何 try/catch 吃掉，headless 冒烟末尾断言的就是它。

### 三、伴生模块是 `src/invariant.ts`，不是 `./invariant` subpath 入口

初稿写"每个包发布一个 `./invariant` 伴生入口"。落地为 `src/invariant.ts` 这个**同名模块**
（有断言的两个包再从包入口导出，其余七个只作为伴生模块存在）：
九个包各加一条 `exports` 与两处 tsconfig paths 映射，换不来任何运行时收益
（这是个源码编译的单仓库，伴生模块本身只有几十行纯逻辑）。
`scripts/check-invariants.mjs` 盯的是模块存在、导出名与包名一致、以及内容规则——
subpath 与否不影响其中任何一条。

`@xm/contracts` 的伴生模块**不标类型**：注册表的类型住在 `@xm/kernel`（它要引用
`SessionState`），而 kernel 依赖 contracts。为了标个类型把依赖方向倒过来才是真的错。

### 四、伪不变量由"接口 + 脚本"两层挡，不只靠脚本

检查函数的入参只有 `{ event, before, after }`——没有服务、没有容器、没有注册表。
"断言 `ctx.tools` 服务存在"因此**在接口上就写不出来**，想写只能闭包捕获一个外部引用。
脚本再补两条判据：检查函数一次都不读入参 → 拒收；不变量名字长得像"××存在" → 拒收。
演练里那条伪不变量被三条规则同时拦下（还额外撞上"非空 installer 必须接入装配"）。

### 五、装配只接非空的伴生模块，接没接由脚本盯着

九个包里只有 `@xm/kernel`（4 条）与 `@xm/runtime`（3 条）有断言，其余七个是
"空 installer + 一句理由"。空 installer 注册与否在运行时完全等价，所以
`invariant-install.ts` 只列这两个。脚本反过来查：**哪个包的伴生模块从空变成非空、
而这张表没跟着加，闸门就红**——"写了一堆断言却没人注册"是这套机制自己身上
最容易长出来的那种失效。

一个由此暴露的边界：`@xm/runtime` 依赖不到 `@xm/storage`，所以存储层将来若长出真的
不变量，它接不进这张表，得单开一行 profile 行。脚本的报错信息里写了这条出路。

### 六、生成表落地四张，第五张（接缝图）M3-b 就有了

`docs/generated/` 现在是五张：接缝图、事件生产消费表、扩展点挂载表、工具目录、配置目录。
`pnpm verify` 里对应两道 `--check`。

**扩展点挂载表要真装配一次**才生成得出来：静态分析看得见 `installStoppingGuard(host)`
这一行，看不见它最终挂在哪个点上、排第几。为此容器新增了 `mounts()` 自省，
并且归属取的是**"装配到哪一行时挂上的"**而不是 `ctx.pluginName`——后者会把所有监听器
都记成 `baseline.turn-driver`（那个 host 是驱动器造的），第一版生成的表就是那样，
四行插件行全被记成同一个，一眼假。
