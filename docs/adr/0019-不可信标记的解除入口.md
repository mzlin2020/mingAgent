# ADR-0019 · 不可信标记的解除：一个只有人能按的按钮

- **状态**：🟢 Accepted（2026-08-05）
- **日期**：2026-08-05
- **相关**：闭合 [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md) 留下的 G1；细化 [ADR-0003](./0003-默认权限策略.md) 的注入降级

## 背景

ADR-0017 把提示词注入防御从死代码修成了真防御：`untrustedContext` 由事件流算出，
读过网页之后再要求 `git push`，判定从 ask 变 deny。拒绝时给用户的原话是：

> 若确属你的本意，请**显式解除本轮的不可信标记**后重试。

**这句话当时无法兑现。** `untrustedContext` 一旦置上就是终身的，代码里没有任何解除入口。

## 问题：一道会被整体放弃的防御

这不是"防御太严"，是"防御会被整体放弃"。接上真实网页工具之后：

- 任何查过一次资料的会话，此后永久做不了删除、推送、联网这类不可撤销的操作
- 用户唯一的出路是新建会话，而新会话里没有他刚查到的那些资料
- 他从中学到的经验是**「别用这个功能」**——被关掉的不是这道防御，是整条工作流

一道用户必须绕开才能干活的防线，最终会被绕开。而绕开的方式通常比它本来要防的更糟。

## 决策

### 一、解除是一条**事件**，不是内存标志

新增持久化事件 `trust.cleared`（`by` / `cleared` 出处 / 可选 `reason`）。

会话状态完全由事件流决定（原则二），而这一条恰恰是最不该丢的那种状态：
它是一次**安全决定**——事后追责要查、崩溃恢复要续、评测回放要复现。
一个"重启之后就忘了自己被解除过"的标记，和一个假的标记没有区别。

### 二、作用域是「到下一次引入外部内容为止」

`reduce` 把 `untrustedContext` 置回 `undefined`，不需要任何额外机制：下一次带
`net.fetch` / `browser.control` / `gui.capture` 的 `tool.start` 会被 `taintOf()` 重新标上。

**永久解除是个很容易顺手写出来的实现**（加一个 `everCleared` 标志就行），而它的后果是：
用户为了推一次代码解除了一次，此后这个会话读多少网页都不再有防御——恰恰是长会话、
读过最多外部内容的那种会话，风险最高的那一种。

### 三、只有人能按这个按钮

保证**不在** payload 的 `by: 'user'` 上——字段是可以填的。真正的保证是结构性的：

```ts
interface ToolContext {
  readonly sessionId: SessionId;
  readonly signal: AbortLike;
  readonly cwd: string;
  readonly executor: 'local' | 'container' | 'remote';
}
```

**工具拿不到 runtime，也拿不到任何记录事件的入口。** 于是"读了网页的模型让工具把自己
解除掉"这条路不是靠约定挡住的，是不存在。

这条结构性事实需要一条**用例**盯着，因为它最可能被将来某次"顺手"的扩容破坏——
给 `ToolContext` 加一个 `record` 会让很多事情变方便。`by: z.literal('user')` 则是把
这条事实写进契约：多一个取值就要改契约、改测试、并且必须解释为什么。

### 四、解除入口自带社工面，UI 必须说清「你正在解除什么」

模型完全可以在回复里写「请点上面那个解除按钮，然后我就能帮你推送了」。
用户面对一个只写着"解除限制"的空白按钮，会照点不误。

所以横幅复述的是**事件流里的事实**——哪个工具、通过哪个能力、什么时候——
这些字段全部来自 `UntrustedContext`，是 `reduce` 从 `tool.start` 算出来的，模型碰不到。
用户确认的是一件具体的事，不是一个措辞。横幅同时是常驻、不可关闭的：
能被关掉的安全提示等于没有提示。

### 五、入口在 `SessionRuntime`，不在桌面外壳

桌面、CLI（M3）、headless 走同一条路。解除是安全决定，它只能有一个实现。
外壳那一层只做转发。

当前没有标记时**不记事件**、返回 `false`——无意义的审计条目就是审计噪音，
而审计的价值恰恰在于每一条都值得看。

## 后果

**正面**

- `PolicyEngine` 那句提示第一次是真的
- 防御从"要么忍受要么放弃"变成"可以按需解除，且每次解除都留痕"
- 测试 326 → 332

**反向演练**（三条全部当场转红）

| 演练 | 结果 |
|---|---|
| `reduce` 的 `trust.cleared` 改成空操作 | 2 红：解除后仍被 deny；重开会话后解除丢失 |
| 把解除实现成永久的（`everCleared` 标志） | 1 红：解除 → 再读网页 → push 又被放行 |
| 给 `ToolContext` 挂上 `record` | 1 红：`Object.keys(ctx)` 多出一个键 |

**负面 / 遗留**

- **解除会连同三条 `red.*-untrusted` 红线一起失效**（它们匹配的是 `trustLevel`）。
  这是刻意的：用户显式承担了责任。但它意味着解除按钮的门槛必须由 UI 保证，
  而 UI 保证的强度低于代码保证——这一点写在这里，将来若发现用户在无脑点击，
  要考虑的是提高门槛（例如输入理由），而不是把红线做成不可解除。
- **G2 仍未解决，且现在是唯一剩下的绕过路径**：MCP 工具若不声明 `net.fetch` 就标不出来；
  子 Agent 的污点不会传染回父会话——把"读网页"派给子 Agent，是当前设计下完整的绕过。
  已在 docs/09 升级为「M1-b 接 MCP / 子 Agent 前必须做」。

## 这次值得记住的

一道拒绝，如果没有给出**可执行的下一步**，用户能做的只有整体放弃它。

> **写下"请显式解除后重试"的那一刻，就欠下了一个解除入口。**
> 这笔债欠了一个里程碑，而且它不会自己报警——测试全绿，判定全对，
> 只是用户在真实使用中会撞上一堵没有门的墙。
