# ADR-0015 · 进程与 IPC 边界：窄 preload、双向校验、渲染层不持有第二份状态

- **状态**：🟢 Accepted（2026-08-05）
- **日期**：2026-08-05
- **相关**：落实 [docs/04 §2](../04-总体架构.md) 的进程模型；[ADR-0004](./0004-主界面形态.md) 的界面形态；[docs/06 §1](../06-安全与权限模型.md) 威胁模型

## 背景

docs/04 §2 定了三条：Agent 循环在主进程、插件进程外隔离、渲染层零 Node 权限。第三条写的是 `contextIsolation: true` + `nodeIntegration: false`，"只通过 preload 暴露的窄接口通信"。

"窄"是个形容词。M0-b 要把它变成一份可以指着看的清单，因为**这条边界一旦开宽就再也收不回来**：每一个多暴露出去的调用都会长出调用方。

## 决策

### 一、三个隔离开关一起开，缺一个等于没开

```ts
contextIsolation: true,   // 页面脚本与 preload 不共享同一个 JS 世界
nodeIntegration: false,   // 页面里没有 require / process
sandbox: true,            // preload 自己也跑在受限上下文里
```

最容易被"为了方便"关掉的是第三个。关掉 `sandbox` 之后 preload 能拿到完整 Node，而 preload 是页面唯一能间接触达的代码——等于把前两个也架空了。

代价要写清楚：`sandbox: true` 的 preload **必须是 CJS**。而 `apps/desktop/package.json` 是 `type: module`，`.js` 会被当 ESM 加载并直接失败。所以 preload 产物的扩展名是 `.cjs`，这在 `tsup.config.ts` 里写死。这个坑的表现是"窗口空白、控制台一句 `require is not defined`"，与业务代码毫无关系。

CSP 写在 `index.html` 里而不是只靠默认值，`connect-src` 只留 `self`：渲染层不许自己发网络请求，所有出网走主进程（docs/06 §4.3 出口控制）。

### 二、preload 是一根管子，不是一道闸门

暴露的接口就四个，且全部具名：

```ts
listSessions()  createSession(req)  sendUserMessage(req)  readSession(req)
onEvent(listener)
```

**不提供 `invoke(channel, args)` 这种通用入口。** 那等于把整个 IPC 表面暴露给页面，"窄接口"就只剩一个说法。

preload 不校验、不解析、不缓存、不聚合，也不 import zod 或 `@xm/*`——只依赖 `electron` 与一个纯常量文件 `shared/channels.ts`。depcruise 规则 `preload-必须保持薄` 盯着它。

理由是**缺口的大小等于这个文件的表面积**。一个"顺手"在这里做的缓存或转换，就是一个页面脚本可以间接影响主进程状态的地方。

把校验放进 preload 更糟：它会让人以为那里能挡住什么，而真正需要防的是"渲染层送上来的东西"，那必须在主进程那一侧挡。

### 三、IPC 载荷两边都校验，但理由不同

**主进程那一侧是安全。** 渲染层将来要渲染模型输出、网页内容、插件 UI；一个 XSS 或一个失控的插件就能让它往 IPC 上发任意东西，而主进程握着文件系统、数据库和权限闸门。`contextIsolation` 挡的是"页面直接拿到 Node"，挡不住"页面调用我们自己开的这四个接口"。

所以入参一律 `strictObject`：幻觉字段、伪造的 `sessionId`、超长文本全部在边界上拒绝。文本长度上限不是洁癖——一条无界的字符串从渲染层进来就是一次无界的落库。

**渲染层那一侧是版本一致性。** 打包后两边理论上同版本，但开发时热重载会让它们错开，而"事件形状悄悄变了"的表现是 UI 静默少一块，最难查。

顺带，它把「契约包必须能在浏览器上下文里 import」从 depcruise 的静态承诺变成了运行时事实。

### 四、失败是返回值，不是异常

```ts
{ ok: true, data } | { ok: false, code, message }
```

不把异常直接扔过 IPC：Electron 会把它序列化成一个丢了类型、丢了 `code`、只剩字符串的东西。而 contracts 里区分 `policy_denied` / `user_rejected` / `permission_denied` 就是为了 UI 能说出「改策略 / 重新审批 / 改系统权限」这三句不同的话（docs/02 记的参考项目的坑正是把它们揉成一个字符串）。

信封与载荷**分两步解**。写成 `ipcResult(schema)` 那种一步到位的泛型工厂更好看，但 Zod 4 推出来的是一个巨大的映射类型，`.ok` 在调用点 narrow 不出来。边界代码上宁可朴素。

### 五、事件推送带 `fromSeq`，订阅在总线上而不是存储上

主进程的 `EventBus` 订阅者把事件转给窗口。**存储不做发布订阅**（ADR-0013 不变量五）——追加成功之后由 runtime 发出来。

订阅带 `fromSeq`，重连时从自己记得的位置续。这是"崩在追加与广播之间不丢事件"唯一需要的机制，也是 `seq` 无空洞这条不变量的直接用途。总线**不缓存历史**：补齐缺口是订阅者拿 `fromSeq` 去 `EventStore.read()` 的事，让总线兼职缓存只会多出一份会过期的真相。

渲染层对解析不了的事件**原样忽略并继续**，不让整条流断掉——未知事件类型是版本漂移的正常形态，不是错误（所以推送用 loose 的 `EventEnvelope` 而不是判别联合）。

### 六、渲染层不持有第二份状态

消息列表、运行中的工具、待审批的权限，全部由 `@xm/kernel` 的 `reduce()` 从事件流算出，跟主进程用的是**同一个纯函数**。

这不是复用代码的小便宜，它是「会话状态 = reduce(events)」在 UI 上唯一成立的方式：只要 UI 自己维护一份 `messages` 数组，它就会和回放出来的那份慢慢分叉，而分叉的表现是"刷新一下内容就变了"。

会话**列表**是例外，走主进程的 `listSessions()` 投影而不是回放——为了拿几百个会话的标题去回放几百条事件流是荒唐的（ADR-0013 决策六）。

## 后果

**正面**

- "窄接口"从形容词变成了四行清单，而且有 depcruise 与 ESLint 各一条规则守着
- IPC 契约是纯数据，因此可以在没有 Electron 的环境里测——`apps/desktop/tests/ipc.test.ts` 的 11 条用例覆盖了上面的每一条主张
- 渲染层跑 `reduce()` 让"内核能在浏览器里跑"有了运行时证据，而不只是 depcruise 的静态承诺

**负面**

- 每加一个 IPC 调用要动四个地方（channels / ipc schema / preload / bridge）。这是刻意的摩擦：让"再暴露一个接口"变成一个需要想一下的动作
- 渲染层每收一条事件多一次 Zod parse。事件流很密（流式 delta 是逐 token 的），若成为热点，缓解方向是对瞬态事件走轻量路径，而不是取消校验

**重新评估的触发条件**

- 插件 UI 需要进渲染进程（M3）——那时"渲染层是单一信任域"的假设不再成立，要重新设计
- 出现需要大吞吐的 IPC（如实时终端输出），届时考虑 MessagePort 直连而不是把现有通道撑大

## 遗留

- **审批 UI 是 M1。** 在那之前 `ask` 一律拒绝（`decide: () => 'deny'`），这在代码里写明了理由：默认放行等于没有闸门。
- **多窗口的事件推送是广播式的**：每个窗口都收到全部会话的事件，由渲染层自己过滤。会话多了之后要改成按窗口订阅。
- **主进程到渲染层没有背压**。流式 delta 密集时可能压垮 IPC，M1 接真实 Provider 后要实测。
