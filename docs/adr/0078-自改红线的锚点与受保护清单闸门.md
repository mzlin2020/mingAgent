# ADR-0078 · 自改红线的锚点与受保护清单闸门

- **状态**：🟢 Accepted
- **日期**：2026-08-17
- **相关**：地基复审四 A1 / A2；细化 [ADR-0014](./0014-数据目录与平台路径.md) 的 `appRoot`；
  红线按目标写 [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md)；
  自我迭代分级 [07-自我迭代能力](../07-自我迭代能力.md) §5；
  同批的另一半是 [ADR-0079](./0079-拆不开的命令的兜底.md)

## 背景

M3.5 收官后的全量复审（地基复审四）在自改红线上抓到两个**各自独立、合起来致命**的缺陷。
两个都不是逻辑写错，都是"规则写得对、指向的东西不在那儿"。

### A1 · 锚点指向一个不存在的目录

`selfModifyRedLines(appRoot)` 把每条 glob 拼成 `<appRoot>/packages/kernel/src/policy/**`，
而 `appRoot` 来自 `desktop-host.ts` 的 `app.getAppPath()`。实测（临时入口跑 Electron）：
**`getAppPath()` 返回的是入口所在目录**。于是

| 运行方式 | `appRoot` 实际值 | 红线指向 |
|---|---|---|
| 开发（`electron .`，cwd 是 `apps/desktop`） | `<repo>/apps/desktop` | `apps/desktop/packages/kernel/…` —— 不存在 |
| 打包（`files: dist/**, package.json`） | `…/resources/app.asar` | asar 里根本没有 `packages/` 与 `scripts/` |

**两种真实运行方式下，27 条自改红线一条也不会命中。** 而全部用例是绿的——
它们喂的是合成的 `appRoot: '/repo'` 与合成路径，那正好是"锚点对了"的那个世界。

根因不在某一行代码，在**字段的两义**：`PolicyEnv.appRoot` 的注释写的是
"小明自身仓库/安装目录"。仓库和安装目录在自改场景里是完全不同的两个目录，
而调用方只要传一个值，就必然有一种含义是错的。

### A2 · 清单在 M3 重构之后腐烂了

M3 把网关搬进 `tool-runtime`、把十二步链拆出 `turn.ts`、把装配改名成 `desktop-host.ts`。
`SELF_MODIFY_PROTECTED` 一条没跟着改。实测（用合成 `appRoot` 排除 A1 干扰）：

```
allow  builtin.no-rule-matched   packages/tool-runtime/src/gateway.ts       ← 路径能力网关本体
allow  builtin.no-rule-matched   packages/runtime/src/turn-tools.ts         ← 十二步链本体
allow  builtin.no-rule-matched   packages/kernel/src/container/container.ts ← 底座在位断言
allow  builtin.no-rule-matched   packages/compose/src/assemble.ts           ← 基线行断言
allow  builtin.no-rule-matched   apps/desktop/src/main/desktop-host.ts      ← 唯一生产装配点
deny   red.self-modify-07-fs-write  packages/tools-core/src/gateway.ts      ← 护着一个已删除的文件
```

三条受保护路径（`tools-core/src/gateway.ts`、`tools-core/src/checkpoint.ts`、
`main/services.ts`）指向已经不存在的文件；搬去的新位置和 M3 新增的那几处安全关键代码
一条都没进清单。**期间 depcruise、typecheck、1412 条用例、`pnpm verify` 全绿**——
因为所有既有护栏查的都是"代码与代码的关系"，没有一道查"规则与代码的关系"。

ADR-0039 让这件事更严重：兜底从"没规则匹配 → ask"变成了"没规则匹配 → allow"，
于是一条指错的红线不再退化成"多问一次"，而是彻底放行。

## 选项

### 选项 A：只改清单，把三条路径修对

- 优点：改动最小。
- 缺点：**只修了这一次的症状**。下一次重命名会原样再来一遍，而且同样全绿。
  本仓库栽在"规则存在但从未生效"上已经九次，这一条的形状是"没有任何东西检验规则指向"。

### 选项 B：清单改成后缀匹配（`**/packages/kernel/src/policy/**`）

- 优点：与锚点无关，搬家也不怕。
- 缺点：`**/scripts/**` 会把**用户任何一个项目**的 `scripts/` 目录变成禁写区。
  红线一旦开始误伤日常工作，用户会去找绕过的办法——那等于全部失效（本仓库的既有判据）。

### 选项 C：锚点从"入口位置"改成"在磁盘上认出来的源码树"，并为清单加一道指向闸门

- 优点：两个缺陷各自被一个机制盯住，且都能反向演练。
- 缺点：多一个概念（三种锚点）、多一道 CI 检查、平台层多一次文件系统探测。

## 决策

**选 C**，分三件事落地。

### 一、锚点分成三种，各有各的名字与来源

`PolicyEnv.appRoot` 拆掉，换成三个字段（`packages/kernel/src/policy/self-code.ts`）：

| 字段 | 是什么 | 谁给的 | 保护范围 |
|---|---|---|---|
| `sourceRoot` | 小明**源码树**的根 | 平台层 `findSourceRoot()` 从入口位置往上找 | `SELF_MODIFY_PROTECTED` 那份清单 |
| `extraSourceRoots` | 会话工作区里那份检出 | 桌面端开会话时按 cwd 判 | 同上，各挂一族 |
| `installRoot` | 打包安装目录 | 桌面端 `app.isPackaged` 时给 | **整棵树**禁写禁删 |

`ResolvePathsOptions.appRoot` 同时改名为 `appPath`——它表达的只是"入口在哪"，
不再兼任"源码树在哪"。**一个字段两种含义，正是 A1 的根因，所以名字必须分开。**

`findSourceRoot()` 认树的标记是三个一起看：`pnpm-workspace.yaml` +
`packages/kernel/src/policy/defaults.ts` + `apps/desktop`。少一个就可能是别人的仓库，
而误判的代价是往用户的项目上扣一族禁写红线。

`extraSourceRoots` 覆盖的是**"改进自己"最真实的那个形态**：用打包版（或另一个 checkout 的）
小明去改一份 clone 下来的源码。那棵树与正在运行的这棵没有任何关系，
只锚"正在运行的这份代码"等于对它完全不设防——而它恰恰是被改的那一棵。
桌面端按会话算一次并缓存（`state.cwd` 定下来就不变），权限规则一改就整体作废。

`installRoot` 是整棵树，因为打包产物里没有源码：能改的只有可执行文件、原生模块与
`app.asar` 本身，而改掉其中任何一样，清单里那些文件就都不作数了。

### 二、清单补齐，且规则 ID 从 slug 派生

清单从 18 条扩到 31 条，覆盖 M3 之后判定与执行真正住的地方（`tool-runtime/src/**`、
`runtime/src/turn*.ts`、`session-runtime.ts`、`kernel/src/container/**`、`compose/src/**`、
`code-runtime/src/**`、`apps/desktop/src/main/**` 与 `preload/**`……）。

规则 ID 由 `slug` 派生（`red.self-modify.app.kernel-policy-fs-write`），**不再用数组下标**：
下标会让"往中间插一条"把后面所有规则的 ID 平移，而 `ruleId` 是落库的审计字段，
平移之后历史事件里的那个 ID 指向了另一条规则。ID 撞车在构造期就抛。

### 三、`scripts/check-redline-targets.mjs`：每条 glob 必须指着真实文件

进 `pnpm verify` 与 CI 的 typecheck job。它用**内核自己的 `globMatch`** 去匹配仓库里的
真实路径——不自己写匹配器，否则会出现"闸门认为匹配、判定引擎认为不匹配"的分叉，
而那种分叉的表现正是它要防的东西（闸门绿着、红线空着）。

## 反向演练（已实机做过）

| 演练 | 结果 |
|---|---|
| 把 `packages/tool-runtime/src` 改名成 `src2`，跑闸门 | ✗ 报出 `tool-runtime packages/tool-runtime/src/**`，退出码 1 |
| 改回来再跑 | ✓ 31 条全部指向真实文件 |
| 把错锚点（`<repo>/apps/desktop`）喂进 `builtinRules()` | 判定文件得到 `allow(builtin.no-rule-matched)` —— A1 的原始形态被用例钉住 |
| 清单里的 13 个 M3 新位置逐个判 `fs.write` | 全部 `deny(red.self-modify.*)` |

用例：`packages/kernel/tests/self-code.test.ts`、`packages/kernel/tests/self-code-gate.test.ts`。
后者直接 import 闸门脚本里那份真实的 `findStaleTargets()`——复制一份逻辑就等于
测了一个不会被跑到的东西。

## 后果

- **正面**：自改红线第一次在真实运行方式下成立；"用小明改小明的另一份检出"这个场景
  被覆盖；清单腐烂从"没人发现"变成"CI 当场红"。
- **负面**：
  - 概念多了一层。读红线现在要先知道"锚在哪棵树上"，而不是一个 `appRoot`。
  - 平台层在 `resolvePaths()` 里做文件系统探测（往上最多 12 级），启动路径上多几次
    `existsSync`。可以接受，但它让 `resolvePaths` 从"纯计算 + 一次 realpath"变成了
    "会看磁盘"的函数。
  - `apps/desktop/src/main/**` 整个进清单，意味着小明改不了自己的装配面。这是有意的
    （那是唯一同时认识 Electron 与业务的地方），代价是将来它自己想改桌面装配时必须由人动手。
  - 清单从 18 条涨到 31 条 → 红线从 54 条涨到 93 条。红线"数量必须少"的判据仍然成立
    （它们是同一类保护的机械展开，不是 31 个独立决策），但下一次扩表前要重新问这个问题。
- **代价与缓解**：会话级规则层是按 cwd 现算的，`findSourceRoot()` 的结果会被缓存；
  设置里改权限规则时整体清空。
- **重新评估的条件**：出现第二个执行世界（容器/远端）时，"源码树在宿主上"这个前提
  会变——那时 H5（docs/09）的句柄形状要一并回答；或者 M4 的插件宿主让"小明自己的代码"
  不再只有一棵树。
