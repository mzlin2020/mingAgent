# ADR-0002 · Agent 循环形态：单主循环 + todo 工具，取代双 Agent 状态机

- **状态**：🟢 Accepted（2026-08-04 确认）
- **日期**：2026-08-04
- **相关**：[02-参考项目评审 §2.8](../02-参考项目评审-manusAgent.md)、[04-总体架构 §5](../04-总体架构.md)

## 背景

参考项目 manusAgent 用 `PlannerReActFlow` 实现了一个硬编码状态机：

```
IDLE → PLANNING(PlannerAgent) → EXECUTING(ReActAgent 逐步) → UPDATING → SUMMARIZING → COMPLETED
```

实际问题：

1. **简单任务被强制走完整流程**。"看下这个文件"也要先生成计划、再执行、再更新计划、再总结，四次以上 LLM 往返。
2. **上下文双份**。Planner 与 ReAct 各存一份 memory（`sessions.memories` 里两条），同一件事的上下文存两遍、也贵两遍。
3. **规划质量受限**。计划在信息最少的时刻（任务开始前）一次性生成，执行中发现的信息只能通过 `UPDATING` 阶段有限回流。
4. **流程僵化**。任何新的执行模式（并行探索、条件分支、递归拆解）都要改状态机本身。

## 选项

### A. 保留 Planner/Executor 双 Agent 状态机
- 优点：流程可预测；进度对用户可见；超长任务（几十步）的可控性好
- 缺点：如上四条

### B. 单一主循环（模型 ↔ 工具），无显式规划阶段
- 优点：简单任务一轮结束；上下文单份；模型自主决定拆解粒度；新执行模式无需改内核
- 缺点：长任务缺乏进度可视化；模型可能"跑偏"而用户看不出来

### C. 单主循环 + `todo` 工具（规划降格为工具）
- 优点：兼具 B 的灵活与 A 的可视化——模型在需要时主动调用 `todo_write` 产出清单，UI 把清单渲染成进度视图；简单任务不产生任何规划开销
- 缺点：依赖模型主动使用该工具（需要提示词引导）；进度的准确性由模型负责

## 决策

选择 **C：单主循环 + `todo` 工具**。

关键认识：**规划是一个动作，不是一个流程阶段。** 把它做成工具，模型就能在任何时刻按需规划、随时重排，而不是被状态机强制在唯一的时间点规划一次。

子 Agent 的定位同步调整：**子 Agent 是能力，不是流程阶段**。主循环在需要隔离上下文时（探索性搜索、大量文件扫描）派生子 Agent，子 Agent 拿独立的上下文窗口，只把结论回传主线。

## 后果

**正面**
- 简单任务的成本从 4+ 次 LLM 往返降到 1 次
- 上下文只有一份主线，token 消耗接近腰斩
- 内核不需要为新的执行模式改动（提示词与工具层就能演化）
- 与主流编码 Agent（Claude Code 等）的实践一致，社区经验可直接借鉴

**负面**
- 长任务的进度依赖模型主动维护 todo 清单，可能不准或忘记更新
- 失去了"流程一定按预期阶段推进"的确定性保证

**缓解措施**
- 提示词中对超过 N 步的任务强引导使用 `todo` 工具
- 主循环设硬性上限（最大轮数、最大成本、最大耗时），超限暂停并询问用户，而不是无声空转
- UI 始终展示当前轮数与累计成本，跑偏时用户能立刻发现并打断

**重新评估的触发条件**
- 真实使用中出现大量"模型不做规划直接乱撞"的案例，且提示词引导无效
- 出现需要严格审批流的场景（如每一步都要人工确认的生产环境操作）——那时可以作为**可选的执行模式**引入显式状态机，而不是回退默认行为
