# ADR-0053 · 微内核的特权底座与扩展点边界

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0039](./0039-放弃审批模式.md) · [ADR-0052](./0052-插件容器与效果模型.md) · [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md) · [ADR-0024](./0024-路径能力网关.md) · [docs/06-安全与权限模型](../06-安全与权限模型.md)

## 背景

ADR-0052 引入插件容器之后，立刻出现一个必须当场回答的问题：**什么是可以被插件替换的，
什么不是。**

参考实现 deepseek-harness 的立场写在它的架构文档第一段：

> There is no privileged core to patch: you extend dsh by mounting a plugin beside the others.

对它成立，因为它的安全模型是"权限判定也是一个插件，返回 allow/deny/ask，没有的话降级为 deny"。
对小明**不成立**，理由是本仓库已经用三次真实事故换来的教训：

- **ADR-0017**：自改红线只挂 `self.modify` 时，一个声明 `fs.write` 的普通写文件工具就能整体
  绕过它。教训是"红线按**目标是什么**写，不能按**调用方自称在做什么**写"。
  如果红线判定本身可以被一个插件替换掉，这条教训等于白学。
- **ADR-0018 / ADR-0024**：判定看到的路径必须就是工具打开的那个路径，靠的是网关在判权**之前**
  做 `realpath.native` 并回写 `input`。如果网关是一个可以被重排到判定之后的监听器，
  Windows 8.3 短名绕过当场复活。
- **ADR-0039**：权限判定收敛成 `allow`/`deny` 二值，`ask` 从 `PolicyVerdict` 删除，
  这是编译期护栏。参考实现保留 `ask` + `ctx.approval`，照搬它的 `PreToolDecision` 会把
  一个刚被删掉的状态原样搬回来。

同时，"完全没有扩展点"也不行——那正是 `turn.ts` 现在的问题。所以需要的不是"要不要扩展点"，
而是**一条精确的边界**。

## 选项

### 选项 A：全可替换（对齐 deepseek）

优点：概念最干净，一句话说得清；扩展体验最好。
缺点：小明的三条红线教训全部作废。而且它把安全性从"结构上做不到"降级为"没人写那种插件"——
本仓库已经证明过八次，"规则存在但从未生效"是这个项目最常见的失效形态。

### 选项 B：全不可替换（只在指定位置留几个回调）

优点：安全性最强。
缺点：等于没做容器。回调数量会随需求线性增长，最终退化成今天的 `TurnDeps` 12 个可选字段。

### 选项 C：特权底座 + 单调扩展点

优点：底座在结构上不可绕过；底座之外全部开放；"扩展点只能收紧"是一条可以被反向演练
证伪的规则，而不是一句自觉。
缺点：需要维护一份"哪些是底座"的清单，并且这份清单必须有装配期断言兜着，否则它又变成
一份没人执行的文档。

## 决策

**选择 C。小明是"微内核 + 不可绕过的安全底座"，不是"一切可替换"。** 这是与参考实现最大的
理念分歧，任何后来者按 deepseek 的形状补代码前必须先读这一条。

### 一、特权底座清单（不可替换、不可卸载、不可重排）

| 底座 | 现在住在哪 | 为什么不能是插件 |
|---|---|---|
| **seq 单点分配** | `SessionRuntime.record()` | ADR-0013 不变量三。两个分配点等于事件流有洞，`reduce()` 不再可信 |
| **权限判定 `evaluate()`** | `@xm/kernel` PolicyEngine | ADR-0039 的三步判定与 27 条红线。可替换等于红线可替换 |
| **路径 / 命令 / 主机网关** | `tools-core/src/gateway.ts` | ADR-0018/0024/0026/0028。它必须排在判定之前并回写 `input`，位置本身就是安全语义 |
| **密钥读取** | `SecretStore` | 配置层刻意不接环境变量（否则 `shell.exec` 会把它交给子进程）。第二条读取路径等于废掉这个设计 |
| **`redact()` 日志脱敏** | contracts / 审计写入点 | 可绕过等于密钥可落盘 |
| **事件落库与广播顺序** | `record()` 先 append 后 publish | ADR-0013 不变量五 |

容器在装配收敛时**断言这六项在位**，缺任何一项拒绝启动并指名缺哪一项。
断言的判据是"这个服务是不是由基线层提供的那一个"，不是"这个 key 上有没有东西"——
后者可以被一个同名冒充插件满足。

### 二、扩展点只能收紧（三条形式化规则）

1. **`waterfall` 监听器不能把 `deny` 变回 `allow`。** 判定结果一旦为 deny，后续监听器
   即使调用 `next()` 也只能保持 deny 或换一个更严的理由。容器对判定类 waterfall
   做单调性检查，检测到放宽当场抛错并记审计。
2. **红线判定是 `guard`，不是 waterfall 上的一环。** `guard` 单调、同步、终局：
   返回拒绝理由即拒绝，返回 `undefined` 即不表态。**后续任何监听器都没有翻案入口**
   ——不是"不应该翻案"，是接口上拿不到那个能力。
3. **收紧的表达方式只有一种：追加 deny。** 与 ADR-0039 一字不差。插件想限制某个能力，
   写一条 deny 规则或注册一个 guard；**不许引入第三种判定值**。

### 三、`ask` 不因为参考实现有就回来

`PolicyVerdict` 保持 `allow | deny` 二值。参考实现的 `PreToolDecision` 有
`{kind:'ask'}` 并由 `ctx.approval` 服务应答，**照搬时必须删掉这一支**。
ADR-0039 的背景值得重读：ADR-0034/0035/0036 是三次真实体验问题，每次都出在
"判完之后再修正一次"那种形状上。`ask` 就是那种形状的入口。

### 四、基线层不可 patch

profile / patch / 三方插件都不能替换或卸载基线层的插件行（ADR-0059 展开）。
`config.json` 的 `permission.rules` 仍然是**唯一**的用户侧权限入口，项目层只能收紧
（`tightenOnly`，ADR-0023）——插件系统不新开第二个入口。

## 后果

- **正面**：扩展点全部开放的同时，安全性不依赖"没人写坏插件"。三条真实教训
  （0017/0018/0039）在结构上继续成立。

- **负面**：底座清单是一份需要人维护的东西。它会漂移——新增一个安全相关组件时忘了加进清单，
  就等于悄悄开了一个可替换的口子。缓解：清单同时存在于本 ADR 与容器的装配期断言里，
  **断言是可执行的那一份**；ADR-0060 的不变量注册表再加一道运行时检查。

- **负面**：某些合理需求会被这条边界挡住。例如"我想在判定之后加一层项目自定义放宽"——
  做不到，只能改 `permission.rules`。这是有意的，不是遗漏。

- **代价与缓解**：`guard` 的单调性让一部分插件写法变笨（想放宽只能不注册，而不是注册一个
  放宽的监听器）。可以接受：放宽本来就该是配置的事，不是代码的事。

- **必做的反向演练**（缺一不可，每条都要先看它红一次）：
  1. 写一个恶意 waterfall 监听器，在红线 deny 之后返回 allow → 必须被单调性检查拦下。
  2. 写一个插件冒充基线层的 `ctx.policy` 服务 key → 装配期断言必须拒绝启动。
  3. 把网关重排到判定之后 → 用一个带符号链接（Windows 上用 8.3 短名）的路径，
     判定与执行必须分叉，测试必须红。
  4. 卸载 `redact` 插件 → 装配拒绝启动。

- **重新评估条件**：如果出现一类真实需求，既不能用 deny 表达、又不能用配置表达，
  且连续被这条边界挡住三次以上——那时要重新评估的是"表达能力不够"，
  应当扩充规则语言，而**不是**放开底座。
