# ADR-0030 · 桌面端三档审批模式：请求批准 / 帮我批准 / 完全访问权限

- **状态**：🟢 Accepted（2026-08-08）
- **日期**：2026-08-08
- **相关**：落地 [docs/09 C6](../09-待讨论的开放问题.md)（桌面端如何降噪）；复用
  [ADR-0003](./0003-默认权限策略.md)（平衡档默认规则、红线不受档位影响）与
  [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md)（C5：YOLO 跳过 `ask`、
  不跳过任何 `deny` 的语义）；**不修改**两者定下的判定逻辑

## 背景

用户真实体验反馈：让小明做一个"写个 todolist"这么朴素的任务，中途弹出的确认框超过
8 次，注意力全耗在点"允许"上。M1-c 的审批 UI（本次 / 本会话 / 永久 / 拒绝）解决的是
"每一条主张要不要问"，没有解决"这一整段时间我根本不想被问"——这是 docs/09 C6
（2026-08-07 提出）已经记录过的开放问题。

用户要求仿照 Codex 做三档模式：**请求批准**（逐项询问）、**帮我批准**（仅检测到
风险项才询问）、**完全访问权限**（任何操作都不问），并明确这是"特别重要"的功能。

C6 早就把关键张力拆清楚了：

1. **"帮我批准"** 与已经实现、已经过 ADR-0017/C5 验证过安全语义的
   `PermissionTier.yolo` 高度重合——`engine.ts` 的 YOLO 语义是"跳过 `ask`，不跳过
   任何 `deny`"（红线与用户自己写的 deny 规则原样生效）。缺的只是桌面端一个开关，
   从未实现过。
2. **"完全访问权限"** 字面意思（"任何操作"）比 YOLO 更进一步：如果连红线也放行，
   就与 ADR-0003 起的地基性质（"红线不受档位影响"）直接冲突。C6 明确写着"这一步
   不该被一个 UI 开关的命名顺带做掉，需要单独拍板"，且倾向是**不与"帮我批准"
   同批做**。

落地前用一个问题跟用户确认了"帮我批准"具体放行到哪一步——用户选择**"连执行命令
也放开"**，即 `shell.exec` 也不再询问，只在撞到红线/deny 时才拦。用户也认可这会让
"帮我批准"和"完全访问权限"在机制上几乎是同一件事，需要靠文案/开启门槛区分，而不是
靠判定逻辑区分。

## 决策

### 一、`ApprovalMode` 是纯桌面层概念，不进 `@xm/contracts`，不碰 `evaluate()`

新增 `apps/desktop/src/shared/ipc.ts::ApprovalMode = 'ask' | 'auto' | 'full'`，只做一件
事：决定这次 `runTurn` 传哪个已有的 `PermissionTier` 进去。

| UI 模式 | `ApprovalMode` | 映射的 `tier` | 行为 |
|---|---|---|---|
| 请求批准（默认） | `ask` | `balanced` | 与今天完全一致 |
| 帮我批准 | `auto` | `yolo` | 跳过所有 `ask`（含 `shell.exec`），红线与全部 `deny` 原样生效 |
| 完全访问权限 | `full` | `yolo`（与"帮我批准"相同的判定机制） | 唯一区别是桌面 UI 的开启门槛与文案 |

**不新增 `PermissionTier` 的第四个值，不修改 `engine.ts` 一行。** 两个新模式都落在
`balanced`/`yolo` 这两个已经在 `approval.test.ts`/ADR-0017 里验证过的既有语义上——
`packages/kernel`、`packages/contracts`、`packages/runtime` 本轮零改动。

这把"完全访问权限是否该越过红线"这个 C6 明确要求"单独拍板"的问题，诚实地记成
本轮**不做**的遗留项（见下），而不是顺手在一次 UI 需求里定案。

### 二、`auto` 与 `full` 映射到同一个 tier 是刻意的，不是偷懒

如果真要让"完全访问权限"字面意义上"允许任何操作"，就必须让它连红线、连内置的
敏感路径读/持久化写/SSRF/危险命令 deny、连用户自己写的 deny 规则都放行——这正是
C6 点名"不该被一个 UI 开关的命名顺带做掉"的那件事：

- 红线（`immutable: true`）是本项目从 ADR-0003 起就有的地基性质，"红线不受档位
  影响"没有任何一条分支能绕开它。做一个能越过它的档位，等于重新回答一个已经
  定案过的问题。
- 内置的非红线 deny（敏感路径读 ADR-0025、持久化写 ADR-0027、SSRF ADR-0028、
  危险命令 ADR-0026）背后每一条都对应一类真实攻击面；用户自己写的 deny 更是
  ADR-0017/C5 刚刚修过的真实 bug——"YOLO 跳过用户自己写的 deny"曾经是一个能被
  实测复现的安全回归，教训是"这一小时别烦我"不该悄悄注销用户的长期意图。

在没有专门 ADR 重新拍板"红线是不是真的还是红线"之前，本轮**不实现**任何越过
`deny`/红线的机制。`auto`/`full` 因此在引擎侧是同一件事，区别完全放在桌面层：

- 切到 `auto`：直接生效，不需要二次确认——它是已验证过的 YOLO 语义，不是新的风险。
- 切到 `full`：不立即生效，先展开一段警告 + "确认开启"按钮，文案明确写清楚
  "完全访问权限不会再向你确认任何操作……红线和你自己写的拒绝规则仍然生效，作为
  最后一道保险"——把"完全"讲清楚是"不再问你"而不是"没有底线"，对应 C6 提的
  两条要求：讲清楚字面意思、给一个比点一下按钮更高的操作成本。

### 三、会话级、不持久化

跟 docs/06 对 YOLO 开关的既有约束一致："必须显式开启""仅限当前会话，不持久化"。
`ApprovalMode` 存在 `apps/desktop/src/main/approval-mode.ts::ApprovalModeStore`
（纯内存 `Map<SessionId, ApprovalMode>`）里，`createSession()` 里一律初始化成
`ask`，不读也不写 `config.json`。重启应用后所有会话回到"请求批准"。

`config.permission.tier`（原来启动时读一次、直接传给 `runTurn` 的那个字段）不再
被 `sendUserMessage` 使用——每次调用改用 `TIER_OF[approvalModes.get(sessionId)]`，
默认值 `ask` 由 `ApprovalModeStore.get()` 兜底，不依赖 `config.json`。这个字段本身
未删除（schema、`loadConfig` 都不受影响），只是桌面端不再是它的消费者。

### 四、把纯逻辑从 `services.ts` 抽出去，为了能在没有 Electron 的环境里单测

`TIER_OF` 映射与 `ApprovalModeStore` 单独放进 `apps/desktop/src/main/approval-mode.ts`，
不写在 `services.ts` 里——跟 `multimodal-input.ts` 抽出去的理由一样：`services.ts`
直接 `import 'electron'`，vitest 在这个仓库的配置下跑不起来。抽出去之后
`apps/desktop/tests/approval-mode.test.ts` 才能不依赖 Electron 独立验证映射关系与
"会话级、立即生效"这两条行为约定。

## 后果

- 用户可以在界面上随时切换审批模式，不用碰配置文件、不用重启会话。
- "写个 todolist 被问 8 次"这个具体场景被解决：`auto`/`full` 下 `fs.write`/
  `fs.delete`/`shell.exec` 等原本逐条 `ask` 的操作全部零确认通过。
- 红线与所有 `deny`（含用户自定义）在三档模式下都不受影响——本轮没有引入任何
  新的越权路径。
- 头部新增一个常驻的 `ApprovalModeSwitcher`，任意时刻都能看到当前生效的模式，
  避免用户忘记自己开着高权限模式继续跑长任务。

## 反向演练

- `packages/kernel`/`packages/runtime` 的既有测试（`approval.test.ts` 等）全部
  不变、全部仍然通过——本轮没有改动判定逻辑，这是"零改动"这个决策本身的验证。
- `apps/desktop/tests/approval-mode.test.ts`：`TIER_OF.ask === 'balanced'`，
  `TIER_OF.auto === TIER_OF.full === 'yolo'`；未记录过的会话默认 `ask`；
  `init()` 把会话重置回 `ask`；`set()` 立即生效；会话之间互不影响。
- `apps/desktop/tests/ipc.test.ts`：三档模式 schema 校验通过，非法字符串
  （如遗留的 `'strict'`/`'yolo'` 这类内部 tier 名）被拒绝——渲染层不能绕过
  `ApprovalMode` 直接指定 `PermissionTier`。
- 手工检查：桌面应用里三个模式来回切换，"完全访问权限"需要二次确认才生效，
  界面任意时刻都能看到当前模式。

## 遗留

**"完全访问权限是否该越过红线（乃至越过 deny）"仍未解决，本轮刻意不做。** 如果
将来真的要做一个字面意义上"允许任何操作"的档位，C6 列的两个前提条件依然成立：

1. 需要重新回答"红线是不是真的还是红线"这个 ADR-0003 起就定案过的问题，而不是
   在现有 `PermissionTier`/`ApprovalMode` 上加一档就完事——那意味着要在 `evaluate()`
   里开一个能跳过 `immutable deny` 的分支，这是本项目安全模型里从未存在过的东西，
   需要独立的、正面回答"这样做是否可接受"的 ADR，不能靠这次的桌面 UI 需求顺带定案。
2. 即使真做，也需要比"点一下按钮"更高的操作成本（例如要求先手改配置文件、或者
   有比现在这个内联二次确认更醒目的警告），否则和"这个应用没有权限模型"没有
   实质区别。

其余已知的、本轮没有触碰的邻近问题：

- `config.permission.tier` 字段本身还在，但桌面端不再读它做默认值——headless/
  CLI（M3）等非桌面入口如果要暴露类似的模式切换，需要各自决定怎么接，本 ADR
  的方案只覆盖了 `apps/desktop`。
- 没有为"帮我批准"/"完全访问权限"下被静默放行的操作补任何额外的事件/日志——
  `evaluate()` 判成 `allow` 本来就不产生 `permission.request`，这与今天所有走
  `allow` 规则的操作（比如 `fs.read`）的可见性一致，没有制造新的不透明。
