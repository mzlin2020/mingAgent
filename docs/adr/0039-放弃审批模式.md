# ADR-0039 · 放弃审批模式：权限模型收敛为「红线 + 拒绝清单」

## 背景

用户的决定，原话：

> 彻底放弃多档模式。小明最终是一个基本可以完全自主的 agent —— **只给几条红线即可**，
> 红线后续可自行展示和配置。之前的审批模式彻底不要了。

这个决定是三次真实体验反馈之后的收尾。前三次都在同一个形状上：
[ADR-0030](./0030-桌面端三档审批模式.md) 加了三档开关、
[ADR-0034](./0034-知情授权穿透注入降级.md) 修了"同一个域名反复问"、
[ADR-0035](./0035-注入降级感知审批档位.md) 修了"降级把 YOLO 刚放行的又打回来问"、
[ADR-0036](./0036-只检查的主张.md) 修了"每次联网弹两个框"。四份 ADR 都在**降噪**，
而用户的结论是这条路走到头也不对：**噪音的根不在某一条路径上，在"要不要问人"这个动作本身。**

### 为什么现在可以干净地做（四条事实核查）

1. **三档在引擎侧本来就只有两档。** `apps/desktop/src/main/approval-mode.ts` 的
   `TIER_OF = { ask: 'balanced', auto: 'yolo', full: 'yolo' }` —— `auto`/`full` 映射同一个
   tier，ADR-0030 §二与 ADR-0035 补记都明写这是刻意的。删掉「完全访问权限」零行为损失，
   而这也是用户最先自己发现的一点。
2. **护栏不依赖审批。** 红线是 `immutable deny`，在 `evaluate()` 第 1 步跨层最先判；
   内置 deny（敏感路径读 ADR-0025 / 持久化写 ADR-0027 / SSRF ADR-0028 /
   危险命令 ADR-0026）同样是 deny。**它们一条都不经过"问用户"这条路径。**
3. **自改红线早就写对了。** `defaults.ts` 的 9 条受保护路径 ×
   `self.modify`/`fs.write`/`fs.delete` = 27 条 `red.self-modify-*`（immutable），
   覆盖 `packages/kernel/src/policy/**`、`packages/contracts/src/permission/**`、
   `scripts/**`、`.github/workflows/**`、`.githooks/**`、`.dependency-cruiser.cjs` 等。
   放开 `def.self-modify` 那条 ask 之后，小明能自由改自己的**业务**代码，
   改不了自己的**判权与护栏**代码——这正是「最终能改进自己」与「还有底线」之间那条线。
4. **还原点与不可篡改的审计仍在。** 写前还原点（ADR-0003 的"无条件还原点"，
   `tools-core/src/checkpoint.ts`）与 `red.audit-log-write`/`red.audit-log-delete`
   都不受本次改动影响。审批换掉之后，**"事后可回滚 + 可审计"是唯一的兜底**。

## 决策

### 一、判定结果收敛为 `allow | deny`，`ask` 从契约里删除

`PolicyVerdict` 去掉 `ask` 那一支（连带它独有的 `risk` 字段），`PolicyRule.effect`
从 `['allow','ask','deny']` 收窄为 `['allow','deny']`。

**这是编译期护栏，不是约定。** 想再加回"问一次"的路径，会先撞上类型错误，
而不是先长出一个悄悄挂起的分支。本项目栽过八次"规则存在但从未生效"，
能让编译器管的就不写成运行时断言——反向演练里第一条就是往 `defaults.ts` 塞
一条 `effect: 'ask'`，它在 `tsc` 阶段就红。

### 二、`evaluate()` 从五步降到三步

```
0  target 规范化，失败关闭 → deny
1  红线：全部层里的 immutable deny，跨层最先判（含 match.trustLevel 维度）
2  分层求值：自后向前第一个有匹配的层定案；层内 deny 胜 allow，同效果后定义者胜
3  没有任何层匹配 → 放行
```

删掉的两步都随"问用户"一起失去落点：

- **档位兜底**（strict/balanced/yolo，ADR-0003）。它唯一的作用是决定"没有规则匹配时
  要不要问"。没有 ask 之后三档退化成同一档，留着等于让调用方在一个没有区别的枚举上
  做选择——而这种选择迟早会被当成有意义的。`PermissionTier` 与 `config.permission.tier`
  一并删除。
- **注入降级**（`untrusted-downgrade.ts`，228 行）。它的全部输出是 `allow→ask` / `ask→deny`。

**第 3 步是本次唯一真正放宽的地方**，所以 `ruleId` 明确写成 `builtin.no-rule-matched`，
不假装是某条规则的功劳：审计里"无规则匹配，默认放行"和"命中某条 allow 规则"是两件事。

### 三、注入降级改写成三条声明式 deny

判据原样照抄 ADR-0035 论证过的那一条——**后果留不留在本会话之外**：

```ts
// kernel/policy/defaults.ts::UNTRUSTED_CONTEXT_RULES
untrusted.git-push          git.push          match: { trustLevel: ['untrusted'] }
untrusted.package-install   package.install   match: { trustLevel: ['untrusted'] }
untrusted.system-settings   system.settings   match: { trustLevel: ['untrusted'] }
```

形状与早就存在的 `red.secrets-read-untrusted` / `red.gui-input-untrusted` /
`red.plugin-install-untrusted` 完全一致，用的是**已经在跑的** `match.trustLevel`
匹配维度，不是新机制。**规则表达在规则表里，而不是一个能推翻前面全部结论的后置修正步骤**
——那个形状正是本项目在 ADR-0034/0035/0036 上连着栽三次的地方。

**三条刻意不是 `immutable`。** 新模型里没有"当场点允许"这个动作，用户表达
"我知道它读过网页，我仍然允许它推这个仓库"的唯一方式是在 `config.json` 里写一条
allow——用户层排在内置层之后，压得住它们（ADR-0023）。这是把 ADR-0034 的
「知情授权」换了个时机：从事中一次点击，变成事前一次配置。
项目级配置盖不住（只能收紧，`tightenOnly`）：那个文件躺在别人的仓库里，
而"仓库里的文件能放开自己被 push 的限制"正好是这条防线要挡的东西。

### 四、内置规则表变成一张纯拒绝清单

12 条 `def.*` 全部删除：10 条 ask 没有落点，2 条 allow（`fs.read`/`env.read`）
与第 3 步的兜底是同一件事，说两遍只会让人以为它们有额外作用。
`builtinRules()` 剩下的全是 deny，读法因此变得很简单：**它列的就是小明不许做的全部事情。**

这也是「红线后续可自行展示和配置」最容易渲染的形状（docs/09 C9）。

### 五、事件保留，状态字段删除

`permission.request` / `permission.decision` 两个事件 schema **一个字没动**，
但只在拒绝时成对产出（`by: 'policy'`，紧挨着 `tool.error`）。它是"为什么拦我"的
审计依据，也是老会话仍然能回放的前提（ADR-0008）。

而 `SessionState` 里由它们派生的东西全部删除：`pendingPermission`（那张卡片）、
`grants`（本会话都允许）、`SessionStatus` 的 `'waiting_permission'`、
`OrphanedTurn` 的 `'permission'` 变体。`reduce()` 对两条事件只推进 `lastSeq`——
**审计记录与会话状态是两件事**，以前混在一起是因为要驱动那张卡片。
回放老事件流不会崩，也不会凭空造出一个当时并不存在的宽松状态（有断言钉着）。

### 六、桌面端：删掉审批 UI，补上那个一直没做的按钮

删除 `PermissionCard`、`ApprovalModeSwitcher`、`ApprovalModeStore`/`TIER_OF`、
`RespondPermission*` 与 `Get/SetApprovalMode` 全链路（shared → channels → preload →
main ipc → services → bridge → store → App），以及 `services.ts` 里那个挂起审批的
`pending` Map 与它"关窗/退出/停止三处都必须兑现成 deny"的纪律。

**顺带修掉一个 ADR-0019 的落地缺口**：`clearUntrusted` 这条 IPC 从 ADR-0019 起就是通的，
但渲染层从来没有入口——那个"只有人能按的按钮"其实不存在。以前这不致命，因为降级
产出的是可当场授权的 ask；现在卡片没了、三条污染 deny 就位，**被拦的用户在应用里
就没有任何出路了**。所以本轮补上 `UntrustedBanner`：说清楚哪三类操作会被拒、
解除的范围是整个会话而不是某一个目标，然后给一个「我看过了，解除标记」。

这是"规则存在 ≠ 规则生效"的另一种形状：**出路存在，用户按不到。**

## 后果

- 用户报过三次的那个症状消失了：真实任务全程零确认框，`pnpm smoke` 里
  `fs.list → fs.read → fs.write ×2` 一条权限事件都不产生。
- 代码净减约 900 行（含测试）：`evaluate()` 392→约 300 行、`turn.ts` 1059→840 行、
  `layers.ts` 129→75 行、`untrusted-downgrade.ts` 与 `layer.ts` 整个删除、
  `defaults.ts` 776→约 690 行、桌面端删掉四个文件。
- **这是一次真实的安全收窄，写清楚是本节存在的意义**：
  - 不可信上下文下，除三条严重项外的不可撤销操作（`net.fetch` / `fs.delete` /
    `shell.session` / `net.listen`）**静默放行**。一个网页说服模型去访问某个网址、
    删掉某个文件，不会再有任何提示。ADR-0035 已经在 yolo 档下接受过这个代价，
    本次把它变成了唯一的模式。
  - 没有规则匹配的操作一律放行。闭集之外的新能力、新工具默认是通的。
  - 兜底是**事后**的：红线 + 拒绝清单 + 写前还原点 + 不可篡改的审计日志。
    "拦住"这件事完全依赖那张清单写得对；清单没覆盖到的，只能靠回滚。
- `shell.session`（PTY）的结构性代价没有变化，但**唯一的缓解手段消失了**：
  ADR-0031 定的是"打开会话时问一次、之后完全不再判权"，那一次 ask 是唯一的知情点，
  现在它按拒绝清单判，撞不上就直接开。见「遗留」。
- 事件流里从此不会出现 `by: 'user'` 的 `permission.decision`（有断言钉着）。
  老会话里的那些仍然读得出来，只是不再影响判定——**回放出的老会话比当时更宽松，
  这是刻意的**：状态里已经没有能表达"本会话都允许"的地方了。

## 反向演练

四条，逐条做过、看它红过、恢复后绿：

1. 往 `defaults.ts` 塞一条 `effect: 'ask'` 的规则 → `tsc -b packages/kernel` 当场红
   （`TS2322: Type '"ask"' is not assignable to type '"allow" | "deny"'`）。
   **它在编译期就红，进不到运行期**，这正是决策一想要的。
2. 把 `evaluate()` 第 3 步的兜底从 allow 改成 deny →
   `policy-no-ask.test.ts` + `no-approval.test.ts` 红 10 条。
3. 删掉 `UNTRUSTED_CONTEXT_RULES` 里的 `untrusted.git-push` → 两个新闸门各红 1 条。
4. 把 `red.self-modify-*` 的 `immutable` 改成 `false` →
   `policy-no-ask.test.ts` 与 `policy-redlines.test.ts` 红 2 条。

新增两个闸门文件：

- `packages/kernel/tests/policy-no-ask.test.ts`：穷举
  `ALL_CAPABILITIES × {user,model,untrusted} × 四种层组合`，断言结果 ∈ `{allow,deny}`、
  永远带 ruleId/reason、内置表里一条 allow 都没有；逐条拿红线自己的 target 打它自己，
  验证用户层 allow-all 翻不了任何一条。
- `packages/runtime/tests/no-approval.test.ts`：端到端照用户的原始场景写
  （ADR-0035 的教训——按用户的场景数框，不按自己修的路径数）：写文件 / 执行命令 /
  读过网页之后再写文件，断言 `permission.request` **为 0**；污染后 `git.push` 被拒
  且恰好一对审计记录；解除标记后能跑；改判权逻辑被红线拒、改业务代码放行。

`pnpm verify` 六个 job 全绿：1033 个测试通过，depcruise 248 模块无违规，headless
冒烟与写租约恢复冒烟通过。

## 遗留

1. **红线与拒绝清单的展示与配置 UI**（用户明确说的"后续"）→ docs/09 C9。
   前提写在那里：**能编辑规则的是人，不是小明**。若规则改成从 UI 写入某个数据文件，
   那个文件必须同样进 `SELF_MODIFY_PROTECTED`，否则等于给小明开了一条改红线的路。
   `platform/src/config.ts::appendUserRule()`（原子写 + 落盘前过构造期闸门）
   本轮起没有消费者了，**刻意保留**：它正是那个 UI 的写入端，且有自己的测试。
2. **`shell.session` 打开之后仍然零覆盖**，而打开时那一次知情点没了。
   缓解手段只剩流程性的（ADR-0031 的原话），或者将来给它单独写一条按 cwd 的 deny。
3. **`docs/06` 对 YOLO 的"必须显式开启，有明确警告"这条约束已被本 ADR 改写**为
   "默认自动放行 + 文档如实告知"。主界面刻意不常驻任何"当前是自动批准"的提示
   （用户明确要求不展示）；如实告知目前落在 docs/06、本 ADR 与不可信横幅的文案上。
   设置页那段只读的「权限模型」说明**没有做**——设置实体页本身还是 M3 的占位
   （`app-menu.tsx`），等它落地时一并补，记进 docs/09 C9。
4. 老会话事件里的 `grants` 不再影响判定（回放更宽松，见「后果」）。若将来要做
   "按当时的授权回放"，需要的是一个只读的历史视图，而不是把 `session` 层加回来。
