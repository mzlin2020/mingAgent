# ADR-0004 · 主界面形态：对话为主 + 可展开观察面板

- **状态**：🟢 Accepted（2026-08-04 确认）
- **日期**：2026-08-04
- **相关**：[01-愿景与设计原则](../01-愿景与设计原则.md)、[05-可插拔与扩展体系 §6](../05-可插拔与扩展体系.md)

## 背景

小明的定位是**通用 Agent**（既改代码也操作电脑），不是代码编辑器，也不是虚拟机控制台。主界面形态决定了产品定位的表达、开发复杂度的量级，以及未来能力扩展的容纳方式。

用户明确要求风格贴近 Claude Code 桌面端。

## 选项

### A. 对话为主 + 可展开观察面板
主视图是对话流，终端 / 浏览器 / 文件 diff / 屏幕四类观察面板按需展开。
- 优点：与"通用 Agent"定位一致；复杂度可控；新增能力只需注册新的观察面板，不动主布局
- 缺点：需要精心设计面板的展开/收起时机，否则用户会错过重要信息

### B. IDE 式三栏（文件树 + 编辑器 + 对话）
- 优点：代码场景直观
- 缺点：要自建编辑器体验（体量巨大）；把产品往"AI IDE"方向拉，与通用 Agent 定位冲突；操作电脑类任务在这个布局里无处安放

### C. Manus 式左右分栏（对话 + 常驻虚拟机视图）
- 优点：操作电脑场景直观
- 缺点：纯对话任务时右侧长期空置；常驻双栏在小屏上体验差

## 决策

选择 **A：对话为主 + 可展开观察面板**。

配套决定：**不内置全功能代码编辑器**，只做只读查看与 diff 审阅。要改代码用用户自己的 IDE。这条省掉的复杂度是整个项目里最大的一笔——编辑器是个无底洞，而它并不服务于"让 Agent 干活"这个核心。

四类观察面板通过[渲染器注册表](../05-可插拔与扩展体系.md)接入，与工具结果的 `display: { kind, payload }` 契约对应，因此**插件可以贡献自己的面板**，主布局不需要为新能力改动。

## 后果

**正面**
- 定位清晰：这是一个 Agent，不是编辑器
- 复杂度集中在对话流与面板系统两处，都是有成熟范式的东西
- 扩展路径明确：新能力 = 新工具 + 新渲染器，主界面零改动

**负面**
- 深度代码审阅体验弱于 IDE 式布局（多文件大改动的浏览会比较累）
- 面板的展开时机需要反复打磨——展开太主动会打断阅读，太被动用户会漏看关键信息

**缓解措施**
- diff 审阅做成一等公民（可逐块接受/拒绝），这是代码场景最高频的需求，值得单独投入
- 面板展开策略：工具产生**需要用户决策**的内容时自动展开（如待审批的 diff），纯过程性输出（命令回显）只显示折叠摘要
- M4 引入多窗口，让"同时盯两个任务"的场景有出口

**重新评估的触发条件**
- 真实使用中发现代码审阅体验成为主要瓶颈，且 diff 面板的改进无法解决
