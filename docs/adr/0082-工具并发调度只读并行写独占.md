# ADR-0082 · 工具并发调度：只读并行，写一律独占

- **状态**：🟢 Accepted
- **日期**：2026-08-17
- **相关**：地基复审四 D1；**收窄** [ADR-0005](./0005-工具并发与资源声明.md)；
  十二步链 [ADR-0055](./0055-Turn驱动器的扩展点契约.md)；
  路径规范化的时机 [ADR-0024](./0024-路径能力网关.md)

## 背景

ADR-0005 定了"混合式资源声明 + 冲突检测调度"，并把接口一路做进了工具定义：

- `ToolSpec.resources?(input)` → `{ kind:'path', mode:'read'|'write', glob }` /
  `pty` / `net` / `global`。`fs.read`、`fs.list`、`search.text`、`fs.write`、
  `edit.*`、`git.*`、`shell.exec`、`pty.*` 全都老老实实声明了。
- `ToolDescriptor.concurrency`（`parallel` / `exclusive`），注册时按"有没有声明资源"推导。

**调度器从来没有被写出来。** 驱动器一直是：

```ts
for (const call of streamed.calls) await dispatchCall(deps, extensions, turnId, call, codeMode);
```

于是模型一次回复里发的 5 个 `fs.read` 串成 5 段执行，而"读 5 个文件要 5 个 LLM 来回"
本来正是 ADR-0005 开头批评参考项目的那件事——小明省掉了模型往返，却把工具执行串了回去。
那两个字段至今**没有任何代码读过**：一整套接口成了注释。

## 选项

### 选项 A：照 ADR-0005 原样实现路径冲突检测

- 优点：并行度最大，"改不同文件的两次 `edit`"也能并行。
- 缺点：**做不到，而且不是工程量的问题**。`resources(input)` 拿到的是网关规范化
  **之前**的入参——相对路径、符号链接、Windows 8.3 短名都还没解析（那些发生在
  `prepareCall` 里，也就是排班之后）。`./a.ts` 与 `/work/a.ts` 在这一层看不出是同一个
  文件，冲突检测会漏判，而漏判一次的代价是并发写坏同一个文件。
  把规范化提到排班之前也不成：规范化要按 `ToolContext` 逐个调用做，
  而那正是十二步链的第 ③ 步——等于把链拆开重排，为的是一个次要收益。

### 选项 B：删掉 `concurrency` 与 `resources()`，承认小明只做串行

- 优点：诚实，代码少一截。
- 缺点：把一个**真实且高频**的收益扔掉。一个编码 Agent 一次读三五个文件是常态，
  而这些调用之间没有任何冲突可言。

### 选项 C：只并行"无论怎么排都不会互相影响"的那一类

- 优点：拿到收益的大头（并行读、并行 fetch、并行搜索），且**结构上不可能写坏数据**。
- 缺点：`edit` 改不同文件仍然串行——ADR-0005 明确想要的那条没兑现。

## 决策

**选 C。** 判据直接引用 ADR-0005 自己写下的那句话：

> 并发的收益是省时间，并发出错的代价是数据损坏，两者不对称。

一次调用算**并行安全**，当且仅当：

1. `descriptor.concurrency === 'parallel'`（工具作者自己的声明），**并且**
2. 它的 `resources(input)` 里没有 `write`、没有 `global`、没有 `pty`——
   只剩 `path/read` 与 `net`。

没有任何资源声明的 `parallel` 工具（`web.fetch`、`index.search`）算并行安全：
`parallel` 本来就是工具作者在 ADR-0005 的接口上做的那个声明。
**任何拿不准的情况一律退回独占**：工具查不到、入参解不开、`resources()` 抛异常。
判不了就串行，只损失时间；判错了就并发，可能损失数据。

调度形状（`packages/runtime/src/turn-schedule.ts`）：把模型给出的调用序列切成
**一串顺序执行的批次**，批次内部并发，单批上限 8（ADR-0005 定的默认值）。
一次写、一次 `shell.exec`、一次 `run_code` 各自独占一批。

**批次之间保序**：模型给出的先后关系只在并行安全的连续段内被打散，
而那一段里的调用按定义互不影响。"先读旧内容 → 写 → 再读新内容"这种序列
会被切成三批，顺序一字不动。

### 为什么不给它一个开关

ADR-0005 的缓解措施里写着"并发上限可配置，出问题时可一键降为全串行"。
不做：能并行的只剩下彼此无影响的只读调用，"出问题"该长什么样都描述不出来。
配置项要为一个可能存在的问题存在，而不是为一个想象中的问题存在（同 ADR-0076 的判据）。

## 反向演练

`packages/runtime/tests/tool-concurrency.test.ts`（用真的驱动器 + 会计数的慢工具）：

| 演练 | 结果 |
|---|---|
| 三个只读调用 | 同时在跑的峰值 = 3，总耗时接近一次而不是三次 |
| 两个"声明 parallel 但没有资源声明"的调用 | 峰值 = 2 |
| 10 个只读调用 | 峰值 = 8（切两批） |
| 读、**写**、读 | 峰值 = 1 |
| 读、`exclusive`、读 | 峰值 = 1 |
| 读、读、写、读 | 峰值 = 2；完成顺序是 {a,b} → w → c，批次之间一步没乱 |

把 `turn.ts` 换回旧的 `for await` 之后，前三条与最后一条当场红（峰值都变成 1）。
后两条**在串行下也是绿的**——这是有意的：它们钉的是"不许并行"，
而一个正确的实现在这两条上本来就该与串行同值。

## 后果

- **正面**：读多个文件、并发抓几个 URL、并发搜索从"串成 N 段"变成一段。
  ADR-0005 那两个字段第一次真的有人读。
- **负面**：
  - 一次回复里的多个工具调用，其 `tool.start` / `tool.end` 事件**会交错**。
    每一对仍然配对（内核不变量按 `callId` 断言，不受影响），但读事件流的人
    不能再假定它们是嵌套的。回放期的卡片按 `callId` 索引，不受影响。
  - 工具作者的 `concurrency` / `resources()` 声明**从今天起真的有后果**了。
    声明成 `parallel` 却偷偷写文件的工具会并发跑——ADR-0005 早就写下这条风险
    （"调度器无法验证"），现在它从纸面变成了实际风险。新工具评审要看这一栏。
  - `edit` 改不同文件仍然串行，ADR-0005 想要的那条没兑现。
- **重新评估的条件**：如果把网关的路径规范化提前到排班之前（那要重排十二步链，
  需要单独一份 ADR），选项 A 才重新成为可能；或者出现"多文件重构慢得受不了"的
  实际体验问题，那时这笔账要重算。
