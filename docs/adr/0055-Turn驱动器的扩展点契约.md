# ADR-0055 · Turn 驱动器的扩展点契约

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0052](./0052-插件容器与效果模型.md) · [ADR-0053](./0053-微内核的特权底座与扩展点边界.md) · [ADR-0024](./0024-路径能力网关.md) · [ADR-0026](./0026-命令的主张分解与argv契约.md) · [ADR-0048](./0048-M2-h上下文预算与持久摘要.md)

## 背景

`packages/runtime/src/turn.ts`（391 行）+ `turn-tools.ts`（376 行）是小明的主循环。
它今天把下面这些全部焊死在流程里：

- 多模态能力检查（`provider.capabilities(deps.model)` 判 vision / documents）
- `maxIterations` 兜底与 `max_tokens` 连续两次的处理
- `ContextBuilder` 组装（预算、持久摘要、稳定前缀）
- 写前 checkpoint
- 结果截断
- 工具分发的完整链条

每一条都是正确的实现，但**没有一条是可替换或可旁挂的**。想加 hooks、plan mode、
文件变更通知、压缩策略实验，只能改 `turn.ts`——于是这个文件会持续膨胀，
而它同时是全仓库最不该被随手改的文件（三条不变量落在这里）。

同时，`turn-tools.ts` 的 `dispatchCall()` 里那条链子是**用三份 ADR 换来的**，
顺序本身就是安全语义：入参先校验再解析最后判权（避免审批噪音与 TOCTOU）、
网关必须回写 `input`（ADR-0024）、主张只能加不能减、任一主张 deny 即整体 deny。
把它改造成可扩展的，**绝不能让扩展点有能力重排它**。

## 选项

### 选项 A：只加"钩子数组"，不改结构

在 `TurnDeps` 上加 `hooks?: { beforeTool?, afterTool? }`。
优点：改动最小。
缺点：钩子数量线性增长；没有撤销语义；没有顺序语义；没有"谁提供了这个钩子"的答案。
本质上是把 12 个可选字段变成 20 个。

### 选项 B：完全照搬参考实现的事件名与语义

优点：概念现成，文档现成。
缺点：它的 `tools/pre-execute` 返回 `allow | deny | ask`，并且**权限判定本身就在这个 waterfall 上**。
照搬会把 ADR-0039 删掉的 `ask` 搬回来，并让红线判定变成一个可被重排的监听器。

### 选项 C：命名扩展点 + 固定的特权链段

把 `turn.ts` 拆成"驱动器 + 命名扩展点"，但把安全链段整体钉死：扩展点插在它的**外侧**，
不能插进它的中间，也不能改写它的输入。

## 决策

**选择 C。**

### 一、工具执行链：十二步，前七步顺序不可变

```
① 工具查找（含 available() 过滤）
② parseInput —— strict 校验，模型给的参数在此定形
③ 构造 ToolContext
④ 网关规范化 —— realpath.native / argv 分解 / DNS 解析，
   回写 input、产出 claims 与 pinnedHosts；失败即失败关闭
⑤ 主张完备性断言 —— 工具声明的每个 capability 都必须有对应 claim，缺一即拒绝
──────────── 以上五步是特权链段，扩展点不得插入、重排或改写 ────────────
⑥ tool/pre-execute（waterfall）—— 插件可**追加 deny**
⑦ PolicyEngine evaluate() + 注册的 guard —— 单调终局，27 条红线在此
──────────── 判定完成，此后不可再放宽 ────────────
⑧ tool/execute（waterfall，around 环绕）—— checkpoint、超时、重试、度量
⑨ 工具体执行（经 ctx.executor，ADR-0054）
⑩ tool/post-execute（waterfall）—— 结果截断、内容替换、附加上下文
⑪ 渲染投影（presentationMeta，ADR-0058）
⑫ tool/result（只读观察）—— 审计、指标，不能改结果
```

三条硬约束，每条都对应一次真实教训：

1. **`tool/pre-execute` 不提供改写 `input` 的能力。** 参考实现也刻意不提供
   （"Input rewrite is deliberately not offered"），但对小明理由更强：④ 已经把判定用的
   路径回写进 `input` 了，让监听器在 ⑥ 改它，等于在判定与执行之间重开 TOCTOU 窗口，
   ADR-0018 的 Windows 短名绕过当场复活。
2. **⑥ 只能收紧。** 返回 deny 即 deny；返回"允许"只表示不表态，最终由 ⑦ 决定。
   容器对这条 waterfall 做单调性检查（ADR-0053 规则一）。
3. **⑧ 的环绕包装只许替换 `signal`。** 它可以为一次调用套一个更短的截止时间，
   但不能换掉工具、换掉入参、跳过 ⑨。原始调用方的 signal 由驱动器在进入 ⑨ 前重新接回。

   > **2026-08-15 定案（M3-c 复审）：这条允许项此前在代码里根本不存在。**
   > 实现把 `ToolContext` 冻结后直接交给 ⑨，监听器没有任何入口把更短的 signal 递进去——
   > 于是 ADR 给 ⑧ 留的**唯一**一件事，恰好是它做不到的那件，而 ⑧ 的典型用途
   > （超时、熔断）全都依赖它。这是本仓库最该警惕的形状：文档里写着、代码里没有、
   > 没有闸门会发现。
   >
   > 机制：waterfall 的 `next` 接受一个可选的 `AbortLike`，容器把它与当前生效的 signal
   > **取并集**（`mergeAbort`）后交给后续监听器与最内层核心，驱动器再把这枚 signal 换进
   > `ToolContext`。**用并集而不是替换**，"只能收紧"就成了结构性质：递一个永不 abort 的
   > signal 什么也放宽不了，原始调用方的取消永远还在。`input` / `tool` 一律沿用 ④ 的产物。
   >
   > 反向演练（`packages/runtime/tests/turn-extensions.test.ts`）：收紧生效、无插件时
   > 工具体拿到的就是原始 signal、收紧之后原始取消仍然穿透，三条都要能红。

### 二、回合级扩展点

| 扩展点 | 模式 | 能做什么 | 谁会用 |
|---|---|---|---|
| `turn/pre-step` | waterfall | 决定模型这一步看到什么：改写待发消息、或整体拒绝这一步 | 上下文预算与压缩、多模态能力检查、hooks、plan mode |
| `turn/request` | waterfall | 请求最终成形前的最后一次修改 | 采样参数、prompt cache 断点、录制 |
| `llm/stream` | waterfall | 包住流式读取 | 重试、录制回放、流量度量 |
| `turn/step-error` | waterfall | 一次模型请求失败后决定重试还是保留错误 | 上下文溢出恢复（压缩） |
| `turn/stopping` | serial | 回合自然停止前的终局检查，可要求再走一步 | `maxIterations` 兜底、`max_tokens` 连续两次、目标持续推进 |

`turn/pre-step` 的返回值是**权威的**：包装 `next()` 的监听器有责任保留下游的修改，
除非它就是要整体替换。这一点与参考实现一致。

### 三、从 `turn.ts` 搬出去的东西

| 现在在 `turn.ts` / `turn-tools.ts` 的 | 搬到哪 |
|---|---|
| `ContextBuilder` 组装（ADR-0048） | `turn/pre-step` 插件 |
| 多模态能力检查（vision / documents） | `turn/pre-step` 插件 |
| 写前 checkpoint | `tool/execute` 环绕插件（先建还原点，再 `next()`） |
| 结果截断 | `tool/post-execute` 插件 |
| `maxIterations` 与 `max_tokens` 连续两次 | `turn/stopping` 插件 |

搬完之后 `turn.ts` 只剩：认领输入 → 派发扩展点 → 读流 → 落事件 → 分发工具调用。
**三条不变量仍然落在它身上，并且更显眼了**：seq 只由 `SessionRuntime` 分配、
广播排在落库之后、工具执行前必过闸门。

### 四、`turn.ts` 仍然是特权文件

它不是插件，不可替换，不可卸载。理由与 ADR-0053 的底座清单同源：
事件的成对性（`turn.start` 必须有 `turn.end`，ADR-0008 的包含性不变量）、
中断必须落两条事件、Provider 抛错不得跨越流读取边界——这些是驱动器的固有责任，
交给可替换的实现等于交给"下一个写驱动器的人会不会记得"。

改 `turn.ts` 的门槛与今天一样高：必须同批更新本 ADR 与 `docs/04`。

## 后果

- **正面**：新行为不再改主循环。hooks、plan mode、目标推进、文件变更通知、压缩策略实验，
  全部是"注册一个监听器"。`turn.ts` 从 391 行降到预估 200 行以内。
- **正面**：扩展点是一份可枚举的清单，ADR-0060 的图谱生成能把"谁挂在哪个点上"生成出来——
  这比读 `turn.ts` 更能回答"这次调用到底经过了什么"。

- **负面**：调试链路变长。一次工具调用可能经过五个插件，栈里看到的是派发框架而不是业务代码。
  缓解：每个扩展点的派发在 trace 里留一条记录（L0 trace 从 M1-d.5 就有骨架），
  出问题时看 trace 而不是看栈。
- **负面**：⑥ 与 ⑦ 分成两处，"权限判定在哪"这个问题变得需要两句话回答。
  这是有意的分离——可扩展的那一半和不可绕过的那一半必须在结构上分开，
  否则 ADR-0053 的边界无处落地。

- **代价与缓解**：把 checkpoint 改造成环绕插件之后，"无条件还原点"（ADR-0003）的保证
  依赖于那个插件在位。缓解：它进 ADR-0053 的装配期断言清单——
  破坏性工具存在而 checkpoint 插件缺席时，拒绝启动。

- **必做的反向演练**：
  1. 写一个 `tool/pre-execute` 监听器试图改写 `input` 里的路径 → 接口上就拿不到写入口；
     若实现里留了口子，用符号链接构造判定与执行分叉的用例，必须红。
  2. 卸载截断插件 → 一个超大工具结果必须让预算测试红，而不是悄悄发给 Provider。
  3. 卸载 checkpoint 插件 → 装配期断言拒绝启动。
  4. 一个 `tool/execute` 环绕插件试图跳过 `next()` 直接返回伪造成功 → 结果必须被
     ⑫ 的审计识别为"没有真实执行"，或在结构上做不到（优先做不到）。
     > **2026-08-14 定案**：这条写的是"或"，也就是没定。
     > [ADR-0062](./0062-扩展点的异步契约与执行收据.md) 选了"做不到"：
     > ⑨ 真实执行时由驱动器签发一枚插件构造不出来的 `ExecutionReceipt`，
     > ⑫ 见到无收据的结果一律判为未执行。跳过 `next()` 仍合法（超时、熔断、干跑），
     > 被挡住的是**短路之后谎称执行过**。

- **重新评估条件**：如果出现一个真实需求，必须在 ⑤ 与 ⑥ 之间插入逻辑——先停下来问
  "它到底是不是在改判定输入"。如果是，答案是不行；如果不是，说明这份扩展点清单少了一个点，
  那就补一个命名点，而不是放开特权链段。
