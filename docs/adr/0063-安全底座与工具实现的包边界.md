# ADR-0063 · 安全底座与工具实现的包边界

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0053](./0053-微内核的特权底座与扩展点边界.md) · [ADR-0054](./0054-能力接缝三角色与执行世界.md) · [ADR-0059](./0059-组合配置profile与patch层.md) · [ADR-0024](./0024-路径能力网关.md) · [ADR-0003](./0003-默认权限策略.md) · [docs/01 原则二](../01-愿景与设计原则.md)

## 背景

`docs/01` 原则二从 M0 起就带着一条可检验约束：

> **约束**：删掉 `packages/tools-core` 后，内核 + UI 必须仍能启动（只是没有工具可用）。
> 这是可以写成集成测试的。

M3 规划复审（2026-08-14）发现：**这条约束在 M3 的设计里被悄悄换成了另一条。**

- [ADR-0059](./0059-组合配置profile与patch层.md) 的 profile 把基线行 `baseline.gateway`
  指向 `@xm/tools-core#gateway`；`@xm/compose` 明确依赖 `@xm/tools-core`。
- 于是 [M3 阶段划分](../M3-阶段划分.md) 的总验收第一条写成了
  "删掉全部**业务插件行**后应用仍能启动"。

**删行 ≠ 删包。** 删掉 profile 里的工具行之后，`@xm/compose` 对 `@xm/tools-core` 的
import 一条不少，物理删除那个目录仍然编译不过。原则二那条约束依旧没被兑现，
只是 DoD 的措辞让它看起来兑现了。这正是本仓库最忌讳的形态——
**规则还在，但检验它的那个测试换成了一个更容易通过的**。

根因不在 profile，在**包的切法**：`packages/tools-core` 里同时住着两类东西。

| 住在 tools-core 的 | 是什么 | 能不能删 |
|---|---|---|
| `gateway.ts` / `gateway-path.ts` / `gateway-path-inputs.ts` | 路径能力网关——判定与执行共用同一个路径的保证（ADR-0024） | **不能**，六项底座之一 |
| `checkpoint.ts` / `checkpoint-restore.ts` | 写前无条件还原点（ADR-0003） | **不能**，ADR-0055 已把它列进装配期断言 |
| `fs-*.ts` / `shell-exec.ts` / `pty-*.ts` / `git.ts` / `web-fetch.ts` / `search-*.ts` / `edit.ts` … | 工具实现 | **能**，它们正是原则二说的"没有工具可用" |

2026-08-14 对原则二的澄清已经把这两类分开了——"能力"与"能力的裁判"——
但那次澄清只改了文字，**没有改包**。裁判和能力还挤在同一个 `package.json` 里。

## 选项

### 选项 A：改原则二的约束，承认 tools-core 不可整体删除

优点：零代码改动，一句话的事。
缺点：把一条从未通过的验收改成一条能通过的验收，等于用降低标准来结案。
而原则二的这条约束是"一切皆插件"唯一可执行的检验方式——放弃它，
原则二就退回成一句没有检验手段的口号（`docs/01:41` 明写"不能被检验的原则等于没有"）。

### 选项 B：保持包不动，用 profile 测试代替物理删除测试

优点：M3-b 反正要做 profile，顺手就有。
缺点：见背景。它检验的是"装配层能不能少装几行"，而原则二问的是
"这个包在结构上是不是可拆的"。两者的差别恰恰是本次重构最该证明的那一点。

### 选项 C：把裁判从工具包里搬出去，新增 `@xm/tool-runtime`

## 决策

**选择 C。**

### 一、新增包 `@xm/tool-runtime`

从 `@xm/tools-core` 迁出三类内容，**只搬位置，不改任何签名或行为**：

```
@xm/tool-runtime            工具执行的安全底座
  ├─ gateway/               路径能力网关（含 realpath.native、argv 分解、pinnedHosts）
  ├─ checkpoint/            写前还原点与恢复
  └─ executor/local/        执行世界的 local 提供者（ADR-0054，M3-e 落地）

@xm/tools-core              工具实现，仅此而已
  └─ fs / shell / pty / git / web / search / edit …
```

`profile` 的基线行随之改指 `@xm/tool-runtime#gateway`、`@xm/tool-runtime#checkpoint`。

### 二、这次拆分顺带把一条规则升级了

[ADR-0054](./0054-能力接缝三角色与执行世界.md) 定过一条硬约束：
"`tools-core` 的工具实现文件不得 import `node:fs` 等模块，只有 local 提供者可以。"

在拆分之前，这条只能靠**包内文件 glob** 来写——depcruise 要精确地列出哪些文件算
"工具实现"、哪些算"提供者"，而新加一个文件忘了进名单就是一个静默的洞。
拆分之后它变成一条**包边界规则**：

- `@xm/tools-core` 不得 import `node:fs` / `node:child_process` / `node:net`（整包禁止）。
- 只有 `@xm/tool-runtime` 可以。

包边界规则是 depcruise 最擅长、也最不容易写漏的形状。**这是拆包的第二个理由，
且它比第一个理由更实用**：原则二那条验收一年跑一次，这条规则每次提交都在跑。

### 三、依赖方向

```
apps/desktop ──┬─→ @xm/compose ──┬─→ @xm/tool-runtime ──→ @xm/kernel（端口定义）
               │                 └─→ @xm/tools-core   ──→ @xm/kernel
               └─→ …
```

- `@xm/tools-core` **不依赖** `@xm/tool-runtime`：工具通过容器注入的 `ctx.executor`
  取用执行世界，不 import 提供者。这正是接缝的意义，也是"删掉 tools-core 仍能启动"
  在结构上成立的原因。
- `@xm/runtime` 依旧只认端口接口（`ToolGateway` 定义在 `kernel/src/port/`，
  `turn-types.ts` 接的是接口不是实现），**依赖方向一字不改**。

包数：8 → **10**（`@xm/compose` + `@xm/tool-runtime`）。这修正
[ADR-0059](./0059-组合配置profile与patch层.md) 里"8 → 9"的说法。

### 四、这不违反"不为插件新建细粒度包"

ADR-0052 的对策一是"**插件**住在现有包里，不为插件新建细粒度包"，
针对的是插件数量线性增长带来的包爆炸（参考实现 51 个包的路线）。
`@xm/tool-runtime` 不是一个插件包，它是**底座与能力之间的一条边界**——
数量是固定的一个，不随插件增长。两条规则不冲突。

### 五、M3 总验收第一条改回物理删除

```bash
rm -rf packages/tools-core
# + 一份不含工具行的 profile
pnpm typecheck && pnpm smoke   # 必须通过：应用启动，工具列表为空
```

这是原则二那条约束从 M0 写下以来**第一次可以真的跑**。它排在 M3-e 之后
（执行世界落地、工具不再直接碰 `node:*` 之后），作为 M3 收官验收的一部分。

## 后果

- **正面**：原则二的可检验约束第一次被兑现，而不是被改写。
- **正面**：ADR-0054 的"工具不得直接碰 `node:*`"从文件名单升级为包边界，
  漏网的可能性从"有人忘了加进名单"降到零。
- **正面**：`@xm/compose` 依赖的是底座包而不是工具包，装配层与业务能力解耦，
  "删掉全部业务能力仍能启动"在 import 图上就成立，不需要运行时来证明。

- **负面**：多一个包。包数是本仓库刻意压着的指标（参考实现 51 个包是反面教材）。
  10 个仍在可控范围，且这一个是边界包不是能力包。
- **负面**：一次跨包搬迁，涉及 import 路径、`tsconfig` 项目引用、
  `apps/desktop` 的 `tsconfig.main.json` / `tsconfig.renderer.json` 的 `paths` 映射。
  后者是 CLAUDE.md 点名过的坑——搬完必须跑 `pnpm check:paths`。

- **代价与缓解**：搬迁期间 `git blame` 会断在这些文件上。缓解：用 `git mv` 保留历史，
  且本次**只搬不改**——同一个提交里不夹带任何行为修改，让 diff 是纯位移。

- **必做的反向演练**：
  1. `rm -rf packages/tools-core` + 无工具行的 profile → `pnpm typecheck` 与
     headless smoke 必须通过。**跑不通就是这次拆分没做到位**，不许改验收标准结案。
  2. 在 `@xm/tools-core` 的任一工具里写一句 `import fs from 'node:fs'` → depcruise 必须红。
  3. 让 `@xm/tools-core` import `@xm/tool-runtime` → depcruise 必须红
     （工具只能经 `ctx.executor` 取执行世界，不许直连提供者）。
  4. profile 的基线行仍指向已删除的 `@xm/tools-core#gateway` → 装配期断言拒绝启动
     并指名缺哪一项（ADR-0053）。

- **重新评估条件**：如果 `@xm/tool-runtime` 开始收纳第四类、第五类内容
  （例如某个"公共工具工具函数"），说明它正在退化成第二个 `tools-core`。
  届时的判据仍是这一条：**它是不是六项底座之一**；不是就不该进来。
