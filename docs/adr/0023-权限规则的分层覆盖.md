# ADR-0023 · 权限规则的分层覆盖：一条"看起来更安全"的优先级，让「永久授权」根本表达不出来

- **状态**：🟢 Accepted（2026-08-06）
- **日期**：2026-08-06
- **相关**：修正 [ADR-0003](./0003-默认权限策略.md) 的求值顺序；不改变 [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md) 决策三（YOLO 跳过 ask、跳不过 deny）；`composeRules()` 的构造期闸门沿用 [ADR-0020](./0020-非路径target的规范化契约.md) 决策五

## 背景

`evaluate()` 的求值顺序从 M0-a 起就是：

```
deny(immutable) → deny → ask → allow      优先级与定义顺序无关
```

`policy-engine.test.ts` 里有一条用例专门钉着它：**「ask 压过 allow（无论定义顺序）」**。
这条规矩单看完全合理——一条写宽了的 `allow` 不该悄悄把一条 `ask` 放松掉。

M1-c 要做审批 UI 的三个范围（本次 / 本会话 / 永久），开工第一件事是问：
"用户点了『永久允许』之后，那条规则长什么样？"

答案是：**它长什么样都没用。**

内置默认里 `fs.write` / `fs.delete` / `shell.exec` / `git.push` / `net.fetch` /
`package.install` / `gui.capture` / `self.modify` **全部是 ask**。用户写

```json
{ "effect": "allow", "capability": "fs.write", "match": { "target": "/proj/**" } }
```

判定照样返回 ask——因为 `def.fs-write` 也匹配，而 ask 压过 allow。

推广开来，结论是一句没有任何地方写过的话：

> **`Config.permission.rules` 里的 `allow` 条目，对所有值得授权的能力一条都不生效。
> 用户只能收紧，不能放松。**

这是本项目第 N 次「规则存在 ≠ 规则生效」，但形状换了一种：
**规则生效了，只是它守的东西和你以为的不是一回事。** 那条测试忠实地保护了
"层内不许被一条宽 allow 放松"，而它顺带保护掉的是"用户的显式配置压过出厂默认"——
后者没有任何测试，因为没有人想到它需要被测。

## 决策

### 一、层序即优先级：**后一层覆盖前一层；同一层内仍是 deny > ask > allow**

```
0  target 规范化，失败关闭                              （不变）
1  全部层里的 immutable deny（红线）—— 任何层都翻不了     （不变，仍是最先）
2  自最后一层向前，第一个「有匹配」的层定案；层内 deny > ask > allow
3  没有任何层匹配 → 档位兜底                             （不变）
4  YOLO：把结论里的 ask 变成 allow                        （不变，仍越不过 deny）
5  不可信上下文降级                                      （不变）
```

层序固定为 **builtin → user → project → session**。

原来那条保护并没有被丢掉，它被**搬进了层内**：同一份规则里写了 ask 又写了 allow，
仍然是 ask。变的只是"我显式配置的东西压过出厂默认"这件常识现在成立了。

`EvaluateInput.rules: PolicyRuleSet` 因此变成 `layers: readonly RuleLayer[]`。
**换类型而不是加一个可选参数**：每个调用点都必须重新做一次"这些规则属于哪一层"的决定，
忘了就编译不过。

### 二、红线不参与层序

`immutable deny` 在分层之前、全局最先判。它是这个函数里唯一"跨层"的一步，也必须是——
红线的定义就是"任何档位、任何用户配置都不可覆盖"，一旦让它进层序，
一条更靠后的层就能把它顶掉。

### 三、**项目层只能收紧**

`.xiaoming/config.json` 躺在用户 clone 下来的仓库里，作者不是用户，而小明自己有 `fs.write`——
模型完全可以在干活的过程中把它写出来。层序里项目层排在用户层之后，
它要是能放松，就等于"仓库里的一个文件可以撤销用户的设置"。

所以加载时对项目层做 `tightenOnly()`：丢掉所有 `effect: 'allow'`，
**并把丢掉的条目变成一条用户看得见的 notice**。不生效可以，不告诉他不行。

这与 `SESSION_FORBIDDEN_CONFIG_PATHS`（会话补丁不许碰 `permission` / `providers`）
是同一条纪律的同一个形状：**能被下游写出来的东西，只许收紧，不许放松。**

### 四、会话授权合成为最后一层，**每次判定现算**

`SessionState.grants` 从 M0 起就在 `reduce` 里算着了（`permission.decision` 里
scope 超过单次的会进去），而**一直没有任何读取端**——于是"本会话都允许"这个选项
即便实现了，下一次调用还是会弹框。

`grantsToRules(state.grants)` 是它的读取端。这样做的好处是授权走的仍然是
**同一个纯函数**：没有第二条"先查一下授权表"的判定路径，也就没有两条路径慢慢分叉的可能。

三个细节，每个错了都放大权限：

1. **target 要转义。** 授权针对的是一个具体目标，不是模式。POSIX 上 `a*b`、`log?.txt`
   都是合法文件名，不转义的话，一次针对单个文件的授权会放行一批文件——
   而授权是会被写进配置长期留着的，这个放大不是一次性的。
   为此给极简 glob 加了反斜杠转义（内置模式里没有反斜杠，不影响存量）。
2. **`always` 也进会话层。** 它同时写进用户级配置，但那要下次启动才读得到；
   不进会话层的话，用户点完"永久允许"，紧接着的下一次调用还会再问一遍。
3. **deny 的授权照样合成。** "本会话都拒绝"和"本会话都允许"一样是决定，
   只合成 allow 就等于回放出来的会话比当时更松。

命令类能力的授权**合成不出来**（`grantable` 判掉）：它的 target 还没有规范化契约
（ADR-0020 决策三），一条基于命令行字符串的授权是一层假防线。
宁可每次都问，也不要给一个错的承诺。

### 五、权限规则**不走配置合并**，走分层

配置的合并语义里数组是**整体替换**（docs/10 §8 写死的）。于是合并之后，
项目级的 `permission.rules` 会把用户级的**整个抹掉**——那与"后一层覆盖前一层"
完全不是一回事，而且抹掉的方向恰好是最坏的那个。

所以 `loadConfig()` 现在把两层的规则分开返回，而**合并结果里的
`config.permission.rules` 恒为空数组**。留一份合并后的副本等于留两份真相，
而这一份恰好是错的。

### 六、「永久」落盘前先过构造期闸门

`appendUserRule()` 在写文件之前跑一遍 `composeRules()` 的断言（命令类能力不许用
target 匹配、红线不许建在没有规范化契约的 target 上）。**在写下来的那一刻炸掉**，
是这类问题唯一的治法——否则它下次启动才失败，而那时用户早忘了自己点过什么。

闸门抛出时不静默：Turn 循环把它变成一条 notice，"永久"降级为"本会话"。
点了"永久允许"、重启后又被问一遍、而没有任何地方解释为什么，是最败坏信任的那种行为。

## 备选方案与否决理由

**授权走一条独立的入参**（`evaluate({ ..., grants })`，在 deny 之后 ask 之前查一次）。
改动面最小，但它只修"用户当场做的决定"这一条路：配置文件里的 `allow` 规则**仍然是死的**，
而"只能收紧不能放松"这件事会继续没有任何地方写着。修一半比不修更糟——
下一个人会以为这里已经想清楚了。

**全局改成"后定义者胜"**（去掉 effect 优先级）。心智模型最简单，但它推翻了那条测试
真正想保护的性质：一条写得宽的 `allow` 可以悄悄把前面的 `ask` 放松掉，
而"前面"可能是几十行之外的另一段配置。层内保留优先级、层间用顺序，两者都要得到。

## 后果

**正面**

- 「永久授权」和「本会话授权」第一次真的能表达出来，`permission.rules` 的 allow 一侧不再是死的。
- 层名不只是标签：`project` 被限制为只能收紧，`session` 由审批决定合成，
  两者都是**类型里就分得开**的东西。
- `Verdict.ruleId` 在 YOLO 跳过时指向**那条本来要问的规则**（`def.fs-write`）
  而不是一个笼统的 `builtin.tier-fallback`——审计里"YOLO 跳过了 def.fs-delete"有用得多。

**反向演练**（每条当场转红，逐一还原）

| 演练 | 结果 |
|---|---|
| 层拍平回一个数组 | 4 红，含「后一层的 allow 压过前一层的 ask」 |
| 红线参与层序（去掉全局最先判） | 2 红，红线被最后一层的 allow-all 顶掉 |
| 授权 target 不转义 glob | 1 红，`/work/a*b` 的授权放行了 `/work/aXb` |
| `tightenOnly` 不丢 allow | 2 红 |
| 项目层不做 `tightenOnly` | 1 红，仓库里的配置放宽了 `fs.write` |
| `permission.decision` 恒记 `once` | 4 红，"本会话允许"点了等于没点 |
| 落盘前不过构造期闸门 | 1 红，一条 `deny shell.exec "rm -rf /*"` 被安静地写进了配置 |

**负面 / 遗留**

- **`fs.read` 仍然是无条件 allow。** docs/06 §默认策略里那四条
  （`~/.ssh/**`、`~/.aws/**`、`**/.env*`、钥匙串）至今一条都没实现，
  而 M1-c 装上了真实的 `fs.read`。现在补它只是加几条规则——分层做完之后，
  用户也能覆盖它了。**建议不晚于 M1-d**：`web.fetch` 一上，"读到 + 发出去"就凑齐了。
- **授权的粒度是单个目标。** "永久允许写这个目录下的一切"表达不了，
  用户要那个得手写配置。做成可选的模式授权很容易，但那意味着审批 UI 要让用户
  当场编一个 glob——那是个比"多点几次"糟糕得多的交互。
- 层数固定为四层。插件与 MCP（M3）带进来的规则该归哪一层，等它们真的存在时再定。

## 这次值得记住的

> **一条规则可以生效，而它守的不是你以为的那件事。**
>
> 「ask 压过 allow，无论定义顺序」有实现、有测试、每次都通过。它保护的是
> "层内不许被一条宽 allow 放松"——完全正确。它顺带保护掉的是
> "用户的显式配置压过出厂默认"，而这一条从来没有测试，因为**没有人想到它需要被测**。
>
> 前几次的教训是"写下的规则要验证它真的生效"。这一次多一句：
> **还要验证它生效的**范围**，恰好就是你想要的那个范围。**
> 而照出它的问题很朴素：*"用户点了『永久允许』之后，那条规则长什么样？"*

## 补记（2026-08-06 当天）：三平台 CI 第一次真跑，Windows 上「授权」整个是死的

推上去之后 `test (windows-latest)` 红了十条。全部指向一句话：

> **规则里的模式与请求的 target 不在同一个坐标系里。**

`evaluate()` 会把请求的 target 规范化成 `C:/Users/...`（正斜杠、盘符大写），
而规则的 `match.target` 是**原样**的字符串。于是 Windows 上：

| 谁写的 | 存的样子 | 判定时比的样子 | 结果 |
|---|---|---|---|
| 用户在 config.json 里写 deny | `C:\Users\me\secrets\**` | `C:/Users/me/secrets/x` | **静默失效** |
| 「本会话都允许」合成的授权 | `C:\work\a.md` | `C:/work/a.md` | 点了等于没点，下次照样问 |
| 「永久允许」写进配置的规则 | 同上 | 同上 | 重启后仍然匹配不上 |

第一行是安全洞（一条用户以为生效了的 deny），后两行是本 ADR 刚刚宣称做成了的功能。
**在 Windows 上，这份 ADR 的成果一条都没有生效。**

### 决策七：归一放在**匹配器**里，不放在模式的生产者那里

`globToRegExp` 在编译路径类模式之前先过 `normalizePathPattern()`。

放在匹配器里的理由和当初"授权走同一个纯函数"是同一条：模式的生产者有**三个**——
内置默认（`normalizedOrThrow`）、配置加载、授权合成——而"三个地方各自记得做同一件事"
正是这个仓库反复栽的形状。匹配器只有一个，让它保证两边同坐标系，就没有分叉的机会。

反斜杠在这里有两个身份（Windows 分隔符 / glob 转义符），二者只在一种情况下不冲突：
**Windows 文件名里根本不允许出现 `\` `*` `?`**。所以归一只对 `^[a-zA-Z]:[\\/]` 打头的模式生效，
POSIX 模式一个字节都不动——`escapeGlobPattern` 的 `\*` 转义完全依赖这一点。

### 决策八：授权合成前先规范化，规范化不了的**直接丢**

`grantsToRules` 现在先 `normalizeTarget(capability, target)`，失败的整条跳过。
理由与 `grantable` 一致：一个判定时必然 deny 的 target，合成出规则来只会让用户
以为授权生效了。这条与决策七有重叠（匹配器那一层也会归一），但它管的是另一件事——
**写进 config.json 的那个字符串长什么样**。持久化下来的东西要是规范形态。

### 这次值得记住的

> **"我们有三平台 CI" 不等于"我们测过 Windows 语义"。**
>
> 内核是平台无关的纯函数——这意味着上面那个洞，**在 Linux 上完全可以被照出来**，
> 只要有人拿 Windows 形状的字符串喂过它一次。没有人喂过。
> 于是它一路穿过 549 条用例、13 项反向演练、两份 ADR，直到 windows-latest 抓住它。
>
> 三平台矩阵的价值不在"跑了三遍"，在于**它是唯一一个我没法在本地自欺的地方**。
> 而它拦下来的东西，本来应该是一个 12 行的纯函数用例
> （`packages/kernel/tests/windows-coordinates.test.ts` 现在就是那 12 行）。
