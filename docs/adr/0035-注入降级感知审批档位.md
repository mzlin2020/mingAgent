# ADR-0035 · 注入降级感知审批档位：「完全访问权限」原来是一句空话

- **状态**：🟢 Accepted
- **日期**：2026-08-10
- **相关**：修正 [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md)（`ask → deny` 那一半的适用范围）
  与 [ADR-0030](./0030-桌面端三档审批模式.md)（`auto`/`full` → `yolo` 的实际效果）；
  接续 [ADR-0034](./0034-知情授权穿透注入降级.md)（它修的是"同一个域名"，本文修"每一个新域名"）；
  不改动 [ADR-0003](./0003-默认权限策略.md) 的红线语义；
  [docs/09 §C6](../09-待讨论的开放问题.md)（审批噪音，本文是它的**第三个**真实实例）

## 背景

**来源：用户真实体验反馈，同一形状的第三次。**

> 「我仅仅搜索一个今日新闻，就让我至少点击了 10+ 次的允许授权，我都快疯了。
> 一旦我开启了自我审批或完全访问权限，非严重问题不要弹让我授权。」

ADR-0034 刚刚修过一轮，用户仍然被问十几次。原因写在 ADR-0034 自己的「后果」里：

> **一次搜索仍然是"每个新域名一个框"。** 根因（没有 `web.search`，一次搜索必然是
> SERP 一次 + 每个结果一次）没有被本 ADR 解决。

也就是说 ADR-0034 消掉的是"**同一个**域名被反复问"，而一次新闻搜索里
**每一个域名都是新的**——SERP 一次、每个新闻站一次，一条都不在 ADR-0034 的覆盖范围内。
用户看到的框数几乎没变。

### 机制

`evaluate()` 的求值顺序（`packages/kernel/src/policy/engine.ts`）里，
**注入降级（第 5 步）排在 YOLO（第 4 步）之后**：

| 步 | yolo 档、已污染、访问一个新域名 |
| --- | --- |
| 2 | `def.net-fetch` → `ask` |
| 4 | YOLO：`ask → allow`（"跳过 ask，不跳过任何 deny"） |
| 5 | 注入降级：`allow → ask` ← **把第 4 步刚放行的又打回来** |

`isInformedGrant`（ADR-0034）只对"污染后 + session 层 + 带具体 target"的授权放行，
而一个从没访问过的新域名根本没有这种授权。于是**「别再问我」这个开关对整个
不可撤销能力子集彻底失效**，恰恰在用户最需要它的场景（放手让它自己跑一段）里失效。

穷举 `evaluate()` 的分支可以得到一条更强的结论：**yolo 档下，
`builtin.injection-downgrade` 是唯一还能产生确认框的东西**——第 0/1/2 步只产出 `deny`，
第 3/4 步只产出 `allow`。修好第 5 步，「完全访问权限」就真的一个框都不弹。

### 证据

改动前，对真实 kernel 跑 `evaluate()`（`net.fetch`，公网地址）：

```
balanced / model      ask    def.net-fetch                   ← 干净上下文，正常的一次提问
balanced / untrusted  deny   builtin.injection-downgrade     ← 硬拒绝，用户连授权的机会都没有
yolo     / model      allow  def.net-fetch                   ← 第一次，开关有效
yolo     / untrusted  ask    builtin.injection-downgrade     ← 之后每一个新域名都问 ★
```

★ 就是用户报的那一行。全部不可撤销能力在 yolo + 已污染下的判定（改动前）：
`fs.delete` / `net.fetch` / `net.listen` / `git.push` / `package.install` /
`system.settings` / `shell.session` **全是 `ask`**；只有 `gui.input` /
`plugin.install` / `secrets.read` 是红线 `deny`。

### 顺带查出来的第二个乘数

同一次测量里还发现：`resolveHost` 给每个 URL 产出**两条**主张（可读域名 +
解析出的 IP），而解析出的 IP 那条也匹配 `def.net-fetch` 的 ask，于是
**每一次 `web.fetch` 弹两个框**——一个域名，一个用户根本无从判断的裸 IP。
它与本 ADR 的问题相乘，才凑出"10+ 次"。这一条单独出 [ADR-0036](./0036-只检查的主张.md)。

## 选项

### 选项 A：把第 5 步挪到第 4 步之前

让注入降级先跑，YOLO 后跑。

- 优点：一行调序，`evaluate()` 的注释里"YOLO 跳过 ask"从此不再被后面的步骤推翻。
- 缺点：**得到的是 `deny` 而不是 `allow`**。降级先把 `ask → deny`，而 YOLO 跳不过任何
  `deny`，于是 yolo 下联网直接失败。比现状更糟：用户从"被问十几次"变成"根本用不了"。
  **否决。**

### 选项 B：yolo 下整个注入降级失效

最简单的规则，与第 4 步的既有承诺完全一致。

- 优点：一个 if，语义干净。
- 缺点：用户自己划的线是"**非严重**问题不要弹"，不是"什么都不要弹"。
  推送到远端、安装依赖这类后果留在会话之外的事，一次搜索里根本不会触发，
  保留它们的提问**降噪代价为零**，放弃它们则是白送的一次收窄。**不采纳。**

### 选项 C：污点源不降级自己（ADR-0034 选项 B 的原样重提）

- 缺点：ADR-0034 已经否过——它对**所有档位**无条件放开"读 evil.com →
  向 evil.com 发东西"这条最经典的路径。**否决。**

### 选项 D：让注入降级感知档位与"严重项"

用户显式开启的档位是一次**预先做出的、会话级的、有开启成本的**回答；
承认它对绝大多数不可撤销操作有效，只对少数几件事保留提问。

- 优点：正好对上用户划的那条线；不动能力闭集、不动红线、不动 YOLO 与 deny 的关系；
  同一个概念还能顺手修掉默认档"新域名硬 deny"的死路。
- 缺点：新增一张需要逐条论证的能力表；**是一次真实的安全收窄**（见「后果」）。

## 决策

选择**选项 D**。

### 一、新增 `CRITICAL_UNDER_UNTRUSTED`：不可信上下文下的「严重项」

放在 `packages/contracts/src/permission/capability.ts`，与
`IRREVERSIBLE_CAPABILITIES` / `UNTRUSTED_CONTENT_CAPABILITIES` 并列，同样是闭集派生表：

```ts
export const CRITICAL_UNDER_UNTRUSTED = ['git.push', 'package.install', 'system.settings'];
```

**判据是"后果留不留在本会话之外"。** 推上去的提交撤不回、装上的包会一直执行、
改掉的系统设置关掉小明也还在——用户回过神来时已经没有现场可以恢复。

其余不可撤销能力分两类，都不进这张表：

- `net.fetch` / `fs.delete` / `shell.session` / `net.listen` —— 正是用户开 YOLO 时
  明确表示"这一段时间别问我"的日常操作。留在表里等于这次改动什么都没做。
- `gui.input` / `plugin.install`（以及不在不可撤销表里的 `secrets.read`）——
  在不可信上下文下**已经是红线硬拒绝**（`red.*-untrusted`），第 1 步就定案，
  根本走不到第 5 步。写进来只会造成"这里也管着"的错觉，而同一条规则表达两处迟早分叉。
  `policy-untrusted-tier.test.ts` 有一条断言钉着"严重项与红线不重叠"。

### 二、yolo 档：非严重项不降级

```
tier === 'yolo' && !isCriticalUnderUntrusted(cap)  →  原样返回 verdict
```

放在 `downgradeIfUntrusted()` 里而不是让 `evaluate()` 跳过第 5 步：
`ask → deny` 那一半和严重项仍然要走完后面的逻辑。
**档位只改变"哪些能力还值得再问一次"，不改变这道防御的形状。**

红线、全部内置 deny、用户自己写的 deny 一个字没动——ADR-0017/C5 与 ADR-0030 的
"YOLO 跳过 ask，不跳过任何 deny"原样成立，有断言钉着。

### 三、默认档：非严重项从硬 `deny` 放宽成「高警示 ask」

同一张表的第二个用法。`ask → deny`（ADR-0017）**只对严重项保留**，其余停在 `ask`，
但换成注入降级自己的 `ruleId` 与理由。

原来的硬 deny 有一个没被算清楚的代价：用户想继续，唯一的出路是点横幅上的
「解除标记」——那把**整轮**防线一起放倒，比"只允许这一个域名"大得多。
**防线越是只剩"全开或全关"，用户就越会选全关。**

ADR-0017 立这一半时担心的是"弹一个和平时一模一样的确认框，用户照点不误"。
这一点由 UI 承担：审批卡看到 `trustLevel === 'untrusted'` 会渲染成**指名污染源**
（哪个工具、经由哪个能力、什么时候）的高警示样式，不是日常那个框。
三个字段都来自 `UntrustedContext`，`reduce` 从 `tool.start` 算出，模型碰不到。

docs/06 §9 的验收项「读过网页后要求 git push → 从 ask 变 deny」**原样成立**：
`git.push` 在严重项里。

**不需要新增 `interactive` 之类的开关**：headless / CLI 没有审批责任人时，
`turn.ts` 的 `decideOrAbort` 已经把 `ask` 自动判成 deny，无人值守场景下
ADR-0017 的保护自动保持原状。

### 四、`isInformedGrant` 补一条条件 ④：授权批准的正是造成污染的那次调用

ADR-0034 的条件 ③（`grantedAt >= untrustedSince`）有一条缝：
**污点标在 `tool.start`，而放行这次调用的授权记在更早的 `permission.decision` 上。**
于是批准了这次污染本身的那条授权反而算"污染之前做的"——用户刚点过
"本会话都允许 a.example"，a.example 的内容一进上下文，下一次访问 a.example 又被问一遍。

修法是拿 callId 对齐。那次授权当然是知情的：用户点"允许"时，接下来要发生的
正是这次污染。而会话早期对 `api.github.com` 的旧授权属于**另一次**调用，
callId 对不上，仍然穿不透——条件 ③ 要挡的攻击一点没放开。

两个 callId 都是事件流里现成的事实（`UntrustedContext.callId` 与
`PermissionRequestPayload.callId`），**不新增任何持久化状态**，与 ADR-0034 同一个手法。
`PolicyRule.grantedCallId` 与 `PermissionGrant.callId` 只由 `grantsToRules()` /
`reduce()` 合成，配置文件里手写无效。`EvaluateInput.untrustedCallId` 不传 = 不算知情，
落在保守的那一侧。

## 后果

- 正面：用户报的症状消失。端到端实测（`informed-grant-noise.test.ts`）：
  yolo 档下 SERP + 5 个各不相同的域名，`permission.request` **从 6 条降到 0 条**，
  6 次工具调用全部执行；同一档下 `git.push` 仍然问一次。
- 正面：默认档下污染后的新域名从"硬失败、只能解除整轮标记"变成"可以当场只授权
  这一个目标"；第一个域名也不再被问两遍。
- 正面：`evaluate()` 仍是纯函数，仍可穷举测试；`PolicyVerdict` 对外契约零变更。
- **负面 / 已知代价，照直说：**
  - **「帮我批准」/「完全访问权限」下，提示词注入可以让小明往任意域名发请求、
    删任意（非红线）文件，全程零提示。** 这实质上是 ADR-0034 否决过的选项 B 的一个
    受限版本。它之所以这次可接受，唯一的理由是**作用域**：不再是对所有档位无条件
    生效，而是锁在一个会话级、不持久化、要显式开、开「完全访问权限」还要过一道
    二次确认的档位后面。这不是零成本，是一次用可见性换掉的收窄——
    所以横幅与二次确认卡片的文案必须把它讲清楚（已改），
    否则用户会以为防线还在，那比没有防线更糟。
  - **默认档下非严重项从 deny 降到 ask，确实比原来松一档。** 押的是
    "指名污染源的高警示框 + 只授权一个目标"比"硬失败 + 用户去解除整轮标记"
    更安全。这是一个关于人的判断，不是关于代码的判断，值得日后回看。
  - **一次搜索仍然是 N 次 `web.fetch`。** 根因（没有 `web.search`）仍未解决，
    见 ADR-0034 选项 C。本 ADR 消掉的是确认框，不是请求数。
- 什么条件下应该重新评估：
  - 若将来做 `web.search`，"每个新域名一个框"在默认档下会自然收敛，
    届时可以重新看默认档那一档放宽还需不需要；
  - 若 `IRREVERSIBLE_CAPABILITIES` 新增成员，`policy-untrusted-tier.test.ts` 会强迫
    加的人当场回答"它算不算严重项"——那个回答应该补进本 ADR，而不是只改表；
  - 若出现"yolo 下也想留一份被静默放行操作的可见记录"的真实需求，
    那是 ADR-0030 定过的"不补额外事件"的重新评估，要单独出 ADR。

## 反向演练

按项目纪律（护栏类改动一律先证明"改之前会失败"）：

- `isCriticalUnderUntrusted` 临时改成恒 `true`（= 本 ADR 之前的行为）→ 4 条用例红，
  其中端到端那条的 `permission.request` 从 0 回到 5 条，**与用户报告的症状完全一致**。
- 改成恒 `false` → 另外 4 条红：yolo 下 `git.push` 不再问、默认档下严重项不再 deny。
  两个方向都红，说明这张表的边界是真的在承重，不是摆设。
- 去掉条件 ④ → `policy-informed-grant.test.ts` 里"时间戳早于污染但 callId 对得上"红。
  **顺带发现一件事并记在这里**：端到端那一层考不了条件 ④——
  `permission.decision` 与紧随其后的 `tool.start` 落在同一毫秒，
  `grantedAt >= untrustedSince` 恰好成立，没有条件 ④ 照样绿。真实桌面上用户点一下
  要几百毫秒，那条缝才会露出来。所以它的护栏放在能精确构造时间戳的纯函数层，
  端到端那层只留确实观察得到的断言——一条"靠巧合通过"的用例比没有用例更糟。
- `pnpm verify` 全段通过（1045 passed，depcruise 无新增边，文件规模闸门未触发）。
