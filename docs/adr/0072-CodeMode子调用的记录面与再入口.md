# ADR-0072 · Code Mode 子调用的记录面与再入口（M3-h 落地）

- **状态**：🟢 Accepted
- **日期**：2026-08-16
- **相关**：[ADR-0061](./0061-CodeMode与工具SDK生成.md)（本 ADR 是它的落地）· [ADR-0069](./0069-CodeMode的隔离机制.md) · [ADR-0071](./0071-工具的规范JSON输出值.md) · [ADR-0055](./0055-Turn驱动器的扩展点契约.md) · [ADR-0039](./0039-放弃审批模式.md) · [ADR-0032](./0032-地基复审三-M1收尾前的原则符合度审查.md)

## 背景

[ADR-0061](./0061-CodeMode与工具SDK生成.md) 定了 Code Mode 要做什么，
[ADR-0069](./0069-CodeMode的隔离机制.md) 定了程序跑在哪里，
[ADR-0071](./0071-工具的规范JSON输出值.md) 定了程序拿到的是什么形状。
三份都定完之后，M3-h 的实现里仍然剩下四个必须做的决定，而它们都改接口或改数据格式：

1. 程序发起的子调用，**在事件流里长什么样**。
2. 工具从哪里拿到"跑程序"和"把调用送回闸门"这两个入口。
3. `run_code` 声明空能力集这件事怎么交代（`defineTool()` 会当场拒绝未登记的空能力集，
   [ADR-0032](./0032-地基复审三-M1收尾前的原则符合度审查.md) #5）。
4. 呈现模式（`native` / `code` / `both`）作用在**哪一层**。

ADR-0061 对第 1 条只写了一句"落一条 `tool.code.dispatch`（persisted）"。
那句话有两种读法，而两种读法的后果差一个量级——本 ADR 先把它读死。

## 决策

### 一、子调用只落一条 `tool.code.dispatch`，**不落** `tool.start` / `tool.end`

ADR-0061 那句话的另一种读法是"照常落 tool.start/tool.end，另外再加一条 dispatch 做关联"。
**否掉它**，理由是那样会把 Code Mode 最大的收益直接抵消：

`tool.end` 带着 `forModel`，而 `reduce()` 会把它变成 `messages` 里的一条 `tool_result`，
下一次模型请求就会带上它。于是"读十个文件、只把摘要交回来"变成"读十个文件、
把十份正文和摘要一起交回来"——比不用 Code Mode 还贵。
ADR-0061 §四 把"程序中间值不落库、不进提示词"写成了 Code Mode 的**前提**，不是优化项。

那条路真正的诱惑在于"审计更完整"，所以要说清楚：**审计一点没少。**
`tool.code.dispatch` 记着谁的第几步、调了什么（网关规范化并回写之后的入参）、
动了哪些能力、成没成、失败原因。少的只有"模型看到了什么"——
而子调用的返回值模型本来就没看到，记一份它没看到的东西不是审计，是虚构。

**`payload` 里因此没有 `forModel` 字段。** 与 `output` 不进 `tool.end` 是同一个手法
（ADR-0071）：没有可放的位置，就不必依赖谁记得别放。`reduce()` 对这条事件只推进 `lastSeq`。

两个次级后果，都是要的：

- 渲染层不会为子调用长出一排卡片。程序内的每一步显示在 `run_code` 自己那张卡片上
  （ADR-0061 后果段第二条），来源是同一份 `dispatched()` 账本。
- `risk` 与 `capabilities` 在 payload 里是**可选**的。这条事件覆盖的范围比 `tool.start` 宽——
  工具名不存在、入参没过 schema、网关拒绝，这些也要记，而那时它们还没有值。
  缺席的意思是"没走到能拿到它的那一步"，不是"没有风险"。

### 二、判定与记录分开：`CallSink`

"子调用重入完整十二步链"（ADR-0061 §一）的字面要求是**不写第二份判定代码**。
但记录面又必须不一样（见上）。所以把十二步链参数化在一个接口上：

```
dispatchCallWith(deps, extensions, turnId, call, sink, codeMode?, caller?)
  ├─ 判定与执行：①~⑫，一份实现，两条路共用
  └─ 记录：sink.fail / start / progress / end
       · modelCallSink  → tool.start / tool.progress / tool.end
       · codeDispatchSink → 一条 tool.code.dispatch
```

判定那一半**连一个分支都没有**——不是靠自觉，是它压根没有可分岔的地方。
反向演练：把子调用的 sink 换成 `modelCallSink`，`code-mode.test.ts` 十条里红七条，
其中包括那条哨兵断言。

`caller: 'model' | 'program'` 只喂给第 ① 步（见 §四），不参与任何判定。

### 三、`ctx.codeMode` 是**再入口，不是权限**

工具从 `ToolContext.codeMode` 拿到两样东西：跑程序的 `runtime`，和把一次调用送回
十二步链的 `dispatch()`。它出现在**每个**工具的上下文里，而不只是 `run_code` 的。

看着像多给了权限，其实一点没多：`dispatch()` 送出去的每一次调用都从头走完整十二步链，
网关规范化、主张完备性、红线判定一步不少，且**不复用**发起方那一次的判定结果。
一个工具能通过它做到的事，它自己声明能力去做也一样做得到；区别只是审计里多一条
`tool.code.dispatch` 说清了是谁发起的。

按名字只给 `run_code`（`if (tool.name === 'run_code')`）也能实现，但那是一道**看起来**
更安全的检查：它保护的东西本来就不需要保护，代价是往特权底座里加一个按名字放行的分支——
那个形状本身比它防的风险更值得警惕。

`codeMode` **不往子调用传**。这是"不做嵌套 `run_code`"（ADR-0061 §六）的结构性落点：
程序里再调一次 `run_code`，拿到的 `ctx.codeMode` 是缺席的。第二道锁在绑定清单里——
`run_code` 本来就不在里面。

### 四、呈现模式作用在"模型视野"，不作用在判定

`native`（默认）/ `code` / `both` 只决定**哪些工具进模型请求**，以及提示词里带不带那段 SDK。
它作用在两处，且**只有这两处**：

- 组装模型请求时过滤 `descriptors()`；
- 十二步链第 ① 步，且**只对 `caller: 'model'` 生效**。

第二处兑现的是 ADR-0061 §二 那句"模型直接点名其它工具时，在判定之前就解析为未知工具"。
它给出的是 `tool_not_found` 而不是 `policy_denied`——两者在事件流里长得不一样，
而这正是要的：**被拒绝**意味着"你想做的事不被允许"，**不存在**意味着"你记错了自己有什么"。
混成一种，模型会换个说法再试一次。

程序发起的子调用不受它约束。要是也约束，`code` 模式下 Code Mode 自己就没工具可调了。

### 五、`run_code` 声明空能力集，登记在案

`capabilities: []`、`risk: 'medium'`。它与 `agent.explore` 是同一类**元工具**：
这一次调用自己什么也不碰——不开文件、不起进程、不发网络；真正动东西的是程序里的
每一次子调用，而那些各自带着自己的能力，各自判各自的。

反过来才是危险的：给 `run_code` 挂一堆能力，红线就会在**父调用**这一层生效，
于是"这段程序被允许了"变成"它里面的每一步都被允许了"。
[ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md) 的教训正是这个形状的镜像。

按 ADR-0032 #5 的要求，已登记进 `EMPTY_CAPABILITIES_ALLOWLIST` 并注明本 ADR 编号。

### 六、SDK 的两处形状修正

- **同步签名**。ADR-0061 §五 写的"生成成一个 TS 异步函数"是照参考实现写的，
  在 QuickJS + asyncify 下不成立（ADR-0069 §三.2 已修正）。程序是一个**同步函数体**，
  用 `return` 交回结果。
- **`xm.fs.read(...)` 的嵌套命名空间**。JS 标识符里不能有点；`xm["fs.read"]` 那种写法
  模型更容易写错。客体域的 prelude 按同一规则装绑定，两边不会漂。

返回类型取自 `RegisteredTool.outputSchema`（Zod 原件），**不是描述符**——
规范值不进提示词（ADR-0071）。没声明 `outputSchema` 的工具（插件、MCP）写 `unknown`，
不编一个形状。

## 后果

- **正面**：一段程序连调三个工具，模型请求从 4 次降到 2 次（`code-mode.test.ts` 断言的是
  `provider.requests.length`）。省下的不只是延迟——每次往返都要重发整个上下文。
- **正面**：三份文件正文一个字节没进事件流。这条由哨兵断言守着，
  而断言按"整份事件流的 JSON 里搜不到那个字符串"写，不按字段名写——后者换个名字就绕过去了。
- **正面**：`CallSink` 这层拆分让"判定只有一份"从一句承诺变成结构。将来若还有第三种
  发起方（定时任务、外部 API），它只需要一个新的 sink。

- **负面**：十二步链多了两个参数（`sink`、`caller`）。`turn-tools.ts` 因此更抽象了一点，
  而它是全仓库最不该被随手改的文件之一。缓解：`caller` 只在第 ① 步被读一次，
  `sink` 不参与任何判定，两者都进不了 `evaluate()` 的输入。
- **负面**：`tool.code.dispatch` 是一条新的持久事件类型，历史会话里没有它。
  这不构成兼容问题（`reduce()` 对它恒等），但**离线扫描器与派生 trace 都要认得它**，
  已同步。
- **负面**：审计要还原一次 Code Mode 调用，得同时看 `tool.start`（程序全文在它的 `input` 里）
  与若干条 `tool.code.dispatch`。比一条 `tool.end` 讲完整个故事要费一点事。

- **必做的反向演练**（每条都已看它红过一次，见
  [M3-h 收官记录](../experience/m3/M3-h-收官记录.md)）：
  1. 子调用改用 `modelCallSink` → 哨兵断言与往返次数断言必须红。
  2. 不覆盖客体域的 `Date` / `Math.random` → 确定性断言必须红（ADR-0069 §三.1）。
  3. 只留 CPU 预算、去掉宿主墙钟 → 绑定永不返回那条必须挂到超时（ADR-0069 §三.3）。
  4. `packages/runtime/src` 里 import `@xm/code-runtime` → depcruise 必须红。
  5. `code` 模式下模型直接点名别的工具 → 必须是 `tool_not_found` 而不是被拒绝。

- **重新评估条件**：如果实测发现模型在 `both` 模式下几乎不用 `run_code`，
  或者写出来的程序失败率高到要靠更多往返去修，那么按 ADR-0061 的"重新评估条件"
  把 Code Mode 降级为实验特性，**而不是继续加功能去救它**。
