# ADR-0048 · M2-h 上下文预算、稳定前缀与持久摘要

- **状态**：🟢 Accepted
- **日期**：2026-08-13
- **相关**：[ADR-0006](./0006-上下文压缩策略.md)、[M2 阶段划分](../M2-阶段划分.md)

## 背景

`turn.ts` 目前把 `SessionState.messages` 全量复制给 Provider。长会话会越过模型上下文上限；
系统段同时包含 cwd、平台和动态的 todo 工具提示，却被整体标成 `cacheable`，声明与字节稳定性
不一致。契约里已有 `context.compacted` 和 BlobStore 引用，但没有真实的构建、预算和复用路径。

## 决策

### 1. 运行时只有一个 ContextBuilder

主回合的每次 Provider 请求都由 `ContextBuilder` 异步构建。它统一计算输出预留、长期预留、
75% 触发线与硬输入上限；`turn.ts` 不再直接读取完整消息数组组请求。Provider 提供
`countTokens` 时使用精确计数，否则使用同一套保守、确定性的 UTF-8 估算器。

### 2. 稳定前缀只含真正稳定的字节

Agent 身份、执行原则组成第一个 `cacheable` system 段，内容不含 cwd、平台、动态工具可用性或
摘要。会话 cwd/平台、动态 todo 提示放到后续非缓存段；工具 schema 继续按当次可用性过滤，
但不能改变已声明稳定的 system 前缀。M2-h 不声明消息级缓存断点。

### 3. 只按已结束回合压缩，近期四轮与当前轮保留原文

ContextBuilder 从持久事件重建「`turn.start` 至配对 `turn.end`」切片。压缩只覆盖连续的、已结束
且尚未压缩的旧切片，不切断 tool use/result 配对；最近四个已结束回合、当前活动回合以及任何
无法归入完整回合的消息始终保留原文。若这些不可压缩内容本身超过硬上限，明确失败，不发送
一个已知超限的 Provider 请求。

### 4. 主 Provider 生成一次，Blob 与事件共同构成持久事实

摘要使用当前主 Provider 和当前主模型、禁用工具，提示中显式要求保留「未解决问题、用户约束、
已做决定」。先把 UTF-8 摘要写入 BlobStore，再记录 `context.compacted`；事件记录源 seq 范围、
压缩前后 token、模型、上下文上限、75% 阈值、预留量和近期边界。后续构建及进程重启只读事件
和 Blob，不再调用模型压缩同一区间。内存中不另建摘要真相缓存。

一次构建可连续压缩多个互不重叠的旧区间，直到请求回到预算内；每个区间仍只生成一次。
摘要调用产生的真实 usage 归入触发压缩的当前 turn。

### 5. 原始事件永不改写

`SessionState.messages`、SQLite 事件和快照仍保存全部原文。ContextBuilder 只在出站投影中用中期
摘要替换已覆盖的旧消息。删除可重建的进程内状态或重新打开会话后，从 `context.compacted` 与
BlobStore 即可得到同一投影。

## 后果

- 长会话请求有显式预算，不会把已知超限请求交给 Provider。
- 摘要质量仍决定长期上下文质量；原始事件保留，可为以后人工重压缩提供依据。
- 每次构建需要扫描持久事件以恢复回合边界。M2-h 先保证唯一事实与正确性；若实测成为热点，
  可在不改变事件语义的前提下增加可重建索引。
- 图片和文档只会在被压缩的旧区间中转为文字摘要；最近原文仍受 Provider 能力检查约束。

## 补记（2026-08-13，M2 复审）：回合切片改增量扫描

本文"后果"一节写过：「每次构建需要扫描持久事件以恢复回合边界。M2-h 先保证唯一事实与
正确性；若实测成为热点，可在不改变事件语义的前提下增加可重建索引。」

它不是"若"。`collectTurnSlices()` 每次 Provider 请求都从 seq 1 全量重放，而一个 turn 内
每次工具往返各触发一次——代价随会话长度呈 O(n²)，而 M2 的目标恰恰是"长会话里写代码"。

现在按本文预留的口子做了：`SessionRuntime.read()` 透传 `ReadOptions`（底层
`EventStore.read` 早就支持 `fromSeq`），切片扫描缓存挂在 SessionRuntime 实例上的 WeakMap，
只消费 `lastSeq` 之后的新事件。

缓存是**可丢派生物**：丢了就从事件重建，结果逐字节相同。事件语义、压缩语义、稳定前缀
都没有变。测试直接数实际读到的事件条数：第二次构建一条也不重放，新回合只消费自己那几条。
