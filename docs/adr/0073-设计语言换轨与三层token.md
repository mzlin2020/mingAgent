# ADR-0073 · 设计语言换轨：三层 token、冷调中性、亮暗分层反转

- **状态**：🟢 Accepted
- **日期**：2026-08-16
- **相关**：M3.5-a；总纲 [12-桌面端界面与设置](../12-桌面端界面与设置.md)、
  分段 [M3.5-阶段划分](../M3.5-阶段划分.md)；
  **部分推翻** [ADR-0004](./0004-主界面形态.md)（"风格贴近 Claude Code 桌面端"）与
  [ADR-0037](./0037-桌面端壳层导航与会话入口.md)（"主题色仍与 Claude Code 一致，不换灰白调"）；
  不改这两份 ADR 的**布局与导航结论**（对话为主 + 可展开面板；去侧栏、顶栏 tabs、Home）

## 背景

ADR-0004 定的产品风格是"贴近 Claude Code 桌面端"，ADR-0037 在换壳层导航时特意重申
"主题色仍与 Claude Code 一致，不换成 openCode 的灰白调"。落地成暖白底
（`canvas #faf9f5` / `surface #ffffff` / `surface-2 #f2f0e9`）+ 橙色强调。

真实使用下来这套配色不成立，原因不是色号选得不好，是**分层方式**：

- 亮色下 `canvas` / `surface` / `surface-2` 是三个挨得很近的米白，`border #e5e2d8` 也在同一色域，
  层次**全靠填充**给出，而三块填充之间的差只有几个百分点——边界既不靠对比也不靠描边。
- 深色下同样靠填充，只能靠"卡片与底色刻意贴得很近"（`styles.css` 里已有的那句注释）
  手动兜住，本质是在给同一个问题打补丁。

对照参考实现 `deepseek-harness` 的 `ui-theme/src/styles/design-platform.css`，
它的亮暗两套是**反着来的**：

| | 亮色 | 暗色 |
|---|---|---|
| `bg-base` / `layer-1/2/3` | **四层同为纯白** | 逐层提亮 `#151517 → #232324 → #2c2c2e → #353638` |
| 层次从哪来 | **只靠描边**：黑 alpha `0.04 / 0.10 / 0.12 / 0.16` | **只靠填充**；描边换成白 alpha，最重才 `0.20` |

同时它把 token 分成三层：`--dsw-static-*`（调色板，**明暗同值**）→ `--dsw-alias-*`（语义）
→ `--dsw-specific-*`（组件）。小明现在只有一层：`@theme` 里 20 个 `--color-*` 直接写死色值，
既是调色板又是语义，于是"换调性"等于"逐个改 20 个色值并逐个重新验证对比度"。

另有两条约束来自本仓库自己的历史：

1. `lib/cn.ts` 的档位表必须与 `@theme` 一一对应，而这条至今写在**注释**里
   （"加 token 时两处一起改"）。本仓库已经栽过八次"规则存在但从未生效"，这是第九个候选。
2. 深色只跟随系统，应用内无开关。M3.5-e 要加"跟随系统 / 浅 / 深"三档。

## 选项

### 选项 A：只调色值，保持单层 token

把 20 个 `--color-*` 换成冷调值，别的不动。

- 优点：改动最小，一次提交完事。
- 缺点：**没有解决问题**。分层仍然全靠填充，亮色照样糊；下次再想换调性还是逐个改 20 个值；
  `cn.ts` 那个洞照旧；主题开关照旧没有落点。

### 选项 B：换成 CSS Modules + 照搬参考实现的 token 文件

- 优点：与参考实现最接近，色号可以直接对照。
- 缺点：`@theme` 的命名空间清零把"想跑偏必须先回文件里登记一档"变成了**编译期事实**
  （`bg-red-500` 根本不存在），换成 CSS Modules 会把这条约束退回人的自觉。
  参考实现的三层 token 文件有 338 行、包含大量当前没有使用者的色号（绿/琥珀/多档蓝），
  与单文件 400 行的规模纪律正面冲突。

### 选项 C：三层 token 落在现有 Tailwind v4 `@theme` 上（选定）

调色板层住普通 `:root`（不生成工具类），语义别名层住 `@theme`（生成工具类），
组件层由组件自己声明。**别名的名字一个不改**，只换它们指向什么。

- 优点：承载方式不变，编译期约束保住；组件文件零改动；换调性变成改别名层一处。
- 缺点：CSS 没有 mixin，深色定义要写两份（跟随系统一份、手动选择一份），
  两份必须同步——这是本决策引入的**新**的"靠自觉"的点，必须配闸门（见下）。

## 决策

选 **C**。四条具体决定：

### 一、三层 token，组件只能看见中间那层

| 层 | 内容 | 住哪 | 生成工具类 | 组件可用 |
|---|---|---|---|---|
| 调色板 `--p-*` | 冷调中性 19 档 + 蓝 10 档 + 红 6 档，**明暗同值** | 普通 `:root` | ❌ | ❌ |
| 语义别名 `--color-* / --radius-* / --text-* / --shadow-*` | 20 个颜色 + 三档圆角 + 四档字号 + 一档阴影 | `@theme` | ✅ | ✅ **只有这层** |
| 组件专用 `--xm-*` | 目前只有滚动条滑块两档 | 组件根节点 | ❌ | 组件自己声明自己消费 |

**别名的名字一个都不改**（`canvas` / `surface` / `surface-2` / `border` / `fg` / `muted` / …）。
这是"M3.5-a 组件文件零改动"能成立的唯一原因：只要名字不变，`bg-surface` 这类工具类
就还在，换的只是它解析成什么。参考实现那套名字（`bg-base` / `label-primary` / `border-l1..l4`）
更规整，但换名意味着 245 个文件里 300 多处类名同批改，把一段纯 CSS 改动变成一次大扫荡。

### 二、亮色靠描边，暗色靠填充

- 亮色：`canvas` 与 `surface` **同为纯白**，`surface-2` 是唯一一档着色（冷调 `#f1f3f5`），
  描边用 `rgb(0 0 0 / 0.10)` 与 `/ 0.16` 两档。
- 暗色：`canvas / surface / surface-2` 逐层提亮 `#151517 / #232324 / #2c2c2e`，
  描边换成 `rgb(255 255 255 / 0.12)` 与 `/ 0.20`。

**「亮色下 `surface` 和 `canvas` 同值」不是漏改，是这个决策本身。**
它成立的前提是：每一处 `bg-surface` 都同时带着 `border border-border`——
`ui.tsx` 的 `Card` / `Button`、汉堡菜单、输入区外壳、tabs、工作区面板，逐个查过，无一例外。
**给 `bg-surface` 去掉边框会让它在亮色下凭空消失**，这条约束比色值本身更要紧，
写进了 `styles.css` 的文件头。

描边用 alpha 而不是实色：实色描边在任何底色上都是同一个灰，压在 `surface-2` 上会显脏；
alpha 描边跟着底下的表面走，这也是暗色能直接换成白色 alpha 的原因。

### 三、强调色换成冷调蓝

`--color-accent` 从暖橙 `#c96442` 换成 `#4176e6`（暗色 `#5686fe`）。

理由**不是**蓝好看：整套交互态（hover / 选中 / 气泡）都是冷灰的叠加，
暖橙压在冷灰上会发脏，而把交互态也改暖就等于没换调性。

**逃生口是明确的**：强调色只有四个别名（`accent` / `-hover` / `-weak` / `on-accent`），
集中在一处，换回暖橙或任何别的色是改四行，不碰任何组件。

hover 往**深**走（`--p-blue-600`）而不是往浅走：实心按钮上压白字，往浅走会掉到 3:1 以下。
参考实现的 info 按钮 hover 往浅走，但它的**主按钮是近黑色**、蓝色只用于选中态与链接；
小明的 `accent` 一个别名同时承担填充、焦点环与选中态，所以取深。
真要分成"品牌色 / 业务色"两支，是 M3.5-c/e 的事，本段不提前拆。

**调色板里有两个色号不来自参考实现，是按对比度实测取的**，理由是同一条：
小明的 `accent` 与 `danger` 各自**一个别名承担两种角色**（既画填充又画压在填充上的文字），
而参考实现把这两种角色拆给了不同的 token，所以它的色号直接搬过来对比度不够：

| 别名 | 参考实现色号 | 实测 | 实际取值 | 实测 |
|---|---|---|---|---|
| `--color-accent` + 白字 | `#4176e6`（blue-500） | **4.23:1** ✗ | `#2f66d8`（新增 blue-550） | **5.23:1** ✓ |
| `--color-danger` 压在 `danger-bg` 上 | `#ec1313`（red-600） | **4.11:1** ✗ | `#c81111`（新增 red-700） | **5.42:1** ✓ |

作为对照，换轨前的暖橙 `#c96442` + 白字是 **3.90:1**——旧配色在这一格本来就不达标，
这次是修好而不是引入。落地后的全表（均 ≥ 4.5:1）：

| | 亮色 | 暗色 |
|---|---|---|
| 正文 `fg` | 18.90 | 17.45 |
| 次级 `muted` | 5.80 | 7.36 |
| `accent` + `on-accent` | 5.23 | 5.61 |
| `danger` 压在 `danger-bg` 上 | 5.42 | 4.94 |

`faint`（列表符号、快捷键提示）仍在 2.7:1 上下——它是"在场即可、不必被读"的一级，
与换轨前的 `#a19d92` 同档，**不是本次引入的**，但也没有被修好，记在这里。

### 四、深色写两份，靠闸门保证一致

跟随系统那份的选择器是 `:root:not([data-theme='light'])` 而**不是**裸 `:root`：
媒体查询与属性选择器特异性相同，媒体查询在后就赢——写裸 `:root` 会让
"系统深色 + 用户手动选浅色"这一格静默失效，用户点了没反应。

新增 `scripts/check-design-tokens.mjs`（进 `pnpm verify`，也进 CI 的 lint job），查四件事：

1. 组件里出现字面色值（`#rrggbb` / `rgb()` / `color-mix()` …）即失败。
   命名空间清零挡得住 `bg-red-500`，挡不住 `bg-[#fff]`。
2. 组件里出现 `--p-` 即失败。
3. 组件里出现 Tailwind 自带调色板族名（`text-white` / `bg-gray-100` …）即失败——
   清零之后它们**不报错，只是什么也不生成**，是一次静默失效。
4. `lib/cn.ts` 的档位表与 `@theme` 一一对应；两处深色定义逐字节一致；
   跟随系统那份的选择器必须带 `:not([data-theme='light'])`。

第 4 条的前半是在**补一个既有的旧洞**（那句"两处一起改"的注释），后半是在给本决策
自己引入的重复上锁——**新增一个靠自觉的点，必须同批给它配一把锁**。

豁免只有一条：`terminal-panel.tsx` 里传给 xterm 的 `'#00000000'`。
它表示"全透明"而不是一个颜色（终端底色由外层 `bg-terminal-bg` 提供），
而 xterm 的 `theme` 只接受字符串、认不得 token 名。豁免连同这句理由写在脚本里，
且脚本会反过来检查"豁免指向的东西已经不存在了"并要求删除。

## 后果

**正面**

- 换调性从"改 20 个色值并逐个重验对比度"变成"改别名层"，强调色更是四行。
- 亮色不再靠三块米白互相区分；暗色不再需要"贴得很近"那种补丁。
- 主题三档有了落点（M3.5-e 只需在启动时写 `data-theme`，CSS 侧已经就位）。
- 顺手补掉 `cn.ts` ↔ `@theme` 这个第九个"规则存在但从未生效"的候选。
- **组件文件零改动**：本段 `git diff` 里 `components/` 为空，全部变化在
  `styles.css` + 新脚本 + CI 一行。

**负面（必须写）**

- **推翻了两份已采纳 ADR 的一部分。** ADR-0004 的"贴近 Claude Code 桌面端"与
  ADR-0037 的"主题色仍与 Claude Code 一致"从本 ADR 起不再有效。
  两份 ADR 的**布局与导航结论仍然有效**，只作废配色那一段。
- **`docs/experience/` 里所有界面截图与配色描述作废**，需要在 M3.5-f 收官时重拍。
- **深色定义写了两份**，是本决策引入的重复。闸门能保证两份一致，但保证不了
  "有人把两份一起改错"——这是 CSS 没有 mixin 的固有代价，接受。
- 别名名字保持旧的一套，与参考实现的命名不一致；照参考实现补代码的人会找不到
  `label-primary` 这类名字。已在 `docs/12 §4.1` 与 `styles.css` 文件头写明对应关系。
- 调色板层只放了中性/蓝/红三族。绿（成功）与琥珀（警告）等到有别名要用时再进——
  现在加进来就是没有使用者的色号。
- 调色板里有两档（`blue-550` / `red-700`）不来自参考实现，对照色号时会对不上。
  两处都在原地写明了为什么以及实测数字。
- **对比度没有进闸门。** 上表是手算的，下次有人改一个色值不会有任何东西提醒他。
  加一条自动检查需要在脚本里解析别名之间的引用关系并知道"谁压在谁上面"，
  那份配对关系目前只存在于组件里。等 M3.5-c 把配对固定下来之后再补。

**什么条件下重新评估**

- 需要区分"品牌色"与"业务色"两支强调色时（选中态与主按钮开始要不同的颜色）。
- 组件专用层 `--xm-*` 超过十来个时：说明别名层缺档，应当先补别名而不是继续往组件里塞。
- 若将来渲染层拆包或引入插件贡献 UI（M4），`@theme` 单文件承载不下时重议选项 B。
