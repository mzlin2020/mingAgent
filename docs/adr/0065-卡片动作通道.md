# ADR-0065 · 卡片动作通道

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0058](./0058-工具渲染意图与结果投影.md) · [ADR-0045](./0045-M2-e-diff审阅不是权限审批.md) · [ADR-0050](./0050-编辑diff的行级hunk与提案投影.md) · [ADR-0055](./0055-Turn驱动器的扩展点契约.md) · [ADR-0033](./0033-G2闸门-MCP工具与子Agent的污点传播.md)

## 背景

[ADR-0058](./0058-工具渲染意图与结果投影.md) 用三件套取代了 `DisplayHint`，
并宣布 M2-e 的 `edit-review` 专用通道退役。复审（2026-08-14）指出这一步跨大了：

`presentCall` / `presentResult` / `presentationMeta` **全是只出不进的数据投影**。
它们能让一张 diff 卡片显示出来，但**逐块接受/拒绝需要的是反方向的一条路**：
用户在卡片上点了"接受第 2 块"，这个意图要回到主进程、要变成一次真实的写入、
要走完整的权限链。ADR-0058 §四 只说了"仍走 ADR-0045 的路径"，
但没定**渲染层用什么把这个意图送出去**。

现状里那条路是专用的：`apps/desktop/src/main/edit-review.ts` + 渲染层专门的组件 +
IPC 上的专门方法。要退役它，就得先有一条通用的替代品；否则 M3-f 交付之后，
第一个需要交互的插件工具还是会再开一条私有通道——`docs/05` 那条承诺又落空一次。

同时这条路**不能随便开**：渲染层零 Node 权限、preload 只转发少数具名调用、
**不提供 `invoke(channel, args)` 这种通用入口**（depcruise 规则 `preload-必须保持薄` 盯着）。
一条"卡片能让主进程干活"的通道，如果设计成通用转发，等于把那条规则作废。

## 选项

### 选项 A：不做动作通道，`edit-review` 继续留着

优点：零风险。
缺点：`docs/05` 的承诺继续挂账；每个需要交互的工具各开一条通道，
而三方工具根本没有开通道的权限——它们的卡片将永远是只读的。

### 选项 B：卡片可以声明"点了这个按钮就调这个工具"

优点：直白，实现简单。
缺点：**这是把工具名交给渲染层**。渲染层拿到的卡片数据来源于模型输出，
一张精心构造的卡片就能诱导用户点出一次任意工具调用——一个像素级的钓鱼面。

### 选项 C：动作是工具自己声明的具名意图，渲染层只能引用不能构造

## 决策

**选择 C。**

### 一、工具声明动作，渲染层引用动作 id

工具描述符新增一个可选字段：

```
actions?: {
  [actionId: string]: {
    schema: ZodType      // 这个动作的载荷形状，.strict()
    label: string        // 给人看的名字
  }
}
```

卡片数据里只能出现 `actionId` 与该动作的载荷，**不能出现工具名、不能出现路径、
不能出现任何"要执行什么"的描述**。渲染层完全不知道点下去会调用什么——
它知道的只有"这张卡片的第 2 块可以被 `accept`"。

### 二、回程只有一个具名 IPC 方法

```
ui.cardAction({ callId, actionId, payload }) → { ok } | { ok: false, code, message }
```

preload 只多这一个具名转发，**不是通用 `invoke`**。主进程侧四步，顺序不可换：

1. **Zod 校验**信封本身（`@xm/contracts`，两侧都校验，失败即拒绝并记录）。
2. **由 `callId` 反查工具**——从**已落库的事件流**里查，不从渲染层传来的任何字段查。
   这一条是选项 B 那个钓鱼面的封堵点：渲染层说了不算，说了算的是历史。
3. 用该工具声明的 `actions[actionId].schema` 校验 `payload`；
   未声明的 `actionId` 直接拒绝（失败关闭，与 ADR-0057 未声明事件即拒绝同形）。
4. 动作转化为一次**新的工具调用**，进 [ADR-0055](./0055-Turn驱动器的扩展点契约.md)
   的完整十二步链。

### 三、动作调用不继承任何东西

三条否定，每条都对应一个已经踩过的坑：

1. **不复用原调用的判定结果。** 原来那次 `edit.preview` 被允许，
   不代表由它衍生的写入被允许。判定重新做一次，
   与 ADR-0061 子调用不复用父判定是同一条规则。
2. **不因为"用户点的"就提升信任级别。** 点击这个动作的是人，
   但**被接受的内容仍然是模型产出的**（diff 的每一行都来自模型）。
   `trustLevel` 按内容来源算，不按谁点的算——ADR-0033 的污点照常传播。
   这也是 [ADR-0045](./0045-M2-e-diff审阅不是权限审批.md) 那句
   "diff 审阅不是权限审批"在新通道上的落点：**点了接受不等于批准了写入，
   写入仍然要过闸门**。
3. **不允许动作跨会话、跨回合引用。** `callId` 必须属于当前会话；
   指向别的会话的 `callId` 一律拒绝。

### 四、`origin` 进事件

`tool.start` 的 payload 增加 `origin`：

```
origin: { kind: 'model' } | { kind: 'user-action', fromCallId, actionId }
```

默认 `model`。有了它，审计能回答"这次写入是模型自己要写的，还是用户在某张卡片上
点出来的"——今天 `edit-review` 那条专用通道产生的写入在事件流里看不出这个区别，
这是它退役时应当顺手补上的一课。

### 五、M2-e 的迁移与验收

`edit-review` 的退役分成两半，**展示先走，交互后走**：

- 展示：`edit.preview` 产出 `diff` 卡片（ADR-0058），渲染层认识卡片种类而不是认识 edit 工具。
- 交互：逐块接受/拒绝改用 `ui.cardAction`，动作载荷是被选中的 hunk 集合，
  仍按 [ADR-0050](./0050-编辑diff的行级hunk与提案投影.md) 生成收窄提案，
  复用完整 apply 分发路径。**权限语义一个字不改。**

两半都完成，`main/edit-review.ts` 与渲染层的专用组件才可以删。
只完成前一半就宣布退役，是把一条还在用的通道从文档里抹掉。

## 后果

- **正面**：`docs/05` 那条"新增工具不需要改 UI 代码"的承诺，
  在**需要交互的工具**上也成立了——这是 ADR-0058 单独做不到的一半。
- **正面**：三方插件的工具可以有交互卡片，而不必拿到任何 IPC 权限。
- **正面**：`origin` 让"谁发起了这次写入"第一次可审计。

- **负面**：多一个具名 IPC 方法。preload 变厚一点点，但仍是具名转发，
  `preload-必须保持薄` 规则的实质（不提供通用入口）没破。
- **负面**：工具作者要多设计一件事——动作的载荷形状。
  与 ADR-0058 让他们设计卡片是同一类成本，同一个理由：交互意图是工具设计的一部分。

- **代价与缓解**：`callId` 反查工具需要读事件流，这是一次同步的历史查询。
  缓解：查的是当前会话的近期事件，`reduce()` 后的状态里本来就有工具调用索引。

- **必做的反向演练**：
  1. 渲染层伪造一个 `callId` 指向别的会话 → 必须拒绝。
  2. 渲染层传一个工具没声明的 `actionId` → 必须拒绝（失败关闭）。
  3. 构造一张卡片，其动作载荷里塞一个越界路径 → **必须被路径网关与红线拦下**，
     不能因为"是用户点的"就放行。这一条是本 ADR 的核心：**动作通道不是审批通道。**
  4. 一次由动作触发的写入 → 事件流里 `origin.kind` 必须是 `user-action`
     且能回指到那张卡片的 `callId`。
  5. 删掉 `main/edit-review.ts` 后，M2-e 的逐块接受/拒绝全套用例必须仍然全绿。

- **重新评估条件**：如果动作开始需要"返回值回到卡片上"（例如点一下要看到结果再决定下一步），
  那是一个新形状——卡片变成了有状态的会话参与者。届时先问它是不是应该做成一个工具调用，
  而不是给动作通道加一条返回路径。
