# ADR-0032 · 地基复审三：M1 收尾前的原则符合度审查与纠正计划

- **状态**：🟢 Accepted（2026-08-08）
- **日期**：2026-08-08
- **相关**：复审对象是 [docs/01](../01-愿景与设计原则.md)（七条原则 + 质量标线）、
  [docs/05](../05-可插拔与扩展体系.md)（六类扩展点）、[docs/07](../07-自我迭代能力.md)
  （L0–L4 分级）；方法延续 [ADR-0012](./0012-地基复审与安全边界修正.md)（地基复审一）、
  [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md)（地基复审二）；触发
  [docs/09](../09-待讨论的开放问题.md) G4/G5 补排优先级；影响
  [docs/08](../08-路线图与里程碑.md) 新增 M1-d.5 阶段；**不修改**任何既有 ADR 的判定逻辑

## 背景

M1-d 交付完成（[ADR-0026](./0026-命令的主张分解与argv契约.md)～[ADR-0031](./0031-shell-session-pty.md)），
M1 只剩 M1-e 收尾。前两次地基复审分别发生在 M0 末尾（ADR-0012）与 M1-a 前后
（ADR-0017），问的问题是"某条规则写没写生效"。这一次不一样：功能面已经堆到
8 个工具、32 份 ADR，用户明确要求在进入 M1 最后一段前做一次不同角度的复审——
**实现过程有没有偏离 docs/01 的七条原则和质量标线、docs/05 设想的可插拔体系、
docs/07 要求的自我迭代地基**，尤其是性能、安全性、可靠性，以及"架构是否强大到
能撑住 M4 操作电脑、M5/M6 自我迭代"这条更长远的线。

方法与前两次一致：**不读意图，读证据**——已经存在的实测数字（G4/G5）、真实的
文件行数、真实的依赖导入路径、真实存在或不存在的目录（`evals/`）。

## 复审结果

### 一、可靠性与性能：两个已实测的问题，从未被排期

`docs/09` 的 G4（会话回放超线性）与 G5（IPC 边界全量物化）早就"📊 实测"过并写了
具体数字，但**从未出现在"讨论优先级"表格里**——没有 P0–P3 标记，处于"记了就忘"
的状态。

- G4 直接证伪 [docs/01](../01-愿景与设计原则.md) 质量标线里"**长会话 1000+ 轮不劣化**"
  这条硬指标：16k 条 `message.end` 回放耗时 1121ms，且随事件数**超线性**增长
  （N 翻倍、耗时 ×10.14，不是 ×2）。
- G5 与**原则五**"流式优先，端到端不阻塞"直接冲突：`readSession` 把整段历史一次性
  物化再过 IPC，5 万事件时单次 `structuredClone` 阻塞主进程与渲染进程各 685ms。
- 两者同源：`SessionState` 没有快照机制，`reduce()` 只能从 seq 0 全量重放。
  docs/09 里已经给出过倾向（checkpoint 顺带做状态快照），但从未转成任务，
  也没有排进优先级表——**问题被发现、被量化、却没有被追踪**，这本身是一个
  流程性缺口，不只是技术缺口。

### 二、单文件规模纪律：约束存在但从未被 CI 强制，已经被实际突破

原则七写的可检验约束是"单文件超过 400 行、单函数超过 60 行触发审查"。对比：
契约体积有 `size-limit`、依赖方向有 `depcruise`、Windows 坐标系有专门测试——
唯独这条**从 M0 起就没有配对应的自动化检查**，纯靠自觉。实测现状：

| 文件 | 行数 | 超限倍数 |
|---|---|---|
| `apps/desktop/src/renderer/App.tsx` | 1023 | 2.6× |
| `packages/kernel/src/policy/defaults.ts` | 776 | 1.9× |
| `apps/desktop/src/main/services.ts` | 517 | 1.3× |
| `packages/kernel/src/policy/engine.ts` | 418 | 1.05× |
| `packages/kernel/src/policy/command-claims.ts` | 404 | 1.01× |

`App.tsx` 最值得警惕：每加一个观察面板（`LiveCalls`/`PermissionCard`/
`ApprovalModeSwitcher`/`TerminalPanel`）都是往这一个文件里追加一段组件。这正是
[docs/05](../05-可插拔与扩展体系.md) 开篇那句"这一层设计错了，后面所有能力都会
被迫走后门"预言的形状——现在还没到"走后门"的地步，但已经是"每次都手工挤进
同一个文件"，与 docs/05 §6 规划的渲染器注册表（工具自带展示契约，新增工具不
用改 UI 代码）背道而驰，且**每晚拆一次，牵扯的组件越多，拆分成本越高**。

### 三、可插拔性：一处 M3 计划内的缺口，暂不算背离，但成本正在累积

原则二的验收约束"删掉 `packages/tools-core` 后，内核 + UI 必须仍能启动"——**从未
写成集成测试**。当前 8 个工具全部在 `apps/desktop/src/main/services.ts` 里直接
`import` + `tools.register()`，没有清单/发现/激活机制的雏形。**这是 M3 的既定
工作，本身不算背离**——`ToolDescriptor.source` 字段（`{kind:'builtin'}`）已经
埋了一个"来源"标记，是留给未来插件来源的挂钩点，只是从未被读取或验证过是否
够用。真正的成本是：工具已经堆到 8 个，每多堆一个，"删掉 tools-core 后能不能
启动"这类验收测试的缺失就多亏一分——现在补一条最小集成测试成本很低，越往后
越像是要补一次大的。

UI 侧对应的缺口更具体：docs/05 §6 规划的"渲染器注册表"完全没有实现，四类
观察面板（对话/终端/文件 diff/屏幕）目前只做出一种（终端）且是写死组件——
第二种面板（M2 的 diff 审阅 UI）一旦落地，大概率会重复"焊进 `App.tsx`"这条
路，届时改造成本比现在更高。

### 四、自我迭代基础：docs/07 明确要求"M1 必须先有"的 L0，完全空白

[docs/07](../07-自我迭代能力.md) 的分级表原话——L0 记录，"何时做：**M1（地基，
必须先有）**"。现状：仓库里没有 `evals/` 目录，没有任何 trace 记录代码，
`packages/contracts` 里唯一出现"trace"字样的地方是 `envelope.ts` 里一句
与子 Agent 隔离相关的注释，与 docs/07 描述的"每次 Turn 落盘一份完整可回放记录"
毫无关系。M1 已经走到 M1-e 前一步，L0 却一行代码都没有。

**这是本次复审里最明确的一条真实背离**——不是"节奏上还没排到"，是**文档白纸
黑字写着这一步必须先做，而实际执行顺序把它跳过了**。后果与 G4/G5 同源：M2 的
记忆（L1）、M3 的技能（L2）都要靠 trace 数据起步，越晚补，能追溯的历史运行
就越少。现在 M1 的全部功能刚好都被真实输入跑过一遍（8 个工具、审批全链路、
PTY），是补 L0 的最佳时间点——再拖过一个里程碑，就少一个里程碑的真实数据
可用于日后校准。

### 五、安全性：无新增的失效，但有一处需要补上机器可检验性的例外

- 本轮**没有**发现"规则写了但没生效"类型的新问题（ADR-0012/0017 的模式）——
  `evaluate()` 本身零改动；抽查了 `capabilities: []` 的使用范围，全项目只有
  PTY 的三个工具（`shell.session.write`/`.resize`/`.close`）用到，没有扩散。
- `shell.session.write/resize/close` 声明空能力集，字面上是**原则四**约束
  "所有产生副作用的工具必须声明 capabilities 与 risk，并经过权限闸门"的一个
  例外——但原则四本身也写了"任何'绕过审批'的代码路径都要有 ADR 说明"，而
  ADR-0031 就是那份说明，**所以字面上不算违反，是一次被记录在案的、经用户
  同意的例外**。
- 真正的缺口是**这条纪律目前完全靠人记得住**：没有任何 lint 规则或测试会在
  "下一个新工具也想抄近道声明 `capabilities: []`"时发出信号，要求它必须先有
  一份 ADR。按 docs/01 自己的元规则——"不能被 CI 或代码审查检验的原则等于
  没有"——这条约束目前不算真正生效，只是恰好还没被滥用。

## 决策：纠正计划

不是所有条目都现在处理——结构性欠账（越拖越贵、且成本主要来自"以后要碰的
代码更多"）现在处理；行为性/规模性优化按既定节奏走，提前做反而是过度设计。

| # | 问题 | 动作 | 目标阶段 |
|---|---|---|---|
| 1 | G4/G5 从未进入优先级表 | docs/09 优先级表新增两行，标 **🔴 P0**（理由：quality bar 已被证伪，且是 L1 记忆检索、长会话都要踩的同一个地基洞，拖到 M2 会同时挡住 checkpoint 通用化） | 表格更新：本次已做；**实现排进 M1-d.5** |
| 2 | `App.tsx` 1023 行 | 按面板拆成独立组件文件（`TerminalPanel`/`PermissionCard`/`ApprovalModeSwitcher`/`LiveCalls` 各自一个文件），`App.tsx` 只保留装配逻辑；顺带看一眼 `defaults.ts`/`services.ts` 能不能按能力分组拆文件（不强制，视拆分后是否真的更清晰） | **M1-d.5** |
| 3 | 400 行约束无 CI 强制 | 新增行数检查（`scripts/check-file-size.mjs` 或 ESLint `max-lines`/`max-lines-per-function`），接入 `pnpm verify`，允许显式豁免清单（豁免需要理由注释，同 `depcruise` 豁免的先例） | **M1-d.5** |
| 4 | L0 trace 完全空白 | 落地最小 trace 记录——**从现有事件流派生一份只读视图，不新起一条独立写入路径**（避免造出 ADR-0015/0021 反复强调的"第二份事实来源"）；建 `evals/` 目录骨架 + 至少 1 条基于真实 M1 用例的回归用例 | **M1-d.5**，作为 M1-e 收尾 DoD 的前置条件 |
| 5 | 渲染器注册表缺失 | 不提前做——按既定节奏，**M2** diff 审阅 UI 落地时与 `TerminalPanel` 一起迁移进去；现在只有两种面板就设计注册表会过度抽象 | **M2**（不变） |
| 6 | 插件宿主/清单机制缺失 | 不提前做，`ToolDescriptor.source` 挂钩点保留，等 M3 落地时验证是否够用 | **M3**（不变） |
| 7 | `capabilities: []` 例外无机器可检验性 | 新增一条测试/lint：任何 `defineTool()` 声明空 `capabilities` 必须出现在一份显式白名单里，且白名单条目要求写明 ADR 编号（当前唯一合法条目是 ADR-0031 的三个 PTY 工具） | **M1-d.5** |
| 8 | Checkpoint 不覆盖 PTY 会话内容 | 维持 [docs/09 C8](../09-待讨论的开放问题.md) #2 已定的安排——随 M2 checkpoint 通用化一起做，不提前、不重复排期 | **M2**（不变，C8 已覆盖） |
| 9 | "删掉 `packages/tools-core` 仍能启动"从未验证 | 补一条最小集成测试（`apps/desktop` 或 `packages/kernel` 层面），锁住原则二的验收约束，防止工具越堆越多、耦合越来越紧而不自知 | **M1-d.5** |

条目 1、2、3、4、7、9 共六项，全部安排进新增的 **M1-d.5** 阶段（见下），因为
它们的共同特征是"结构性欠账，且此刻处理成本最低"；条目 5、6、8 维持既定节奏
不变——提前做属于在证据不足时过度设计，与本项目"没有载体就无法在真实输入下
验证"的一贯原则（ADR-0020 决策三、docs/09 G2 的处理方式）相悖。

## 后果

- 正面：M1-e 开工前，quality bar 造假（G4）、观测边界阻塞（G5）、L0 数据基础
  缺失、规模纪律无强制、`capabilities:[]` 例外无检验，五类"实现期悄悄偏离
  文档"的问题被一次性拉平，M1-e 的崩溃恢复与总验收可以建立在一个真正被检验
  过的地基上，而不是在漂移的地基上再摞一层。
- 正面：L0 补上之后，M2 记忆（L1）从第一天起就有真实数据可用，不用等 M2
  再单独补录历史。
- 负面：M1-e 的开工时间往后推一小段（M1-d.5 本身有真实工作量，粗估 3–5
  个工作日：快照+分页 2 天、拆文件+行数检查 1 天、最小 trace+`evals/` 骨架
  1–2 天、`capabilities:[]` 白名单测试半天）。
- 需要接受的代价：M1-d.5 不是免费的复审，是真实的返工时间；但对照 ADR-0012/
  0017 的历史——**每一次"先复审再继续"都在事后被证明比"发现时再改"更便宜**
  （8.3 短文件名、注入降级失效、Windows 坐标系失效都是"早发现成本低、晚发现
  改的地方更多"的例子）。
- 什么条件下应该重新评估这个决策：如果 M1-d.5 的快照实现发现 `SessionState`
  的不可变数据结构与快照机制有更深的耦合问题（比如快照本身的 schema 演进
  与 ADR-0008 的 upcaster 机制冲突），需要单独出一份 ADR，不能在 M1-d.5 里
  用一个临时方案糊过去。

## 遗留

- 本 ADR 只排出"做什么、什么时候做"，**不在此处给出 M1-d.5 六个条目的具体
  实现方案**——那是 M1-d.5 阶段动工时各自的设计工作，尤其是条目 4（trace 视图
  怎么从事件流派生、`evals/` 判定式怎么写）与条目 1（快照的 schema 演进策略）
  都有明显的设计空间，不该在一份复审 ADR 里顺手拍板。
- 条目 5/6/8 明确"不提前做"，但这不等于"不重要"——它们仍然是 M2/M3 的硬性
  前置条件，只是提前做的收益低于风险（没有第二种面板类型、没有第二个工具
  来源之前，抽象的形状容易设计错）。
