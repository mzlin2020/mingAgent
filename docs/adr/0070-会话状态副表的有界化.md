# ADR-0070 · 会话状态副表的有界化

- **状态**：🟢 Accepted
- **日期**：2026-08-15
- **相关**：[ADR-0058](./0058-工具渲染意图与结果投影.md) · [ADR-0050](./0050-编辑diff的行级hunk与提案投影.md) · [ADR-0032](./0032-地基复审三-M1收尾前的原则符合度审查.md)（G4/G5 是同一形状）· [ADR-0057](./0057-扩展事件通道与未知事件语义.md)（`ReadOptions.types` 是将来按需回填的路）

## 背景

`SessionState` 里有两张**只增不删**的副表：

| 字段 | 每条装什么 |
|---|---|
| `presentations`（`Map<CallId, unknown>`） | 每次工具调用落库的展示事实（ADR-0058） |
| `editProposals`（数组） | 每份编辑提案的**完整** diff，以及每一处 `oldText`/`newText` |

`context.compacted` 在 `reduce` 里只记标记，不动这两张表；`readSession` 会把整个状态过一次
IPC（ADR-0032 修 G5 时定的形状）；快照序列化也把它们整份写下去。

问题不在条数，在**单条的体积**：一份改了三个文件的提案带着三段完整 diff 与全部替换文本，
可以比产生它的那条 `tool_use` 消息大一个量级。一个用了几周、改过几百个文件的会话，
这两张表会把 `readSession` 的负载和快照撑得比会话本身还大。

这与已经修过一次的 G4/G5 是**同一个形状**：存储层克制、状态层不克制，代价在边界上兑现。

## 决策

**两张表都有界。淘汰的是投影里的驻留副本，不是数据——事件流仍是唯一真相。**

### 一、`presentations`：留最近 256 条，按插入顺序淘汰最旧

缺失时 `projectResultCard()` 拿到的 `presentation` 是 `undefined`，退成通用卡片。
这条降级路径是 **ADR-0058 本来就规定好的**（"畸形/旧参数返回 `undefined` 降级为通用卡片，
绝不允许崩掉回放"），不是为这次改动新造的退路。

同一个 `callId` 重复写入会**重新排到队尾**，不留在原位——它刚被更新过，是最不该被淘汰的那条。

### 二、`editProposals`：留最近 64 条，优先淘汰终态

终态 = 已应用，或已审阅但未应用。顺序是先按终态、再按新旧：终态提案只对"翻历史看那次
改了什么"有用，而未应用的提案还等着被 `edit.apply` 引用。

终态不够时才淘汰最旧的非终态。那种情况下模型堆了 64 条以上没人应用的提案，
最旧的那条本来也已经过期（`beforeHash` 多半对不上了）。

被淘汰的提案再被 `edit.apply` 引用时，命中 `packages/tools-core/src/edit.ts` 里**已有的**
`找不到当前会话中的编辑提案。`——与模型编了一个不存在的 id 走同一条路径。
**复用一条已经存在、已经测过的失败路径，不新增错误语义**，模型重跑一次 `edit.preview` 即可。

### 三、实现落在一个独立文件

`packages/kernel/src/state/bounded-index.ts`。`reduce.ts` 当时 394/400 行，塞不下——
规模纪律要求**拆分而不是加豁免**，这也是 M3-g 处理 `reduce.ts` / `container.ts` 超线的同一做法。

### 四、这次没有做的：按需回填

淘汰之后老卡片就是通用卡片，不会去把展示事实读回来。真要做，路已经铺好了：
M3-g 给 `EventStore.ReadOptions` 加的 `types` 过滤能单读 `tool.end`。
**但那要引入一次 IPC 往返和一份渲染层缓存**，在有人真的抱怨"往上翻的卡片变素了"之前不值得。

明确写下来是因为反方向的诱惑更大：把字段加回 `SessionState` 看起来更简单，
而那正好回到本 ADR 要解决的问题上。

## 后果

- **正面**：两张表的体积有上界，`readSession` 的 IPC 负载与快照大小随之有界。
- **正面**：淘汰是插入顺序的纯函数，"从快照 + 尾部回放"与"全量回放"给出同一张表，
  `reduce` 的纯函数性质不受影响。
- **负面**：往上翻很久以前的工具卡片会退成通用卡片；很久以前的编辑提案不能再 apply。
  两者都是可见的降级，不是静默的错误。
- **负面**：256 / 64 这两个数字是拍的。它们的量级依据是"一个会话里同时活着的富展示调用"
  与"同时挂着的未应用提案"，没有实测支撑。真要改，改常量即可。

- **必做的反向演练**（已完成）：把两个上界调成一个大到形同不存在的值，
  三条淘汰用例必须红。**已验证**：`expected 296 to be 100000` / `expected 74 to be 100000` /
  `expected 69 to be 100000`。两条快照一致性用例仍绿是对的——它们测的是确定性，不是上界。

  > 用例里的循环条数**写死，不从上界常量算**。第一版是从常量算的，
  > 于是把上界调大之后测试自己跑到内存耗尽——**那不叫红，那叫没跑**。
  > 这是"反向演练本身也会失效"的一个具体样本。

- **重新评估条件**：如果用户真的抱怨"往上翻的卡片变素了"，做第四节的按需回填，
  而不是把上界调大——调大只是把同一个问题推远一点。
