# ADR-0064 · Inbox 的持久化边界与 `steer` 的生效时点

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0056](./0056-Agent句柄与Inbox.md) · [ADR-0008](./0008-事件持久化分层与演进.md) · [ADR-0013](./0013-存储引擎选型与EventStore端口.md) · [崩溃恢复](../04-总体架构.md)

## 背景

[ADR-0056](./0056-Agent句柄与Inbox.md) 定了 Inbox 的三入口与认领语义，但复审
（2026-08-14）指出它**没有回答崩溃时会发生什么**：

- `inject` 落了 `context.injected`（persisted），可认领之后它从内存队列里被取走——
  **"取走"这件事没有任何记录**。重启后怎么知道这条注入是该重发还是已经消费过？
- `followup` / `steer` **连事件都没有**。用户在回合进行中排了一条消息，
  进程此刻崩溃，那条消息去哪了？文档没说。
- `steer` 的语义是"当前回合的下一步认领时优先"，但**没说它拿在飞的工具调用怎么办**。
  用户打字"别改那个文件"的时候，`fs.write` 可能已经在执行了。

第三条是三条里最要紧的：它直接决定用户看到的行为对不对得上他的预期。

复审建议的解法是加一条 `context.claimed` 事件、给注入编 `injectionId`、
定义 exactly-once 语义。**问题成立，但这个解法比需要的重。** 下面说为什么。

## 选项

### 选项 A：加 `context.claimed` 事件，显式记录消费

优点：消费状态是显式的，重启后一目了然。
缺点：为每一条注入多写一条事件，事件流长度翻倍；而且它引入了一个新的不一致窗口
——"落了 injected 但还没落 claimed"时崩溃，仍然要靠规则去判该不该重发。
**它把问题推后了一步，没有消灭问题。**

### 选项 B：定义 `reduce()` 语义，让消费成为隐式且天然幂等的

### 选项 C：把整个 Inbox 持久化（未认领的也落库）

优点：崩溃零丢失。
缺点：未认领的排队消息是**尚未被接受的输入**，把它落进会话事件流等于承认它已经是历史的
一部分；用户排队后又反悔，会话里就留下一条从未生效的消息。
且它与 ADR-0008 的持久化包含性冲突：事件流是"发生过什么"的记录，不是"打算做什么"的队列。

## 决策

**选择 B。** 三条规则。

### 一、`context.injected` 参与 `reduce()`，消费因此是隐式的

`context.injected` 是 persisted、有 seq、按 seq 折进消息历史的**同一条时间线**上。
`reduce()` 把它的 `content` 投影进模型可见的历史，位置就是它的 seq 所在处。

推论——而且这是本 ADR 最重要的一句：

> **注入内容一旦落库，它就已经在历史里了。"认领"只是决定它何时被送进下一次请求，
> 不决定它是否存在。**

于是"重启后该不该重发"这个问题**根本不成立**：重启后 `reduce(events)` 重建出的历史里
本来就有它，位置和顺序都由 seq 决定。既不会重复（同一条事件只有一个 seq），
也不会丢失（它是 persisted）。exactly-once 不是靠协议保证的，是**靠它和别的历史内容
走同一条路**保证的——这正是"状态 = `reduce(events)`"这条第一不变量的价值所在。

内存里的那个队列因此只是一个**待送达指针**，不是真相的持有者。它丢了不影响正确性。

### 二、未认领的 `followup` / `steer` 不落库，崩溃即丢失

明确写下这条语义，不留给读者猜：

| 阶段 | 持久性 |
|---|---|
| 已调用 `followup()` / `steer()`，尚未被认领 | **易失**。进程崩溃即丢失 |
| 已被认领，进入某个回合 | 持久——认领的那一刻随 `turn.start` 的 `input` 落库 |

这是 **at-most-once**，且与今天的行为一致：现在用户在 `sendUserMessage()` 之前打的字
本来也只在渲染层的输入框里。把"排队中"的消息落库会让一条从未生效的消息永久留在
会话历史里，代价比丢失一条尚未开始处理的消息大。

两条配套要求：

1. **UI 必须显示待处理队列。** 用户看得见"这条还没被接走"，就知道它此刻还不牢靠。
2. **崩溃恢复不合成未认领输入。** 崩溃恢复（[docs/04 §6](../04-总体架构.md)）的
   `synthesizeInterruption()` 只补收尾事件，不凭空补造用户输入——
   一条没进过 `turn.start` 的消息，对小明就等于没发生过。

### 三、`steer` 不取消在飞的工具调用

`steer` 在**下一个认领点**生效，也就是当前这一步（含它已经发起的工具调用）跑完之后。
它不打断、不取消、不回滚。

理由不是实现难，是语义：取消一次已经过闸门、已经开始执行的工具调用，
后果是**部分完成的副作用**——写了一半的文件、跑了一半的命令。而"停在中间"这件事
本仓库已经有一条正规路径（用户手动停止 + ADR-0003 的还原点），
不该由一条纠偏消息隐式触发。

给用户的表达要诚实：`steer` 的 UI 文案是"下一步生效"，不是"立即停止"。
想立刻停就点停止——那条路径会落中断的两条事件，语义清清楚楚。

**唯一的例外**：`steer` 到达时如果当前步骤尚未发起任何工具调用（模型还在流式输出），
认领点本来就在眼前，此时它自然就"看起来像立即生效"。这是时序造成的，不是第二条规则。

## 后果

- **正面**：Inbox 的崩溃语义完整了，且没有新增事件类型——`context.injected` 一条
  同时承担"内容"与"消费凭证"两个职责，靠的是 seq 而不是第二条事件。
- **正面**：`steer` 的行为可以对用户如实描述。含糊的"纠偏"变成一句
  "下一步生效"，比一个偶尔能打断、偶尔打不断的实现好得多。

- **负面**：at-most-once 意味着极端情况下用户排的队会白排。
  缓解：UI 显示待处理队列 + 崩溃恢复后输入框保留草稿（渲染层已有能力）。
- **负面**：`steer` 不能救"模型已经开始写那个文件了"。缓解：那是还原点的职责，
  ADR-0003 的写前 checkpoint 覆盖它，且 M3-c 之后 checkpoint 是一个装配期断言在位的插件。

- **代价与缓解**：`reduce()` 多认识一种会影响消息历史的事件，
  投影逻辑与 `turn.start` 的输入折叠有相似之处但不完全相同。
  缓解：两者共用同一个"把内容并进 messages"的内部函数，不写第二份。

- **必做的反向演练**：
  1. 注入一条内容 → 立刻杀进程 → 重开会话，注入内容必须在历史里且**只出现一次**、
     位置与 seq 一致。重复或丢失都是一级缺陷。
  2. `followup` 排队后立刻杀进程 → 重开后**不得**出现那条消息，
     也不得出现一个空的孤儿回合。
  3. 一次 `fs.write` 执行途中 `steer("别改那个文件")` → 那次写入照常完成，
     纠偏在下一步生效；事件流里看得出先后。
  4. 模型流式输出途中 `steer` → 下一个认领点生效，`turn.start`/`turn.end` 成对性不变。

- **重新评估条件**：如果真实使用中反复出现"我 steer 晚了一步，它已经把文件改了"，
  那缺的不是打断能力，是**更快的认领点**（例如每个工具调用前都认领一次）——
  先调认领粒度，不要给 `steer` 加取消语义。
