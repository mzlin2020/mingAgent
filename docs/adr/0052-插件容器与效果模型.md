# ADR-0052 · 插件容器与效果模型

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[docs/11-微内核与插件容器](../11-微内核与插件容器.md) · [ADR-0053](./0053-微内核的特权底座与扩展点边界.md) · [ADR-0059](./0059-组合配置profile与patch层.md) · 参考实现 `/code_mine/deepseek-harness`（Cordis）

## 背景

M2 收官时，小明的**安全底座**是这个项目最扎实的部分（红线跨层、路径网关、seq 单点分配、
reduce 可回放），而**组合能力接近于零**：

1. `apps/desktop/src/main/services.ts` 1043 行手工接线，是唯一的装配路径。headless 冒烟是另一条
   独立脚本，`xm` CLI 还不存在——**同一套引擎从来没有被第二次装配过**，"内核可被装配"
   至今是一个只在测试里成立的说法。
2. `packages/runtime/src/turn.ts` 把上下文组装、checkpoint、工具分发、结果截断焊死在流程里。
   想加 hooks、压缩策略、plan mode、文件变更通知，只能改 `turn.ts`——一个扩展点都没有。
3. `packages/runtime/src/subagent.ts` 靠 `tool?.descriptor.source.kind === 'builtin'` 手工过滤
   父工具集来构造子 Agent 的能力范围。这是"作用域"这个概念缺席之后的必然产物。
4. `docs/05` 承诺的六类扩展点、`PluginManifest` 里的 `events` 字段、渲染器注册表，
   **一个消费者都没有**。

参考实现 deepseek-harness 把这一层做到了极致：整个产品——包括模型适配器、工具注册表、
会话日志、Agent 循环本身——都是挂在 Cordis 容器上的插件，没有特权内核，一切从配置替换。
它的组合能力正是小明缺的，但它的安全立场比小明弱（保留 `ask` 与审批、三方插件全进程内、
没有红线跨层判定），不能整体照搬。

约束：内核必须保持纯逻辑、零 I/O、零 `node:*`，能在浏览器里跑；`.dependency-cruiser.cjs`
的 20 条规则是本仓库唯一的硬架构约束，不能因为引入容器就废掉。

## 选项

### 选项 A：不引入容器，继续手写装配，按需加接口

优点：零风险，护栏一条不动。
缺点：不解决任何一条上述问题。每加一个扩展点都要在 `TurnDeps` 上加一个可选字段
（现在已经有 12 个），而可选字段既表达不了"谁提供它"，也表达不了"卸载时怎么撤销"。
`services.ts` 会继续长。

### 选项 B：依赖 npm 上的 `cordis`

优点：省下容器实现，拿到成熟的 fiber / effect / HMR 语义。
缺点：内核多一个外部依赖，与"contracts 只依赖 zod、kernel 只依赖 contracts"的现有格局冲突；
更实际的问题是**引入第二套事件与类型体系**——Cordis 有自己的事件声明合并机制，而小明的事件
真相在 `@xm/contracts` 的 Zod 注册表里。两套并存，"契约单一来源"这条不变量当天就破。

### 选项 C：vendor `cordis` 源码进 `vendor/` 并 rescope

优点：可控性最好，deepseek 就是这么做的。
缺点：一次性引入数千行非自有代码，与本仓库单文件 400 行的规模纪律正面冲突（需要成片豁免）；
而且我们只需要它五个概念中的五个，其余（HMR、fiber 树、loader、`!!js` 表达式）当前用不上。
维护一份自己不需要的框架分支，成本长期存在。

### 选项 D：自研最小容器，放进 `@xm/kernel/src/container/`

优点：纯逻辑、零 I/O、零新增依赖——天然满足"内核能在浏览器里跑"，而且这条约束反过来
保证了容器不会偷偷长出文件读写或进程管理。事件走 `@xm/contracts` 已有的 Zod 校验，
不引入第二套真相。规模可控（预估 600–800 行，拆 4–5 个文件）。
缺点：HMR、依赖环检测、生命周期边界要自己实现并自己测；写错了没有上游帮忙修。

## 决策

**选择 D。** 自研最小容器，落在 `@xm/kernel/src/container/`，只实现五个概念：

| 概念 | 语义 | 对应现状里的什么 |
|---|---|---|
| **服务（Service）** | 一个稳定的 `ctx.<key>`，例如 `ctx.tools`、`ctx.policy`、`ctx.events`。消费者按 key 取，不 import 具体实现 | 现在是 `TurnDeps` 上的 12 个字段 |
| **插件（Plugin）** | `{ name, inject?, apply(ctx) }`。`inject` 声明它需要哪些服务，容器据此决定装配顺序 | 现在是 `services.ts` 里的手工顺序 |
| **效果（Effect）** | 一切注册都经 `ctx.effect()` 并返回撤销函数：工具、监听器、提示词段、渲染器 | 现在没有对应物——注册了就撤不掉 |
| **类型化事件** | 四种派发模式，见下表。进程内、瞬态、不落库 | 现在没有对应物 |
| **作用域（Scope）** | `ctx.fork()` 出的子上下文，卸载父即卸载子；子 Agent 用它承载自己的工具子集 | 现在是 `subagent.ts` 里手工过滤 `source.kind === 'builtin'` |

派发模式照搬 Cordis 的四种，语义一字不改（它们是被验证过的正交集合）：

| 模式 | 是否 await | 顺序 | 有返回值 | 典型用途 |
|---|---|---|---|---|
| `emit` | 否 | 注册序 | 否 | 通知（工具注册表变了） |
| `waterfall` | 否 | 注册序，环绕中间件 | 是 | 拦截与改写（工具执行前的判定链） |
| `parallel` | 是 | 并发 | 否 | 扇出（多个观察者各自落审计） |
| `serial` | 是 | 注册序 | 是 | 有序决策（回合终止检查） |

`waterfall` 的语义同样照搬：监听器签名 `(...args, next)`，**调用 `next()` 才把结果交给下一个
监听器，不调用即短路**。这一条必须原样保留——ADR-0055 的闸门顺序和 ADR-0053 的
"扩展点只能收紧"都建立在它之上。

### 与 `EventBus` 的分工（不合并）

`packages/runtime/src/event-bus.ts` 保留现职责不变。两者是**两种东西**，文档里必须写死：

| | 会话事件（`@xm/contracts` `EVENT_SPECS` + `EventBus`） | 容器事件（扩展点） |
|---|---|---|
| 落库 | 是（`persisted`）或显式瞬态 | **从不落库** |
| seq | 有，由 `SessionRuntime` 单点分配 | 无 |
| 跨进程 | 是（IPC 两侧 Zod 校验） | 否，进程内 |
| 可回放 | 是，`reduce(events)` | 否 |
| 谁能加 | 只有 contracts（或 ADR-0057 的 `ext.*` 通道） | 任何插件 |

合并它们看起来更"统一"，但那会让扩展点的每一次派发都要考虑要不要占一个 seq，
而 seq 单点分配是 ADR-0013 不变量三——不能为了优雅去动它。

### 不做的

- 不做 HMR（热替换）。效果撤销让它成为可能，但真正要用是 M7 自改闭环的事，现在不实现。
- 不做 `!!js` 之类的配置表达式求值。profile 只做静态行 + patch（ADR-0059）。
- 不做 fiber 树 / 生命周期钩子的完整形态。只保留"卸载即撤销全部效果"。

## 后果

- **正面**：装配从手写变成组合；`services.ts` 可拆成插件行；子 Agent 的作用域、
  未来的插件热加载、profile 多入口装配，全部落在同一个机制上。
  "内核可被装配"第一次有第二个装配入口来证明（ADR-0059）。

- **负面（真损失，必须写明）：静态可分析性下降。** 现在 `.dependency-cruiser.cjs` 能靠 import 图
  证明"内核没有碰 electron"；改成按 key 取服务之后，**一部分依赖关系从 import 图挪到运行时**，
  import 图看不见了。这不是可以粉饰的代价。三条对策，缺一不可：
  1. **插件住在现有包里，不为插件新建细粒度包。** 20 条包边界规则一条不改，
     `@xm/kernel` 不许 import electron 这类约束依然由 import 图强制。
     （deepseek 走的是一插件一包、51 个包的路线；小明明确不走。）
  2. **import 图看不见的那部分，由从代码生成的接缝图补上**，并进 `pnpm verify`（ADR-0060）。
     生成的图是唯一能回答"谁提供 `ctx.executor`、谁消费它"的地方。
  3. **未满足的 `inject` 必须 fail loud**：装配期报错并指名缺哪个服务，不许静默挂起。

- **负面：错误从编译期挪到装配期。** 现在 `services.ts` 漏传一个依赖是编译错误；
  之后变成"插件等一个永远不会出现的服务"。上面第 3 条对策就是为它准备的。
  容器必须在装配收敛时检查是否还有插件在等待，有就报错并列出等待链。

- **负面：多一层间接性。** 读代码时"这个行为是谁注册的"要查 profile 而不是顺调用链看。
  对人是损失；对小明自己读自己反而是收益（生成的图谱比调用链好用）——这也是
  ADR-0060 的图谱生成必须与容器同批交付、不能当可选项的原因。

- **代价与缓解**：容器 600–800 行会撞单文件 400 行闸门，**拆成多文件解决，不申请豁免**。

- **重新评估条件**：
  - 如果自研容器在依赖环、卸载顺序、并发派发上连续出现两次以上真实缺陷，说明这五个概念
    的实现难度被低估了，应重新考虑选项 B/C。
  - 如果小明开始需要真正的热替换与 fiber 级生命周期（M7 自改闭环），届时重新评估是否
    vendor 一个成熟实现。
