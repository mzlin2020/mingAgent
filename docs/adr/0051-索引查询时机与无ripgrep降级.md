# ADR-0051 · 索引的查询时机、工作区身份与无 ripgrep 降级

- **状态**：🟢 Accepted
- **日期**：2026-08-13
- **相关**：[ADR-0042](./0042-M2-b文本检索与会话内结果展开.md)、[ADR-0047](./0047-M2-g可重建WASM符号与FTS索引.md)、[ADR-0016](./0016-原生模块与打包.md)
- **Supersedes**：[ADR-0047](./0047-M2-g可重建WASM符号与FTS索引.md) 第 2、3、4 节；[ADR-0042](./0042-M2-b文本检索与会话内结果展开.md) 中"ripgrep 是硬依赖"的部分

## 背景

M2 复审发现索引这条线有三个互相咬合的问题，合起来的效果是**索引比不用索引更慢，
而且在很多机器上根本建不起来**。

**一、查询路径同步等一次全仓扫描。** `search.symbol` / `search.indexed` 在查询前
`await index.refresh(...)`——每一次调用都同步做一遍枚举 + 逐文件 stat + 变更文件
tree-sitter 重解析。ADR-0047 §3 写的是"打开/创建工作区后只后台触发一次 refresh，
不阻塞会话"，实现与它正好相反。

**二、后台刷新挂在工具调用的 signal 上。** turn 一结束就被取消，索引几乎永远停在半成品。

**三、工作区身份取自模型给的 `path`。** 模型查一次子目录就会另建一整份索引（连全文
副本一起复制）；而装配层预热用的是会话 cwd，两个 key 对不上，预热出来的索引永远命中不到。

另外两条是实现细节但后果一样硬：`errors.length === 0 ? 'ready' : 'stale'` 让**一个**
读不了的文件把整库标成 stale，此后每次查询都 fallback 并再触发一次全量重扫，形成稳定的
重扫循环；`#refresh` 无条件置 `building`，配上"查询触发刷新"就成了来回摆。

**ripgrep 的位置也需要重定。** ADR-0042 把它定成硬依赖，理由是"缺失时显式报错，不静默
降级"。报错确实显式，但后果被低估了：`search.text`、两个索引工具的 fallback、以及工作区
索引的文件枚举**全都**要 rg。普通 Windows / macOS 用户装上小明之后整条检索能力开箱即废，
而 M2 的目标是"日常写代码可以用它"。本机没有 rg 时 `pnpm verify` 直接红 9 个用例——
CI 里那句 `choco install ripgrep` 只是让流水线看起来是绿的。

## 决策

### 1. 查询只读状态，刷新在后台且节流

`state()` 为 `ready` 就直接查，查完**不等待**地触发一次后台刷新，按 root 节流到 30 秒
一次（节流状态挂在索引实例的 WeakMap 上，不是模块级变量）。后台刷新使用装配层给的
应用级 `backgroundSignal`，不是某一次工具调用的 signal。

已经 ready 的索引在增量刷新期间**保持 ready**。`building` 的本意是"还没有可用索引"，
不是"正在更新"；一份已建好的索引在增量更新期间仍然可用，结果最多稍旧——这正是
ADR-0047 明说可以接受的（"同一查询在索引完成前后可能排序不同"）。

### 2. 工作区身份是会话 cwd，`path` 只是结果过滤

索引 root 恒为 `ctx.cwd`（与装配层预热用的 `state.cwd` 是同一个字符串，因此不会再有
realpath 差异导致的 key 不匹配）。模型给的 `path` 降级为 `WorkspaceQuery.pathPrefix`
结果前缀过滤；前缀进 SQL 前转义 `%` / `_` / `\`，模型的路径不会变成通配符。

### 3. 逐文件错误不是整库的健康状态

扫描跑完就是 `ready`。逐文件错误照旧回传在 `WorkspaceIndexRefresh.errors` 里，
但不再改变整库状态。符号能力若整体降级（WASM 资产缺失等）也走这条通道说出来——
`@xm/storage` 不许 `console`，日志走事件流。

### 4. ripgrep 从硬依赖降为优先项

- `search.text` 启动不了 rg 时退到纯 Node 遍历 + `RegExp`，输出**同一套**
  `path:line:column` 契约与同一批参数语义（smart-case、glob、上下文、上限、二进制跳过）。
- 工作区索引的文件枚举同样 rg 优先、Node 遍历兜底。
- 退路**不假装等价**：它不读 `.gitignore`，只跳过隐藏项和一份固定的依赖/构建目录名单，
  不跟随符号链接，正则按 JavaScript 语法解析。结果里标 `source: node-fallback` 并把这些
  差异写清楚。宁可说明差异，也不要让调用方以为两条路径的召回集合完全一样。
- 索引工具回退时的标记从 `ripgrep-fallback` 改为 `text-fallback`——它现在可能是任一条。

不随包分发 rg 二进制：那要动 `allowBuilds` 白名单、electron-builder 配置与供应链检查脚本，
而纯 Node 退路已经让"开箱可用"这件事成立。装了 rg 的机器仍然自动走更快、忽略规则更完整的那条。

### 5. 测试按可用性分组，退路那条恒定跑

rg 专属行为（`.gitignore` / `.ignore`）按 `rg --version` 探测结果跳过；其余契约都钉在
退路上——退路才是普通用户开箱即得的那条。两处遍历器因 depcruise 的
`内核与装配层不得依赖-tools-core` 不能共用代码，各自实现；这份重复是依赖方向刻意换来的，
不是疏忽。

## 后果

- 正面：查询不再付全仓扫描的代价，索引真正起到加速作用。
- 正面：没有 ripgrep 的机器上检索与索引都可用（实测：移走 `/usr/bin/rg` 后全量测试
  1137 passed / 12 skipped，headless 冒烟含 M2-b 与 M2-g 全段贯通）。
- 正面：一个读不了的文件不再让索引进入永久重扫循环。
- 负面：Node 退路不读 `.gitignore`，在有大量被忽略产物的仓库里召回集合更大、更慢。
  缓解：固定排除名单覆盖最常见的几个目录，且结果里如实标注。
- 负面：查询结果可能比磁盘状态旧最多一个节流周期（30 秒）。这是 ADR-0047 已经接受的语义，
  现在只是显式了。
- 需要接受的代价：两处文件遍历器重复。缓解：各自都有确定性用例；真要合并需要先想清楚
  依赖方向，不在本轮顺手做。
- 什么条件下应该重新评估：如果实测发现 Node 退路在大仓库上慢到影响可用，再回到"随包
  分发 rg"那个选项，并同时评估 `allowBuilds`、打包体积与供应链检查。
