# ADR-0007 · 平台支持分级：Linux 作为 Tier 2，用 PlatformPort 预付保险

- **状态**：🟢 Accepted（2026-08-04 确认）
- **日期**：2026-08-04
- **相关**：[03-技术选型](../03-技术选型.md)、[06-安全与权限模型 §5 §6](../06-安全与权限模型.md)、[08-路线图](../08-路线图与里程碑.md)

## 背景

原定发布目标是 Windows + macOS，Linux 仅"尽力而为"。现提出希望小明也能在 Linux 上运行，需要评估成本并决定投入方式。

关键判断：**Linux 支持的成本不是均匀分布的，它高度集中在少数几个点上。** 笼统地问"贵不贵"没有答案，要拆开看。

## 成本拆解

### 几乎零成本（同一套代码直接跑）

Electron 外壳、React UI、Node 运行时、SQLite、node-pty、ripgrep、chokidar、tree-sitter、模型 Provider、MCP 客户端、插件宿主、本地/容器/远程三种执行器——全部平台无关。这覆盖了 M0–M3 的绝大部分工作量。

### Linux 反而更好的部分（意外收获）

| 能力 | 原因 |
|---|---|
| 容器执行器 | Docker 原生，无需 VM 层，启动快、开销低 |
| 沙箱隔离 | bubblewrap / namespaces / seccomp 比 macOS seatbelt 和 Windows Job Object 都更强更可控 |
| 无头部署 | 未来把小明跑在服务器上（配合 CLI 形态），Linux 是唯一现实的目标 |

### 有真实成本的部分

**1. 密钥存储（低成本，但必须现在处理）**

macOS Keychain 和 Windows Credential Manager 都是统一且必然存在的。Linux 是 libsecret（gnome-keyring / KWallet），而且**在没有可用 keyring 的环境下（无桌面会话、部分发行版、容器内），Electron `safeStorage` 会退化为明文存储**。

这不能靠"到时候再说"——密钥明文落盘是[原则四](../01-愿景与设计原则.md)和 [ADR-0003](./0003-默认权限策略.md) 明确禁止的。必须在 M1 就设计成：`SecretStore` 是一个接口，有 keychain 实现和"口令加密文件"实现，**运行时探测后端能力，退化时明确告知用户而非静默降级**。

> 这项工作即使不支持 Linux 也该做——它同时解决了无头/CI/容器环境下的密钥问题，是 CLI 形态的前置条件。**顺手做，不算 Linux 的增量成本。**

**2. 计算机操作（高成本，且是唯一真正贵的部分）**

这是全部成本的集中点，原因是 Linux 的显示服务器分裂：

| | X11 | Wayland |
|---|---|---|
| 屏幕捕获 | 直接可用，成熟 | 必须走 `xdg-desktop-portal` + PipeWire，需用户授权，各合成器实现有差异 |
| 输入注入 | XTEST，成熟 | **被设计性地禁止**。只能走 portal 的 RemoteDesktop / libei，且**合成器支持程度不一**（GNOME/KDE/wlroots 各不相同） |
| 窗口枚举 | X11 API | 无统一 API |

而 Wayland 已是主流发行版的默认。也就是说 Linux 上的 computer use 不是"再写一个实现"，而是"写两个实现，其中一个在部分环境下可能根本做不到输入注入"。

**3. 打包与分发（中等，主要是持续维护成本）**

AppImage / deb / rpm / Flatpak 多格式、glibc 版本差异、托盘图标（StatusNotifierItem 与旧规范并存，历来不稳定）、通知实现差异、自动更新机制各不相同。CI 矩阵增加一维。

**4. 测试负担（中等）**

Linux 不是一个平台，是「发行版 × 桌面环境 × 显示服务器」的组合空间。不可能全覆盖，只能选定基线。

## 决策

### 平台分级

| 等级 | 平台 | 承诺 | CI |
|---|---|---|---|
| **Tier 1** | macOS、Windows | 完整功能，全部特性 | 构建 + 全量测试 + E2E，阻断发布 |
| **Tier 2** | Linux（基线：Ubuntu LTS + GNOME） | **除计算机操作外全部功能**，正式发布产物 | 构建 + 单元/集成测试，阻断发布 |
| **Tier 3** | Linux 上的计算机操作 | 尽力而为。X11 优先实现；Wayland 单独评估，可能长期缺失 | 不阻断 |

### 现在就付的"保险"（低成本，回报极高）

这四条即使从不支持 Linux 也基本无损失，但如果不做，未来补 Linux 的成本会翻数倍：

1. **所有平台相关代码收敛到 `PlatformPort` 接口之后** —— 密钥、屏幕、输入、窗口、通知、托盘、路径。**严禁在业务代码里散落 `process.platform` 判断**（dependency-cruiser 加规则拦截）。这样加平台 = 实现一个适配器，而不是在全代码库里考古。
2. **`SecretStore` 不假设钥匙串存在** —— 接口 + 能力探测 + 显式降级告知。
3. **M0 起 Linux 就进 CI 构建矩阵**（构建 + 单测，不含 E2E）。现在加是改几行 workflow，等到 M4 再补要处理几十处已经漂移的平台假设。
4. **路径处理零假设** —— 不硬编码分隔符，用 `env-paths` 解析配置目录，显式处理大小写敏感性差异（Linux 敏感、macOS 默认不敏感、Windows 不敏感）。这条会在 Linux CI 上**提前暴露**本来就存在的路径 bug，是净收益。

### 时间安排

- **M0–M3**：Linux 与 Tier 1 平台同步推进（增量成本约 5%，几乎全是 CI 与打包）
- **M4**：计算机操作只做 macOS + Windows。Linux 上该能力标记为不可用，UI 明确提示，**不做半吊子实现**
- **M4 之后**：若确有需求，单独评估 Linux computer use（X11 优先）

## 后果

**正面**
- Linux 的日常能力（改代码、终端、文件、浏览器自动化、MCP、插件）全部可用——这已经覆盖了绝大多数实际使用场景
- 浏览器自动化在 Linux 上完全可用，它本就能覆盖"操作电脑"的大部分真实需求，computer use 的缺失没有想象中致命
- 为未来的无头/服务器部署（配合 CLI）铺好了路
- `PlatformPort` 的抽象让代码结构更干净，对自我迭代也友好——平台差异集中在一处，小明自己改起来不容易出错

**负面**
- Linux 上无 GUI 自动化能力，功能宣传要诚实分级，不能笼统说"支持 Linux"
- CI 时长与维护面增加约三分之一
- 多一个平台的 bug 报告面

**缓解措施**
- UI 中不可用的能力显式灰显并说明原因，不让用户在 Linux 上撞上"点了没反应"
- 基线只承诺 Ubuntu LTS + GNOME，其它组合社区尽力而为
- Tier 3 的缺失写进 README，不含糊其辞

**重新评估的触发条件**
- Linux 成为主要使用平台（那时 computer use 值得单独投入）
- Wayland 的 libei / portal 生态成熟到有统一可靠的输入注入方案
