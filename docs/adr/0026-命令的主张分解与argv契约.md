# ADR-0026 · 命令的主张分解：`shell.exec` 落地时，ADR-0020 决策三欠下的那半张契约到期了

- **状态**：🟢 Accepted（2026-08-07）
- **日期**：2026-08-07
- **相关**：还 [ADR-0020](./0020-非路径target的规范化契约.md) 决策三 / 四 / 五欠下的债；
  直接复用 [ADR-0024](./0024-路径能力网关.md)（网关回写）与
  [ADR-0025](./0025-敏感路径的读取拒绝.md)（读取侧红线，一条新规则都不用写就白拿）；
  部分回答 [docs/09 C2](../09-待讨论的开放问题.md)（本地执行是否强制沙箱）、
  关闭 [docs/09 C4](../09-待讨论的开放问题.md) 遗留的最后一段

## 背景

M1-a 在 `normalizeTarget` 的 `command` 分支放了一道失败关闭的闸门：带非空 target
的命令类判定一律判不了。那道闸门当时是对的——没有任何 shell 工具能喂它，写出来
就是再造一个"测试全绿、真实输入下从未跑过"的东西，`trustLevel` 硬编码（ADR-0017）
与 Windows 8.3 短名（ADR-0018）两次翻车都是这个形状。ADR-0020 决策四把契约本身
定死（`{ argv, cwd }`，只匹配 `argv[0]` 的 basename 与解析后的参数），把实现推给
"`shell.exec` 落地时"。现在 `shell.exec` 落地了，账到期。

`normalizeTarget` 只解决"同一条命令的不同写法归到同一个串"。它解决不了 M1-d DoD
的真正要求：

> `rm -rf ~` 被拦；`rm  -rf /`（双空格）、`/bin/rm -rf /`、`sh -c 'rm -rf /'`
> 四种写法判定一致。

在这份契约出现之前，`shell.exec` 的判定路径是：

```
shell.exec + 一条命令行 → def.shell-exec → ask
```

而 `red.fs-delete-home-root`（M0 就写好的红线，挂在 `fs.delete` 上）压根不会被查——
`rm -rf ~` 的结局是一个确认框，不是拦截。ADR-0020 说过"别用 glob 匹配命令行"，
这句话是对的，但它留下的空白一直没人填：**不匹配命令行，那匹配什么？**

`turn.ts` 的判定循环还有一个更底层的假设：`ResolvedCall.target` 是一个字符串，
一次调用只有一个判定对象。这对 `fs.read` / `fs.write` 成立（一个工具动一个文件），
对 `shell.exec` 不成立——一条命令可以同时是"执行"和"删除某个具体路径"，
把它们硬塞进同一个 target 判两次，要么信息丢失，要么无处安放。

## 选项

### 选项 A：真正的执行器沙箱（容器 / seccomp / Job Object）

直接从"能不能"这个维度解决问题，不需要理解命令的语义。但 docs/09 C2 至今没有
定案，本段如果把"拆解语义"和"选沙箱方案"两件事捆在一起做，沙箱选型一旦推翻，
两件事要一起重做。更关键的是：**沙箱管的是"进程能碰到什么"，不是"这次操作该不该
被允许"**——一个被允许访问真实文件系统的沙箱，一样能把 `~/.ssh/id_rsa` 读出来
塞进模型上下文。路径红线、ADR-0025 的敏感路径 deny，都是在"该不该"这层起作用的，
沙箱替代不了它们。

### 选项 B：给命令行字符串写更精细的 glob 或正则

ADR-0020 已经否决过一次，结论直接引用，不重新论证：命令行有无数种等价写法，
`rm  -rf /`（双空格）、`rm -fr /`、`/bin/rm -rf /` 对 glob 来说是互不相同的字符串，
写得再精细也只是扩大一点覆盖率，不改变"总有一种写法绕过去"的性质。

### 选项 C（选中）：把命令拆成一组「能力 + 目标」的主张，交给已经存在的规则去判

不新建一套命令专属的防线，而是把命令**翻译**成路径 / 主机类规则已经听得懂的话。
`rm -rf ~` 翻译成一条 `fs.delete /home/ming` 的主张，撞上的是一条 M0 就写好、
在这份 ADR 之前从未被 `shell.exec` 触发过的红线。

代价对称地写清楚：这张翻译表**必然不完备**，一个改了名的 `rm` 或表里没有的 bin
不会被翻译，退回今天的行为（一个确认框）。这不是缺陷，是这张表可以慢慢长、
不必先证明自己完备的前提——见决策三"只能加、不能减"。

## 决策

### 一、命令行 target 的规范化：归一到规范形式，但归一本身依然不是防线

`command-target.ts` 新增一个纯词法的规范化器：

- `argv[0]` 取 basename——`/bin/rm`、`/usr/bin/rm`、`rm` 归到同一个串
- 参数之间恒为单个空格——`rm  -rf /`（双空格）与 `rm -rf /` 是同一条命令
- 需要引号的参数按**唯一一种**写法加引号，使归一**幂等**——`quoteArg` 的输出
  再被解析一遍必须还原成同一个值，否则事件里记的串、授权里存的串、规则匹配的串
  会变成三个东西（ADR-0024 的同一个教训）

词法器解析的构造，全部是**展开结果与运行时环境无关**的：引号、管道、重定向、
`&&` / `||` / `;`。拒绝的构造相反——`$(...)`、反引号、`$VAR`、通配符、子 shell、
花括号展开——它们的展开结果取决于执行那一刻的环境，判定看到的和真正执行的会是
两个东西。**解析不了就拒，不是降级 ask**：ask 的下一步是用户点"允许"，而 M1-d 的
DoD 要求四种写法判定一致，只要 `sh -c 'rm -rf /'` 落成 ask，这条 DoD 就是假的。

⚠️ **归一到的这个串依然不是安全边界**——`rm -fr /` 与 `rm -rf /` 归一后仍是两个
不同的串，没有人能穷举命令行的等价写法。它的用途收窄成两样：会话授权的载体、
判不了的 bin 的便利过滤。真正拦住危险操作的是决策三。

### 二、命令 → 一组「能力 + 目标」主张（`command-claims.ts`）

一张画像表 `PROFILES`，把常见 bin 的操作数翻译成 `{ capability, target }`：
`rm` 产出 `fs.delete`，`cp` 的最后一个操作数是 `fs.write`、其余是 `fs.read`，
`mv` 的来源同时是 `fs.read` 与 `fs.delete`（移走和删掉对来源来说是同一件事），
`curl <url>` 产出 `net.fetch`、非 URL 的操作数按 `fs.write` 处理（`-o out.txt`
会落盘），`git push` 产出 `git.push`，`npm install` 产出 `package.install`。

命令前缀（`env` / `nohup` / `timeout` / …）与 `sh -c` **必须递归**，否则
`env FOO=1 rm -rf /` 的 bin 是 `env`，表里查不到，整条命令的语义就消失了。

挑选标准写在代码里，只有一条：

> **这个 bin 的典型用法会碰到一个"已经有规则管着"的目标**（路径、网络目的地）。

`echo` / `ls` 之外的绝大多数命令不进表，不是因为它们安全，是因为翻译过去也匹配
不到任何规则，徒增噪音；`ls` 进表是因为 `ls ~/.ssh` 确实该被 ADR-0025 拦下
（列目录也是 `fs.read`）。

顺带白拿两样东西，都不需要新写一条规则：

- `cat ~/.ssh/id_rsa` 产出 `fs.read /home/ming/.ssh/id_rsa`，撞上 ADR-0025 那
  20 条读取 deny；
- `curl` 产出 `net.fetch`，于是 `tool.start.capabilities` 里有了它，
  `untrustedContext` 自动置上——否则"用 shell 跑 curl"就是整套注入降级
  （docs/06 §4.2）的绕过口。

### 三、这张表只能加主张，不能减——安全性由此不依赖它的完备度

表里没有的 bin，`analyzeArgv` 产出的主张永远至少有一条：`shell.exec` 本身，
落回 `def.shell-exec` 的 ask。**漏了一条表项的后果是退回今天的行为，不是放行。**
这条性质有专门的用例钉着（`command-claims.test.ts` "任何命令都至少产出
shell.exec"），它是这张表可以慢慢长、而不必先证明自己完备的全部依据。

`sudo` / `su` / `doas` / `xargs` / `dd` 这五个是结构性地判不了——`sudo` 之后
跑的东西不再受本进程的任何约束（连 env 白名单都失效），`xargs` 的参数来自
标准输入，`dd` 的 `if=` / `of=` 是一套自成体系的参数语法。处置不是就地抛错，
是产出一条**带目标**的 `shell.exec` 主张，交给 `defaults.ts` 里新增的
`commandDenyRules()` 接住——用户在自己的配置里写一条 allow 就能放开某一条
（ADR-0025 定下的形状：给不出出口的安全措施最后都会被整体关掉）。目标用**这一层**
的规范形式，所以 `env sudo rm -rf /` 里的 `sudo …` 照样露头，不会被一层 `env`
包住就绕过去。

### 四、红线仍然不许建立在命令 target 上；普通规则放开（修正 ADR-0020 决策五）

`assertRules` 的构造期闸门原来是"命令类能力一律不许用 `match.target`"，
一刀切。现在改成"**红线**（`immutable: true`）仍然不许，普通规则放开"：

```ts
if (kind === 'command' && r.immutable) {
  throw new Error(/* 红线不可覆盖、用户没有兜底手段，因此只能建立在
                      路径或主机这类契约足够强的 target 上 */);
}
```

红线那一半理由没有变——`rm -fr /` 与 `rm -rf /` 归一后仍是两个串，命令 target
不够格当红线的地基。但一刀切禁掉的同时也禁掉了两样必须存在的东西：

- **会话授权**。"本会话允许这条命令"合成的正是一条带 target 的会话规则
  （`grantsToRules`）。旧版本里 `grantable()` 直接把命令类能力整个排除，用户
  唯一能点的是"允许 `shell.exec` 这个能力"——一次授权放开的是**所有**命令，
  这是一个收紧不了的安全开关，比没有更糟。契约补上之后，`grantable()` 被删掉，
  失败关闭改由 `normalizeTarget` 本身承担：规范化不了的授权（比如带 `$(...)`
  的）一律丢弃，不留一份要人记得维护的名单。
- **决策三的默认 deny**（判不了的 bin）。它同样是普通规则，同样需要能挂在
  命令 target 上。

### 五、`ResolvedCall.target: string` → `ResolvedCall.claims: readonly PermissionClaim[]`

```ts
export interface PermissionClaim {
  readonly capability: Capability;
  readonly target: string;
}
```

一次调用可能同时过好几道闸门。`turn.ts` 的判定循环改成逐条主张判定，任一被拒
即整体拒绝（取最严的那个），全部判完再问（边判边问会让用户为一次注定失败的调用
做一次决定，而"审批噪音"会直接转化成"下次顺手点允许"）。

**主张只能加、不能减**：`turn.ts` 断言工具静态声明的每个能力都必须出现在
`claims` 里，缺一个就整体拒绝而不是放行——否则一个工具可以靠"网关少产出一条
主张"绕开自己的能力声明。这条不变量放在 `turn.ts` 而不是某个网关实现里，
因为网关不止一个（Node、pure、将来的容器执行器），它对每一个都必须成立。

`Checkpointer.before()` 与 `tool.start.capabilities` 的判据都从"工具声明了
什么能力"换成"这次调用主张了什么"，理由相同：`shell.exec` 跑 `rm foo.txt`
现在也建还原点、也点亮 `net.fetch` 的污点标记，而按静态声明判的话，
`shell.exec` 声明的只有 `shell.exec` 自己，两样都不会发生。

### 六、`~` 的展开留在网关，命令行匹配用户所见即所判

内核零 I/O，展开不了 `~`；`shell.exec` 网关分支拿到的 `home` 选项负责把
命令参数里词首的 `~` 与 `~/…` 换成真实路径再送去 `resolveDeep`。不展开的话
`rm -rf ~` 判成"删一个叫 `~` 的文件"，与模型的本意不是一回事，而这正是 M1-d
DoD 的第一条。`~user` 不展开（不知道别的用户的家目录在哪，词法器直接拒）；
段中间的 `~` 是合法文件名（Windows 8.3 短名、emacs 备份文件），不碰。

路径类 claim 的 `raw` 值经网关 `resolveDeep` + realpath 之后**回写进
`PermissionClaim.target`**（判定用严格值），但**不回写进 argv**——命令执行时
由操作系统按同一个 cwd 解析同一个相对路径 / 符号链接，落到的是同一个文件，
判定与执行不会分叉；而回写会实实在在改变命令的行为（`git status`、`find .`
的输出依赖参数原样）。`~` 是唯一的例外：它必须回写，因为没有 shell 参与时
`~` 就是一个普通文件名，判定按家目录判、执行按字面量跑，那才是两个东西。

### 七、进程级硬约束——docs/09 C2"默认不强制沙箱"那句话的兑现物

C2 的倾向是"默认不强制沙箱，依赖策略闸门 + 还原点"。这句话必须与"什么都不做"
区分开，`shell-exec.ts` 落的是几条具体、可测的约束，每一条对应一种真实的失控
方式：

| 约束 | 挡住的失控 |
|---|---|
| env **白名单**（不是黑名单） | 不白名单，`sh -c 'echo $XM_API_KEY'` 能读出小明自己的密钥（ADR-0022 放进钥匙串的那把） |
| stdin 接 `/dev/null` | 继承 stdin 的话，一条等输入的命令会永远挂着，挂住的是整个 Turn |
| 超时 + **按进程组** kill | 只杀直接子进程，它派生的孙进程会活下来——"点了停止但东西还在跑"比不能停更糟，因为用户以为已经停了 |
| 输出上限（256 KB） | 一条 `find /` 能吐几百 MB；截断发生在已经付过内存代价之后，与 `fs.read` 按行流式读同一个理由 |

这不是 C2 的完整答案——**沙箱模式开关、对来源不明代码自动切容器执行器，
两样都还没有**，见下方遗留。

## 后果

**正面**

- M1-d DoD 第一条第一次有了真实实现：`rm -rf ~` 的四种等价写法里，能被词法器
  静态解析的三种（空格差异、绝对路径、`sh -c`）归一到同一个规范串，且无论归不归一，
  都会产出同一条 `fs.delete /home/ming` 主张，撞上同一条红线
- `curl` 自动点亮不可信标记、`cat` 私钥自动撞现有 deny——这套翻译层建成之后，
  ADR-0025 与 docs/06 §4.2 的覆盖面在**没有新增一条规则**的情况下延伸到了
  `shell.exec`
- "本会话都允许这条命令" 第一次能对具体某一条命令生效，而不是被迫放开
  整个 `shell.exec` 能力

**负面 / 需要接受的代价**

- **画像表必然不完备。** 一个改了名的二进制、一个表里没有的 bin，都会退回
  今天的"一个确认框"。这不是这次决策的缺陷，是它的设计前提——安全性不依赖
  这张表的完备度，依赖的是"漏了就退回今天的行为"这条不变量本身
- **`bash ./build.sh` 这类脚本文件，内容判不了**——只能认出"要读这个脚本"，
  脚本里写什么完全是黑盒。这是一个已知缺口，不是疏漏
- **C2 仍未完全定案。** 沙箱模式开关、对不可信来源代码自动切容器执行器，
  两样 C2 原倾向里写的东西都还没有；本 ADR 只把"进程级硬约束"这一半做实

**什么条件下应该重新评估**

- 如果将来接入真正的容器 / 沙箱执行器（C2 剩下的那一半），这张主张分解表的
  角色会从"唯一的语义防线"退化成"锦上添花"——那时真正兜底的是执行环境本身
  碰不到的资源，而不是判定层猜出来的目标
- 如果画像表长到需要用户自定义扩展，"表只能加、不能减"这条不变量要重新审查：
  用户自定义的画像项是否也必须满足同一条安全性质

## 反向演练

| 演练 | 结果 |
|---|---|
| `rm -rf ~`（四种写法：单/双空格、绝对路径、`sh -c`）过完整判定链路 | 全部命中 `red.fs-delete-home-root`（`shell-claims.test.ts` "M1-d DoD"） |
| 去掉 `commandDenyRules()` | `sudo` 这类判不了的 bin 退回 ask（`command-claims.test.ts` "判不了的那几个 bin"） |
| 表里查不到的 bin | 只产出 `shell.exec` 一条主张，不产出任何路径 / 主机主张（"表里没有的 bin"用例） |
| `env sudo rm -rf /`（前缀套判不了的 bin） | `sudo …` 仍在这一层的规范形式里露头，不会被 `env` 包住绕过（"包一层 env 也躲不掉"） |
| `curl <url>` | 产出 `net.fetch`，`tool.start.capabilities` 含它，`untrustedContext` 置上（`shell-claims.test.ts` "curl 不再绕过不可信标记"） |
| 工具声明了命令类能力但不声明 `commandInputs` | 网关当场拒绝（`shell-exec.test.ts` "声明了 commandInputs"） |
| 主张缺失工具静态声明的能力 | `turn.ts` 断言当场拒绝执行（"主张只能加，不能减"用例） |
| 把命令类红线的构造期闸门去掉 | 假防线可以被写下来而不炸（沿用 ADR-0020 的闸门用例，改造后仍然守着） |

63 条新增用例覆盖以上路径（`command-claims.test.ts` 28 条、`command-target.test.ts`
6 条、`policy-persistence-write.test.ts` 8 条见 ADR-0027、`shell-claims.test.ts`
8 条、`shell-exec.test.ts` 13 条），加上既有套件因 `claims` 契约改动而调整的
用例。`pnpm verify`：766 测试全绿（9 skipped）、187 模块 683 边零违规、
size-limit 7.13 kB。

## 遗留

- **`bash ./build.sh` 之类的脚本文件内容判不了**——只认出"要读这个脚本"这一条
  `fs.read` 主张，脚本里做什么是黑盒。真要判只能在执行前读取并递归解析脚本内容，
  尚未评估这样做的代价
- **C2 尚未完全定案**：沙箱模式开关（用户可选强制隔离）、对不可信来源代码
  自动切容器执行器，两样都还没有。当前只有"默认不强制 + 进程级硬约束"这一半
- **`shell.session`（PTY）、`web.fetch` 的 IP 级判定、多模态**仍是 M1-d 剩余的
  三项，见 [docs/08](../08-路线图与里程碑.md) M1-d 小节

## 补记：推上去之后，windows-latest 红了六条（2026-08-07）

本地 `pnpm verify` 全绿之后推送，CI 三平台矩阵的 `test (windows-latest)` 红了六条。
一条是真正的实现缺口，五条是测试自己在 Windows 坐标系下不成立——这个仓库对这两类
问题的处理历来不同（前者补代码，后者修用例），这次也一样。

**真正的缺口**：`red.fs-delete-filesystem-root` 从 M0 起就只认 POSIX 的 `/`。
Windows 没有单一的文件系统根，盘符根目录（`C:/`、`D:/`）才是等价物，而
`normalizePathTarget` 从不把两者归成同一个串。这条红线在此之前从未被真实
调用点触发过——第一个把 `fs.delete` 的 target 喂到 Windows 盘符根的，正是这一段
的 `shell.exec`：`rm -rf /` 拆出主张后，网关按会话 cwd 把 POSIX 写法的 `/` 解析成
当前盘符根，两个坐标系第一次真实相遇就对不上。补了一条 `red.fs-delete-drive-root`
（`match.target: '?:/'`，`?` 是极简 glob 里"单个非 `/` 字符"的通配），两条红线
各自守自己的坐标系。

**测试自己的问题**（不改生产代码，改用例）：

- `shell-exec.test.ts` 的进程级约束用例把 `os` 写死成 `'linux'`，导致
  `killTree()` 在真实 Windows 上走了 POSIX 的 `kill(-pid)` 分支——不报错，
  只是默默不生效（Windows 上这个调用的语义完全不同，被 `killTree` 的
  try/catch 当成"已经退出"吞掉）。超时/中断类用例看起来"通过"，其实只是
  子进程自然跑完了 `sleep`；直到测一条真正跑不完的命令（`yes` 无限输出），
  才彻底暴露：进程一直挂着，`afterAll` 清理临时目录时因为文件被占用而
  `EBUSY`。改成用 `@xm/platform` 的 `osFamily()` 读真实平台——这与
  `services.ts` 给生产代码传真实 `platform.os` 是同一件事，测试同样不该
  对自己测的东西撒谎。
- env 白名单用例把 `PATH` 硬编码成 POSIX 写法的字面量，Windows 上分隔符
  都不对，子命令根本起不来，测的变成"命令能不能跑"而不是"密钥漏不漏"。
- 网关"段中间 `~` 不动"用例选了 `a~1.txt` 当文件名——这个形状恰好也是
  Windows 8.3 短文件名的形状（`SHORT_NAME_8_3`），撞上一条完全无关、
  但同样正确的失败关闭规则。这不是两条规则打架，是测试数据凑巧同时
  落进了两个不相关判据的交集。
- `.zshrc` 写入 deny 用例把 `join()` 产出的反斜杠路径直接拼进 `sh -c` 的
  shell 源码字符串——反斜杠是这个词法器（以及真实 shell）的转义符，
  会被逐个吃掉，这与实现是否正确无关，是真实 shell 语义本该如此。

768 测试全绿（+2，新增红线的正反两个用例）。**这批修复本身又是一次"Windows
语义只有三平台矩阵测得出来"**——六个坑没有一个能在 Linux 开发机上复现，
包括那条真正的实现缺口：`normalizePathTarget('/')` 在任何平台上都合法地
返回 `"/"`，只有真的在 Windows 上把它喂进真实的 `path.resolve` / `realpath`
链路，坐标系不对齐这件事才会现出原形。

### 补记的补记：修红线的用例，断言本身写死了单一平台的答案

推上去之后又红了两条，都是上面这批修复自己带的：

- `rm -rf /` 命中哪条红线的用例断言死了 `red.fs-delete-filesystem-root`。
  新红线 `red.fs-delete-drive-root` 一加，Windows 上正确命中的变成了那一条——
  测试断言没跟着改。这条用例要证明的本来就是"总有一条红线接住"，不是
  "是哪一条"，改成匹配两者之一。
- env 白名单用例断言 `$PATH` 的回显与 `process.env.PATH` **字面相等**。
  Windows 上 `sh` 是 Git for Windows 的 MSYS shell，它进入 shell 时会自己把
  `PATH` 重写成 POSIX 形态（`C:\a\b` → `/c/a/b`、`;` → `:`，还会在前面插入
  `/usr/bin`、`/mingw64/bin` 这些 MSYS 自己的目录）——这是那个 shell 的行为，
  不是白名单传错了。改成断言非空。

两条都是"测试断言比实现更死板"的形状：改红线、改测试环境的适配代码时，
容易只顾着让"该拦的拦住"，却忘了断言里还留着一份写死单一平台答案的期望值。
这提醒了一件更通用的事——**跨平台测试的断言本身也要按"能不能观察到这件事"
来写，而不是先入为主地假设某个具体值**，这条纪律和判据的选取同样重要。

## 补记（2026-08-07）：多条 ask 主张时，点「允许」没反应

用户在 Windows 本地跑真实 DeepSeek 时报的第二个 bug——跟本 ADR 直接相关，
因为它是"一次调用可以产出多条 `PermissionClaim`"这件事在**问用户**这一步
留下的后半个洞。前半个洞（判定要按主张判，不能只按声明的能力判）本 ADR
正文已经解决；这次翻车的是"判完之后怎么问"。

`turn.ts` 的审批循环一直是两段式（见上面「先把全部主张判完，再问」那条
comment）：第一段把每条主张都 `judge()` 一遍，遇到 policy 层的 `deny` 立刻
失败退出；剩下判成 `ask` 的收进 `pending` 数组。第二段再遍历 `pending`，
对每一条重判一次（防止上一条的授权已经覆盖这一条），然后才真的调用
`decide()` 去问人。

问题出在**第一段** duplicated了不该做的事：它在判到 `ask` 的那一刻就把
`permission.request` 事件发出去了——这本是为了让审批卡片"尽早出现"，但
一次调用如果有两条以上的 `ask` 主张（`mv a b` 就有三条：`shell.exec` +
`fs.delete(a)` + `fs.write(b)`），第一段会把这几条 `permission.request`
**连着发完**，而对应的 `permission.decision` 要等到第二段依次调用
`decide()` 才会一条一条落下。事件流因此变成：

```
request(1) → request(2) → request(3) → decision(1) → decision(2) → decision(3)
```

而不是设计里默认的

```
request(1) → decision(1) → request(2) → decision(2) → request(3) → decision(3)
```

`SessionState.pendingPermission`（`reduce.ts`）是**单槽位**——每条
`permission.request` 都会覆盖上一条。三条 request 连着落下之后，UI 看到的
`pendingPermission` 已经是 request(3)，卡片上的 `requestId` 也是它的。
可是运行时此刻的 `decide()` 其实还卡在 request(1) 上——桌面主进程的
`pending` Map（`services.ts`）用 request(1) 的 `requestId` 登记了 waiter。
用户对着卡片点"允许"，`respondPermission` 拿 request(3) 的 id 去 Map 里找，
找不到人接，返回 `accepted: false`，卡片纹丝不动。这就是"点了没反应"的
完整机制——不是权限判定错了，是**判定对了、问的方式把状态问乱了**。

修法只有一处：把 `permission.request` 事件的发出时机从"判到 ask 的那一刻"
挪到"即将调用 `decide()` 的那一刻"，紧挨着它自己的 `decision`。第一段循环
现在只做纯判定——遇到 `deny` 时 request/decision 仍然一次性配对发出（不需要
问人，中间没有缺口）；遇到 `ask` 只把 `PermissionRequest` 存进 `pending`，
不发事件。第二段循环里，重判、发 `permission.request`、调用 `decide()`、
记 `permission.decision`，四步紧挨着按顺序做，中间不会再插进另一条
`request`。事件流因此永远是 `request → decision` 逐对出现，`pendingPermission`
覆盖的时机与 `decide()` 登记 waiter 的时机对齐。

顺带把两处配套的健壮性缺口一起补了（同一份用户报告里提的次要项）：

- `respondPermission` 返回的 `accepted: false`（这个字段从一开始就在契约里，
  注释写着"对不上时 UI 该把那张卡片收起来"）一直被渲染层的 `store.ts` 直接
  丢弃——请求过期时用户点了按钮，界面上什么反馈都没有。现在改成置一条
  错误提示。
- `waiting_permission` 状态下，输入框旁边的"停止"按钮之前只认
  `status === 'running'`，主进程的 `interrupt()`（先 `denyAllPending` 兑现
  挂起的审批，再 `abort()`）明明也认这个状态，UI 却没给出口——用户卡在
  一张对不上号的确认卡片前，连"算了，别跑了"的入口都没有。

新增回归用例在 `packages/runtime/tests/shell-claims.test.ts`：用 `mv` 产出
三条 ask 主张（`fs.read` 因为 `def.fs-read` 无条件 allow 不会问，其余三条要问），
断言事件流里 `permission.request`/`permission.decision` 严格逐对交替出现，
且每条 `decision.requestId` 恰好等于它前面那条 `request.requestId`。选
`mv` 而不是专门造一个假工具，是因为它是本 ADR 那张画像表里第一个天然会
产出多条 ask 主张的真实命令——复用 M1-d 已经在验的基础设施，而不是另起一套
只服务这一个用例的夹具。

## 补记（2026-08-17，[ADR-0079](./0079-拆不开的命令的兜底.md)）

决策三写的那句"表里没有的 bin 落回 `def.shell-exec` 的 ask，所以漏一条表项的后果是
退回到今天的行为，不是放行"——**在 [ADR-0039](./0039-放弃审批模式.md) 删掉 `ask` 与
`def.shell-exec` 之后不再成立**。同一条路径的终点变成了兜底放行，于是
`python3 -c "…"`、`node -e "…"`、`sed -i … ` 可以绕过全部路径红线，且因为拆不出
`fs.write`/`fs.delete` 主张而**没有还原点**（地基复审四 A3 实测）。

ADR-0079 的处置：解释器与原地编辑/解包/同步类进 `deny` 画像，走本 ADR 已有的
"带目标的 `shell.exec` 主张 → 普通 deny 规则 → 用户可逐条 allow"这条路。
本 ADR 的其余部分（argv 契约、主张分解、红线不建立在 command target 上）不变。

**这条补记本身也是一个教训**：一个决策的正确性依赖另一个决策的某条性质时，
后者被推翻不会让前者报错——它只是安静地换了个结论。
