# ADR-0041 · M2-a 可见任务清单与窄事件写入口

- **状态**：🟢 Accepted
- **日期**：2026-08-12
- **相关**：[ADR-0002](./0002-Agent循环形态.md)、[ADR-0019](./0019-不可信标记的解除入口.md)、[M2 阶段划分](../M2-阶段划分.md)

## 背景

`Todo`、`todo.updated`、`SessionState.todos`、快照与桌面 IPC 镜像都已经存在，但没有真实工具能产生 `todo.updated`，桌面端也没有消费 `todos` 的视图。M2-a 要补齐这条纵切。

现有 `ToolContext` 刻意不提供通用 `record()`：若模型工具能任意写事件，就可以自行写入 `trust.cleared` 等只允许人触发的安全事实，绕过 ADR-0019。为了一个 todo 工具把通用事件写入口挂到所有工具上，不可接受。

同时，todo 更新只改变当前会话内的可见任务清单，不读取或修改文件、网络、进程、密钥或系统设置。现有 `Capability` 闭集没有对应能力；为了它新增一个进入 PolicyEngine、却没有安全判定语义的能力同样是伪抽象。

## 选项

### 选项 A：给 `ToolContext` 增加通用 `record()`

工具实现最直接，但所有当前与未来工具都会获得写任意事件的结构性能力，破坏 ADR-0019 的安全边界。

### 选项 B：运行时按工具名识别 `todo.update`，在 `turn-tools.ts` 特判

不扩大工具能力，但工具描述与执行副作用分居两处；重命名或新增调用入口时容易只改一半，形成隐式协议。

### 选项 C：todo 工具只接收一个窄回调

工具工厂接收 `update({ sessionId, todos })`；桌面/headless 装配方把它绑定到对应 `SessionRuntime.record({ type: 'todo.updated' })`。工具拿不到通用 runtime，也不能选择事件类型。

## 决策

选择 **C**。

1. 内建工具名为 `todo.update`，入参是完整 `todos` 快照。全量替换与事件既有语义一致，避免增量命令的同步分叉。
2. 工具实现在 `@xm/runtime`：它是会话编排能力，不做 Node I/O，不属于 `@xm/tools-core`。
3. 工具仅持有 `TodoUpdater` 窄回调。`ToolContext` 保持不变，仍没有任何通用事件写入口。
4. `todo.update` 声明空能力集并登记进 `EMPTY_CAPABILITIES_ALLOWLIST`。理由是它没有会话外副作用，不是安全例外；它仍经过统一的参数校验、工具生命周期与结果截断链路。
5. 工具输入中的 todo 条目使用与 `Todo` 同一字段源生成的 strict schema；事件中的 `Todo` 兼容语义不变。
6. 系统提示词只在 `todo.update` 实际可用时提示：预计至少三个实质步骤的任务维护清单，简单任务不要建清单。不会引入 Planner 状态机。
7. UI 只渲染 `SessionState.todos`，空清单不展示面板；不维护第二份任务状态。

## 后果

- 正面：工具调用、持久事件、状态回放、IPC 与 UI 形成一条真实可测链路。
- 正面：`trust.cleared` 等事件仍然不可能由工具自行写入，ADR-0019 的结构性防线不变。
- 负面：todo 工具需要装配方提供回调，不能像纯计算工具一样无参数构造。
- 需要接受的代价与缓解措施：所有生产装配和 headless 测试都必须显式绑定 updater；遗漏时由函数签名在编译期报错。
- 什么条件下应该重新评估：如果后续出现三种以上需要受控写入不同会话事件的内建工具，再考虑一个闭集的“工具状态效果”契约；在那之前不抽象通用事件总线。
