# ADR-0006 · 上下文压缩：分层混合 + 75% 阈值 + 主模型压缩并缓存

- **状态**：🟢 Accepted（2026-08-04 确认）
- **日期**：2026-08-04
- **相关**：[04-总体架构 §5](../04-总体架构.md)、[02-参考项目评审 §2.12](../02-参考项目评审-manusAgent.md)

## 背景

参考项目的 `compact_memory()` 只是简单压缩，没有 token 预算核算、没有分层、没有按需检索。长会话必然劣化。

小明的硬指标是「1000+ 轮不劣化」，上下文管理是达成它的核心机制。

## 决策

### 1. 分层结构

```
[稳定前缀]  系统提示词 + 技能元数据 + 工具 schema      ← 恒定不变，命中 prompt cache
[长期]      记忆检索结果（按当前意图 Top-K，非全量）
[中期]      历史轮次的摘要
[近期]      最近 N 轮原文
[当前]      本轮消息
```

### 2. 触发阈值：75%

不是 90%。压缩本身要消耗一次模型调用，如果等到快撞上限才压缩，很可能压缩请求自己就超限了。75% 留出足够的操作空间。

### 3. 压缩用主模型，但只压一次并缓存结果

**这一条是刻意反直觉的**：用便宜的小模型压缩看似省钱，但摘要质量直接决定长会话会不会劣化——摘要丢了关键信息，后续每一轮都在错误的上下文上工作，浪费的 token 远超省下的。

关键在于「只压一次并缓存」：某个区间的历史一旦被压缩成摘要，摘要结果持久化，后续轮次直接复用，不重复压缩。因此主模型压缩的成本是**一次性**的，摊到几十轮上可以忽略。

### 4. 稳定前缀约束（对其它设计的硬约束）

系统提示词前缀必须逐字节稳定，否则 prompt cache 全部失效，成本翻数倍。

这条**反过来约束了工具的动态过滤**：`Tool.available()` 的过滤结果不能出现在稳定前缀里。工具 schema 的排布必须是「全量稳定列表在前 → 会话级增删在后」，或者以会话为单位固定一次工具集，中途不变。

> 这是一个容易被忽略的耦合点：一个看起来只关乎工具系统的设计（动态可用性），会直接决定缓存命中率和实际成本。**记在这里，防止未来的实现者踩坑。**

### 5. 技能与记忆的加载策略

- **技能**：元数据（名称 + 描述，几十 token）常驻稳定前缀，正文按需加载。技能数量增长不影响每轮成本
- **记忆**：按当前意图检索 Top-K，不全量注入。全量注入会让记忆系统随使用时长线性推高每轮成本，最终不可用

## 后果

**正面**
- 长会话成本可控且可预测
- prompt cache 命中率高，实际成本可能只有名义 token 数的 20–30%
- 技能和记忆可以放心增长，不会拖垮每轮成本

**负面**
- 摘要必然丢失信息，某些"很久以前提过一次"的细节会丢
- 缓存的摘要如果质量差，会持续污染后续所有轮次（且不会自动修复）

**缓解措施**
- 摘要中显式保留「未解决的问题」「用户明确的约束」「已做出的决定」三类信息——这些是丢了最致命的
- 原始事件流始终完整保留在 SQLite 中，摘要只影响送进模型的上下文；需要时可以检索回原文
- 提供「重新压缩」的手动入口，摘要明显有问题时可重来

**重新评估的触发条件**
- 实测发现主模型压缩的成本占比超过总成本的 10%（说明压缩过于频繁，需要调阈值或换模型）
- 出现摘要质量导致的实际任务失败（说明需要更结构化的摘要格式，而非自由文本）
