# ADR-0001 · 桌面技术栈选型：Electron + TypeScript 7.0 单语言 monorepo

- **状态**：🟢 Accepted（2026-08-04 确认）
- **日期**：2026-08-04
- **相关**：[03-技术选型](../03-技术选型.md)

## 背景

小明要做成 Windows/macOS 桌面应用，同时满足四个互相拉扯的约束：

1. **自我迭代**——Agent 要能读懂、修改、测试自己的代码，语言与工具链的反馈速度直接决定这个闭环的成本
2. **操作电脑**——需要 PTY、屏幕捕获、输入注入、进程隔离等系统能力
3. **高性能**——内存与启动时间可控
4. **UI 贴近 Claude Code 桌面端**——需要 Web 技术栈级别的排版能力

参考项目 manusAgent 是 Python + FastAPI + Next.js 的 Web 多容器形态，与桌面产品形态不兼容，需要重新选型。

## 选项

### A. Electron + TypeScript（单语言）
- 优点：单语言（自我迭代成本最低）；MCP 官方 TS SDK、node-pty、各家模型 TS SDK 生态最全；VS Code 已验证上限；打包分发（签名/公证/自动更新）成熟
- 缺点：内存基线约 150MB；包体约 120MB；CPU 密集任务弱

### B. Tauri + Rust
- 优点：内存约 40MB；启动快；安全模型更强
- 缺点：双语言；Rust 编译慢（增量 10s+）会拖垮"改一版→跑评测→再改"的自我改进闭环；借用检查对模型生成的代码是高频挫败源；MCP 与模型 SDK 需自行封装

### C. Electron + Python sidecar
- 优点：可复用 manusAgent 约 40% 代码；Python AI 生态成熟
- 缺点：双运行时（内存 250MB+，启动慢）；PyInstaller 打包痛苦；跨语言契约维护成本长期存在；**而可复用的 40% 恰好是评审中判定要推翻的部分**（非流式模型层、僵化 Flow、重依赖持久化）

## 决策

选择 **A：Electron + TypeScript 单语言 monorepo**，语言版本锁定 **TypeScript 7.0**（Go 原生编译器 tsgo）。

决定性理由是**自我迭代**：跨语言边界会让每一次自我修改都需要同时理解两套类型系统、两套构建、两套测试，L3/L4 级自我迭代的成本呈指数上升。性能短板可以事后用 Rust sidecar（napi-rs）针对性解决；错误的架构无法事后补救。

选项 C 是明确的亏本买卖——为复用注定要重写的代码而背上永久的双运行时技术债。

## 后果

**正面**
- 单一语言、单一构建、单一测试体系，Agent 自我修改的认知负担最小
- 生态齐全，M1–M4 的能力几乎都有第一梯队的现成实现
- Electron 的插件宿主进程模型（VS Code 同款）可直接作为小明扩展体系的参考

**负面（必须接受）**
- 内存基线高于 Tauri 约 110MB
- 包体约 120MB（与 Cursor/VS Code 同量级）
- Node 主线程是单线程，CPU 密集任务必须外移

**缓解措施**
- 严控渲染进程数量（单窗口多视图）；索引与缓存设内存上限
- 索引、大 diff、图像处理下沉到 worker 或 Rust sidecar
- 差量更新降低更新成本

**保留的退路**
> `@xm/kernel` 与 `@xm/runtime` 对 Electron **零依赖**（由 dependency-cruiser 在 CI 强制）。若未来核心稳定、自我迭代主要发生在插件层，可只替换外壳为 Tauri 而不动内核。`apps/cli` 的存在就是这条退路的持续性验证。

**重新评估的触发条件**
- 内存占用在真实使用中长期超过 800MB
- Electron 的安全模型出现无法缓解的问题
- 内核稳定到一年内无重大变更，且性能成为主要瓶颈

## 补充决策：TypeScript 版本选 7.0

**理由**：tsgo 的类型检查速度是数量级提升。对小明而言这不只是开发体验——**自我迭代闭环（改一版 → 类型检查 → 跑测试 → 跑评测）的单次循环时长直接决定 L3/L4 的可行性**，编译反馈速度是生产力乘数。

**接受的约束**（详见 [03-技术选型 §4.1](../03-技术选型.md)）：tsgo 不支持 AMD/UMD/System 模块、node10/classic 解析、`baseUrl`、`outFile`、`target: ES5`。绿地项目全部无痛，但要在 M0 定死：**禁止用 `baseUrl` 做路径别名**，跨包引用一律走 workspace 依赖 + package `exports`。

**风险与对策**：最大不确定项是**编译器 API 的成熟度**——typescript-eslint 的类型化 lint、ts-morph、api-extractor 等依赖 TS 编译器 API 的工具在原生端口上的可用性需实测（本 ADR 撰写时无法验证 7.0 正式版的实际状态）。

对策：M0 第一件事是建"工具链冒烟仓库"，跑通 `tsc --noEmit` + typed lint + d.ts 生成 + Vite 构建，再正式开工。若有缺口，两条退路：
1. 双版本并存——tsgo 负责日常类型检查与构建，保留 TS 6.x 供依赖编译器 API 的工具使用
2. 整体回退 TS 6.x——**代码零改动**，因为上述约束我们本来就遵守

退路成本接近零，因此这是低风险决策。

> **2026-08-04 冒烟验证结论 → 见 [ADR-0010](./0010-TypeScript双编译器工具链.md)**
>
> 上述"最大不确定项"已兑现：TS 7.0.2 **完全不提供 JS 编译器 API**，typescript-eslint 对其硬失败。**已采用退路 1（双版本并存）**，官方机制为 `@typescript/typescript6` 别名双装：`npx tsc` 走 TS 7 原生二进制，`require('typescript')` 走 TS 6 的 JS API。实测 `--build` / `--watch` / 项目引用 / pnpm workspace / typed lint 全部可用，两编译器结论一致。
>
> 同时修正本节"数量级提升"的表述：**实测为 2.1x**（16k 行 zod 重负载，8.6s vs 17.9s），且 CI 的类型相关耗时由 typed lint 主导（26.4s，走 TS 6 检查器），总体收益约 1.26x。仍然值得，但不是数量级。
