# ADR-0028 · `web.fetch` 的 IP 级 SSRF 判定与 DNS 重绑定防护

- **状态**：🟢 Accepted（2026-08-08）
- **日期**：2026-08-08
- **相关**：细化 [ADR-0020](./0020-非路径target的规范化契约.md)（`host` 归一自己写明
  "真正的 SSRF 防御在能力网关的网络一侧"）与 [ADR-0024](./0024-路径能力网关.md)
  （"`web.fetch` 的 IP 级判定接在同一个位置上"）；判断标准沿用
  [ADR-0025](./0025-敏感路径的读取拒绝.md) / [ADR-0027](./0027-持久化路径的写入拒绝.md)
  的"红线 vs 普通 deny"；关闭 [docs/08](../08-路线图与里程碑.md) M1-d DoD 里
  唯一明确写着"待完成"的一条

## 背景

`normalizeHostTarget`（ADR-0020）从写下的第一天起就在注释里点名了自己的边界：

> 归一之后的匹配仍然只是"目的地写法"层面的防线。真正的 SSRF 防御是在发请求的
> 那一层按解析出的 IP 判定（内网段、link-local、重绑定）。

`resolveHost`——这个"发请求的那一层"——在此之前一次都没有被创建过。`web.fetch`
这个能力名字甚至没有对应的工具：契约（`net.fetch`、`host` kind、`def.net-fetch` 的
`ask`）齐全，`nodeToolGateway` 却只有 `command` 和 `path` 两条分派分支——如果原样
注册一个声明 `net.fetch` 的工具，网关会落进"两者都不需要"的兜底分支，静默给出一个
空 target，使得包括未来任何 IP 段红线在内的全部按目标写的规则一条都匹配不上。这与
ADR-0024 描述的"能力网关一次都没有被创建过"是完全同一种缺口，只是这次缺的是网络那半。

M1-d 的 DoD 原文明确点名要验收的目标：

> `web.fetch http://169.254.169.254/` 被拦

这条地址不是随手挑的——它是云环境（AWS/GCP/Azure 通用）的实例元数据端点，返回内容
包括临时安全凭据。一旦模型能让 Agent 发一次 `GET` 到这个地址，凭据就直接进了模型
上下文，这与 ADR-0025 里"`.pem` 文件一旦被读到就等于泄露"是同一个伤害模型，只是
入口从文件系统换成了网络。

## 决策

### 一、判定与执行必须共用同一个已解析地址——这是整份决策的核心

DNS 重绑定攻击的原始形态是：判权时解析域名拿到一个"看起来安全"的地址，请求时域名
第二次被解析、指向了别处（比如内网）。防它的唯一结构性做法不是"判得更细"，而是让
"判权用的地址"与"真正建连用的地址"**物理上是同一个值**——判过一次之后，不允许
再有第二次解析。

具体落在三处：

- `packages/tools-core/src/gateway.ts` 的 `resolveHost()` 是这条调用链上**唯一**
  发起真实 DNS 查询的地方，且每个 URL 只查一次。
- 解析结果通过 `ResolvedCall.pinnedHosts`（一条新的带外通道，见决策二）交给
  `turn.ts`，`turn.ts` 把它合并进 `ToolContext.pinnedHosts`。
- `web.fetch` 工具的 `execute()` **没有能力再发起一次解析**——它把 undici `Agent`
  的 `connect.lookup` 钩子替换成"忽略参数、直接回调 `pinnedHosts` 里的地址"，找不到
  对应条目就拒绝执行并报内部错误，绝不退化成自己查一次 DNS。

`ToolContext.pinnedHosts` 的注释把这句话原样写死：*"自己解析等于重开一个 rebinding
窗口"*。这不是一句提醒，是这个字段存在的全部理由。

### 二、为什么走带外通道 `pinnedHosts`，不像路径分支那样回写入参

路径分支（ADR-0024）靠"回写 `input`"解决同一个问题：判定看到的 realpath 就是执行
打开的那个字符串。网络场景做不到同样的事——URL 字符串本身不能被网关改写成解析出的
IP：改了 Host 就变了 SNI／虚拟主机语义，工具连的就不再是同一个"名字"了。真正需要
"判定与执行共用同一个值"的是**地址**，不是 URL 本身，所以只能走带外通道。

### 三、一次调用产出两条 claim，各自命中不同的规则

`resolveHost()` 对每个 `hostInputs` 字段：归一 → 解析 DNS → 产出：

- **claim A**：原始 URL 的域名部分，命中已有的 `def.net-fetch`（`ask`）——用户在
  确认框里看到的是可读域名，不是一串数字。
- **claim B**：解析出的 IP 拼成的合法 URL，命中本次新增的 `def.no-fetch-private-network`
  （见决策四）。

两条都挂在同一个 `net.fetch` 能力上。`turn.ts` 现有的"一次调用的任一 claim 被拒即
整体拒"逻辑**不用改一行代码**就能让"域名允许列表"和"IP 段红线"两道闸门同时生效——
这与 ADR-0026 里"一条命令拆成多条主张、复用已有判权循环"是完全同一个手法。

### 四、`def.no-fetch-private-network` 是普通 deny，不是红线

挑选标准与 ADR-0025/0027 完全相同：**做了就回不来、且没有正当自动化理由的才是
红线；这里不是**。访问内网/回环地址有大量正当用途——用户完全可能真的想让小明访问
自己电脑上的 `localhost:3000` 开发服务器，或者局域网里的路由器管理页。云元数据
地址的伤害是"凭据进了模型上下文"，与 ADR-0025 里 `.pem` 文件的伤害模型完全同构，
而 `.pem` 本身也只是普通 deny。所以这批判定**全部**做成 `immutable: false`，拒绝
文案里带着出口的说法：*"确属你的本意的话，在用户配置里对解析出的那个具体地址写一条
allow 即可放开"*——用户写 `{effect:'allow', capability:'net.fetch',
match:{target:'127.0.0.1*'}}` 即可放开，按 ADR-0023 的分层覆盖语义自动生效，不需要
为覆盖 `ipRange` 单独写逻辑。同时给 `browser.control`（同为 `host` kind）挂一条
同款规则——M4 之前没有工具用到它，但补一条的成本是零，漏掉的代价是那个能力接上
工具的第一天就敞着（ADR-0025 的论证方式）。

### 五、为什么用一个新的 `ipRange` 匹配维度，不是把网段拼成一批 glob 规则

极简 glob（`*`/`?`/`**`）能精确表达 `10.*`、`127.*`、`192.168.*`、`169.254.*`这类
对齐在点分段边界上的网段，但表达不了 `172.16.0.0/12`（横跨 `172.16.*` 到
`172.31.*` 共 16 段）。可以枚举 16 条 glob，但枚举容易漏、容易在网段变化时忘记同步，
而且完全无法表达 IPv6 的前缀网段。`PolicyRule.match` 因此新增一个**闭集字面量**
字段 `ipRange: 'private'`（目前只有这一个取值，需要新的内置网段清单时新增字面量 +
新 ADR，不开放成自由 CIDR 字符串）——原因与 `Capability`/`TargetKind` 用闭集而不是
自由字符串防止插件自造能力名完全一致：SSRF 防护不需要用户可配置网段，用户要放行的
是"这一个具体地址"，走已有的 `match.target` 字面量 allow。`ipRange` 判定本身
（`packages/kernel/src/policy/ip-range.ts`）是一段纯函数、零 I/O 的位运算，覆盖
IPv4 的 12 个网段（0.0.0.0/8、RFC 1918 三段、RFC 6598 CGNAT、回环、link-local、
IETF 保留、TEST-NET-1、基准测试网段、组播、保留+广播）与 IPv6 的 5 类
（回环/未指定、IPv4-mapped 递归判定、ULA、link-local、组播），构造期由 `assertRules()`
强制它只能挂在 `host` kind 的能力上——挂在别处会永远不匹配，是一条"看起来配置了、
实际是死规则"的规则，与"红线不许建在没有规范化契约的 target 上"是同一类失效。

### 六、HTTP 客户端选 `undici`，不裸用 Node 全局 `fetch`

Node 18+ 的全局 `fetch` 底层就是 undici，但全局作用域不暴露 `Agent`/`Dispatcher`，
拿不到 `connect.lookup` 这个钩子——而这正是"钉住已解析地址、不让请求库自己重新解析
一次"的唯一入口。显式依赖 `undici`（`packages/tools-core` 第一次引入网络依赖）可以
拿到同一个实现，但版本由自己的 `package.json` 钉死，不随 Node 版本漂移。`fetch()`
本身继续处理 TLS SNI、`Host` header、chunked 编码这些细节；只要 `connect.lookup`
被接管，"用哪个 IP 建连"就完全在掌控之下。

`connect.lookup` 有一个容易踩的坑，记在 `pinnedLookup()` 的注释里：Node 的
`net.connect`（`autoSelectFamily`/Happy Eyeballs，Node 18.13+ 起默认开启）会带
`{ all: true }` 调用 `lookup`，此时期望回调的是**地址数组**而不是单个地址——
两种调用形态 `LookupFunction` 的类型都允许，不按 `options.all` 分流的话，在真实
连接中会被 `net` 内部当成"没有任何地址"直接报 `ERR_INVALID_IP_ADDRESS`（这不是
猜测，是一次真实调试撞到的错误，详见反向演练里对应的一条记录）。

### 七、不自动跟随重定向

`fetch(url, {redirect: 'manual'})`。自动跟随会让攻击者用一个公网可控地址返回
`302 Location: http://169.254.169.254/`，重定向目标从未经过 gateway→policy→DNS pin
这条完整链路，整套判定形同虚设。3xx 响应原样报告状态码与 `Location`，逼模型对新
地址重新调用一次 `web.fetch`——这是唯一能保证"每一次真实网络连接都被判过权"的做法，
内部再做一层自动跟随反而是又开一个不经过闸门的口子。

### 八、只处理文本响应

二进制响应体（图片、压缩包）塞进模型上下文既无意义又浪费预算，处理它需要
`BlobStore` 参与——`ToolContext` 目前不含它，留给多模态那一段一并解决（见
docs/08 M1-d 的设计存档）。这里按 `fs-read.ts` 对二进制文件的同一个哲学：明确
说明"响应不是文本内容"，不硬塞。响应体按流读、读满 512KB 上限即停，不先囤积
整份响应体再截断——代价与结果大小同阶，与 `fs-read.ts`/`fs-write.ts` 的既有纪律
一致。

## 后果

- `web.fetch` 是 `packages/tools-core` 第一个需要外部网络依赖（`undici`）的工具，
  也是第一个让网关走三分支分派（`command`/`host`/`path`）而不是两分支的工具
- `RegisteredTool`/`ToolContext` 分别新增 `hostInputs`/`pinnedHosts` 两个字段，
  与 `pathInputs`/`commandInputs` 完全同构的失败关闭纪律：声明了 `host` kind 能力
  却不声明 `hostInputs` → 网关当场拒绝
- `PolicyRule.match` 新增 `ipRange` 匹配维度，`evaluate()` 的求值顺序（0-5 步）
  一字未改，只是在"这条规则命不命中"这一步多了第三种判法
- YOLO 档跳不过它——它是普通 deny，YOLO 跳的是 ask 不是 deny（docs/09 C5）

| `web.fetch http://169.254.169.254/` | deny，命中 `def.no-fetch-private-network`，零确认框（`packages/runtime/tests/web-fetch-ssrf.test.ts`） |
| `http://127.0.0.1:9/`、`http://10.1.2.3/`、IPv6 各网段 | 同上，逐段边界值覆盖（`packages/kernel/tests/ip-range.test.ts` 61 条用例） |

| DNS 只解析一次的结构性验证 | 注入的 `dnsLookup` 全链路只被调用一次，工具实际建连的地址就是那一次解析给出的地址（`web-fetch-ssrf.test.ts` "DNS 只解析一次"，`gateway.test.ts` 同款单元验证） |
| 主机名解析不出任何真实地址（RFC 2606 `.invalid`），但 `pinnedHosts` 指向本机服务器 | 请求依然打到了本机服务器——证明工具全程没有自己发起过 DNS 解析（`web-fetch.test.ts`） |

## 遗留

- **图片/二进制响应体不支持**，留给多模态那一段（docs/08 M1-d 设计存档）一并解决——
  需要 `ToolContext` 携带 `BlobStore`。
- **图片自动缩放/尺寸限制之外的内容协商**（比如根据 `Accept` 头做内容类型协商）
  不在这次范围内，MVP 阶段按最简单的"文本才读"处理。
- **`net.listen` 尚无对应工具**，`TargetKind` 里已经写明它的 target 语义（绑定地址）
  与 `net.fetch`（远端目的地）方向相反，真有监听类工具时需要单独设计规范化契约，
  不能直接套用这里的 `host` kind。

## 补记（2026-08-17，地基复审四 B2）

`pinnedHosts` 是本 ADR 那条"判定用的 IP = 实际建连的 IP"的**唯一**传递通道，
而它的**键**当时没有契约：网关按 `normalizeHostTarget` 归一后的主机名写进去
（IPv6 带方括号 `[::1]`、FQDN 去掉尾点），`web.fetch` 却按
`new URL(url).hostname` 再手工剥方括号去查（`::1`、`example.com.`）。

两侧各写了一份"同一个"算法，于是这两类 URL **从来没有成功过一次**：

```
http://[::1]:8080/     网关写 [::1]        工具查 ::1            → 落空
http://example.com./   网关写 example.com  工具查 example.com.   → 落空
```

落空的表现是工具抛一句"内部错误：找不到已解析地址"——看起来像 bug，
实际上是本 ADR 这条防线的接缝错位。判定链本身一个字没错。

处置：键的算法收敛成内核里的一个函数 `pinnedHostKey(rawUrl)`，**两侧都调它**
（`packages/kernel/src/policy/host-target.ts`）。这与 ADR-0078 那道闸门坚持
"用内核自己的 `globMatch`"是同一个教训：安全边界两侧的同一个算法只能有一份实现。
端到端用例在 `packages/runtime/tests/web-fetch-ssrf.test.ts`——真网关、真判定、
真 TCP 连接，IPv6 字面量与带尾点的 FQDN 各一条。
