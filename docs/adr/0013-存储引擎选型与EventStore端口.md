# ADR-0013 · 存储引擎选型：SQLite，以及 EventStore 端口的契约

- **状态**：🟢 Accepted（2026-08-04）
- **日期**：2026-08-04
- **相关**：细化 [docs/03 §4](../03-技术选型.md) 表格里那一行；落实 [ADR-0008](./0008-事件持久化分层与演进.md) 的持久化分层；闭合 M0-a 复审报告的遗留项"`redact()` 有契约、无执行点"（该项未收进 [ADR-0012](./0012-地基复审与安全边界修正.md)，因为当时给不出执行点）

## 背景

事件流是这个系统里**唯一的真相**，其余一切（消息、成本、会话列表、索引）都是可重建的派生数据。承载它的存储引擎因此是继事件格式之后第二重的决定。

但截至 M0-a 结束，这个决定的全部记录是 docs/03 技术清单里的一行：「SQLite（better-sqlite3 或 node:sqlite），WAL 模式 —— 零依赖、事务、够快」。三个词撑不住一个五年期的决定，也回答不了"为什么不是 PostgreSQL"。

同时，`EventStore` 端口至今没有定义——docs/04 §1 画了"Ports（纯接口，内核定义）"这一层，`ModelProvider` 有草案，存储这一格是空的。M0-b 第一件事就是写 SQLite 适配器，而适配器要实现的接口不存在。

两件事必须一起定：**没有端口，引擎选型就是不可逆的**；只要端口在，选错了也只是换一个适配器。

### 负载形状

选型的依据是负载，不是"轻量"这种形容词。小明真正要做的读写只有四种：

| 操作 | 频率 | 形状 |
|---|---|---|
| 追加事件 | 每轮几十~几百次 | 单行 insert，**单写者** |
| 打开会话 → reduce | 每次打开一次 | `WHERE session_id=? ORDER BY seq` 顺序全扫 |
| 会话列表 | 启动时 | 读投影，几十行 |
| 全文 / 向量检索（M2+） | 用户主动触发 | 本地索引 |

没有一项需要网络数据库解决的问题。而 MySQL / PostgreSQL 的核心价值——多进程、可能跨机器、并发读写同一份数据，需要 MVCC 与锁管理器调停——**恰好是本架构明令禁止的东西**：ADR-0008 与 docs/10 §4.1 把"一个会话同一时刻只允许一个写者"定成了硬不变量，`PRIMARY KEY(session_id, seq)` 就是用来检测违反的。

也就是说，SQLite 最常被诟病的短板（写并发只有一个），在这里不是短板，是我们主动选择的不变量。

## 选项

### 选项 A：SQLite（WAL 模式），进程内

**优点**

- 进程内调用，无 IPC。追加是本地 WAL 顺序写，`synchronous=NORMAL` 下不等 fsync
- 零外部依赖启动 —— 这是 docs/02 §2.5 从参考项目评审里提炼的原则，装个数据库才能聊天等于原则作废
- 数据是**一个文件**：可复制、可备份、`VACUUM INTO` 一句话做快照（M5 的还原点直接受益）、卸载即干净
- FTS5 与 sqlite-vec 与事件同库同事务：写一条 `message.end` 并更新它的全文索引，要么一起成功要么一起回滚
- `:memory:` 让每个测试有独立的库，零启动成本 —— 对三平台 CI 是实打实的时间
- 文件格式承诺长期向后兼容。ADR-0008 花力气做事件版本演进就是为了"三年前的会话今天还能打开"，底下的格式也得扛得住

**缺点**

- 无复制、无内建同步（D2 多设备同步）
- 单写者。多个小明进程写同一会话会失败——但那正是我们要的失败
- 不适合放大二进制（截图、PDF），必须走 `BlobRef` + 文件

### 选项 B：PostgreSQL / MySQL

**优点**

- 真正的多写者并发、成熟的复制与备份生态、pgvector 等扩展齐全
- 若将来出现"服务端小明 / 团队版"，天然就位

**缺点（决定性的）**

- **桌面应用塞不进一个数据库服务器**。electron-builder 要打包服务端二进制，然后处理：daemon 生命周期（应用崩了谁回收）、端口占用、data 目录跨大版本不兼容（PG 升级要跑 `pg_upgrade`，一次失败用户全部会话打不开）、macOS 代码签名与公证要覆盖它、Windows 服务注册。三平台各一遍
- 每条查询都是一个进程间往返（0.1–1ms 量级），而追加是每轮几十到几百次的高频操作
- **审计日志的保护机制会被迫分裂成两套**。docs/06 §7 规定审计库是独立文件 `~/.xiaoming/audit.db`，"小明自身的策略规则禁止写入该路径"——这条之所以成立，是因为它是**一个路径**，落在 ADR-0012 刚修好的那套红线体系里，与保护 `packages/kernel/src/policy/**` 用的是同一个机制、同一批测试。换成服务端库，就要另建一套角色与 GRANT，而小明是拿着连接串跑的同一个 OS 用户。**两套互不相通的授权机制 = 两倍的"规则生效了但没长在攻击路径上"的机会**
- 连接凭据本身又是一份要存的密钥，与"配置里只能有 SecretRef"的设计多绕一圈

### 选项 C：append-only JSONL 文件 + 旁路索引

**优点**：极简、可 `grep`、天然只增不改、格式永不过期。

**缺点**：没有事务，摘要投影与事件无法原子更新（崩在中间就有"事件在、会话列表里没有"的会话）；崩溃可能留下半行；区间读要么全文件扫要么自建偏移索引；FTS 与向量全部要另起炉灶——最后会写出一个更差的 SQLite。

## 决策

### 一、存储引擎选 SQLite（WAL 模式）

理由如上。**否决 PostgreSQL 的理由要单独记下**（ADR README：否决理由比采纳理由更值得记录）：不是"PG 太重"，而是它的核心能力与本架构的核心不变量正面冲突，且会把审计日志的保护拆成两套机制。

### 二、驱动选 better-sqlite3

`node:sqlite` 在 Electron 内置的 Node 22 上仍是实验状态，且 sqlite-vec 所需的扩展加载能力要实测。better-sqlite3 的代价是原生模块——每次 Electron 升级要 `electron-rebuild`、三平台预编译产物要进 CI——但那是**一次性且可自动化**的痛苦，而实验 API 的行为漂移是持续的。

同步 API 在这里反而是优点：单写者模型下，`append` 不需要把 async 传染进调用链。

> 重新评估条件：`node:sqlite` 在我们所用的 Electron/Node 版本上转正，**且**扩展加载可用。

### 三、`EventStore` 端口 —— 七条不变量

端口定义在 `packages/kernel/src/port/event-store.ts`（内核定义端口，适配层实现，docs/04 §1）。类型只是外壳，端口的真正内容是这七条：

1. **`append` 原子** —— 一批要么全落要么全不落。一次工具调用产出 `tool.end` + `usage.recorded`，只落前一半，回放出的成本就永久少一截，且没人会发现。
2. **只接受持久化事件** —— 类型层面拒绝，见决策五。
3. **`seq` 由调用方分配，存储只验证** —— `PRIMARY KEY(session_id, seq)` 是并发写检测器，不是索引优化。冲突即抛 `SeqConflictError`，**不重试、不重新分配**。
4. **写要拿排他标记，读不用** —— 做成 `SessionWriter` 句柄的生命周期而不是每次 `append` 都检查一遍：拿不到句柄就根本调不到 `append`。WAL 下多读者 + 单写者，第二个窗口只读历史是允许的。
5. **存储不做发布订阅** —— 追加成功后由 runtime 往事件总线上发，"谁通知"只有一个答案。若把通知放进存储，第二个进程就会想去轮询它，而轮询意味着它认为自己也能写。崩在追加与广播之间不丢数据：订阅者重连时从自己的 `lastSeq` 续读。
6. **落库的事件必须已脱敏** —— 见决策四。
7. **blob 先于引用它的事件落盘** —— 事件不可变，指向不存在内容的坏引用永远修不掉。

另外两条形状上的规定：`read()` 返回 `AsyncIterable` 而不是 `Promise<Event[]>`（几万条事件一次性物化会在打开会话时占几十 MB 并阻塞主进程）；库的 schema 版本高于本机即抛 `StoreVersionError` 拒绝打开，与 ADR-0012 ⑤ 对未来版本事件的处理保持一致——那条管 payload，这条管表结构。

### 四、`SealedEvent`：`redact()` 的执行点

M0-a 复审留下一条已知缺口：`redact()` 的注释写着"日志与审计**强制**经过它"，但没有任何东西强制它——事件的 `error.detail`、工具输出都能绕过。当时没收进 ADR-0012，因为给不出执行点；现在有了——`SessionWriter.append` 只接受 `SealedEvent`，而 `sealEvent()` 是这个品牌类型唯一的生产者，它内部先脱敏再**重新按 schema 校验**。绕过它需要显式 `as`，那是 reviewer 看得见、lint 拦得住的动作；而"忘了调用"是看不见的。

**重新校验这步不是防御性冗余，它当场抓到了一个真实缺陷**：`redact()` 的敏感键名正则里 `token` 不带边界，于是 `usage.recorded` 的 `inputTokens: 1234` 命中键名匹配，被换成 `'***'`；`context.compacted` 的 `tokensBefore/tokensAfter` 同理。

如果按最自然的做法——"在 append 路径上统一 redact"——直接上线，**成本核算会从第一天起就是错的，且没有任何报错**：payload 是 `looseObject`，类型也拦不住。

修法不是调正则（`accessToken` 与 `inputTokens` 都以 Token 结尾，词法上区分不了），而是从值这边收口：**密钥不可能是数字或布尔**，键名命中且值可能承载密钥（字符串或对象）时才替换。回归用例见 `kernel/tests/event-store.test.ts`，已实测反向演练——去掉这道判断，该用例立刻红。

### 五、`PersistedEvent`：瞬态事件在编译期就进不了存储

从 `EVENT_SPECS` 的 `durability` 标注推导出 `PersistedEventType` / `PersistedEvent`。`append` 只收后者，把 `message.delta` 递进去连显式 `as` 都过不了（已演练：TS2352，"两个类型没有足够重叠"）。

ADR-0008 的分层此前只有事后的包含性测试在拦，现在写入侧当场拦得住。

### 六、`SessionSummary` 是投影，投影规则在内核

会话列表要显示标题和时间，回放几百个会话只为拿标题是荒唐的。所以引入本系统第一个读模型，由适配器在 `append` 的**同一个事务**里更新——分两次写，崩在中间就会出现"事件在、列表里没有"的会话，用户再也找不到它。

推进规则 `applyToSummary()` 放在内核而不是各适配器里，理由与 `reduce` 相同：让 SQLite 用 SQL 写一遍、内存实现用 TS 写一遍，两边会慢慢分叉，而分叉的表现是"列表里的标题跟打开后看到的不一样"——用户会发现、开发者查不出来的那类问题。

投影可随时用 `rebuildSummaries()` 从事件流重建，所以它坏了不算数据丢失。反过来：**任何信息都不许只存在于摘要里**。

### 七、端口契约做成可执行的测试套件，且放在 `src/` 而不是 `tests/`

`EVENT_STORE_CONTRACT` 是一组不依赖任何测试框架的用例（每条就是一个抛异常表示失败的 async 函数），因此能被 `packages/storage` 的测试直接 import——跨包 import 一个 `.test.ts` 是走不通的。

同时提供 `MemoryEventStore` 作为参考实现并让它先跑通全部用例。它不是玩具：headless 冒烟、评测回放、以及每个需要"一个真实会话"的单元测试都用它，而这些场景都不该碰文件系统。它还是 SQLite 适配器的对照物——**内存过、SQLite 不过，是 SQLite 的问题；两边都不过，是契约写错了。**

只写在 ADR 里的端口契约，和 ADR-0012 ⑧ 记下的那三个"文档里存在、代码里不存在"的扩展点是同一种东西。

## 后果

**正面**

- 存储选型第一次有了可追溯的理由，包括否决 PG 的理由
- M0-b 的 SQLite 适配器开工即有 11 条现成的验收用例，不必边写边猜契约
- M0-a 复审的两项遗留债务中的一项（`redact()` 无执行点）关闭；并在关闭过程中抓出一个会永久污染成本数据的缺陷。另一项（`SessionState.messages` 无界增长）仍在，属 M2 上下文压缩的范围
- 内核新增 4 个模块、体积仍是契约包 6.75 kB（预算 15 kB），依赖图 61 模块 126 边，零违规

**负面**

- `sealEvent()` 让每个写入点多一次调用与一次 schema 校验。校验的开销是真实的（每条事件一次 Zod parse），若日后成为热点，缓解方向是批量校验而不是取消校验
- `MemoryEventStore` 与 SQLite 适配器是两套实现，存在分叉风险。这正是端口契约套件要防的，但它只覆盖被写下来的那部分行为
- 多设备同步（docs/09 D2）在 SQLite 上没有现成方案。缓解：同步的对象是不可变、有序、单写者的事件流，比同步可变关系表容易——真要做时是事件层的同步，不是数据库层的复制。选 PG 也一样得自己写，流复制解决不了"两台设备各自离线编辑"

**重新评估的触发条件**

- 出现真正的多进程写同一会话的需求（说明单写者不变量本身该重新讨论，而不是先换数据库）
- 单库体积或事件条数达到打开会话明显变慢的量级（先查 blob 是否被塞进了库，再谈换引擎）
- 出现服务端/团队部署形态（那是另一个产品形态，不是同一个产品换数据库）

## 遗留

- **`ext.*` 事件的持久化层级未定。** 插件事件不在 `EVENT_SPECS` 里，因此也不在 `PersistedEvent` 里，当前端口写不进它们。但插件状态若要能回放就必须落库。留给 M3 与 docs/05 一并决定（涉及插件卸载后历史会话还能不能 reduce）。
- **`BlobStore` 端口未定义**，M0-b 补。本 ADR 只定下"blob 先于引用它的事件落盘"这条顺序约束。
- **审计库是否复用同一个端口**待验证。它同样是只增不改的本地 SQLite，但记录的不是 `XmEvent`。
