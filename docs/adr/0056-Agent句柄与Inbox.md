# ADR-0056 · Agent 句柄与 Inbox

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0055](./0055-Turn驱动器的扩展点契约.md) · [ADR-0008](./0008-事件持久化分层与演进.md) · [ADR-0049](./0049-M2-i串行只读子Agent.md) · [ADR-0002](./0002-Agent循环形态.md)
- **补充**：崩溃语义（认领前/后进程崩溃会怎样）、`followup`/`steer` 的持久性、
  `steer` 是否取消在飞的工具调用——本 ADR 都没有回答，由
  [ADR-0064](./0064-Inbox的持久化边界与steer生效时点.md) 补齐

## 背景

小明今天只有一条输入路径：`services.sendUserMessage()` → `runTurn()`。它是同步的、一次性的、
只接受用户手打的一条消息。这带来一个结构性的空缺——**下面这些场景在当前结构里没有落点**：

| 场景 | 现在会发生什么 |
|---|---|
| 回合进行中用户想补一句"顺便把测试也跑了" | 没有队列。要么等回合结束，要么打断 |
| 长任务跑到一半，用户想纠偏（"别改那个文件"） | 只能点停止，然后重开一轮，上下文全靠模型自己记 |
| 后台任务完成（M5 的"长任务脱离窗口生命周期"） | 无处告知模型 |
| 定时/触发式任务（M5） | 同上 |
| 子 Agent 得出结论回传（ADR-0049 已实现） | 走的是工具返回值，只能在派生它的那次调用里回来 |
| 文件被外部改动、CI 结果、编辑器打开了新文件 | 无处告知 |

这些都不是"缺一个功能"，是**缺一块骨架**：没有"给一个正在运行的 Agent 递东西"这个概念。
路线图里 M5/M6/M7 的一大半（后台任务、定时任务、记忆召回、目标持续推进、失败聚类的自动发现）
都要先有这块骨架，否则每一个都会自己发明一条私有路径塞进 `turn.ts`。

参考实现在这一点上的设计很清楚：一个 `Agent` 句柄 + 一个 inbox，
三个入口（`followup` / `steer` / `inject`），驱动器在每一步开始时"认领"待处理输入。

## 选项

### 选项 A：每种场景各开一条路

后台任务完成时直接 `record()` 一条事件，让 UI 提示用户手动转告模型；定时任务直接
`sendUserMessage()` 伪装成用户消息。
优点：不改结构。
缺点：定时任务伪装成用户消息会污染会话历史的真实性（ADR-0038 的会话命名就吃过
"谁说的话"分不清的亏）；而且每加一个场景就多一条私有路径，正是本仓库反复批评的形态。

### 选项 B：只做队列，不做 `inject`

优点：简单，解决"回合中补一句"。
缺点：不解决异步通知。后台任务完成时如果只能"排队一条用户消息"，那它会**唤醒一个空闲的
Agent 自己动起来**——这是用户没有要求过的自主行为，属于惊吓而不是自主。

### 选项 C：三入口 + 认领语义（照搬参考实现，加落库约束）

## 决策

**选择 C。** `Agent` 句柄提供三个入口，语义严格区分：

| 入口 | 什么时候进模型视野 | 会不会唤醒空闲 Agent | 典型来源 |
|---|---|---|---|
| `followup(content)` | 下一步认领时 | **会** | 用户发消息；显式要求继续 |
| `steer(content)` | 当前回合的下一步认领时，**优先于队列中其它消息** | 会（若空闲则等同 followup） | 用户中途纠偏 |
| `inject(context)` | 下一次**已经被唤醒**的请求里 | **不会** | 后台任务完成、定时器、文件变更、子 Agent 回传、记忆召回 |

### 一、`inject` 不唤醒空闲 Agent

这是三个入口里最重要的一条语义。一个空闲的小明**不应该因为"CI 跑完了"就自己动起来**——
除非用户或一个明确的目标域要求它这么做。`inject` 只往下一次请求里塞上下文；
Agent 空闲时它就静静躺着。

想要"通知即行动"的场景，用 `followup` 并在事件里标明来源（例如 `source: { kind: 'cron' }`），
让它在会话历史里可辨认，而不是伪装成用户说的话。

### 二、`inject` 必须落一条 `context.injected` 事件（persisted）

这是本 ADR 与参考实现最重要的差异，也是不可让步的一条：

> **模型可见 ⟺ 已落库。** 任何进入模型请求的东西，必须能从会话事件流重建。

不落库的注入会当场破掉 ADR-0008 的持久化包含性与"状态 = `reduce(events)`"这条第一不变量：
重开会话后，模型看到的历史与注入前不一致，而**这种不一致是静默的**——它不会报错，
只会让模型在续跑时莫名其妙地忘掉一件事。

新增事件：

```
context.injected  (persisted)
  payload: { content, source: { kind, ... }, turnId? }
```

`source` 必须能区分：`plugin`（哪个插件）、`subagent`（哪个子会话）、`job`（哪个后台任务）、
`cron`、`watcher`。这不只是为了 UI 说人话——**注入内容是不可信输入的一个新入口**，
来源决定它要不要触发污点传播（ADR-0033 的闸门在这里有第二个真实载体）。

### 三、认领（claim）语义

驱动器在每一步开始时认领 inbox 中待处理的输入：一次认领取走"下一步该看的全部内容"，
认领后的批次交给 `turn/pre-step` waterfall（ADR-0055），由它决定改写或整体拒绝。
被拒绝的批次**不退回 inbox**，但那个回合仍然要落 `turn.start` / `turn.end` 一对事件——
如实记下"来过一次、什么也没做"，比让它凭空消失好排查。

### 四、`ctx.agents` 与子 Agent

ADR-0049 的子 Agent 目前是"工具返回值"形态。本 ADR 不改它的隔离与只读约束，
但把回传路径统一到 `inject`：子 Agent 的结论以 `source: { kind: 'subagent' }` 注入父会话，
粘性污点照旧。这样"派生 → 干活 → 回传"三段中最后一段不再绑死在那次工具调用的生命周期里，
为将来的并行子 Agent 留出空间（并行本身仍不在 M3 范围）。

## 后果

- **正面**：M5/M6/M7 的后台任务、定时任务、记忆召回、目标推进、失败自动发现，
  全部变成"注册一个监听器 + `inject()`"。这是本次重构对"高自主性"最实质的贡献。
- **正面**：回合中排队与纠偏是用户当场能感知的体验改善，且不需要打断。

- **负面**：会话事件流多一类事件，历史库需要接受一个新的事件类型。
  仓库仍是 pre-release，`EVENT_SPECS` 的演进规则（ADR-0008）本来就覆盖新增事件类型，
  成本可接受。
- **负面**：`inject` 的内容会占用上下文预算，而它的产生者（插件、定时器）不一定知道预算状况。
  缓解：注入内容与其它上下文一样受 ADR-0048 的预算与压缩管辖，超预算时按同一套规则被压缩；
  插件不得假设自己注入的东西一定进得去。

- **代价与缓解**：`steer` 的"优先于队列中其它消息"引入了顺序语义，测试要覆盖
  "先 followup 再 steer"与"先 steer 再 followup"两种交错。缓解：inbox 的 FIFO 守恒
  写成一条运行时不变量（ADR-0060），由不变量注册表持续断言，而不是只靠几个用例。

- **必做的反向演练**：
  1. 让 `inject` 不落事件 → 重开会话后模型看到的历史与注入前不一致，测试必须红。
     （这一条是本 ADR 的核心约束，没有它的演练等于没有这条约束。）
  2. 对一个空闲 Agent 调 `inject` → 它必须保持空闲；如果动起来了，是本 ADR 的一级缺陷。
  3. 注入一段来自 `net.fetch` 的网页内容 → 污点必须传播，后续判定按不可信走。
  4. 回合进行中 `followup` 两条 + `steer` 一条 → 认领顺序与 FIFO 守恒必须可断言。

- **重新评估条件**：如果出现"必须唤醒空闲 Agent"的正当场景且用 `followup` 表达不了，
  说明缺的是一个目标域（goal）而不是第四个入口——按 docs/09 的开放问题处理，
  不要在 inbox 上加第四种语义。
