# ADR-0080 · 项目层权限规则按会话工作区加载

- **状态**：🟢 Accepted
- **日期**：2026-08-17
- **相关**：地基复审四 B1；修正 [ADR-0023](./0023-权限规则的分层覆盖.md) 的落地方式；
  与 [ADR-0078](./0078-自改红线的锚点与受保护清单闸门.md) 同一个形状（规则对、锚点错）；
  会话工作目录见 [ADR-0037](./0037-桌面端壳层导航与会话入口.md)

## 背景

ADR-0023 定下三层权限规则：内置 < 用户级 < 项目级，且**项目级只能收紧**
（`.xiaoming/config.json` 躺在别人的仓库里，作者不一定是用户）。
`loadConfig()` 把这套东西完整实现了，`tightenOnly()` 有用例，被丢弃的条目会进 `problems`。

桌面装配这样调它：

```ts
const loaded = await loadConfig({ paths, cwd: app.getPath('home') });
```

`cwd` 是**项目层的查找起点**。传家目录，就意味着"项目层"永远等于
`~/.xiaoming/config.json` ——一个多半不存在的文件。而用户真正打开的那个仓库里的
`.xiaoming/config.json`，**从应用第一天起就没有被读过一次**。

三件事让它一直没被发现：

- `packages/platform` 的用例全绿——它们直接给 `loadConfig({ cwd })` 传对了目录。
  **错的不是加载器，是调用方给的锚点**，而没有任何一层测试覆盖"装配把什么传了进去"。
- 项目层只能收紧，所以它失效的表现是"某条限制没生效"，不是报错。
- 桌面端至今没有任何界面显示"项目层加载了没有"。

根因是**时机**，不是笔误：`loadConfig()` 在应用启动时跑一次，那一刻一个会话都还没有，
它拿不到任何工作目录。而工作目录是**每个会话各自的**（`session.created` 那一刻定下来）。
一个进程级的加载函数，天生回答不了一个会话级的问题。

## 选项

### 选项 A：把 `cwd` 换成"当前会话的工作目录"

- 缺点：没有"当前会话"这种东西。桌面端可以同时开着多个会话，各自的 cwd 不同，
  而 `config` 是一份进程级的值。这个选项在多会话下无法自洽。

### 选项 B：整份配置改成按会话加载

- 优点：分层语义一以贯之。
- 缺点：`config` 的其余字段（模型、Provider、价格、禁用工具、呈现模式）在小明里
  全是**进程级**的：Provider 实例、设置页、状态栏、自动命名都读同一份。
  给它们加一个"按会话不同"的维度，是为了一个从未生效过的层重写整条配置链路。
  而且"仓库里的一个文件能换掉你的模型与 Provider"本身就该单独论证，不该顺手带进来。

### 选项 C：只把**权限规则**这一层按会话加载

- 优点：改动落在真正需要它的那一半上。权限规则本来就分层，且项目层只能收紧——
  那正是"它属于某个工作目录"的理由。
- 缺点：配置的分层语义从此分成两半（权限按会话、其余按进程），要写清楚。

## 决策

**选 C。**

- 启动时 `loadConfig({ paths })` **不传 `cwd`**：进程级配置只有内置默认与用户级两层。
- 新增 `loadProjectPermissionRules(cwd)`（`@xm/platform`），只读
  `${cwd}/.xiaoming/config.json` 里的 `permission.rules`，照旧过 `tightenOnly()`。
- 桌面端新增 `session-policy.ts`：按会话算一次规则层并缓存，合进
  **项目层规则** + **工作区里那份小明源码的自改红线**（ADR-0078 的 `extraSourceRoots`）。
  两件事的触发条件都是"这个会话的 cwd 是什么"，合在一处只摸一次磁盘。
- 被丢弃的项目规则**在会话里落一条 `notice.posted`**，与配置加载的其它问题同一个姿态：
  不生效可以，不告诉他不行。缓存保证同一个会话只落一次，不会每回合刷一遍。
- 设置页改了权限规则 → `invalidate()`，全部会话级缓存作废。

**项目配置在会话开着的时候被改，不重新加载。** 这是有意的：项目层只能收紧，
重载唯一能带来的新能力是"仓库里的一个文件能在半途改变判定"——而那正是 ADR-0023
要防的东西。想让新规则生效，开一个新会话。

## 反向演练

`apps/desktop/tests/session-policy.test.ts`（**测的是装配那一侧**，这正是漏掉的地方）：

| 演练 | 结果 |
|---|---|
| 工作区里写一条 `deny fs.read **/secrets/**`，会话 cwd 指向它 | 该路径 `deny`；另一个会话（cwd 不同）同一路径 `allow` |
| 工作区里写一条 `allow fs.write **` | 被 `tightenOnly` 丢掉，会话里落一条 `config.project_rules_dropped` 的 notice |
| 同一会话连问三次 | 同一个对象（磁盘只读一次），notice 只有一条 |
| `invalidate()` 之后再问 | 重算，且项目层的 deny 仍在 |

反向演练的判据是"把 `cwd` 传错就该红"：第一条用例里两个会话拿到的规则层不同，
而旧实现（按 `app.getPath('home')` 加载）给它们的是同一套。

## 后果

- **正面**：ADR-0023 的项目层第一次真正生效；"给这个仓库单独收紧一点"从此可用。
- **负面**：
  - 配置的分层语义分成两半：权限规则按会话，其余按进程。文档里必须写清楚，
    否则下一个人会以为在 `.xiaoming/config.json` 里写 `model` 也能生效（不能）。
  - `~/.xiaoming/config.json` 不再被当成项目层读取。它从来没有被文档承认过
    （用户级配置在 `${paths.config}/config.json`），但如果有人靠它做过覆盖，这次会失效。
  - 开会话时多一次读文件。已按会话缓存。
- **重新评估的条件**：出现第二种"按工作区变化"的配置项时，就该重新问一次
  选项 B——那时"配置按会话"可能已经不是一个额外维度，而是本来就该有的形状。
