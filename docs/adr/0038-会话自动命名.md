# ADR-0038 · 会话自动命名：标题只从用户的第一条消息生成，模型输出永不参与

- **状态**：🟢 Accepted
- **日期**：2026-08-11
- **相关**：兑现 [ADR-0037](./0037-桌面端壳层导航与会话入口.md)「后果·负面」记下的
  "大量「新会话」同名时更难辨"与「重新评估的触发条件」里的"同名会话在无 cwd 下列表不可用"；
  落实 [docs/01](../01-愿景与设计原则.md) 原则四（模型输出是不可信输入）与原则六
  （状态必须由 `reduce(events)` 得出）；`config.model.summarize` 是
  [docs/08](../08-路线图与里程碑.md) M3「角色路由」槽位的第一个真实消费者；
  顺带修掉一个 [ADR-0013](./0013-存储引擎选型与EventStore端口.md) 不变量三管辖范围内的
  并发写缺陷；不改 [ADR-0015](./0015-进程与IPC边界.md)（零新增 IPC 通道）

## 背景

新建会话的标题永远是 `'新会话'`（无 cwd）或目录名——硬编码在
`apps/desktop/src/renderer/store.ts` 的 `newSession`。会话一多，顶栏 tabs 与 Home
最近会话列表全是同名条目：用户只能靠相对时间猜哪个是哪个；从目录建的会话叫目录名，
同一个仓库开三次就是三个同名条目，目录名反而更没有区分度。

ADR-0037 落地壳层导航时已经预见到这条，写在它自己的「后果·负面」里，
当时的缓解手段是"可后续加相对时间或 cwd"——相对时间已经加了（ADR-0037 补记），
但它只回答"什么时候"，不回答"这是什么"。用户真实使用后提出，重新评估的条件已经满足。

一个此前没人注意到的事实：**`session.renamed` 事件的实现一直是死代码**。
payload（`packages/contracts/src/event/payloads.ts`）、注册表（`persisted / v1`）、
`reduce()` 分支、会话列表的摘要投影、乃至 `eventStoreContract()` 里的断言，
五处全都写好了，而**生产代码从未发出过一次**。所以这件事缺的从来不是持久化能力，
只是一个写入方。

## 选项

### A. 用用户的第一条消息（选定）

回合一开始就发起一次小模型调用，输入只有用户刚打的那一句话。

优点：注入面最小——模型输出与工具结果永远进不了标题；命名可以在模型还在回答时就完成，
用户看到的是 tab 当场改好。  
缺点：首条消息很含糊时（"帮我看看"）标题质量差。

### B. 用回合结束后的完整对话（含模型输出）

优点：标题质量更高，含糊的首条消息也能命名准。  
缺点：**否决**。标题显示在顶栏 tab 上，而助手的回复可能已经读过网页、跑过工具——
`docs/01` 原则四说模型输出是不可信输入，让它参与命名等于把一条常驻 UI 文本的
控制权交给外部内容。一个叫「已完成，无需确认」的 tab 不需要很高的技术门槛就能造出来。
且必须等回合跑完才能命名，用户在整个首轮里都盯着「新会话」。

### C. 给模型一个 `set_title` 工具，让它在回合里自己调

优点：模型知道任务全貌，时机也由它挑。  
缺点：**否决，且比 B 更糟**。它把"写一条事件"这个能力直接交到模型手里。
本仓库到目前为止的每一条模型可触发的写入都要过工具网关与权限判定，
而标题不值得为它开一条新的授权路径；更不用说注入内容可以直接指挥模型去调它。

### D. 做成子 Agent / 插件

优点：形态上更"正规"，将来好替换。  
缺点：**否决（时机）**。`subagent.start`/`subagent.end` 现在一写就抛
（ADR-0033 的 G2 失败关闭闸门），真做要先实现污点传播——那是 M2 的范围；
插件宿主是 M3。而命名需要的隔离（独立 prompt、独立模型、输出不进 `messages`）
靠一个模块边界就全拿到了。没有载体就不写实现。

## 决策

### 一、标题只从用户的第一条消息文本生成

`packages/runtime/src/session-title.ts` 是唯一实现。它不读会话历史、不读 cwd、
不带工具列表——命名的输入面就是那一句话，截到 2000 码点。

### 二、本轮只做自动命名，不做手动重命名入口

零新增 IPC 通道：命名发生在主进程内部，已有的事件推送把 `session.renamed` 送回渲染层。
**也正因为没有手动改名入口，就不需要"手动改过不再自动改"的抑制逻辑**——
那会是一份从未被真实输入验证过的代码。判据只看"messages 里有没有 user 消息"，
第二条消息进来时它自然为假，结构上不可能重复命名。

### 三、从目录创建的会话也自动改名

判据不看 `state.title`。同一目录开多个会话照样撞名，内容标题信息量更大。

### 四、模型起的标题是不可信输入，`sanitizeTitle()` 是唯一那道门

契约层对标题零约束（`SessionRenamedPayload` 只有 `z.string()`），存储层也不管长度。
净化按顺序做七件事：取第一段非空行（含 U+2028/U+2029）→ 删控制字符 → 删不可见与
双向控制符 → 去包裹与「标题：」前缀 → 空白折叠 → 一个字母数字都没有就判为空 →
按**码点**截到 24。净化不出内容时**一条事件都不发**：命名失败的正确表现是标题保持原样，
不是变成"未命名"。

### 五、`config.model.summarize` 没配就回落 `config.model.main`

**不给 `DEFAULT_CONFIG` 塞默认小模型。** 默认值会绑死某一家，于是只配了另一家 key 的
用户会拿到 `provider === undefined`——自动命名对他永远静默失效，而主对话完全正常，
那是最难自查的一类故障（"为什么别人的会话会自己起名字，我的不会"）。
"对所有人都能用、对某些人略贵"是可接受的降级；"对一部分人更便宜、对另一部分人静默
失效"不是。

### 六、`SessionRuntime.record()` 必须串行化（前置修复）

`record()` 在读 `#state.lastSeq` 与写 `#state` 之间隔着一次 `await append()`，
而两个存储实现的 `append` 都是"async 声明、体内全同步"——让出的那一拍里，
第二个写者读到陈旧的 `lastSeq`、算出同一个 seq，被不变量三的并发写检测器整条打回
`SeqConflictError`。

**这不是自动命名引入的缺陷**：`services.ts` 的 PTY `emit` 早就在并发写
`shell.session.opened`/`closed`（持久事件），撞上时被一句 `console.error` 吞掉，
会话里从此少一条"终端关了"的事实。自动命名只是让第二个写者从偶发变成常态
（每个会话的第一条消息都会有）。

修法只能在分配 seq 的那一侧：不变量三写死了"冲突即抛，**不重试、不重新分配**"，
因为冲突的含义就是"有第二个写者"，静默补救会把一次事故变成一段查不清的历史。
于是 `record()` 变成"挂上 FIFO 链"，真正的工作移进 `#recordNow()`。

### 七、不给端口加 `complete()`

`packages/kernel/src/port/model-provider.ts` 的禁令是硬的（"非流式接口一旦存在，
就一定会有调用点图省事用它"）。取标题走 `packages/runtime/src/drain-text.ts` 的
`drainText()`——抽干流式、只拼 `text_delta`、如实回报 `stopReason`。
取消信号照样一路传到底层 fetch，"200ms 内真停"不因为调用方只想要个字符串而被绕过。
ADR-0006 的上下文压缩是它的下一个消费者。

## 后果

### 正面

- 顶栏 tab 在模型**还在回答时**就已经改好名（决策一的直接副作用）。
- `session.renamed` 从死代码变成有真实写入方，`reduce`/摘要投影/契约测试三处实现
  第一次被真实路径覆盖。
- 顺带关掉一个已经在生产路径上、且被日志吞掉的并发写缺陷。
- 存储层、契约层、IPC 层、preload、`store.ts` 全部零改动。

### 负面（必须写）

- **标题起得不准，而用户没有任何手动改回去的入口。** 这是决策二的直接代价，
  也是本 ADR 最可能在几天内引来下一条真实反馈的地方。写在这里是为了那时有据可依，
  而不是重新讨论一遍要不要做自动命名。
- **这次调用的 token 不进用量统计。** `UsagePayload.turnId` 是必填，且 `reduce` 的
  `usage.recorded` 分支每收一条就把回合数 +1。编一个假 turnId → 会话回合数凭空多一，
  与用户看到的对话轮数对不上；挂到当前回合上 → 那条回合的输入 token 会多出用户永远
  解释不了的一截。`drainText` 其实**把 usage 返回出来了**——丢弃它不是因为拿不到，
  是因为没有合法的归属，而没有归属的记账比不记账更糟。量级有界：每会话至多一次，
  输入 2000 码点以内（约 700 token）+ 约 120 token 的 system，输出 64 token 以内。
- **每个会话多一次模型调用与一次网络往返。**
- **串行化 `record()` 顺带取消了 seq 冲突对"两个回合并发跑同一会话"的偶然探测。**
  那层保护本来就是"随机丢一条事件"式的，不该依赖；真正的闸门是 `running` Map 与写租约。

### 已知遗留（本轮刻意不做）

`sendUserMessage` 的 `running.has()` 检查与 `running.set()` 之间隔着一次
`await runtimeFor()`，两次并发调用可以同时通过 busy 检查，理论上能发出两条
`session.renamed`。本轮不改，因为把 try/finally 前移会让 `runtimeFor` 抛
`WriteLeaseError` 时也走 `denyAllPending()`，而它是**全局**的（会拒掉别的会话正在等的
审批）——那是个跨会话的行为变更，不该搭车在本功能里。现实触发条件是"UI 并发送出两条
首消息"，而渲染层的 `busy` 标志挡着。

### 什么条件下应该重新评估

- **手动重命名入口落地那天**：那时"标题是人写的还是模型写的"第一次有两种取值，
  `SessionRenamedPayload` 该加一个**可选**的 `source` 字段（`z.looseObject`，
  不升 version、不需要 upcaster），并补上"手动改过就不再自动改"的抑制逻辑。
  本轮不加是因为 100% 的写入都是自动的，那个字段永远不携带信息。
- **出现第二个非回合内的模型调用时**：用量漏记就不再有界，需要连同
  `UsagePayload` 加 `role` 字段、放宽 `turnId` 一起做（对齐 M3 的角色路由分账）。
- **`config.model.summarize` 有第二个消费者时**：重新讨论要不要给它默认值。

护栏放进测不到的文件等于写下就作废。

## 反向演练

**一、并发写 seq。** `packages/runtime/tests/session-runtime-concurrency.test.ts`：
同一个同步栈里连发两次 `record()` 不 await。
*改之前*——第一次的 `append` 在返回前就把 seq=2 落定，第二次读到的 `lastSeq` 必然还是 1，
`SeqConflictError` 必抛（确定性，不靠时序运气；实测就是这样失败的）。
*改之后*——两条都落库、seq 连续无空洞、`state.lastSeq` 正确、广播顺序等于调用顺序。

**二、标题净化。** `packages/runtime/tests/session-title.test.ts`：
*改之前*（绕过净化直接 `record`）——换行、ESC/BEL 引导的 OSC 序列、RTL override、
2000 字长串**全都原样进了 `state.title`**，证明契约层与存储层对标题零约束，
`sanitizeTitle` 是这条路径上唯一那道门，不是装饰。
*改之后*——同一批输入经**真实路径**（Provider → `drainText` → 净化 → `record`）
全部满足标题不变量。不变量是**循环断言**的，不是逐条写死期望值：
将来有人放宽某条规则，这个循环会先炸。

**三、顺序即判据。** 正例：不 await 地起命名 → 再写 `turn.start` → 标题落定。
对照组：先写 `turn.start` 再起命名 → 判据为假，事件流里零条 `session.renamed`。
这条护的是"调用点的位置本身就是功能的一部分"。

## 非目标（本 ADR 明确不做）

- 手动重命名入口、重新生成标题、批量重命名历史会话
- 从模型输出或工具结果命名
- 新增 IPC 通道
- 给 `DEFAULT_CONFIG.model` 加 `summarize` 默认值
- 给 `SessionRenamedPayload` 加 `source` 字段
- 给 `ModelProvider` 加 `complete()`
- Home 展示 cwd / 项目实体（仍是 ADR-0037 的非目标）

## 补记（2026-08-11）：三条测试全绿，功能一次都没成功过

真机（Windows）第一次用起来，反馈是"标题还是目录名"。翻数据库：
**全库 `session.renamed` 事件数为 0**——不是标题起得不好，是这条路径从头到尾
一次都没走通过。上面那三条反向演练当时全是绿的。

### 判据输给了钥匙串

`services.ts` 的装配写成了这样：

```ts
void providerFor(ref).then((p) => autoTitleSession({ provider: p, … }, text));
```

`providerFor()` 要读一次钥匙串，是异步的。于是判据（`shouldAutoTitle`）被推迟到
Provider 造好之后才求值——而那一拍里 `sendUserMessage` 已经跑进 `runTurn`、
`turn.start` 已经落库、用户消息已经进了 `state.messages`。判据于是**恒为假**。

这个功能设计上"失败就保持原标题、一条事件都不发"，所以它失效的样子与
"功能没上线"在界面上完全一样。**没有任何一条日志、没有任何一个异常。**

### 为什么测试没拦住

用例里的 Provider 是现成的对象：

```ts
autoTitleSession({ runtime, provider: saying('改 CI 三平台矩阵'), … }, text)
```

判据与调用点之间**没有任何异步间隙**，于是那条"顺序即判据"的用例对生产装配的
真实形状完全免疫。它验的是"`autoTitleSession` 内部把判据放在了第一个 await 之前"，
而出事的地方在这个函数**外面**——调用方在调它之前先 await 了别的东西。
护栏立在函数里，缺口开在函数外。ADR-0022 那几次补记的形状在这里重演了一遍：
**测试覆盖的是我以为的路径，不是真实走的那条。**

### 修法：把顺序交给类型，而不是交给注释

`AutoTitleDeps.provider: ModelProvider` 换成
`openProvider: () => ModelProvider | undefined | Promise<ModelProvider | undefined>`。

判据仍在第一个 await 之前求值，开 Provider 排在它后面——装配层拿不到一个"先造好的
Provider"，也就写不出"先 await 再判"这个形状。原来 `services.ts` 里那句
`if (provider === undefined) return;` 一并收进 `session-title.ts`（那里有测试）。

一条注释能被下一次改动绕过，一个类型不能。这与本 ADR 原本的取舍是同一条路子：
判断放进测得到的包，`services.ts` 只留装配。

### 顺带：DeepSeek 上还有第二道关

即使判据赢了，标题在 DeepSeek 上仍然出不来。`TITLE_MAX_OUTPUT_TOKENS` 原本是 64，
而**会思考的模型默认开着思考**，推理文本同样吃 `max_tokens`——预算被推理烧光，
`drainText` 只收 `text_delta`，拿到空串，`sanitizeTitle` 判空，一条事件都不发。

原来 `buildTitleRequest` 里写的是"`thinking` 必须不开"，做法是**省略字段**。
省略不等于关掉：省略是"交给服务端默认"。改成显式的 `thinking: { enabled: false }`，
由 OpenAI 兼容适配器翻成 `thinking: { type: 'disabled' }`（只对能力表里会思考的
模型发，理由见 ADR-0022 同日补记）；Anthropic 侧维持原状（它只认 `enabled === true`）。
`TITLE_MAX_OUTPUT_TOKENS` 顺带提到 256——那是兜底，不是修法：遇上不认关思考参数的
端点，256 还有赢的可能，64 是必输。按实际输出计费，代价仍然有界。

### 新增的用例（先确认是红的）

| 用例 | 锁住什么 |
|---|---|
| 🔴 开 Provider 是异步的，期间 `turn.start` 已落库 → 判据仍须成立 | 生产装配的真实形状 |
| 判据为假 → `openProvider` 一次都不会被调用 | "判据在前、开 Provider 在后"这个顺序本身 |
| `openProvider` 给 `undefined` → 一条事件都不发 | 没配 key 时不拿兜底回显当标题 |
| 显式关思考 —— 不是省略字段 | `thinking: { enabled: false }` 真的发得出去 |

四条在改代码前逐条确认失败（第一条报 `expected undefined to be '改 CI 三平台矩阵'`）。

### 这次学到的

**"函数内部的顺序正确"证明不了"调用点的顺序正确"。** 当一个不变量跨越模块边界时，
要么让类型承载它（本次的做法），要么用例必须复制调用方的真实形状（异步 Provider、
并发的回合），而不是复制一个方便断言的简化形状。

另外记一笔：这个 bug 是被**用户**发现的，不是被 `pnpm verify` 发现的。原因写在
本 ADR 的「实现落点」下面那句话里——`services.ts` 零测试覆盖。当时把它当成一个
已知的、可接受的空白（"只留装配"），而这次出事的恰恰就是装配那几行。
缓解手段只能是继续把可判定的东西往 `packages/runtime` 挪，直到装配层无话可说。
