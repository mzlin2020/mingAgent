# ADR-0061 · Code Mode（`run_code`）与工具 SDK 生成

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0053](./0053-微内核的特权底座与扩展点边界.md) · [ADR-0055](./0055-Turn驱动器的扩展点契约.md) · [ADR-0054](./0054-能力接缝三角色与执行世界.md) · [ADR-0009](./0009-工具Schema子集与结果截断.md) · [ADR-0006](./0006-上下文压缩策略.md)

## 背景

小明的三条核心目标里，"高性能"目前没有任何结构性支撑。一次朴素的多步任务
（读三个文件 → 改一处 → 跑测试）今天要走五到六次模型往返，每次往返都要重发整个上下文。
成本与延迟都是线性叠加的，而其中大部分往返里模型并没有做什么判断——它只是在
"调工具 → 看结果 → 调下一个工具"。

参考实现给出的答案是 Code Mode：把每个可见工具生成成一个 TS 异步函数，
模型写一段程序一次调完多步，整段程序作为一次工具调用 `run_code` 执行。
它同时带来一个次级收益——工具 schema 从提示词里折叠成一个 `run_code` + 一段 SDK 声明，
稳定前缀更短也更稳（ADR-0006 关心的 prompt cache）。

但它同时是一个明显的安全面：一段模型写的程序在宿主里跑，能连调任意工具。
这件事必须一次定死，否则它就是一条绕过 27 条红线的通道。

## 选项

### 选项 A：不做，继续每步一次往返

优点：零新增攻击面。
缺点："高性能"这条目标继续没有抓手。多工具任务的成本与延迟不会改善。

### 选项 B：做，但程序在宿主主线程里直接跑

优点：实现最简单。
缺点：一个死循环或一次 OOM 直接拖垮主进程，违反 `docs/05` 红线第三条
（扩展失败不得中断主循环）。

### 选项 C：做，程序在 worker 里跑，工具调用经绑定回到主线程重入完整闸门链

## 决策

**选择 C。** 排在新 M3 的最后一段（M3-h），砍掉不影响前七段。

### 一、安全立场（先写这条，因为它决定其余一切）

> **worker 隔离是稳定性手段，不是安全边界。**

程序拿不到 `node:fs`、`child_process`、`net`，它**唯一**能做的事是调用注入的绑定函数。
每个绑定函数把调用送回主线程，**重新走 ADR-0055 的完整十二步链**：
入参校验 → 网关规范化并回写 → 主张完备性断言 → `tool/pre-execute` → 红线 guard →
checkpoint → 执行 → 截断 → 观察。

一条也不能跳。具体说：

- 子调用**不复用**父 `run_code` 那一次的判定结果。父调用被允许，不代表它内部要调的
  `fs.write` 被允许。
- 子调用携带父调用的 token，落一条 `tool.code.dispatch`（persisted）事件，
  让审计能还原"这次写文件是某段程序里的第三步"。
- 被拒绝的子调用以**程序内的异常**返回（模型能 catch 并调整），
  而不是让整段程序静默失败。拒绝理由与直接调用时一致。
- 程序本身是**不可信输入**（模型输出）。它经过的每一处都按不可信处理，
  污点传播照 ADR-0033 走。

### 二、呈现模式

`native`（默认）/ `code` / `both`，由配置选择，可按 Agent 覆写：

- `native`：今天的形态，函数调用。
- `code`：只暴露 `run_code` + 生成的 SDK 段；模型直接点名其它工具时，
  在判定之前就解析为"未知工具"。
- `both`：两种都给，各有各的用途。

默认保持 `native`——Code Mode 是 opt-in。理由与 ADR-0038 里
"`summarize` 没配就回落 `main`"同源：**不给一部分人静默变好、另一部分人静默变坏的默认值**。

### 三、代码运行时是一个接缝

`ctx.codeRuntime`（ADR-0054 的三角色）：定义"跑一段程序、给一组绑定、返回
`{ value, logs, error? }`"，不关心工具、不关心会话。M3 只交付一个 Node worker 提供者，
语言只做 TypeScript。

运行时**只报告失败，不抛失败**：解析错、抛异常、超预算、被取消、substrate 死亡，
全部作为结果里的 `error` 字段返回。它只在调用方违反接口契约时才 reject。

### 四、预算

- 程序**中间值**（子调用的返回）不落库、不进提示词、不受结果截断管辖——
  它们是执行局部的。
- 只有 `run_code` 这一次调用的**最终输出与日志**跨越模型可见边界，
  受 ADR-0009 的截断契约管辖。
- 时间预算与输出上限是提供者的配置字段，不是硬编码常量。

这条分界很重要：它让"读十个文件、只把摘要交回来"这种模式成为可能——
而那正是 Code Mode 对上下文预算最大的贡献。

### 五、SDK 生成

从同一份工具 schema 生成 `ToolArgsMap` / `ToolOutputMap`，
保证程序里的类型与真实入参、真实返回一致。生成物进 ADR-0060 的图谱闸门。

前提：工具必须有一个**规范的 JSON 返回值**，而不是只有给人看的文本。
这一点在 ADR-0058 已经铺好（`presentationMeta` 与模型可见内容分离），
M3-h 只是把它用起来。

### 六、不做的

- 不做 Python 运行时。
- 不给程序任何直通能力（网络、文件、进程）。想要就调工具，让闸门看见。
- 不做"程序里再套一层 `run_code`"。

## 后果

- **正面**：多工具任务的往返次数与 token 成本大幅下降；提示词稳定前缀更短。
  这是"高性能"这条目标第一个结构性抓手。
- **正面**：一次读十个文件只回传摘要，直接缓解上下文预算压力（ADR-0048 的同向支援）。

- **负面**：新增一个 worker 运行时与一个类型生成器，是新 M3 里最大的单件，
  也是唯一引入新运行时复杂度的一段。缓解：排在最后，可砍。
- **负面**：新增一个安全审视面。即使子调用重入闸门，"模型写了一段什么程序"
  本身需要在 UI 与审计里可见——否则用户失去了对"它到底做了什么"的直观把握。
  缓解：`run_code` 的卡片必须显示程序全文（ADR-0058 的 `generic` 卡片 + `locations`），
  以及它内部发起的每一次子调用。
- **负面**：程序里的错误处理逻辑会让模型的失败被"吞掉"（catch 之后继续）。
  这既是优点也是风险。缓解：子调用的拒绝一律落 `tool.code.dispatch` 事件，
  即使程序 catch 了，审计里也看得见。

- **代价与缓解**：`both` 模式下同一个能力有两条路径，判定逻辑要保证两边完全一致。
  缓解：两边共用 ADR-0055 的同一条链，不写第二份判定代码——
  这也是"子调用重入"而不是"子调用走快路径"的根本理由。

- **必做的反向演练**（每条都要先看它红一次）：
  1. 程序里调一个撞红线的工具（例如写 `.git/index`、读 `~/.ssh/id_rsa`）→
     必须被拒绝，且拒绝理由与直接调用时一模一样。
  2. 程序里调一个带符号链接的路径 → 网关必须照常规范化并回写；
     如果子调用跳过了网关，用 Windows 8.3 短名构造判定与执行分叉，必须红。
  3. 程序死循环 / OOM → worker 被终止，主循环不受影响，用户看到明确提示。
  4. 程序试图 `require('fs')` / `import('node:child_process')` → 拿不到。
  5. 父 `run_code` 被允许，内部 `fs.write` 应被拒 → 必须拒；
     若因复用父判定而放行，是本 ADR 的一级缺陷。
  6. 程序 catch 掉一次被拒的子调用并继续 → 审计里仍必须有那条 `tool.code.dispatch`。

- **重新评估条件**：如果实测下来 Code Mode 的往返节省不明显（例如模型倾向于写单步程序），
  或者程序失败率高到需要更多往返来修，那么它没有兑现"高性能"的承诺——
  应当降级为 opt-in 的实验特性并停止投入，而不是继续加功能去救它。
