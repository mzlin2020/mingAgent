# ADR-0016 · 原生模块与打包：N-API 让"两轨 ABI"不成立，以及一条不管用的护栏

- **状态**：🟢 Accepted（2026-08-05）
- **日期**：2026-08-05
- **相关**：修正 [ADR-0013](./0013-存储引擎选型与EventStore端口.md) 决策二里关于 electron-rebuild 的说法；[ADR-0010](./0010-TypeScript双编译器工具链.md) 遗留的构建验证

## 背景

ADR-0013 选了 better-sqlite3，并把代价写成：

> better-sqlite3 的代价是原生模块——每次 Electron 升级要 `electron-rebuild`、三平台预编译产物要进 CI——但那是**一次性且可自动化**的痛苦。

M0-b 要把这句话变成真实的构建流程。做的过程中发现，这句话对我们选的这个版本**不成立**。

## 实测结果

### 一、better-sqlite3 13 的预编译产物是 N-API

```
$ nm -D prebuilds/linux-x64.node | grep -c napi_
61
$ nm -D prebuilds/linux-x64.node | grep node_module_register
（无输出）
$ nm -D prebuilds/linux-x64.node | grep napi_register
napi_register_module_v1
```

它依赖 `node-addon-api`，随包发 `prebuilds/<平台>-<架构>.node`，并且 `lib/binding.js` 的加载顺序是**先 `prebuilds/`，再 `build/Release/`**。

N-API 的 ABI 在 Node 与 Electron 之间是稳定的，因此**同一份二进制两边都能加载**。「Node ABI 与 Electron ABI 是两轨」这个经典问题，对这个依赖不适用。

### 二、`electron-rebuild` 在这里是个报成功的空操作

跑 `electron-rebuild -f -w better-sqlite3`：

```
✔ Rebuild Complete
```

而 `build/Release/` 里只有 `obj.target`，**没有任何 `.node`**。就算它真编出来了，加载器也会优先用 `prebuilds/` 那份。

也就是说：它打印成功、什么也没做、而且做了也用不上。同时，跑完之后 Node 侧的 269 个存储用例仍然全绿——如果按"两轨"的直觉去理解，这里本该炸。

这是本项目在 2026-08-05 一天里遇到的**第三个"输出全绿、实际没管住"**（另两个：depcruise 因 electron 未安装而看不到 import；depcruise 因 `dist/` 被 exclude 而看不到全部跨包 `@xm/*` 边）。区别在于这一个更隐蔽：前两个是护栏没生效，这一个是护栏本身没有意义。

## 决策

### 一、不引入 `@electron/rebuild`

既然它在当前依赖集上不管用，就不留。留着一个报成功的空操作，比没有它更糟——它会让人以为原生模块的问题已经被处理了。

`electron-builder` 自己会调一次 `@electron/rebuild`（日志里能看到 `executing @electron/rebuild`）。

**补记（2026-08-05，交叉打包时暴露）**：原文写的是"那是它的内部行为，我们不额外配置"。这句话只在**本机打包**时无害。第一次交叉打包 macOS 产物时它直接失败：

```
• preparing  moduleName=better-sqlite3 arch=arm64
⨯ node-gyp does not support cross-compiling native modules from source.
```

它在为目标架构**从源码重编**，而按本 ADR 的实测，那次重编本来就是多余的——`prebuilds/` 里 8 个平台的 `.node` 全都随包发着。所以 `electron-builder.yml` 增加 `npmRebuild: false`：这一步在本机打包时是空转，在交叉打包时是纯阻塞。

关了之后，Linux 上交叉打出的 win-x64 与 mac-arm64 产物里，`app.asar.unpacked/.../prebuilds/` 下对应平台的 `.node` 都在。

这条与决策一同进同退：**引入非 N-API 的原生依赖那天，`npmRebuild: false` 必须一起删掉**，否则会从"多跑一步"变成"该编的没编"。

> **重新评估条件**：引入一个**不是 N-API** 的原生依赖（node-pty、tree-sitter 原生版、computer use 的平台模块都有可能）。那一天两轨问题真的回来，`electron-rebuild` 要一并加回，并且必须配一个能验证它真的产出了 `.node` 的检查——不能只看它打印什么。

### 二、把 ADR-0013 决策二的那句话标为不准确

原文：「每次 Electron 升级要 `electron-rebuild`、三平台预编译产物要进 CI」。

准确的说法是：**better-sqlite3 13 随包发 N-API 预编译产物，Electron 升级不需要重编**。选型结论（选 better-sqlite3、暂不用 `node:sqlite`）不变，只是它比当时估计的更便宜。

### 三、真正要防的是**打包**，自检的措辞随之改写

原生模块在这个项目里的真实风险有三样，都跟编译无关：

1. **`.node` 被打进 asar。** `require()` 加载的是真实文件路径，而 asar 里的路径不是真实路径。对策：`electron-builder.yml` 里 `asarUnpack: '**/node_modules/better-sqlite3/**'`。已验证打包产物里 `app.asar.unpacked/.../prebuilds/linux-x64.node` 确实存在。
2. **`files` 漏了 `prebuilds/`。**
3. **数据目录在用户机器上不可写。**

三样的共同表现是：窗口起来了、会话列表空的、点什么都没反应——看着像 UI bug，实际是数据库根本没打开。

所以 `assertStorageWorks()` 保留，但它拦的东西改写成上面三条，并且**排在创建窗口之前**：坏掉时给一个说清原因的错误框，而不是一个点不动的窗口。

自检做在 `:memory:` 上——要验的是原生模块能不能加载与执行，不是磁盘上有什么，它不该在用户的真库里留下垃圾会话。

### 四、`pnpm allowBuilds` 白名单只加两项，并留痕拒绝第三项

```yaml
allowBuilds:
  esbuild: true
  better-sqlite3: true   # 原生模块，取预编译产物
  electron: true         # 下载与本机匹配的运行时
  electron-winstaller: false
```

`pnpm-workspace.yaml` 开头写着"白名单越短越好——安装脚本是供应链攻击的主要入口"，这条没变。`electron-winstaller` 显式写 `false` 而不是删掉：Windows 安装包由 CI 的 Windows runner 做，本地不需要它跑脚本，而写下 `false` 让"看过并决定了"这件事留痕。

### 五、构建分三段，产物存在性单独检查

| 产物 | 工具 | 格式 |
|---|---|---|
| renderer | Vite | ESM，`base: './'` |
| main | tsup | ESM（`type: module` 下 `.js` 即 ESM） |
| preload | tsup | **CJS，`.cjs`** —— sandbox 下的 preload 只能是 CJS |

`base: './'` 是必须的：打包后主进程用 `file://` 加载，绝对路径会 404。这类问题在 `pnpm dev` 下永远不出现（那时走 http），**只在打包产物里炸**——所以"dev 起得来"不等于"能发布"。

`scripts/build.mjs` 在最后检查三个产物都在。三段里少一段的表现是白屏，而白屏在 CI 里是看不见的。

Vite 与 tsup 都用 esbuild 转译、**不做类型检查**；类型检查仍然只由 `tsc -b` 与两份 `tsconfig.*.json` 负责，ADR-0010 的双编译器纪律不受影响。这一条补上了 ADR-0010 留的"Vite / electron-builder 在双装工具链下的构建验证"。

### 六、签名与公证推迟到 M1+

M0-b 的 `electron-builder.yml` 三平台都是 `target: dir`、`identity: null`。没有证书时强行开启会让本地构建直接失败，而那与本轮要验的东西无关。

## 后果

**正面**

- 存储选型的代价被下修：不需要为每次 Electron 升级维护重编流程
- 打包路径端到端验证过一次（构建 → 打包 → `.node` 确实在 `app.asar.unpacked` 里）
- 少了一个报成功的空操作

**负面**

- **应用没有在真机上启动过。** 本轮的开发环境缺 GUI 系统库（libatk / libgtk / libnss）且无安装权限，`electron .` 起不来。这一格由 CI 的 `desktop` job 补：三平台各跑一次 `XM_SMOKE=1 electron .`（Linux 加 `xvfb-run`），跑的是打包产物。**需要有远端仓库之后才能实跑**，在那之前这条是欠着的。

  **补记二（2026-08-05，远端仓库就位、CI 第一次真跑之前发现）**：上面这句"跑的是打包产物"是**假的**，`main/index.ts` 里冒烟模式的注释（"这里跑的是 asar 里的产物"）同样是假的。CI 里那一步实际写的是

  ```yaml
  run: pnpm --filter @xm/desktop exec electron .
  ```

  而 `apps/desktop/package.json` 的 `main` 指向 `./dist/main/index.js`——**源码树，根本没有 asar**。`electron-builder --dir` 把产物造了出来，然后从来没有人运行它。

  于是这个 job 唯一无法覆盖的，恰好就是本 ADR 决策三列出的、它声称要覆盖的那两条：`.node` 被打进 asar、`files` 漏了 `prebuilds/`。两处文档都写明了意图，没有一处代码是那么做的——本项目第九次「规则存在 ≠ 规则生效」，这一次的形态是**CI 步骤与它自己的注释说的不是一回事**。

  修法：`desktop` job 改为定位并运行**打包出来的可执行文件**，且先 `test -f` 断言存在——路径拼错时要当场报"文件不在"，而不是回退到某个碰巧能跑的东西上，那等于把这一格又打一个假勾。

  连带修掉一个让它"不好写所以绕开"的诱因：`productName: 小明` 是非 ASCII，Linux 上不能直接当可执行名，electron-builder 悄悄回退到包名，于是三平台产出 `@xmdesktop` / `小明.exe` / `小明.app` 三个不同的名字，跨平台脚本没法写。现在用 `executableName: xiaoming` 固定下来，用户看到的应用名仍走 `productName`。

  macOS 上另加一步 ad-hoc 签名：`identity: null` 是 M0-b 刻意的（没有证书），而 electron-builder 改写过二进制、Electron 自带的签名已失效，未签名的 arm64 产物在 Apple Silicon 上不给运行。这与用户在自己 Mac 上要做的是同一件事。
- `XM_SMOKE` 模式是主进程里的一个分支，属于测试用途的代码进了产品路径。它很短且不改变默认行为，但要记着它在。

**重新评估的触发条件**

- 引入非 N-API 的原生依赖（见决策一）
- 需要自动更新（那时签名与公证不能再推迟，`target: dir` 也要换成真实安装包格式）

## 三平台 CI 首跑记录（2026-08-05）

远端仓库就位后 CI 第一次真跑。**四个红叉，没有一个是产品代码的 bug，全部是"从没在真平台上跑过"才会暴露的装配问题**——这正是这条遗留欠了两个里程碑的代价。

| 平台 | 失败 | 性质 |
|---|---|---|
| **Windows** | `spawnSync pnpm.cmd EINVAL`，`prepare` 失败 → **`pnpm install` 整个失败** | 🔴 真 bug，见下 |
| macOS | 找不到 `小明.app` | 我的路径假设错了 |
| Linux | `chrome-sandbox` 不是 root:root 4755，Electron 主动 abort | CI 环境 |
| （全平台）| workflow YAML 语法错误，六个 job 一个没跑 | 已修，并加了本地闸门 |

### Windows 上 `pnpm install` 一直是失败的

`scripts/assert-toolchain.mjs` 挂在 `prepare` 上，它用 `execFileSync('pnpm.cmd', ...)` 取 tsc 版本。原作者**已经想到了 Windows**（所以特意选了 `.cmd`），但那个修复写在 Node 改行为之前：Node 从 18.20.2 / 20.12.2 起（修 CVE-2024-27980）**禁止 `execFile`/`spawn` 直接执行 `.cmd` / `.bat`**，必须显式 `shell: true`。

于是那条分支必然抛 EINVAL，`prepare` 退出 1，`pnpm install` 失败。**不是 CI 的问题——任何人在任何 Windows 机器上都装不上这个仓库。**

这条值得单独记，因为它是 [ADR-0007](./0007-平台支持分级.md)「Windows 是 Tier 1」这句话第一次被真的检验。在此之前"支持 Windows"完全建立在**代码里没有硬编码 POSIX 路径**这个静态观察上，而真正拦住人的是一个跟路径毫无关系的进程启动 API。

> **教训**：跨平台支持不能靠"读代码觉得没问题"来断言。它和红线、和护栏是同一类东西——**没在那个平台上真跑过，就是没有支持**。

### 另外两条

- **macOS 的 `.app` 目录名跟 `executableName` 走**，不是 `productName`：产物是 `xiaoming.app`，而 `Contents/Frameworks/` 下的 Helper 仍叫「小明 Helper (GPU).app」。改用 `*.app` 通配（Helper 都在 `Frameworks/` 下，不会误匹配）。
- **Linux 需要给 `chrome-sandbox` 设 root:root + 4755**，Ubuntu 24.04 还要放开 `kernel.apparmor_restrict_unprivileged_userns`。
  **刻意不用 `--no-sandbox` 绕过去**：那是最省事的一行，也正是 [ADR-0015](./0015-进程与IPC边界.md) 点名的"为了方便关掉隔离"。这个 job 要验的恰恰是产物在真实隔离下能不能起来，用 `--no-sandbox` 换来的绿证明不了任何用户会遇到的场景。

### 补记（2026-08-06，run #9）：护栏编码了「上次的修法」，不是不变量

M1-b 推上去之后，12 个 job 里 11 绿，`secrets` 红。日志里只有一行：

```
Post job cleanup.
Error: Path Validation Error: Path(s) specified in the action for caching do(es) not exist,
       hence no cache is being saved.
```

密钥扫描本身是过的（在 CI 那个精确的 diff 范围下本地复现，退出码 0）。红的是
`actions/setup-node` 的 **post 步骤**：它的 `package-manager-cache` 默认 `true`，
读到 `packageManager: pnpm` 就自动开缓存，而 `secrets` 这个 job **从不 `pnpm install`**——
于是收尾时要存的那个目录根本不存在。

**这个坑之前栽过一次，就在同一个 job 上。** 首跑时它挂在 setup-node 的 *pre* 步骤
（`Unable to locate executable file: pnpm`），当时的修法是给它补一行 `pnpm/action-setup`，
并把这条写进了 `check-workflows.mjs`：「setup-node 之前必须先装 pnpm」。

那条规则**编码的是那次的修法，不是不变量**。真正的不变量是：

> 包管理器缓存要么整个不开，要么开了就得有依赖被真的装出来。

按修法编码的后果有两层，都兑现了：它拦不住 post 那一头（run #9 照样红），
而且当有人写出正确的修法（关掉缓存、连 pnpm 一起去掉）时，它会把正确答案判成违规。

修法：`secrets` job 写 `package-manager-cache: false`，pnpm 那行随之删掉
（它当初只是为了喂饱缓存那一步）；`check-workflows.mjs` 的规则改成上面那条不变量，
两条反向演练分别复现 pre 与 post 两种红法。

> **这次的形态**：护栏本身是活的、也确实在跑，但它守的是一条**症状级**的规则。
> 「规则存在 ≠ 规则生效」再往下一层是——**规则生效了，可它守的不是那件事。**
