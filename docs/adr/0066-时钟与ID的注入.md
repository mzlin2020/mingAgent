# ADR-0066 · 时钟与 ID 的注入

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0052](./0052-插件容器与效果模型.md) · [ADR-0059](./0059-组合配置profile与patch层.md) · [ADR-0013](./0013-存储引擎选型与EventStore端口.md) · [ADR-0062](./0062-扩展点的异步契约与执行收据.md)

## 背景

[M3 阶段划分](../M3-阶段划分.md) 给 M3-b 与 M3-c 定的验收是：

> 同一输入在迁移前后跑出的**事件流快照逐条一致**。

复审（2026-08-14）核对了代码：**这条验收照现在的实现跑不出稳定结果。**

| 位置 | 不确定性来源 |
|---|---|
| `packages/runtime/src/turn.ts:74` | `newTurnId()` —— 随机 id |
| `packages/runtime/src/turn.ts:319` | `ts: Date.now()` —— 消息时间戳 |
| `packages/runtime/src/turn-tools.ts:256,335` | `Date.now()` 两次相减得到 `durationMs` |

同一份输入连跑两次，这三处必然不同。于是"逐条一致"要么变成一句跑不了的口号，
要么退化成"人眼看着差不多"——而 M3-b / M3-c 是**搬家**，
静默回归恰恰是搬家最典型的失败模式，这条验收不能是摆设。

顺带一提：内核的设计约束是"纯逻辑、零 I/O、能在浏览器里跑"。
`Date.now()` 与随机数虽然在浏览器里也有，但它们同样是**外部世界的输入**——
一个声称纯净的内核从环境里直接取时间和随机数，本来就是一处没被认真对待的裂缝。

## 选项

### 选项 A：快照比较时把 id / 时间 / 耗时抹掉

优点：不改代码，写一个规范化函数就行。
缺点：抹掉之后，**时间与 id 相关的回归就再也测不到了**——例如"某次重构让
`durationMs` 变成了从错误的起点算起"这类 bug，正好落在被抹掉的字段里。
而且规范化函数会随字段增加而膨胀，最后没人知道它到底抹了什么。

### 选项 B：把时钟与 id 工厂做成容器服务，测试里给确定实现

## 决策

**选择 B。**

### 一、两个服务，随容器一起落地（M3-a）

```
ctx.clock   now(): number            当前时间（epoch ms）
ctx.ids     turn() / message() / call() …   各类 id 的工厂
```

生产 profile 装 `local` 提供者，行为与今天完全一致（`Date.now()` 与现有的 `rawId()`）。
测试与 `eval` profile 装确定性提供者：时钟从固定起点按步进推进，id 是递增序列。

**凡是要落进事件的时间与 id，一律从这两个服务取**，不许再直接调 `Date.now()`。
这条由一条 lint / depcruise 规则强制：`packages/runtime` 与 `packages/kernel`
不得出现裸的 `Date.now()` 与 id 生成调用。

### 二、这不是六项安全底座之一，但它是基线行

`baseline.clock` / `baseline.ids` 用 `baseline.` 前缀，
因此**用户 patch 不能替换它们**（[ADR-0059](./0059-组合配置profile与patch层.md) §三）。
理由不是安全判定——它们不参与任何判定——而是**审计完整性**：
一个能改写时钟的插件可以让事件流里的时间戳撒谎，而事件流是所有事后追责的底稿。

它们仍**不进** [ADR-0053](./0053-微内核的特权底座与扩展点边界.md) 的六项清单。
那六项的判据是"绕过它就能越权"，时钟不符合这个判据。
清单只增不减，但也不该因为"看起来重要"就往里塞——否则"不可绕过"会稀释成"比较重要"。

### 三、快照验收因此变成可执行的

M3-b / M3-c 的行为等价验收改为：在确定性 profile 下跑同一份输入，
**事件流逐条逐字节一致**，包括 id、时间戳与 `durationMs`。
不需要规范化函数，也就不存在"这个函数到底抹了什么"的问题。

## 后果

- **正面**：M3-b / M3-c 的核心验收从"跑不了"变成"跑得了且严格"。
  搬家阶段的静默回归第一次有了真正的拦截手段。
- **正面**：内核与 runtime 对外部世界的依赖少两处，"纯逻辑"更名副其实。
- **正面**：将来的 eval 复现、回放调试、失败用例最小化，全部受益于同一对服务——
  一个能重放到同一秒的引擎，比一个"大致能重现"的引擎好用得多。

- **负面**：多两个服务、多一条 lint 规则。写代码时想取个时间要多想一步。
- **负面**：搬迁要扫一遍现有的 `Date.now()` 调用点。数量不多（runtime 内三处），
  但 `tools-core` 里可能还有，需要一次全仓扫描。

- **代价与缓解**：确定性时钟会让"超时"这类逻辑在测试里表现不同（时间不会自己走）。
  缓解：确定性提供者提供显式的 `advance(ms)`，测试主动推进——
  这反而让超时用例比 `setTimeout` 等真实时间稳定得多。

- **必做的反向演练**：
  1. 在 `packages/runtime` 里写一句裸的 `Date.now()` → 闸门必须红。
  2. 确定性 profile 下同一输入连跑两次 → 事件流必须逐字节一致；
     **先让它红一次**（例如故意保留一处裸 `Date.now()`），证明这条验收真的在看这些字段。
  3. 用户 patch 试图替换 `baseline.clock` → 拒绝启动。

- **重新评估条件**：如果确定性提供者开始需要模拟"并发下的时间交错"
  （两个异步分支各自看到不同的 now），说明单一时钟不足以描述被测场景，
  届时该做的是把那个场景拆小，而不是给时钟加并发语义。
