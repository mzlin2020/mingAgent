# ADR-0076 · `logging.*` 的处置：删死配置，`redact` 不可配是底座属性

- **状态**：🟢 Accepted
- **日期**：2026-08-16
- **相关**：M3.5-e 前置；总纲 [12-桌面端界面与设置](../12-桌面端界面与设置.md) §9.1；
  六项安全底座 [ADR-0053](./0053-微内核的特权底座与扩展点边界.md)；
  配置树 [docs/10 §8](../10-契约设计.md)

## 背景

`Config` schema 里有 `logging.level` 与 `logging.redact`，`DEFAULT_CONFIG` 里有默认值，
**全仓库没有任何一行生产代码读它们**。`redact()` 在 `sealEvent()` 里无条件执行。

给死配置做设置行，等于给用户一个不生效的开关——比没有开关更糟。
M3.5-e 设置中心动手前必须先处置，否则设置页会把这两项当成可配项。

## 选项

### 选项 A：接到真实出口上，设置页提供开关

- 优点：schema 不用收缩，旧 `config.json` 里写过的值突然有意义。
- 缺点：目前没有可配置的日志出口。为了让设置页多两行去接一个不存在的后端，
  是倒过来为 UI 发明能力。`redact` 一旦可配，就与 ADR-0053「脱敏是不可替换的底座」冲突。

### 选项 B：只删 `redact`，把 `level` 接到 `console`

- 优点：少动一个字段。
- 缺点：桌面端 / headless 的日志并不是按这个字段分流的。接上之后仍是半吊子——
  看起来能配，实际只影响我们刚好改到的那几处 `console.*`。半吊子可配项是下一次死配置的种子。

### 选项 C：两个字段都从 schema 删除（选定）

- 优点：契约与事实一致。`redact` 继续是底座，不可配。没有可配置日志出口就不假装有。
- 缺点：契约收缩。别人的 `config.json` 里可能已经写了它们（虽然从未生效）。

## 决策

选 **C**。

1. **`logging.redact` 删除。** 它是六项安全底座之一（ADR-0053）。
   「可配置的脱敏」本身就与底座定义冲突。留一个永远为 `true` 的字段，
   只是在邀请下一个人把它接到一个能关掉的开关上。
2. **`logging.level` 一并删除。** 没有可配置的日志出口。先删，真有出口时再加回——
   那时写新 ADR，而不是复活一个从未被读过的字段。
3. **旧文件里残留的 `logging`：剥离，不报错，不让整份配置退回默认。**

   加载器在 schema 校验**之前**剥掉顶层键 `logging`（`stripRetiredConfigKeys()`）。
   其它未知字段仍按 `z.object()` 的默认行为剥离，**不**把它们当成 `config.invalid`。

   选剥离而不是报错：删字段是契约收缩，报错会让一份「只有一个从未生效的键」的
   `config.json` 整份退回内置默认——模型、工作目录、工具停用一起丢，比死字段本身更糟。

   写入路径（`persistUserConfigPatch` / `persistProviderConfig`）合并后再剥一次，
   避免把死字段继续写回去。

## 后果

**正面**

- 设置中心不会出现一个不生效的日志开关。
- `redact` 继续是底座属性，编译期与 schema 都不再暗示它可以关掉。

**负面（必须写）**

- 契约收缩。已经写了 `logging` 的 `config.json` 在加载后看不到这个键；
  下一次经由设置中心保存时，文件里的 `logging` 会被剥掉。这是有意的清理，不是数据丢失——
  那个键从未被读取。
- `session.configured` 的补丁仍是 `ConfigPatch`（任意 JSON）。历史事件里若带
  `logging`，`reduce()` 会原样留在 `SessionState.config` 里。它不进 `Config` schema，
  也不再有消费者。不为此做 upcaster：会话补丁本来就不是完整 `Config`。

**什么条件下重新评估**

- 真的出现可配置的日志出口（按会话、按文件、按级别分流）。那时新写 ADR 加回 `level`，
  **不要**把 `redact` 一并加回。
