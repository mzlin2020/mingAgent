# ADR-0024 · 路径能力网关：判定看到的那个路径，必须就是工具打开的那个路径

- **状态**：🟢 Accepted（2026-08-06）
- **日期**：2026-08-06
- **相关**：闭合 [ADR-0012](./0012-地基复审与安全边界修正.md) ① 与 [ADR-0018](./0018-Windows短文件名与路径规范化契约.md) 留下的"另一半"；细化 [ADR-0009](./0009-工具Schema子集与结果截断.md)（结果截断的调用点）；`ToolContext` 的结构性约束沿用 [ADR-0019](./0019-不可信标记的解除入口.md)

## 背景

内核零 I/O，所以 `normalizePathTarget()` 只做**词法**规范化：分隔符统一、`.`/`..`
按字面消解、盘符大写、去尾斜杠。做不了的它明确地拒绝（相对路径、未展开的 `~`、
Windows 8.3 短名），这叫失败关闭。

两份 ADR 都把剩下的一半推给了同一个东西：

> ADR-0012 ①：*"符号链接解析仍归运行时的能力网关（有文件系统才做得了），两层职责不重叠。"*
>
> ADR-0018：*"真正的解法是能力网关在判定前 realpath，那属于 docs/09 G3，
> **M1 引入真实文件工具时一并做**。"*

M1-c 就是"引入真实文件工具"的那一段。开工时的事实是：

**那个网关不存在。** 两份 ADR 里的分工，一年多来只有一半有实现，
而另一半的名字在文档里出现过三次。

它具体漏掉什么：

| 漏洞 | 症状 |
|---|---|
| **符号链接** | 工作区里一个指向 `~/.ssh/id_rsa` 的链接，词法规范化看到的是工作区内的路径，判定于是完全合规地放行 |
| **相对路径** | 模型给 `src/a.ts`，内核判"判不了"直接 deny——行为安全，但用户撞到一个他自己解决不了的拒绝 |
| **Windows 8.3 短名** | `C:/PROGRA~1/x` 与 `C:/Program Files/x` 是同一个文件的两种写法，红线按长名写、请求按短名来就匹配不上 |

## 决策

### 一、新增端口 `ToolGateway`，实现在 `@xm/tools-core`

```ts
interface ToolGateway {
  resolve(tool: RegisteredTool, input: unknown, ctx: ToolContext): Promise<ResolvedCall>;
}
interface ResolvedCall {
  readonly input: unknown;   // 回写后的入参
  readonly target: string;   // 判权用的 target
}
```

端口在内核（零 I/O），实现要 `node:fs`——与 `ModelProvider` / `EventStore` 完全同构。
解析失败**抛**（`GatewayError`）：返回一个"没解析成功但你凑合用"的值，
等于把失败关闭悄悄改成了失败放行。

### 二、**必须回写入参**，不是只算出一个 target

这是本 ADR 最要紧的一条。

如果判定用解析后的路径、执行用模型给的原始入参，两者就是两个不同的东西。
权限判定是对的、审计日志也是对的，而工具按**进程的 cwd** 解析那个相对路径——
文件落在小明自己的安装目录里，判定放行的却是工作区里的那个路径。

这是权限判定上的 TOCTOU，只不过 T 和 O 之间隔的不是时间，是两个值。
`turn.ts` 已经为 `parseInput` 的顺序写过一遍同样的理由（schema 的 `.default()`
让原始 JSON 与校验后的值可能不同），这里是它的第二半。

于是 `dispatchCall` 的顺序定死为：

```
parseInput → gateway.resolve → evaluate(逐能力) → execute(解析后的 input)
```

`permission.request.target` 与 `tool.start.input` 都记解析后的值。

### 三、工具**自己声明**哪些入参是路径

`ToolSpec.pathInputs: readonly string[]`，按判权重要性排序（第一个作 target）。
**不进 `ToolDescriptor`**——模型不需要知道我们内部怎么解析它给的路径，
而描述符的每个字段都要进提示词、占 token。

声明了路径类能力（`fs.*` / `self.modify`）却不声明 `pathInputs`，**当场拒绝**。
放行的后果是这次调用的 target 是空字符串，于是它只被能力级规则判定，
所有基于路径的规则**包括红线**全部匹配不上——那是一个安静的整体绕过，
而起因只是有人加工具时漏写了一个字段。

这个判据与权限判定读的是同一份声明。维护第二份"哪些工具碰路径"的名单，
在这个仓库里已经见过一次代价：自改红线只挂 `self.modify`，
而普通写文件工具声明的是 `fs.write`，于是九条红线被整体绕过（ADR-0012 复审）。

### 四、不存在的文件：取**最深的存在祖先**再拼回去

`realpath` 对不存在的路径直接抛 ENOENT，而 `fs.write` 的目标经常还不存在。
做法是逐级向上找到最深的存在祖先、realpath 它、把剩余段原样拼回去。

这不是权宜之计：**符号链接逃逸的载体一定是某个已经存在的目录段**，
而那一段必然落在这个祖先里。`/work/link-to-etc/brand-new.txt`
因此正确地解析成 `/etc/brand-new.txt`。剩余段按定义不存在，没有链接可解。

### 五、网关**只管解析，不管放行**

工作区边界、敏感目录、能不能写，一律仍由 `evaluate()` 的规则决定。
docs/06 §2 写着"闸门 1 是纯函数，安全逻辑绝不散落在各个工具里"——
网关一旦开始自己判 allow/deny，那条纪律就破了，而且破得很难发现：
两处判定会慢慢分叉，谁也说不清最终生效的是哪一份。

### 六、顺带补上的两个"实现存在、调用点不存在"

同一段路径上还躺着两件从 M0 起就写好、却从没被调用过的东西。第一个真实文件工具
把它们全部引爆，所以一并接上：

- **结果截断**（`truncateResult` + 12 条用例）：`executeCall` 从没调过它。
  `fs.read` 一个大文件会把整份原文塞进事件流与模型上下文。
  现在先不带 ref 截一次，只有真截断了才写 blob——绝大多数小结果一次盘都不落。
  顺带把截断标记里那句"可用 `result.expand` 工具按行范围读取"改掉了：
  **那个工具不存在**，一旦真截断，模型会去调一个没注册的工具。改成指向
  `fs.read` 的 `offset` / `limit`。文案里的承诺也是承诺。
- **写前还原点**（`checkpoint.created` + BlobStore）：无人发出。
  而 ADR-0003 承诺的是"平衡档 + **无条件**还原点"，`fs.write` 是第一个破坏性工具。
  新增 `Checkpointer` 端口，判据同样来自工具的自描述（`fs.write`/`fs.delete` + `pathInputs`）。
  **快照失败不中止执行**，只落一条 notice：用户要的是把活干完，
  但他必须知道"这一步没有退路"。

### 七、挂起的审批由 Turn 循环兜底，不靠调用方自觉

一个挂起的审批就是一个挂起的 promise，而 `AbortController` 唤不醒它——
"点了停止但界面一直在转"的完整条件是：某个应答者忘了在中断时兑现。
而应答者不止一个：桌面 UI、headless 注入的函数、CLI（M3）、插件宿主。

所以 `decide` 的等待与取消信号**在 `turn.ts` 里 race**，中断时算 deny；
应答者自己抛错也算 deny——"审批出错"绝不能变成"于是就放行了"。

形状与 ADR-0022 补记那道兜底完全一致，理由也相同：
**能在这里结构性地保证的事，不要写成对调用方的要求。**

## 后果

**正面**

- 红线**第一次在真实工具输入下被验证**：一个指向敏感文件的符号链接，
  判定落在链接指向的地方（`approval.test.ts`）。这是 M1-c DoD 的一条。
- ADR-0018 的遗留关闭：`realpath.native` 在 Windows 上顺带把短名展开成长名。
- 换执行后端（container / ssh，M1-d 之后）只要换 `@xm/tools-core` 一个包——
  端口在内核，工具与网关在同一层。

**反向演练**（每条当场转红，逐一还原）

| 演练 | 结果 |
|---|---|
| 网关去掉 realpath | 4 红，含"指向敏感文件的符号链接判定落在链接上" |
| 判定用解析后的 target、执行用原始 input | 2 红，文件落在了进程 cwd 而不是工作区 |
| `executeCall` 不调 `truncateResult` | 2 红 |
| 去掉写前 checkpoint | 2 红 |
| `tool.progress` 不随 `tool.end` 归零 | 1 红（live buffer 的互斥判据） |

**负面 / 遗留**

- **解析完到工具真正 open 之间仍有窗口。** 中途把某一段换成符号链接，
  判定就落在旧目标上。关它需要在**已打开的文件描述符**上判定——要么网关自己开文件、
  把 fd 交给工具，要么依赖执行器沙箱（docs/09 **C2**，M1-d 前定案）。
  现在的姿态是：把窗口从"整条路径随便换"缩到"要在毫秒级里抢"，并如实记在代码注释里。
- **`ResourceClaim` 仍然没有消费者。** 三个工具都老实声明了，但并发调度是 M2。
- 网关每次调用都做若干次 `realpath` 系统调用。目前没有缓存——
  缓存一个"这个路径解析到哪"的结果，正是符号链接攻击最想要的东西。

## 这次值得记住的

> **把一件事拆成两半、写清楚"另一半归谁"，仍然可能只有一半被实现。**
>
> ADR-0012 与 ADR-0018 都正确地识别了边界，也都正确地写下了分工。
> 两次都说"那归运行时的能力网关"，而那个网关**一次都没有被创建过**。
> 分工写得越清楚，越容易让人觉得它已经有人负责了。
>
> 判据也很朴素：**一个被推给"将来某个组件"的责任，要么现在有载体，
> 要么在待办清单里有一个带里程碑的条目。** 前者本轮补上了，
> 后者其实一直都在（docs/09 G3），只是没人把它和"红线其实没生效"联系起来。

## 补记（2026-08-06 当天）：ADR 里写的是 `.native`，代码里用的是另一个

三平台 CI 第一次真跑，顺带照出本 ADR 自己的两处。

### 一、`realpath` vs `realpath.native`

上面「正面」一栏写着：

> ADR-0018 的遗留关闭：`realpath.native` 在 Windows 上顺带把短名展开成长名。

而 `gateway.ts` 里 import 的是 `fs/promises` 的 `realpath`——那是 JS 实现，
它解符号链接，**解不了 8.3 短名**。也就是说这条"遗留关闭"当时只关在了文档里。
（`fs/promises` 上没有 `.native`，得从回调版 `promisify` 过来，这大概就是当初写岔的原因。）

第十一次「规则存在 ≠ 规则生效」，而这次规则写在**它自己的 ADR** 里。

### 二、网关的 target 要一路归到最终形态

原来的实现回写的是**平台原生**路径（`C:\work\a.md`），而 `evaluate()` 拿到之后
还会再规范化一次（`C:/work/a.md`）。于是事件流里记的、授权里存的、规则里写的，
在 Windows 上又变成了三个不同的字符串——「本会话都允许」下一次照样弹框，
而没有任何地方看得出为什么。

本 ADR 的要害本来就是"判定与执行是同一个串"。现在把它贯彻到底：
**入参、target、事件、授权，从网关这一行起是同一个串**，形态是内核规范化后的那个。
Node 的 fs API 在 Windows 上一律接受正斜杠，所以这不影响任何工具；
POSIX 上这一步是恒等变换——它改变的只有 Windows 的行为。

顺带处理掉 `\\?\` 长路径前缀（`realpath.native` 在某些卷上会返回它）：
内核会把它当成以 `/` 开头的 POSIX 路径，规范化成 `/?/C:/...`，那是个匹配不上任何规则的怪串。
**一条静默失效的红线，比一条报错的红线危险得多。**

### 三、顺带：CI 的 lint job 是唯一没有构建产物的那个

同一次推送里 lint job 也红了，8 条 `no-unsafe-*`，全在 `services.ts`。
原因不在代码，在装配：`tsconfig.main.json` 把 `@xm/*` 逐个映射到各包的 `src/index.ts`，
而新加的 `@xm/tools-core` 漏了一行。少那一行，类型解析就退回 `dist/index.d.ts`——

- 本地：`dist` 早就 build 出来了，看不出来；
- `desktop` / `test` job：跑之前都有 `tsc -b`，也看不出来；
- `lint` job：**只 install，不 build**。干净检出上没有 dist，于是一片红。

治法不是"给 lint job 也加一次 build"（那会把这个洞永远藏起来），
而是 `scripts/check-tsconfig-paths.mjs`：源码里 import 到的每个 `@xm/*`
必须在对应 tsconfig 的 `paths` 里有映射，且映射指向的文件真的存在。
进 `pnpm verify`，也进 lint job 的第一步。
