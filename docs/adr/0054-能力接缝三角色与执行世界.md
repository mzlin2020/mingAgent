# ADR-0054 · 能力接缝三角色与执行世界

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0052](./0052-插件容器与效果模型.md) · [ADR-0022](./0022-Provider传输层与密钥归宿.md) · [ADR-0040](./0040-M1.5自主安全边界与受控终端.md) · [docs/04-总体架构](../04-总体架构.md)

## 背景

小明从 M0 起就是六边形架构：端口定义在 `packages/kernel/src/port/`，适配器在
`platform` / `storage` / `providers` / `tools-core`。这条依赖方向由 depcruise 强制，运行良好。

但"端口"这个词只描述了**三个角色中的一个**。实际使用中缺的两半：

1. **提供者怎么注册**没有统一形状。`ModelProvider` 由 `openConfiguredProvider()` 每轮现造；
   `EventStore` 由 `openStore()` 造一次；`WorkspaceIndex` 在 `productionTools()` 里传进去。
   三种端口，三种装配写法，没有一种能表达"运行时换一个实现"。
2. **消费者怎么取**同样各不相同：有的从 `TurnDeps` 的可选字段拿，有的从闭包捕获，
   有的是构造函数参数。

后果是**换一个实现要改的地方散落在装配层各处**，而这恰恰是端口存在的理由。

最尖锐的例子是**执行世界**。`ToolContext.executor` 和 `ToolAvailabilityContext.executor`
现在是一个字符串字面量：

```ts
readonly executor: 'local' | 'container' | 'remote';
```

它被传遍全场，但**没有任何一处代码根据它切换真实行为**——`fs.read` 直接调 `node:fs`，
`shell.exec` 直接 spawn 本地进程，PTY 直接开本地伪终端。也就是说：路线图里的
"容器执行器"（原 M4）和"不信任代码走 Docker"，在当前结构下**只能靠在每个工具内部加分支**
来实现，而工具有二十多个。

参考实现在这一点上给出了明确答案：filesystem 与 subprocess 提供者共享一个执行世界，
把它们指向远端沙箱，Bash / PTY / LSP 全部跟着搬家，不需要任何工具分叉。

## 选项

### 选项 A：保持现状，容器执行器到时候在每个工具里加分支

优点：现在零成本。
缺点：二十多个工具各加一次分支，任何一个漏了就是一条绕过沙箱的路径——而"某个工具忘了判"
正是本仓库反复出现的失效形态。这是把安全性押在遍历完整性上。

### 选项 B：只规范注册与注入形状，`executor` 仍是字符串

优点：改动小，解决装配散乱。
缺点：不解决执行世界的问题，容器执行器仍然无处落脚。

### 选项 C：接缝三角色规范化 + 执行世界升为真实接缝

优点：一次把两个问题一起解决；"换一个提供者整片跟着换"成为结构事实而非承诺。
缺点：需要把 `fs` / `subprocess` / `pty` 三类底层操作从工具实现里抽出来，
落在执行世界接口后面。这是 M3 里改动面最大的一段。

## 决策

**选择 C。**

### 一、接缝（Seam）的定义：三角色齐全才算一个接缝

| 角色 | 是什么 | 住在哪 |
|---|---|---|
| **接缝定义（Definition）** | 接口 + 词汇类型 + 服务 key。声明"这个能力长什么样" | `@xm/kernel/src/port/`（沿用现址，只是正名） |
| **提供者（Provider）** | 实现，注册到 `ctx.<key>` 上 | `platform` / `storage` / `providers` / `tools-core` |
| **消费者（Consumer）** | 通过 `inject` 取用，通常是工具或运行时 | `tools-core` / `runtime` |

**一个角色不构成接缝。** 只写了接口没有第二个提供者的，不叫接缝，叫接口——
这条区分很重要，因为"端口中立性"只有在有第二个实现时才被真正检验过
（ADR-0022 记过这一笔：接第二家的第一小时抓到三处绑死 Anthropic 的假设）。

新增接缝时，三个角色必须一起设计。允许一个包同时承担多个角色（例如 `providers` 既定义
不了端口、又是提供者，这没问题），但**不允许只交付一个角色就宣称接缝完成**。

### 二、现有端口的正名与补齐

`port/` 下的九个端口全部正名为接缝定义，并统一提供者注册形状：
`ctx.effect(() => registerProvider(key, impl))`，返回撤销函数。消费者一律 `inject` 取。

不改任何一个端口的接口签名——**这一段是纯装配形状的统一，不是接口重构**。

### 三、执行世界（Execution World）接缝

`executor` 从字符串字段升为真实接缝 `ctx.executor`，接口覆盖三类底层操作：

```
ExecutionWorld
  ├─ fs        读 / 写 / 列举 / stat / realpath
  ├─ process   spawn（argv 契约，ADR-0026）
  └─ pty       开 / 写 / 关（受控 argv，ADR-0040）
```

M3 只交付 `local` 一个提供者，行为与今天完全一致。容器与远端提供者留到 M5/M6，
但**接口形状现在就要完整**——不完整的接口等于没有接口，届时还是要改二十多个工具。

三条硬约束：

1. **工具不许绕过执行世界直接碰 `node:fs` / `child_process`。**
   由 depcruise 规则强制：`tools-core` 的工具实现文件不得 import `node:fs` 等模块，
   只有 `local` 提供者可以。这是"换一个提供者整片跟着换"唯一可靠的保证方式。

   > **2026-08-14 升级**：[ADR-0063](./0063-安全底座与工具实现的包边界.md) 把网关、checkpoint
   > 与 local 提供者迁出 `@xm/tools-core`，这条规则随之从**包内文件名单**升级为
   > **包边界规则**（`@xm/tools-core` 整包禁止 import `node:*`）。
   > 文件名单会因为"新加的文件忘了进名单"而漏，包边界不会。
2. **路径网关排在执行世界之前，不随提供者变化。** 网关做规范化与回写 `input`（ADR-0024），
   执行世界拿到的已经是判定过的绝对路径。**在同一个执行世界内**，提供者不得重新解析路径——
   与 `pinnedHosts` 不许重新解析 DNS 是同一个理由（判定与执行必须共用同一个值）。

   > **2026-08-14 收窄**：这一条只对 `local` 世界成立，因此对 M3 完全够用（M3 只交付 local）。
   > 跨世界时它是**错的**：容器 / 远端的根目录、符号链接、大小写规则都可能与宿主不同，
   > 宿主上的 `realpath.native` 结果代表不了远端真正打开的那个对象——
   > 判定与执行会在两个命名空间里各自解析同一个字符串，而这正是 ADR-0018 那类绕过的形状。
   > 非 local 执行世界落地前必须先回答 `docs/09` 的 **H5**：解析由谁做、
   > 判定与执行是否共用一个不可伪造的句柄。**在 H5 定案之前不得实现第二个执行世界提供者。**
3. **`available()` 仍是纯函数且结果稳定。** 执行世界的能力探测结果进
   `ToolAvailabilityContext`，它决定工具列表，而工具列表是 prompt cache 稳定前缀的一部分
   （ADR-0006）。换世界会让工具列表变化，这是对的；但**同一个世界内不许逐轮抖动**。

## 后果

- **正面**：容器执行器、远端沙箱、E2B 式云端工作区，从"改二十多个工具"变成"写一个提供者"。
  M7 自改闭环需要的"在隔离环境里跑自己改出来的代码"，也落在同一个接缝上。
- **正面**：接缝的三角色形状是 ADR-0060 图谱生成的输入——生成的接缝图能回答
  "谁提供、谁消费"，补上容器化之后 import 图看不见的那部分（ADR-0052 的对策二）。

- **负面**：`tools-core` 的工具实现要整体改写为"经 `ctx.executor` 操作"，
  这是 M3 中改动面最大、最容易引入回归的一段。缓解：M3-e 单独成段，
  用同输入的事件流快照与既有的 dist smoke 逐条对齐。
- **负面**：多一层间接调用。对 `fs.read` 这种高频路径有轻微开销。可接受——
  瓶颈在模型往返与磁盘 I/O，不在一次方法分派。

- **代价与缓解**：只有一个提供者时，接缝的中立性无法被检验（ADR-0022 的教训）。
  缓解：M3-e 的验收强制要求写一个**假的 executor 提供者**（记录调用、不做真实 I/O），
  让全部 fs/shell/pty 工具跑在它上面。跑不通就说明有绕过。

- **重新评估条件**：如果 `ExecutionWorld` 的接口在容器提供者落地时被发现绑死了本地假设
  （例如同步 stat、本地路径语义、进程树信号），说明只有一个实现时的接口设计没经住检验——
  按 ADR-0022 的先例，届时以第二个实现为准修接口，不为兼容第一个实现打补丁。
