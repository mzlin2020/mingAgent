# ADR-0050 · 编辑 diff 的行级 hunk 与提案投影

- **状态**：🟢 Accepted
- **日期**：2026-08-13
- **相关**：[ADR-0044](./0044-M2-d精确编辑与多文件事务.md)、[ADR-0045](./0045-M2-e-diff审阅不是权限审批.md)、[ADR-0009](./0009-工具Schema子集与结果截断.md)
- **Supersedes**：[ADR-0044](./0044-M2-d精确编辑与多文件事务.md) 第 4 节与第 1 节关于提案投影的部分

## 背景

M2 复审在真实尺寸的输入上实测出：**多文件编辑在超过约 5 KB 的文件上根本无法完成**。

ADR-0044 §4 定的是"首版每个文件一个完整 hunk"。实现把它做成了"整文件对倒"——一个
`@@ -1,N +1,M @@` 头，后面跟全部旧行（`-`）再跟全部新行（`+`）。它形式上是 diff，
但体积随**文件大小**而不是**改动量**增长；而 `createEditProposal()` 又给每条 replacement
各生成一份这样的整文件 diff。

实测（两个 400 行 / 各 20 KB 的普通源文件，共 3 处单行替换）：

```
单文件字节: 20580   提案 JSON 字节: 223123   放大 5.4 倍
单个 hunk 的 diff 行数: 803（改了 1 行）
```

后果链条是闭合的：

1. `edit.preview` 把 `JSON.stringify(proposal)` 整个交给模型；
2. 它撞上默认 64 KB、`strategy: 'middle'` 的统一结果截断，**中段被挖掉**；
3. `edit.apply` 强制要求逐项传回每个文件的 `path` + `beforeHash`（ADR-0044 §2，这条本身是对的）；
4. 第二个文件之后的 `beforeHash` 恰好落在被挖掉的中段 → 模型无法构造合法调用；
5. 唯一补救是 `result.expand`，而它一次最多 50 行——要从 223 KB 里捞一个哈希。

同一个根因还打穿 M2-e：`boundedDiff` 取前 400 行，而前 400 行**全是 `-`**。
任何超过 400 行的文件，diff 审阅面板只显示删除、一行新增都看不到，ADR-0045 §4 的
"有界渲染"于是只渲染了一半语义。

这条一直是绿的，因为原有夹具全是几十字节的 `a.txt` / `b.txt`——测试正好绕开了失效区。

## 选项

### 选项 A：保留整文件对倒，只把提案改存 BlobRef

事件行不再变大，但模型可见结果、UI 渲染、审阅逐块选择三处的问题一个都没解决，
而且要多维护一套"什么时候进 blob"的双格式。ADR-0044 自己写过"不能提前造双格式"。

### 选项 B：引入现成 diff 依赖

省事，但常见库自带可选启发式（patience / histogram、空白折叠），默认值随版本变化。
这段文本要进持久事件、要与内容哈希一起构成 `edit.apply` 的前置条件，**确定性**是硬要求，
而不是"通常一致"。

### 选项 C：自写行级 diff + 收窄模型可见投影

## 决策

选择 **C**。

### 1. diff 是真正的行级多 hunk unified diff

新增 `packages/tools-core/src/diff.ts`：先剪掉公共前后缀，再对中间段跑 Myers 的 O(ND)
贪心算法，输出带 3 行上下文的多个 hunk。两侧内容相同返回空串。同一对输入在三平台、
任何 Node 版本上产出逐字节相同的文本——不加依赖正是为了保证这一点。

两道显式的闸：

- **编辑距离上限 1200**。Myers 的回溯需要保存每一步的 V 窗口，空间是 O(D²)。
  超过上限就退化为"整段替换"，仍是合法 unified diff。不假装还能算出最小编辑脚本，
  也不无声地吃掉几百 MB。
- **末尾换行参与行比较**。`"a"` 与 `"a\n"` 按 `\n` 切完都是 `["a"]`；不带标记的话
  diff 会说两者相同，而内容哈希会（正确地）说不同，打架时出问题的是 `edit.apply` 的
  前置校验。这条是本模块的测试当场抓出来的，不是设想的风险。

### 2. 模型可见结果是紧凑信封，不是整份提案

`edit.preview` 不再回吐 `JSON.stringify(proposal)`。改为：**apply 所必需的最小信息**
（`proposalId` + 每个文件的 `path` / `beforeHash` / `afterHash`）逐行自足地排在最前，
diff 排在后面。即使 diff 段被截断，apply 需要的东西也一定还在；被截掉的部分仍可通过
`result.expand` 取回。

完整提案照旧完整落 `edit.proposed` 事件——renderer 与 headless 仍消费同一份契约
（ADR-0044 §1 的这半条不变）。变的只是**投影给模型的形状**。

### 3. `edit.preview` 有单文件字节上限

2 MiB。比 `fs.read` 的 512 KB 宽，因为精确编辑必须拿到全文才能算命中数与 afterHash；
但一次最多 100 个文件，没有上限时一个失手的 path 就能把大文件批量拉进主进程内存。

### 4. 判据写进冒烟，且必须读模型真正看到的东西

headless 冒烟原来从**事件投影**取提案再构造 apply——真实模型没有这条捷径，所以这条
纵切在整个失效期间一直是绿的。现在冒烟改读 `tool.end.forModel`，断言每个文件的
`beforeHash` 都在截断后存活。

## 后果

- 正面：提案体积随改动量而不是文件大小增长；多文件编辑在真实源文件上可用。
- 正面：diff 审阅面板显示的是真正的改动块，逐块选择有了意义。
- 正面：不新增依赖，确定性由自己的测试守着（空 diff、纯插入/纯删除、CRLF、末尾无换行、
  hunk 合并、超距退化、重复调用逐字节一致）。
- 负面：自写 diff 意味着自己承担正确性。缓解：算法只有一种（Myers），没有可选启发式，
  且每条边界都有确定性用例。
- 需要接受的代价：编辑距离超过 1200 的改动会退化成一个大 hunk。那种改动本来也不适合
  逐块审阅，退化是显式的、有界的。
- 什么条件下应该重新评估：如果出现"提案本身（不含 diff）就撞截断"的场景——即一次编辑
  涉及的文件数多到连路径清单都放不下——再考虑把提案改存 BlobRef。当前 100 文件上限下
  路径清单约 10 KB，离 64 KB 还很远。
