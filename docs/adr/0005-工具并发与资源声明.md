# ADR-0005 · 工具并发：混合式资源声明 + 冲突检测调度

- **状态**：🟢 Accepted（2026-08-04 确认）
- **日期**：2026-08-04
- **相关**：[04-总体架构 §4.3 §7](../04-总体架构.md)、[02-参考项目评审 §2.2](../02-参考项目评审-manusAgent.md)

## 背景

参考项目 manusAgent 强制单工具调用（`tool_calls[:1]` + `parallel_tool_calls=False`），读 5 个文件要 5 个 LLM 来回。小明已决定支持并行工具调用（[02 §2.2](../02-参考项目评审-manusAgent.md)），但"两个工具会不会打架"的判定粒度直接决定 `Tool` 接口的形状——这个接口一旦定死，后期改动要动所有工具。

## 选项

### A. 能力级声明：只声明 `parallel` / `exclusive`
- 优点：接口最简单，工具实现无负担
- 缺点：误串行严重——两个改**不同文件**的 `edit` 本可并行，却因为同为写操作被串行

### B. 路径级声明：工具声明要触碰的路径，调度器做区间冲突检测
- 优点：精确，并行度最大
- 缺点：要求工具在执行前就知道自己要碰什么。`shell.exec("./build.sh")` 根本做不到——脚本里干什么无法静态得知

### C. 混合式：能声明的声明，声明不了的按 exclusive 处理
- 优点：`fs.*` / `edit` 这类高频且可静态分析的工具拿到完整并行度；`shell` 这类不可预测的安全降级
- 缺点：`Tool` 接口多一个可选方法

## 决策

选择 **C：混合式**。在 `Tool` 上增加可选的 `resources?(input): ResourceClaim[]`：

```ts
type ResourceClaim =
  | { kind: 'path'; mode: 'read' | 'write'; glob: string }
  | { kind: 'pty';  sessionId: string }
  | { kind: 'net';  host: string }
  | { kind: 'global'; name: string };
```

**调度规则**：

1. 未实现 `resources()` 或返回 `undefined` → 视为"可能碰任何东西" → exclusive，独占执行
2. 全部为 `read` 的声明之间不冲突 → 并发（默认上限 8）
3. `write` 与任何同路径的 `read`/`write` 冲突 → 串行，按模型给出的调用顺序执行
4. 同一 `pty.sessionId` 恒冲突（同一个终端不能并发写）
5. `global` 是兜底的具名互斥锁，给无法用路径表达的独占场景（如"同一时刻只能有一个 npm install"）

**关键取舍**：`resources()` 是**可选**的。工具作者不确定就别声明，安全降级为串行。宁可少一点并行度，也不要因为一个声明错误导致并发写坏文件——**并发的收益是省时间，并发出错的代价是数据损坏，两者不对称**。

## 后果

**正面**
- 高频只读操作（读文件、搜索、看 git status）完全并行，这是实际使用中占比最大的部分
- `edit` 类工具改不同文件时可并行，多文件重构明显加速
- 接口是可选的，工具实现门槛不变，插件作者不声明也能正常工作

**负面**
- 声明与实际行为可能不一致（工具声明只读 `a.ts` 却写了 `b.ts`），调度器无法验证
- glob 的冲突判定要处理符号链接、相对路径、大小写敏感性差异（见 [ADR-0007](./0007-平台支持分级.md)），实现有细节复杂度

**缓解措施**
- 路径声明统一走**规范化**（解析符号链接、转绝对路径、按平台处理大小写），与权限闸门共用同一套路径规范化代码——**一处实现，两处受益**
- 开发模式下做**声明校验**：记录工具实际触碰的路径，与声明比对，不一致则告警。这也是给未来自动生成的工具准备的护栏
- 并发上限可配置，出问题时可一键降为全串行

**重新评估的触发条件**
- 出现声明不一致导致的实际数据损坏（说明需要强制校验而非告警）
- 并行带来的实际收益低于预期（说明瓶颈在模型侧而非工具侧，可简化为方案 A）

## 补记（2026-08-17，[ADR-0082](./0082-工具并发调度只读并行写独占.md)）

**这份 ADR 的接口全做了，调度器一直没有做。** `resources()` 与
`ToolDescriptor.concurrency` 一路落到了每个工具定义里，而驱动器从 M0 起就是
`for (const call of calls) await dispatch(call)` ——**没有任何代码读过那两个字段**
（地基复审四 D1）。于是"读 5 个文件"仍然要串 5 段执行，
而本文开头批评参考项目的正是同一件事的另一半。

ADR-0082 把它兑现了，但**收窄**成"只并行无论怎么排都不会互相影响的调用"：
`concurrency: 'parallel'` 且资源声明里没有 `write` / `global` / `pty`。

上文选项 B 被否掉的理由（"`shell.exec("./build.sh")` 静态分析不出要碰什么"）成立，
但真正挡住路径冲突检测的是另一件当时没看见的事：**`resources(input)` 拿到的是
网关规范化之前的入参**。`./a.ts` 与 `/work/a.ts` 在排班这一层看不出是同一个文件
（规范化发生在 `prepareCall` 里，也就是排班之后）。冲突检测因此会漏判，
而按本文自己的判据——收益是省时间、代价是数据损坏，两者不对称——漏判不可接受。

于是决策段里"`edit` 类工具改不同文件时可并行"这一条**没有兑现**，
后果段里那句"多文件重构明显加速"随之作废。其余部分（可选声明、
声明不了就降级独占、上限 8）仍然有效。
