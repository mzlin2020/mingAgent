# ADR-0017 · 地基复审二：注入防御从未生效，以及红线挂错了能力

- **状态**：🟢 Accepted（2026-08-05）
- **日期**：2026-08-05
- **相关**：修正 [ADR-0003](./0003-默认权限策略.md)（YOLO 语义）、[ADR-0012](./0012-地基复审与安全边界修正.md)（同类失效的第七、八次）；定案 [docs/09 C5](../09-待讨论的开放问题.md)；新开 docs/09 G1–G5

## 背景

M0-a（契约与内核）与 M0-b（外壳与持久化）交付后，对整个地基做一次针对**安全性、扩展性、性能**的复审，判断它能不能承接 docs/05（可插拔体系）、docs/06（四道闸门）、docs/07（L4 自我迭代）写下的后续需求。

复审的方法是刻意选的：**不读注释判断，用真实内核跑一遍**。这个项目已经栽过六次「规则存在 ≠ 规则生效」，而那六次里没有一次是靠读代码发现的——读代码看到的永远是意图，测试全绿看到的永远是"已配置"。

结论：地基的**结构**是好的（六边形分层、事件溯源、纯函数判定、契约先行都站得住），但有**两处安全防御在真实调用路径上从未生效过**，另有两处规模问题在实测下已经出现。

## 实测结果

### 一、注入降级与三条 untrusted 红线，从写下起一次也没触发过

`PermissionRequest.trustLevel` 在整个代码库里只有一个赋值点——`runtime/src/turn.ts`，硬编码 `'model'`。没有任何路径产出过 `'untrusted'`。

用真实 `builtinRules()` 跑：

```
untrusted + git.push      → DENY  [builtin.injection-downgrade]   ← 设计意图
model     + git.push      → ASK   [def.git-push]                  ← 实际唯一可达
untrusted + secrets.read  → DENY  [red.secrets-read-untrusted]    ← 设计意图
model     + secrets.read  → ASK   [builtin.tier-fallback]         ← 实际唯一可达
```

于是全部落空的有：`downgradeIfUntrusted()` 的两半（allow→ask、ask→deny）、`red.secrets-read-untrusted`、`red.gui-input-untrusted`、`red.plugin-install-untrusted`。docs/06 §9 的验收项「读过网页后要求 git push → 从 ask 变 deny」**不可能通过**。

这是第七次。它比前六次更值得记，因为前六次是护栏没接上，这一次是**护栏写得最精细的那一处没接上**——`engine.ts` 里 ask→deny 那段注释足足写了十行，解释注入的形状、解释为什么只做 allow→ask 不够、引用了 docs/06 §9 的验收项。写得越细，越没人怀疑它没在跑。

### 二、九条自改红线，一个普通写文件工具就能整体绕过

```
self.modify 改 <appRoot>/packages/kernel/src/policy/defaults.ts → DENY [red.self-modify-00]
fs.write    改同一个文件                                        → ASK  [def.fs-write]
fs.delete   删同一个文件                                        → ASK  [def.fs-delete]
fs.write    改 <appRoot>/.github/workflows/ci.yml               → ASK  [def.fs-write]
fs.write    改 <appRoot>/scripts/check-secrets.mjs              → ASK  [def.fs-write]
```

原因是红线写成了 `capability: 'self.modify'`，而**能力是工具自报的**。一个通用写文件工具报的是 `fs.write`，它根本不知道自己正在改的是权限判定逻辑。九条红线降级成一个用户会顺手点掉的确认框。

`defaults.ts` 里紧挨着的审计库红线**写对了**（挂在 `fs.write` / `fs.delete` 上，还专门盖住了 `-wal` / `-shm`）。所以这不是想不到，是同一个教训只学了一半。

### 三、YOLO 越过了用户自己写的 deny（docs/09 C5）

```
用户规则 deny fs.delete /home/ming/work/prod/**
tier=balanced  → DENY  [user.protect-prod]
tier=yolo      → ALLOW [builtin.tier-fallback]
```

### 四、会话回放是超线性的（实测）

`reduce` 每条 `message.end` 做一次 `[...state.messages, m]`：

| 事件数 | 回放耗时 | N 翻倍后的倍率 |
|---|---|---|
| 1 000 | 11.6 ms | — |
| 4 000 | 69.1 ms | ×3.79 |
| 8 000 | 110.6 ms | ×1.60 |
| 16 000 | **1121.2 ms** | ×10.14 |

且 `state.messages` 永不收缩。5 万条事件全量物化：堆 +41.9 MB，`structuredClone` 一次 685.6 ms。

### 五、存储层的流式克制在 IPC 边界被完整抵消

`SqliteEventStore.read()` 分页 500 条，注释写着"绝不 `all()`"。而 `apps/desktop/src/main/ipc.ts`：

```ts
const out = [];
for await (const e of ...read(...)) out.push(e);
return out;          // 整个数组一次性过 IPC
```

## 决策

### 一、`trustLevel` 改为从事件流**算出来**，而不是由调用方填

新增 `UNTRUSTED_CONTENT_CAPABILITIES = ['net.fetch', 'browser.control', 'gui.capture']`（contracts）。`reduce` 在 `tool.start` 分支读 payload 里**已有的** `capabilities` 字段，命中即在 `SessionState.untrustedContext` 上置标记；`turn.ts` 据此填 `trustLevel`。

三个设计点，每个都是针对一种复发方式：

- **不加新字段。** 直觉写法是给 `ToolSpec` 加一个 `introducesUntrustedContent: boolean`。那正是本项目反复栽跟头的写法——多一个可以忘记填的地方，就多一条会安静失效的防线。改读 `capabilities` 之后，工具只要如实声明 `net.fetch` 就自动被覆盖，**没有第二个地方需要人记得**。附带好处：不动事件 schema、不升版本、老会话回放即生效。
- **标在 `tool.start` 而不是 `tool.end{ok:true}`。** 一次 `net.fetch` 完全可能先收到响应体、再在处理阶段抛错——那时内容已经在上下文里了。按成功与否标记会漏掉这一整类。
- **粘性，跨回合不清除。** 不可信内容进了 `messages` 就一直在里面，回合结束并不会把它从模型上下文里拿走。按回合清空等于"上一轮读的网页这一轮不算数了"，而跨回合正是注入最自然的形状。

能力子集为什么是这三个：多了会自毁——`fs.read` 也可能读到别人写的文件，但它默认放行且几乎每轮都发生，算进来等于会话一开始就永久不可信，用户会直接关掉整道防御；少了会漏——`gui.capture` 截的如果是浏览器窗口，和 `net.fetch` 拿回来的是同一段载荷，只是换了条路进来。

### 二、红线按"目标是什么"写，不按"调用方自称在做什么"写

九条受保护路径各自同时挂 `self.modify` / `fs.write` / `fs.delete` 三条红线（27 条）。

这条要当成通用规则记住：**任何按 `capability` 写的红线，都隐含假设调用方会如实声明能力。** 这个假设对自己写的工具成立，对插件和 MCP 工具不成立，对被注入操纵的模型更不成立。红线是最后一道防线，不能建立在被防对象的自我申报上。

同时把 `policy-engine.test.ts` 里"红线数量保持克制"那条用例的分组依据从 `capability !== 'self.modify'` 改成 rule id 前缀——那个写法把能力当成了"是不是自改红线"的代理，而这次加固恰好让代理不成立，会导致一次**正确**的加固报红。

### 三、YOLO 只跳过 `ask`，跳不过任何 `deny`（定案 docs/09 C5）

求值顺序改为 `红线 → deny → YOLO → ask → allow → 档位兜底`。

理由：用户写下一条 deny 是**长期意图**，开 YOLO 是**"这一小时别烦我"**。前者省的是确认框，后者删掉的是用户唯一能表达"这里绝对不行"的手段。而且它恰好在最危险的时候失效——开 YOLO 正是为了放手让它长时间自己跑。

⚠️ docs/06 §3 "YOLO = 全 allow，只有绝对红线不受影响"的措辞与本决策冲突，需同步改为"只有 deny 不受影响"。

### 四、工具入参**先校验、再判权限**

`RegisteredTool` 增加 `parseInput()`；`turn.ts` 先校验，把**校验后**的对象同时交给 `targetOf()` 与执行。

两条理由：

1. 入参 schema 允许 `.default()`（`.transform()` 已被 `assertToolSchema` 禁掉），所以原始 JSON 与校验后的值可能不是同一个东西。判定看着 A、执行的是 B，就是权限判定上的 TOCTOU。
2. 参数根本不合法的调用不该惊动用户。旧顺序会先发 `permission.request`、弹审批框，等用户点了"允许"才在执行时因 `invalid_input` 失败。**审批噪音会直接转化成"下次顺手点允许"**——这是权限系统最实际的失效方式。

`execute()` 内部仍然再校验一次：它是公开入口，不能假设每个调用方都记得先校验。允许的 schema 子集里 transform 被禁，所以重复校验是幂等的。

### 五、两处小修

- **`StopReason` 增加 `max_iterations`。** 此前跑满回合上限记成 `max_tokens`，等于把"Agent 跑飞了"记成"回复太长"——两者的处置完全相反（调大 `maxOutputTokens` vs 去看它在循环什么），而 `turn.end.reason` 正是 UI 提示与将来评测集分类的依据。
- **`GLOB_CACHE` 加上限（1024，满了整体清空）。** 模块级只增不减的 Map，在一个跑几周不重启的常驻进程里就是内存泄漏。今天规则数量是常数，不代表明天是——切项目、装插件、接 MCP server 都会带来新 pattern。

## 反向演练

按本项目纪律，护栏改动一律做反向演练。三条全部当场转红：

| 演练 | 结果 |
|---|---|
| `trustLevel` 退回硬编码 `'model'` | `injection-defense.test.ts` 3 条中 2 条红（第 3 条是"日常不误伤"，本就不该变） |
| 自改红线退回只挂 `self.modify` | `policy-redlines.test.ts` 10 条红 |
| YOLO 判定挪回普通 deny 之前 | `policy-engine.test.ts` 1 条红 |

新增用例 27 条（287 → 314）。其中 `packages/runtime/tests/injection-defense.test.ts` 刻意**不直接调 `evaluate()`**，全部经由 `runTurn()` 只看落库事件——因为这次断掉的那一环恰恰是"判定对了但没长在调用路径上"，而只测 `evaluate()` 的用例对此完全免疫。

该文件里最关键的一条断言不是"判成了 deny"，是**"`git.push` 没有出现在 `tool.start` 里"**：闸门判了拒绝却照样执行，事件流看起来一模一样。

## 后果

**正面**

- 注入防御第一次真的在调用路径上生效，docs/06 §9 的验收项现在有对应的可执行用例
- 自改红线不再依赖被防对象的自我申报
- 用户手写的 deny 在任何档位下都拦得住
- 契约包 6.75 kB → 6.78 kB（预算 15 kB）

**负面**

- **`untrustedContext` 目前没有解除入口**，而 `PolicyEngine` 的拒绝文案已经承诺了"请显式解除本轮的不可信标记后重试"。这是一句还没兑现的话，且会自己长大：接上真实网页工具后，任何查过资料的会话都会永久失去做不可撤销操作的能力。列为 docs/09 G1，**M1 必须做**，需要一个新事件类型（状态必须完全由事件决定）。
- 自改红线从 9 条变 27 条。红线一多用户就会去找绕过的办法——这里的取舍是它们共用 9 个目标、面向的是同一件事，且全部落在 `appRoot` 内，不影响用户自己的工作区。
- `gui.capture` 进入不可信内容源，意味着截一次屏之后本会话的不可撤销操作全部收紧。这是刻意的，但它是本次三个能力里最可能引发"太吵"投诉的一个。

**未修，已记入 docs/09**

- **G2 污点传播的两个洞**：MCP 工具不声明 `net.fetch` 就标不出来；**子 Agent 的污点不会传回父会话**——把"读网页"派给子 Agent 正好是当前设计下绕过注入防御的完整路径。
- **G3 非路径能力的 target 没有规范化契约**（与 C4 同源）。在拿到契约之前，`shell.exec` / `net.fetch` 上的 target 匹配规则**不应被当作安全边界**。
- **G4 / G5 规模问题**：回放超线性 + `messages` 无上界 + IPC 全量物化。倾向是 M2 随 checkpoint 一起做状态快照，让 `readSession` 返回"快照 + 尾部增量"而不是整条历史。

**重新评估的触发条件**

- 引入 MCP 或子 Agent（G2 必须先解决，否则注入防御有已知绕过路径）
- 引入 `shell.exec` 或真实网络工具（G3 必须先解决）
- 单会话事件数进入万级（G4/G5 从"实测数字"变成"用户能感觉到的卡"）
