# ADR-0057 · 扩展事件通道与未知事件语义

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0008](./0008-事件持久化分层与演进.md) · [ADR-0052](./0052-插件容器与效果模型.md) · [ADR-0053](./0053-微内核的特权底座与扩展点边界.md) · [docs/10-契约设计](../10-契约设计.md)

## 背景

`packages/contracts/src/plugin/manifest.ts` 从 M0 起就有这个字段：

```ts
/** 插件自定义事件：类型名（不含 ext.<id>. 前缀）→ 持久化层级 */
events: z.record(z.string(), Durability).default({}),
```

**它至今没有任何消费者。** 而一旦插件真的存在，这个问题就绕不过去：插件要记录自己的持久状态
（技能被调用了、MCP server 断线重连了、后台任务的进度），它需要一个落点。

三条现有约束把可选空间压得很窄：

1. `EVENT_SPECS` 是**闭集**，`AnyEvent` 是判别联合，`reduce()` 有穷尽性检查。
   插件不能往里加成员——那等于让插件改契约包。
2. `durability` 是**静态标注**，理由写在 `registry.ts` 里：ADR-0008 的持久化包含性测试
   需要在不跑真实会话的前提下把事件流拆成两份。运行时决定层级会让那个测试失去意义。
3. `docs/05` 的扩展点红线第二条：**扩展不得修改内核状态或事件流，只能追加自己的事件。**

## 选项

### 选项 A：插件不写事件，自己管自己的存储

优点：契约完全不动。
缺点：插件状态与会话事件流分家，回放会话时插件状态对不上；`ADR-0013` 的单写者不变量
被绕过（第二个写者出现在同一个数据目录里）；而且"状态 = reduce(events)"对插件部分不再成立。

### 选项 B：动态注册事件类型，`EVENT_SPECS` 变成可运行时扩展的表

优点：插件事件与内建事件完全同构。
缺点：破坏上面三条全部。`AnyEvent` 不再是闭集，`reduce()` 的穷尽性检查失效；
静态 durability 拆流测试作废；而且插件能声明一个与内建事件同名的类型。

### 选项 C：两个静态信封 + 插件自有 schema

## 决策

**选择 C。**

### 一、两个信封类型，durability 保持静态

`EVENT_SPECS` 新增**两个**成员，此后不再为插件新增：

```
ext.persisted   durability: 'persisted'
ext.transient   durability: 'transient'
```

载荷同形：

```ts
{
  pluginId: string,     // 形如 "com.xiaoming.git"，与 PluginManifest.id 一致
  name: string,         // 不含前缀的事件名
  version: number,      // 该插件事件的载荷版本，演进规则同 ADR-0008
  data: unknown         // 由插件注册的 Zod schema 校验
}
```

事件的完整标识是 `ext.<pluginId>.<name>`，但**类型字段只有两个取值**。这样：
判别联合仍是闭集，`reduce()` 的穷尽性检查仍然成立，ADR-0008 的拆流测试仍然只看
静态 `durability`——三条约束一条没破。

### 二、未声明即拒绝写入（失败关闭）

插件写一条 `ext.*` 事件时，运行时按 `pluginId` + `name` 去它的 `PluginManifest.events` 里查：

- 查不到 → **当场拒绝写入并报错**，不静默丢弃、不猜一个层级。
  与网关"声明了路径能力却没声明 `pathInputs` 就当场失败关闭"是同一个形状、同一个理由：
  不知道这条事件该不该持久，就不能替它决定。
- 查到的层级与实际写入的信封不符 → 同样拒绝。
- `data` 不过插件注册的 Zod schema → 拒绝并记录。校验失败即抛出，**不静默兜底**
  （契约单一来源那条不变量）。

`pluginId` 由运行时按写入者的身份填，**不由插件自己填**——否则一个插件可以冒充另一个插件
写事件，而事件流是审计的底稿。

### 三、`reduce()` 对 `ext.*` 是恒等

核心 `SessionState` **不因插件事件而改变**，一个字段都不加。这直接落实 `docs/05` 的红线第二条。

插件要投影自己的状态，就订阅事件流自建投影，并通过自己注册的服务把投影暴露给消费者
（UI 经 IPC 取，两侧仍走 Zod 校验）。好处是：一个插件的投影写错了，
炸的是它自己的面板，不是整个会话状态。

**未知 `pluginId` 的处理**：读一个装着某插件事件、而该插件当前没装的历史会话时，
`reduce()` 照样恒等，事件**留在日志里不丢**，UI 显示为"来自未安装的扩展 `<pluginId>` 的记录"。
不报错、不清理——历史事件流是只增不改的（ADR-0008），删掉别人的记录是更糟的选择。

### 四、seq 仍由 `SessionRuntime` 单点分配

插件事件与内建事件共用同一条序列。ADR-0013 不变量三不因为写入者变多而放松：
插件拿到的是一个窄写入口（`ctx.session.recordExt(name, data)`），
**不是 `record()` 本身**——与 ADR-0041 给 todo 工具的窄回调同一个形状，
理由也一样：给出通用事件入口，等于让插件能伪造 `tool.end`。

## 后果

- **正面**：插件有了合法的持久状态落点，且不破坏任何一条现有不变量。
  `PluginManifest.events` 第一次有真实消费者。
- **正面**：插件事件与内建事件在同一条 seq 上，回放、审计、崩溃恢复自动覆盖它们。

- **负面**：插件事件在 `AnyEvent` 上的类型是 `ext.persisted` / `ext.transient`，
  消费者要先按 `pluginId` + `name` 二次分派。比原生事件多一层。可接受——
  代价换来的是闭集与穷尽性检查。
- **负面**：`data: unknown` 意味着 contracts 包本身对插件载荷零类型信息。
  插件自己导出类型给自己的消费者用；跨插件消费别人的事件，属于耦合，不鼓励也不禁止。

- **代价与缓解**：一个插件可以用 `ext.transient` 高频刷事件，占满总线。
  缓解：与 `message.delta` 一样不落库、不占 seq；若出现真实滥用，
  按 `docs/05` 红线第三条（扩展失败不得中断主循环）加频率限制，届时另写 ADR。

- **必做的反向演练**：
  1. 写一条清单里没声明的 `ext` 事件 → 必须当场拒绝，不得静默丢弃。
  2. 插件伪造 `pluginId` 冒充别人 → 运行时按身份覆盖，伪造无效。
  3. 插件试图通过 `recordExt` 写一条 `tool.end` → 接口上做不到。
  4. 读一个含未安装插件事件的历史库 → `reduce()` 恒等、事件不丢、UI 有说明。
  5. 声明 `persisted` 却写进 `ext.transient` 信封 → 拒绝。

- **重新评估条件**：如果插件普遍需要往核心 `SessionState` 里加字段（而不是自建投影），
  说明那个字段本来就该是内建事件——把它提升进 `EVENT_SPECS`，而不是放开红线第二条。
