# ADR-0062 · 扩展点的异步契约与执行收据

- **状态**：🟢 Accepted
- **日期**：2026-08-14
- **相关**：[ADR-0052](./0052-插件容器与效果模型.md) · [ADR-0055](./0055-Turn驱动器的扩展点契约.md) · [ADR-0053](./0053-微内核的特权底座与扩展点边界.md) · [ADR-0013](./0013-存储引擎选型与EventStore端口.md)

## 背景

M3 规划复审（2026-08-14）在扩展点契约上抓到两个未闭合的口子。两个都不是笔误，
是**决策没做完就写成了 Accepted**。

**一、`waterfall` 的异步语义自相矛盾。**
[ADR-0052](./0052-插件容器与效果模型.md) 的派发模式表把 `waterfall` 标成"是否 await：否"，
但 [ADR-0055](./0055-Turn驱动器的扩展点契约.md) 让它承载的全是异步工作：
⑧ `tool/execute` 要环绕写前 checkpoint 与工具体执行，`llm/stream` 要包住流式读取，
`turn/step-error` 要决定重试。一个不 await 的派发模式做不了这些事——
表错了，不是 ADR-0055 用错了。

顺带没定的还有三件，每件都会在第一次真实故障时变成排查地狱：
监听器抛异常怎么传播、取消（`AbortSignal`）怎么穿过链条、同一个扩展点在一次调用里
被重入（例如 Code Mode 的子调用）算不算合法。

**二、"跳过 `next()` 返回伪造成功"至今不是一个决定。**
ADR-0055 的反向演练第 4 条写的是：

> 一个 `tool/execute` 环绕插件试图跳过 `next()` 直接返回伪造成功 → 结果必须被
> ⑫ 的审计识别为"没有真实执行"，**或在结构上做不到（优先做不到）**。

"或"就是没定。而这条的后果不小：⑧ 是环绕中间件，它天然有能力不调 `next()` 就编一个
`{ ok: true }` 回去。此时前面的判定全都通过了、审计里也会记一条成功的 `tool.end`，
但**工具体从未执行**。对模型来说这是幻觉输入，对用户来说这是一条骗人的审计记录——
后者更严重，因为事件流是本仓库所有事后追责的底稿。

## 选项

### 选项 A：`waterfall` 保持同步，异步工作另开一个派发模式

优点：同步派发实现简单，没有并发时序问题。
缺点：会长出 `asyncWaterfall`，而它与 `waterfall` 的区别只有一个 `await`——
两个几乎同名的模式是最容易被写错的那种 API。且 ADR-0052 已经写明四种模式是
"被验证过的正交集合"，加第五种就破了这个说法。

### 选项 B：`waterfall` 统一为异步，伪成功靠审计事后识别

优点：改动最小，只改一张表加一条审计规则。
缺点：事后识别意味着**伪造成功已经进了事件流**才被发现。而 ⑫ 只能看到"结果长什么样"，
看不到"它是不是真的跑过"——一个足够像样的伪造结果在 ⑫ 那里与真结果无法区分。
把安全性押在"审计能看出来"上，正是本仓库反复批评的形态。

### 选项 C：`waterfall` 统一为异步 + 真实执行签发不可伪造的执行收据

## 决策

**选择 C。**

### 一、四种派发模式的异步契约（修正 ADR-0052 的表）

| 模式 | 是否 await | 顺序 | 有返回值 | 监听器签名 |
|---|---|---|---|---|
| `emit` | 否（fire-and-forget） | 注册序 | 否 | `(...args) => void` |
| `waterfall` | **是** | 注册序，环绕中间件 | 是 | `(...args, next) => R \| Promise<R>` |
| `parallel` | 是 | 并发 | 否 | `(...args) => void \| Promise<void>` |
| `serial` | 是 | 注册序 | 是 | `(...args) => R \| Promise<R>` |

`waterfall` 从"否"改为"**是**"。这是本 ADR 对 ADR-0052 的唯一修正，其余四项语义不变。
`emit` 仍不 await——它是通知，不是链条；监听器里的异步工作由监听器自己负责，
派发方不等待也不感知。

### 二、错误、取消、重入三条传播规则

1. **错误即中止，不吞。** `waterfall` / `serial` 中任一监听器抛出，整条链立即中止，
   异常原样上抛给派发方（不包装成 `{ ok: false }`，也不替换成默认值）。
   派发方按它所在的步骤决定后果：工具链上的抛出等于这次调用失败，
   `turn/*` 上的抛出等于这一步失败并进 `turn/step-error`。
   **`parallel` 是唯一的例外**：它是扇出观察，一个观察者炸掉不该影响其它观察者，
   因此收集全部结果后再抛聚合错误，且不影响主流程——与 `docs/05` 红线第三条
   "扩展失败不得中断主循环"一致。
2. **取消是第一个参数，不是环境变量。** 所有 await 型派发的参数里必须带 `AbortSignal`，
   由派发方提供、监听器只读。⑧ 的环绕插件**可以替换为一个更短的 signal**
   （ADR-0055 已允许），但驱动器在进入 ⑨ 之前把原始 signal 接回——
   插件缩短截止时间是合法的，延长或摘掉不是。

   > **2026-08-15 定案（M3-c 复审）**：收紧的入口是 `next(narrower?)`，容器把递进来的每一个
   > signal 与当前生效的那个**取并集**。"接回原始 signal"因此不是驱动器事后补的一步，
   > 而是并集的固有性质——延长或摘掉在结构上做不到。详见
   > [ADR-0055](./0055-Turn驱动器的扩展点契约.md) §一硬约束 3 的定案块。
   >
   > 同批发现并修掉的一条连带缺陷：**用户点停止最常见的时机是"工具正跑着"**，
   > 而本条规则让扩展点派发对已 abort 的 signal 一律抛。工具执行完紧接着的
   > `turn/stopping` 于是把整个 `runTurn` 掀成异常，而不是干净地返回 `'aborted'`。
   > 取消要在派发扩展点**之前**由驱动器兑现成 `'aborted'`——停止是驱动器的固有责任
   > （ADR-0055 §四），不能指望插件替它兜。
3. **重入必须显式允许。** 同一个扩展点在一次调用的调用栈内被再次派发（Code Mode 的
   子调用是唯一已知场景，ADR-0061），容器按**独立的一次派发**处理，不做去重、不做合并。
   监听器若持有跨派发的可变状态，那是监听器自己的 bug——容器不提供"这是第几层"这类
   上下文，因为提供了就会有人依赖它写出只在第一层正确的逻辑。

### 三、执行收据（ExecutionReceipt）

工具执行链的第 ⑨ 步——也就是**驱动器真正调用工具体的那一处**——签发一枚收据，
随结果一路传到 ⑫：

```
ExecutionReceipt
  callId       这次调用的 id
  issuedAt     由 ctx.clock 提供（ADR-0066）
  toolName     实际被执行的工具
```

三条规则：

1. **只有驱动器能签发。** 收据的类型带一个模块私有的 brand，插件拿不到构造入口——
   这就是 ADR-0055 说的"优先做不到"，现在把它兑现成一个具体机制而不是一句期望。
2. **⑫ 见到没有收据的结果，判定为"未真实执行"**：不落 `tool.end` 的成功分支，
   改落一条失败结果并在审计里指名是哪个插件短路了链条。
3. **收据不跨进程、不落库。** 它是进程内的执行凭证，不是审计记录本身；
   审计要的那条信息（"这次调用真的跑过"）由 ⑫ 的判定结果表达。

> **2026-08-15 补记（M3-c 复审）**：规则 1 只写了"只有驱动器能签发"，实现照做了
> （模块私有 `WeakSet`，插件构造不出来），但**验收时只查了出处，没查身份**——
> 于是一个环绕插件把上一次真实执行拿到的收据缓存下来、挂到下一次短路结果上就能通过：
> 收据是真的，执行没发生，⑫ 照常落成功分支。
>
> `callId` / `toolName` 两个字段本来就是为绑定而存在的，不比对等于没写。
> 定案：**⑫ 的判定是"出自驱动器 **且** 就是这一次调用的那一枚"**，三者全中才算真实执行。
> 反向演练：一次真实调用 + 一次挂着前一枚收据的短路调用，后者必须失败关闭
> （`packages/runtime/tests/turn-extensions.test.ts`）。

跳过 `next()` 本身**仍然是合法的**——一个环绕插件当然可以决定"这次不执行"
（超时、熔断、干跑模式都是正当理由）。收据要挡的不是短路，是**短路之后谎称执行过**。
两者的区别正是收据能表达而审计表达不了的那一点。

## 后果

- **正面**：`waterfall` 能承载 ADR-0055 派给它的全部工作，扩展点契约第一次是自洽的。
- **正面**：ADR-0055 反向演练第 4 条从"或"变成一个可写测试的断言：
  构造一个跳过 `next()` 返回伪造成功的插件，⑫ 必须把它判为未执行。

- **负面**：`waterfall` 每一层多一次 `await`，深链条上有微小开销。可接受——
  这条链的实际耗时由工具体与模型往返支配，不由派发次数支配。
- **负面**：收据是一个只为防御而存在的字段，读代码的人会问"这玩意干嘛的"。
  缓解：它的存在理由写在本 ADR，且 ⑫ 的判定代码必须注释指回这里。

- **代价与缓解**：错误"不吞"意味着一个写得差的插件能让整次调用失败。这是有意的——
  静默降级会让插件的 bug 以"工具偶尔不生效"的形态存在半年。缓解：装配期与
  `--dump-config` 能看到谁挂在哪个点上，出问题时第一现场明确。

- **必做的反向演练**：
  1. `tool/execute` 环绕插件跳过 `next()` 返回伪造成功 → ⑫ 必须判为未真实执行，
     且 `tool.end` 不得出现成功分支。**这一条是本 ADR 的立身之本。**
  2. `waterfall` 监听器里 `await` 一个永不 resolve 的 Promise + 触发 `AbortSignal`
     → 链条必须能被取消，不能挂死。
  3. `parallel` 的一个观察者抛出 → 其余观察者仍执行完毕，主循环不受影响。
  4. `serial` / `waterfall` 的一个监听器抛出 → 整条链中止且异常原样上抛，
     **不许被替换成默认值**。
  5. 插件试图自己构造一枚 `ExecutionReceipt` → 类型上就拿不到构造入口。

- **重新评估条件**：如果出现一个正当场景，需要在 `waterfall` 里做"部分失败继续"，
  先问它是不是应该改用 `parallel`。如果确实需要有序且容错的链条，
  那说明缺的是第五种模式，届时单独补 ADR——不要在 `waterfall` 上加容错开关。
