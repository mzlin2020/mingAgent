# ADR-0008 · 事件契约：持久化分层、Schema 演进与 Trace 分离

- **状态**：🟢 Accepted
- **日期**：2026-08-04
- **相关**：[10-契约设计 §4](../10-契约设计.md)、[04-总体架构 §6 §8](../04-总体架构.md)、[07-自我迭代能力](../07-自我迭代能力.md)、[02 §2.4](../02-参考项目评审-manusAgent.md)

## 背景

原则六要求"会话状态 = `reduce(events)`，不允许存在只写内存不写事件的状态"。字面执行会得出结论：所有事件都要落库，包括 token 级的 `message.delta`。

算一下量级：一次 1000 轮长会话，模型输出按每轮 800 token 计，delta 事件约 80 万条；加上工具进度事件，百万级。这会带来三个问题：写放大让事件表比实际信息大两个数量级；`reduce` 与回放被拖慢到不可用；参考项目 2.4 的 O(n²) 问题会以另一种形式重现。

但简单地"不存 delta"会引出下一个问题：那"可回放"还成立吗？评测与调试需要还原模型当时逐 token 的行为。

同时还有一个必须现在解决的问题：**事件是永久数据，schema 会变**。三个月后加一个字段、改一个语义，旧事件流还能不能 reduce？这件事没有第二次机会——等到有了半年的历史数据再补迁移机制，成本是现在的十倍。

## 选项

### A. 全部落库
- 优点：字面满足"状态即事件"，回放天然全保真
- 缺点：写放大与回放性能不可接受；且 delta 不携带终态信息，存的是冗余

### B. 只存终态事件，放弃 token 级回放
- 优点：事件表紧凑，reduce 快
- 缺点：无法复现模型的流式行为，评测与"为什么它那时那样做"的调查失去材料

### C. 分层：事件表存状态，独立的 trace 存全保真
- 优点：两个用途各用合适的存储，互不拖累
- 缺点：两套记录，需要一条硬不变量防止它们语义漂移

## 决策

选择 **C**，并配以三条强制规则。

### 1. 事件分持久 / 瞬态两层

每个事件类型在 `event/registry.ts` 里静态标注 `durability: 'persisted' | 'transient'`。瞬态事件只走内存总线推给订阅者，不落库。

**硬不变量**：*transient 事件不得携带 persisted 事件流中不存在的信息。*

这条用 CI 测试强制：跑脚本化会话，对「完整流」与「仅 persisted 流」分别 reduce，两者在持久化投影上必须逐字节相等。**没有这条测试，分层就是在给未来埋一个"重启后状态少了一块"的幽灵 bug。**

### 2. Trace 与事件表分离

需要 token 级保真时开启 trace 模式，写入独立的、可轮转的 trace 文件。

- **事件表管状态**：紧凑、永久、是真相
- **trace 管取证**：全保真、可轮转删除、只在需要时开启

两者不混用。混用的后果是：为了取证保留 trace 就得永久保留百万行事件，为了性能删事件就丢了状态。

### 3. Schema 演进：版本 + upcaster + fixture 回归

- 信封带 `v`（该事件类型的 payload 版本）
- 加**可选**字段 → `v` 不变
- 加必填字段 / 改语义 / 删字段 → `v` 加一，**必须**同时提供 `upcasters[v] → v+1`
- 读取路径：按存储的 `v` 逐级升到当前版本，再校验
- `fixtures/events/v*/` 归档各版本样本，CI 强制"所有历史 fixture 都能 parse + reduce 出预期状态"

### 4. 派生决策：事件 payload 用宽松 object，工具入参用 strictObject

这看似违反原则四（严格校验、禁止静默丢弃），实则是两个不同场景：

- 模型给的工具入参：未知字段 = 模型幻觉，静默丢弃会让它误以为参数生效（参考项目 2.7 的坑）→ **严格拒绝**，`z.strictObject()`
- 落库的事件 payload：未知字段 = 版本漂移，丢弃等于**永久损坏数据** → **保留**，`z.looseObject()`

> **实测补充（2026-08-04 冒烟）**：这里必须显式写 `z.looseObject()`。Zod 的默认 `z.object()` 是 **strip 模式，静默丢弃未知字段**——不报错、不告警，数据就那样没了，正是本条要防的事故本身。冒烟中该项一次未过，是本次验证最有价值的发现。
>
> 同时确认 `looseObject` 放进 `discriminatedUnion` 后判别正常、未知字段保留、未知判别值仍被拒，嵌套层也保留——这套组合可以直接用。

### 5. 派生决策：子 Agent 不共享父会话的 seq 空间

`seq` 必须是会话内单调无空洞的整数（增量订阅、UI 重连、回放都依赖它），这要求单写者。并发子 Agent 会破坏这个前提。

因此子 Agent 拥有自己的 `sessionId`（`parent_session_id` + `parent_call_id` 指回父），父会话日志里只有 `subagent.start` / `subagent.end`。附带收益：子 Agent 的上下文隔离在存储层是真实的，且其 trace 可独立回放。

## 后果

**正面**
- 事件表规模与"真实发生的事"成正比，长会话不劣化，直接支撑质量标线里的"1000+ 轮"
- 全保真回放能力保留，且开销只在需要时付
- Schema 演进有明确路径，第一天就有，不用等到有历史包袱时补
- 单写者 + `PRIMARY KEY(session_id, seq)` 让并发写变成插入冲突，即时暴露而非静默损坏

**负面**
- 多一层概念（持久/瞬态），新增事件类型时必须想清楚归属，容易想错
- upcaster 是永久债务：v5 的代码要维护 v1→v2→…→v5 的全部升级链
- fixture 集会持续增长，每次发版都要新增归档

**缓解措施**
- 归属想错的防线就是那条包含性测试——想错了 CI 会红，不依赖人的自觉
- upcaster 链长到影响可读性时（经验阈值：单类型 5 个版本以上），做一次离线批量迁移把历史数据升到当前版本，然后删除旧 upcaster，并写 ADR 记录
- fixture 只保留每个 minor 版本的一份代表性会话，不是全量归档

**重新评估的触发条件**
- 包含性测试反复因为"合理的例外"而被放宽 → 说明分层边界划错了，需重新划分
- trace 从未被真正使用 → 说明可以简化为方案 B，省掉一套存储
