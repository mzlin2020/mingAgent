# 10 · 契约设计 · `@xm/contracts`

> 本文是 M0 的**实现级规格**，不是草案。这里写的 schema 直接对应第一批代码。
>
> 为什么这个包值得单独一篇：`@xm/contracts` 是整个系统唯一的事实来源，且**事件一旦落库就是永久格式**。内核可以重写、UI 可以换、Provider 可以删，但三个月前的事件流必须还能 reduce 出正确状态。返工成本在所有包里最高，所以它必须第一个定死。

---

## 0. 铁律

| # | 规则 | 检查方式 |
|---|---|---|
| 1 | 依赖只有 `zod`，不得出现 `node:*`、`electron`、任何其它 `@xm/*` | `depcruise` + `package.json` 白名单 |
| 2 | 只导出**数据**：schema、推导类型、纯常量、纯函数（校验/升级/脱敏）。**不导出任何含 I/O 或状态的东西** | 代码审查 + 包内禁止 `async` 顶层导出（lint 规则） |
| 3 | 每个导出同时有 schema 和类型，类型**从 schema 推导**，禁止手写 `interface` 再手动对齐 | 约定 + 审查 |
| 4 | 跨进程传输的一切必须在这里有 schema。渲染层禁止手写事件类型 | `depcruise`：renderer 不得定义 `*Event` 类型 |
| 5 | 该包必须能在浏览器里 `import` 且体积 < 100KB（min+gzip） | size-limit，CI 阻断 |

**命名约定**：schema 与类型同名（`export const XmEvent = ...; export type XmEvent = z.infer<...>`）。TS 的类型/值命名空间分离让这个写法合法，且调用点不用记两个名字。

## 2. 基础类型

### 2.1 ID

```ts
// base/ids.ts
const uuid = z.uuid();   // 仅约束格式，不约束版本

export const SessionId = uuid.brand<'SessionId'>();
export const EventId   = uuid.brand<'EventId'>();
export const TurnId    = uuid.brand<'TurnId'>();
export const MessageId = uuid.brand<'MessageId'>();
export const CallId    = uuid.brand<'CallId'>();   // 工具调用
export const RequestId = uuid.brand<'RequestId'>(); // 权限请求
export const AgentId   = uuid.brand<'AgentId'>();
export const CheckpointId = uuid.brand<'CheckpointId'>();

export type SessionId = z.infer<typeof SessionId>;
// ...

// ⚠️ 不要写成泛型工厂 `newId<T extends string>()`。类型参数只在返回值出现一次，
//    等于伪装的类型断言，调用点写错品牌也不会报错。typed lint 的
//    no-unnecessary-type-parameters 会直接拦下（2026-08-04 冒烟实测抓到）。
//    改为逐类型的显式构造器——多几行，但调用点无法写错。
const rawId = () => globalThis.crypto.randomUUID();
export const newSessionId = (): SessionId => rawId() as SessionId;
export const newEventId   = (): EventId   => rawId() as EventId;
export const newCallId    = (): CallId    => rawId() as CallId;
// ...
```

两个决定：

**用品牌类型。** `sessionId: string` 和 `callId: string` 在类型系统里没有区别，参数传反了编译器一声不吭——这类 bug 在事件系统里极难查（数据写进了错误的会话）。品牌化零运行时成本，纯类型层收益。

**用 UUIDv4，不追求可排序 ID。** 有人会想用 ULID/UUIDv7 让 ID 天然有序。不需要：会话内顺序由 `seq` 保证，跨会话顺序由 `ts` 保证，ID 只需唯一。`crypto.randomUUID()` 在 Node 与浏览器都是全局可用，零依赖——这条对铁律 1 很重要。

### 2.2 错误

```ts
// base/error.ts
export const ErrorCode = z.enum([
  'invalid_input',      // schema 校验失败（含模型幻觉参数）
  'not_found',
  'policy_denied',      // 策略闸门拒绝
  'user_rejected',      // 用户在审批弹窗点了拒绝
  'permission_denied',  // 操作系统层面拒绝（EACCES 等）
  'aborted',            // 用户主动停止
  'timeout',
  'executor_failed',    // 执行器层面失败（容器起不来、SSH 断了）
  'provider_error',     // 模型侧错误
  'rate_limited',
  'context_overflow',
  'tool_not_found',
  'unsupported',        // 当前平台/执行器不支持该能力
  'internal',
]);

export const XmError = z.object({
  code: ErrorCode,
  message: z.string(),          // 面向用户，中文
  retryable: z.boolean(),
  detail: z.record(z.string(), z.unknown()).optional(),  // 结构化上下文
  causeChain: z.array(z.string()).optional(),            // 原始错误的字符串化链
});
```

**`policy_denied` / `user_rejected` / `permission_denied` 必须分开。** 三者的用户处置完全不同：改策略、重新审批、改系统权限。参考项目全部揉成一个字符串，导致 UI 无法给出正确的下一步引导。

**错误不跨越主循环抛出。** 工具失败一律转成 `tool_result{ isError: true }` 回灌给模型——模型有机会换个方式重试，这是 Agent 能力的重要来源。只有内核自身的不变量被破坏才 throw。

### 2.3 BlobRef

```ts
// base/blob.ts
export const BlobRef = z.object({
  hash: z.string().regex(/^[a-f0-9]{64}$/),  // sha256，内容寻址
  mime: z.string(),
  size: z.number().int().nonnegative(),
  name: z.string().optional(),               // 原始文件名，仅展示用
});
```

规则：**事件与消息里永远不放二进制或大文本，只放 `BlobRef`**。截图、附件、超长命令输出全部进 blob 表。内容寻址意味着同一张截图在一次会话里出现十次只存一份。

## 3. 内容块与消息

```ts
// content/block.ts

// 能出现在工具结果里的块（不含 tool_use/tool_result，避免递归）
export const ResultBlock = z.discriminatedUnion('type', [
  z.object({ type: z.literal('text'),     text: z.string() }),
  z.object({ type: z.literal('image'),    source: BlobRef }),
  z.object({ type: z.literal('document'), source: BlobRef }),
]);

export const ContentBlock = z.discriminatedUnion('type', [
  z.object({ type: z.literal('text'),     text: z.string() }),
  z.object({ type: z.literal('image'),    source: BlobRef }),
  z.object({ type: z.literal('document'), source: BlobRef }),

  // 思考块：signature 必须原样回传，否则多轮工具调用会被模型侧拒绝
  z.object({ type: z.literal('thinking'), text: z.string(), signature: z.string().optional() }),
  z.object({ type: z.literal('redacted_thinking'), data: z.string() }),

  z.object({ type: z.literal('tool_use'),  id: CallId, name: z.string(), input: z.unknown() }),
  z.object({
    type: z.literal('tool_result'),
    toolUseId: CallId,
    content: z.array(ResultBlock),
    isError: z.boolean(),
  }),
]);
```

三个要点：

1. **`tool_result.content` 用 `ResultBlock` 而非 `ContentBlock`**。递归类型要 `z.lazy()`，而 `z.lazy` 生成的 JSON Schema 带 `$ref`，跨进程与给模型时都会掉坑。用非递归子集把问题从根上消掉——工具结果里嵌套工具调用本来也没有语义。

2. **`redacted_thinking` 从第一天就在。** 它看起来是 Anthropic 的私有细节，但漏了它会导致开启扩展思考后的多轮工具调用整体失败，且报错信息晦涩。参考项目连普通 thinking 都没有。

3. **`tool_use.input` 是 `z.unknown()`。** 契约层不知道具体工具的入参形状，校验发生在 ToolRegistry 拿到工具自己的 schema 之后。这里如果试图 `z.record()` 就会限制入参必须是对象——大部分是，但不该由契约层强加。

```ts
// content/message.ts
export const Role = z.enum(['user', 'assistant']);

export const Message = z.object({
  id: MessageId,
  role: Role,
  blocks: z.array(ContentBlock),
  model: z.string().optional(),        // assistant 消息记录来自哪个模型
  tokens: z.number().int().optional(), // 计算后缓存，用于上下文预算
  ts: z.number().int(),
});
```

**只有两个 role。** 工具结果作为 `tool_result` 块放进 `user` 消息——这与 Anthropic 的 wire format 一致，是我们中立模型的形状。OpenAI 适配器负责把它拆成独立的 `tool` role 消息。选 Anthropic 形状为中立层，是因为它的块模型表达力更强（拆容易、合难）。

**system prompt 不是 Message。** 它由 ContextBuilder 组装成 `SystemSegment[]`（见 §7），因为它需要携带缓存断点信息，而普通消息不需要。

## 4. 事件契约

### 4.1 信封

> 🔴 **信封本身也用 `z.looseObject()`**（ADR-0011 ④ 修正下面示例里的 `z.object`）。
> "未知字段 = 版本漂移，丢弃 = 永久损坏数据"这条理由对信封层同样成立。
> 已实测 `.extend()` 保留宽松性，判别联合照常工作。

```ts
// event/envelope.ts
export const EventEnvelope = z.looseObject({
  id: EventId,
  sessionId: SessionId,
  seq: z.number().int().positive(),   // 会话内从 1 递增，无空洞
  ts: z.number().int(),               // epoch ms，仅供展示与排序参考
  turnId: TurnId.optional(),          // 归属回合；会话级事件无此字段
  type: z.string(),
  v: z.number().int().positive().default(1),  // 该 type 的 payload 版本
  payload: z.unknown(),
});
```

**`seq` 的分配规则（关键不变量）**：

- 一个会话在同一时刻**只允许一个写者**。会话打开时在 `sessions` 表上取排他标记（含进程 PID + 启动时间，用于识别陈旧标记）。
- `seq` 是会话内单调递增、**无空洞**的整数。持久化表 `PRIMARY KEY(session_id, seq)` 天然充当并发写检测——插入冲突即说明有第二个写者，属于必须立刻崩溃的不变量破坏，不做重试。
- 无空洞是为了让"从 seq N 开始增量订阅"这件事无需额外元数据。UI 重连、CLI attach、评测回放都靠它。
- **瞬态事件不占用 seq 空间**（ADR-0011 ③）。`seq` 是**持久化流**的位置；瞬态事件携带的 seq 等于当时已持久化的最大 seq，仅供 UI 排序参考，`reduce` 处理它们时连 `lastSeq` 都不推进。否则 `events` 表必然出现空洞，上一条就不成立了。

**子 Agent 不共享父会话的 seq 空间。** 子 Agent 拥有自己的 `sessionId`（`sessions.parent_session_id` 指回父会话，`parent_call_id` 指回派生它的工具调用），父会话的日志里只有 `subagent.start` / `subagent.end`。这样单写者规则不被并发子 Agent 破坏，子 Agent 的上下文隔离在存储层也是真实的，且子 Agent 的 trace 可以被独立回放。

### 4.2 持久化分层 → [ADR-0008](./adr/0008-事件持久化分层与演进.md)

事件分两类，在注册表里静态标注：

| 层 | 含义 | 例子 |
|---|---|---|
| `persisted` | 落 `events` 表，永久保存，是状态的真相 | `turn.start`、`message.end`、`tool.start/end`、`permission.*` |
| `transient` | 只走内存总线推给订阅者，**不落库** | `message.delta`、`thinking.delta`、`tool.progress` |

**为什么必须分层**：一次 1000 轮的长会话，token 级 delta 有百万量级。全部落库会让事件表膨胀两个数量级，reduce 与回放都被拖垮，而它们**不携带任何终态信息**——`message.end` 里有完整消息，`tool.end` 里有完整结果。

**硬不变量**：*transient 事件不得携带 persisted 事件流中不存在的信息。*

这条用测试强制：跑一个脚本化会话，分别对「完整流」和「仅 persisted 流」做 reduce，两者在持久化投影上必须逐字节相等。这个测试在 M0 就要写——它是防止未来某人图省事把关键状态只放进 delta 的唯一屏障。

**全保真回放走 trace，不走事件表。** 需要 token 级还原（评测、复现模型行为）时，开启 trace 模式，写到独立的、可轮转的 trace 文件。**事件表管状态，trace 管取证**，两者不要混。详见 [07 文档](./07-自我迭代能力.md)。

### 4.3 事件全集

```ts
// event/payloads.ts   —— 每条 payload 后标注 [P]=persisted [T]=transient

// ── 会话 ────────────────────────────────────────────────
'session.created'   [P]  { cwd: string; modelRef: string; title?: string }
'session.title'     [P]  { title: string }
'session.config'    [P]  { patch: ConfigPatch }         // 会话内配置覆盖

// ── 回合 ────────────────────────────────────────────────
'turn.start'        [P]  { turnId: TurnId; input: ContentBlock[] }
'turn.end'          [P]  { turnId: TurnId; reason: StopReason }

// ── 模型消息 ─────────────────────────────────────────────
'message.start'     [P]  { messageId: MessageId; role: Role; model?: string }
'message.delta'     [T]  { messageId: MessageId; blockIndex: number;
                           kind: 'text' | 'thinking'; text: string }
'message.end'       [P]  { message: Message }
'message.interrupted' [P] { messageId: MessageId; reason: 'aborted' | 'crash' }

// ── 工具 ────────────────────────────────────────────────
'tool.start'        [P]  { callId: CallId; messageId: MessageId; name: string;
                           input: unknown; risk: RiskLevel; capabilities: Capability[] }
'tool.progress'     [T]  { callId: CallId; message?: string; data?: unknown }
'tool.end'          [P]  { callId: CallId; ok: boolean; durationMs: number;
                           forModel: ResultBlock[];       // 已截断，就是喂给模型的原文
                           fullRef?: BlobRef;             // 未截断全文（若发生截断）
                           display?: DisplayHint;
                           error?: XmError }

// ── 权限 ────────────────────────────────────────────────
'permission.request'  [P] { requestId: RequestId; callId?: CallId;
                            capability: Capability; target: string;
                            risk: RiskLevel; reason: string; preview?: DisplayHint }
'permission.decision' [P] { requestId: RequestId; effect: 'allow' | 'deny';
                            scope: 'once' | 'session' | 'always';
                            by: 'policy' | 'user'; ruleId?: string }

// ── 任务与子 Agent ────────────────────────────────────────
'todo.updated'      [P]  { todos: Todo[] }
'subagent.start'    [P]  { agentId: AgentId; childSessionId: SessionId;
                           callId: CallId; purpose: string }
'subagent.end'      [P]  { agentId: AgentId; ok: boolean; summary: ResultBlock[] }

// ── 上下文与运维 ──────────────────────────────────────────
'context.compacted' [P]  { fromSeq: number; toSeq: number; summaryRef: BlobRef;
                           tokensBefore: number; tokensAfter: number }
'usage.recorded'    [P]  { turnId: TurnId; provider: string; model: string;
                           usage: Usage; costUsd: number }
'checkpoint.created'  [P] { checkpointId: CheckpointId; kind: 'fs' | 'git';
                            ref: string; label: string }
'checkpoint.restored' [P] { checkpointId: CheckpointId }
'notice.posted'     [P]  { level: 'info' | 'warn'; code: string; message: string }
'error.raised'      [P]  { error: XmError; fatal: boolean }
```

> **事件名一律 `<实体>.<动作>`，没有裸名。** `usage` / `notice` / `error` 曾是裸名，
> 2026-08-04 落库前改掉（ADR-0012 ⑨）。理由不是整齐：`ext.` 前缀机制、UI 按前缀订阅、
> 策略按前缀匹配，全都建立在"每个事件名都有前缀"这个假设上，裸名是这套机制里的特例。
> **改名的窗口只有落库前这一次**——第一条事件写进 SQLite 之后，改名就要写 upcaster 了。

三处值得单独说：

**`tool.end.forModel` 存的是截断后的原文，不是引用。** 因为回放上下文时必须逐字节还原当时喂给模型的内容——存引用会让"当时模型看到了什么"依赖 blob 表的存活状态。全文另存 `fullRef`。这点看起来冗余，但它是"可回放"这条原则能否成立的分水岭。

**`context.compacted` 必须是持久事件。** 压缩改变了后续所有轮次的输入，不记录就永远无法解释"为什么那一轮模型忘了前面的事"。这是参考项目完全缺失的一类可观测性。

**`notice` 是给 ADR-0007 的保险 2 准备的。** 比如 Linux 无 keyring 环境下 SecretStore 退化，必须有一条持久化的、用户可见的记录，而不是一行 console.warn。

### 4.4 扩展事件

插件需要自定义事件（自带面板的状态更新）。约定：

```ts
'ext.<pluginId>.<name>'   [P|T 由插件清单声明]   payload: unknown
```

核心不校验 `ext.*` 的 payload，由插件清单里声明的 schema 在插件宿主边界校验。核心的 reducer 遇到 `ext.*` 一律忽略（只转发给订阅了该插件的渲染器）。**核心状态永远不依赖扩展事件**——否则删掉插件就无法 reduce 历史会话，直接违反原则二。

### 4.5 版本演进与 upcaster

事件永久保存，schema 却会变。规则：

1. **加可选字段** → `v` 不变。老数据 parse 通过（缺省），新数据老代码忽略多余字段。
2. **加必填字段 / 改字段语义 / 删字段** → `v` 加一，且必须提供 upcaster。

```ts
// event/registry.ts
type EventSpec = {
  schema: z.ZodType;
  durability: 'persisted' | 'transient';
  version: number;                                   // 当前版本
  upcasters?: Record<number, (old: unknown) => unknown>;  // v → v+1
};

export const EVENTS: Record<XmEventType, EventSpec> = { /* ... */ };

/** 读取路径：先按存储的 v 逐级升到当前版本，再校验 */
export function parseStoredEvent(row: EventRow): XmEvent { /* ... */ }
```

**事件 payload 用 `z.looseObject`，工具入参用 `z.strictObject`。** 这条与原则四（严格校验、禁止静默丢弃）看似矛盾，实则是两个不同场景：

| 场景 | 构造 | 未知字段行为 | 理由 |
|---|---|---|---|
| 模型给的工具入参 | `z.strictObject()` | **报错**（`unrecognized_keys`） | 未知字段说明模型幻觉，静默丢弃会让它以为生效了（参考项目 2.7 的坑） |
| 落库的事件 payload | `z.looseObject()` | **保留** | 未知字段说明版本漂移，丢弃等于**永久损坏数据** |

> 🔴 **必须用 `z.looseObject()`，不能用 `z.object()`。** Zod 的默认 `z.object()` 是 **strip 模式——静默丢弃未知字段**，正好是这里最不能接受的行为，而且它不报错、不告警，数据就那样没了。
>
> 2026-08-04 冒烟实测：`z.object()` 丢弃、`z.looseObject()` 保留、`z.strictObject()` 报错；且 `looseObject` 放进 `discriminatedUnion` 后**判别正常、未知字段照样保留、未知判别值照样被拒**，嵌套层也保留。

把这条写进契约包的 README，否则一定会有人"为了一致性"把事件也改成 strict，或者顺手写成看起来更朴素的 `z.object()`。

**兼容性回归测试（M0 交付）**：`fixtures/events/` 下按版本存归档事件流，每次发版新增一份。CI 跑「所有历史 fixture 都能 parse 并 reduce 出预期状态」。这是唯一能防住格式漂移的手段。

### 4.6 reduce 的形状

```ts
export type SessionState = {
  id: SessionId;
  title: string;
  cwd: string;
  status: 'idle' | 'running' | 'waiting_permission' | 'error';
  messages: Message[];              // 上下文装配的输入
  activeTurn?: { turnId: TurnId; startedAt: number };
  pendingPermission?: PermissionRequest;
  todos: Todo[];
  runningCalls: Map<CallId, { name: string; startedAt: number }>;
  usage: UsageTotals;
  lastSeq: number;
};

export function reduce(state: SessionState, e: XmEvent): SessionState;
```

`reduce` 是纯函数，放在 `@xm/kernel`（契约包只放数据）。三条约束：

- **必须全量处理所有 persisted 事件类型**，用 TS 穷尽性检查（`never` 兜底）保证漏了一种就编译不过。
- 不得依赖事件之外的任何输入（当前时间、随机数、文件系统）。
- `runningCalls` 里在 `turn.end` 时仍存在的条目 → 崩溃恢复时标记为 `interrupted`（见 04 文档 §8）。

## 5. 工具契约

### 5.1 描述符与接口分离

契约包只放**可序列化**的部分：

```ts
// tool/descriptor.ts
export const RiskLevel = z.enum(['safe', 'low', 'medium', 'high']);

export const ToolDescriptor = z.object({
  name: z.string().regex(/^[a-z][a-z0-9]*(\.[a-z][a-z0-9_]*)+$/),  // "fs.read"
  group: z.string(),
  description: z.string().max(4096),   // 提示词的一部分，计入 token 预算
  inputSchema: z.unknown(),            // JSON Schema（由 Zod 导出）
  risk: RiskLevel,
  capabilities: z.array(Capability),
  concurrency: z.enum(['parallel', 'exclusive']),
  resultLimits: ResultLimits,          // 见 §5.3
  source: z.discriminatedUnion('kind', [
    z.object({ kind: z.literal('builtin') }),
    z.object({ kind: z.literal('plugin'), pluginId: z.string() }),
    z.object({ kind: z.literal('mcp'),    serverId: z.string() }),
  ]),
});
```

带 `execute()` 的 `interface Tool` 留在 `@xm/kernel`——它含函数，不可序列化，跨不了进程。**跨进程的是描述符，不是工具本身**。这条分界让插件工具、MCP 工具、内置工具在注册表里长得完全一样，是"一切皆插件"落地的关键。

`source` 字段的用处：权限 UI 要显示"这个工具来自哪个三方 MCP server"，以及注入防御要对非内置来源的工具结果做不可信标记（见 06 文档）。

### 5.2 输入 Schema 的可序列化子集 → [ADR-0009](./adr/0009-工具Schema子集与结果截断.md)

工具入参 schema 要同时满足三件事：Zod 严格校验、导出 JSON Schema 给模型、跨进程传输。不是所有 Zod 构造都能做到。**合法子集**：

| 允许 | 禁止 | 原因 |
|---|---|---|
| `strictObject` / 基本类型 / `enum` / `literal` | `.transform()` | 输入输出类型不一致，`Tool<I>` 的 `I` 失去意义 |
| `array` / `optional` / `nullable` / `default` | `z.lazy()` / 递归 | JSON Schema 出 `$ref`，模型侧支持参差 |
| `discriminatedUnion`（成员均为 object） | 裸 `union` 混合类型 | 模型极难稳定产出 |
| `record`（key/value 各自也要合规，ADR-0011 ⑤） | `tuple` | 环境变量/headers 是真实需求；元组模型难稳定产出 |
| `.describe()`（**强烈建议每个字段都写**） | `z.any()` / `z.unknown()` | 等于没有约束，模型必然乱填 |
| `.refine()`（但约束也要写进 description） | `z.function()` / `z.map()` / `z.set()` | 不可 JSON 序列化 |

**注册时强制**：`assertToolSchema(schema)` 在 `ToolRegistry.register()` 里跑，违规直接抛出。开发期就炸，而不是等模型在生产里填出一个诡异参数。

`.refine()` 允许但有附加要求：refine 的约束在 JSON Schema 里**不可见**，模型看不到。所以凡是 refine 表达的约束，必须在 `.describe()` 里用自然语言重复一遍。这条写进工具开发规范。

**JSON Schema 导出**用 Zod 4 内置的 `z.toJSONSchema()`（免掉 `zod-to-json-schema` 这个依赖）。2026-08-04 冒烟实测结论：

```ts
export const toModelSchema = (s: z.ZodType) => z.toJSONSchema(s, { io: 'input' });
//                                                              ^^^^^^^^^^^^^^ 必须
```

> 🔴 **必须传 `io: 'input'`。** 默认是 `io: 'output'`，而 output 视角下带 `.default()` 的字段**一律进 `required`**——模型会被告知这些可选参数是必填的，每次都得填，纯属浪费 token 且徒增出错面。
>
> 实测对照：`edits[].replaceAll`（有 default）在 `io:'output'` 下进了 `required`，在 `io:'input'` 下正确地不在。

其余实测结论（均已达标）：合法子集导出**无 `$ref` / 无 `$defs`**，`additionalProperties: false` 正确生成，`.describe()` 正确落到 `description`（中文无损），`discriminatedUnion` 导出为 `oneOf` + `const` 判别键。

**违规构造的实测行为，正是 `assertToolSchema()` 必须自己检测的原因**：

| 构造 | `toJSONSchema` 的表现 | 结论 |
|---|---|---|
| `.transform()` | `io:'output'` 抛错，但 **`io:'input'` 静默通过** | 导出不报错 ≠ 合法，**必须结构化检测** |
| `z.any()` / `z.unknown()` | 产出 `{}`——语法合法，语义为零约束 | 只能靠断言拦截 |
| `z.lazy()` 递归 | 产出 `{"$ref":"#"}` | 只能靠断言拦截 |

也就是说：**不能用"导出是否抛错"来当合法性检查**，`assertToolSchema()` 必须遍历 Zod 的内部结构自行判定。

### 5.3 结果与截断契约

```ts
// tool/result.ts
export const ResultLimits = z.object({
  maxBytes: z.number().int().default(64 * 1024),
  maxLines: z.number().int().optional(),
  strategy: z.enum(['head', 'tail', 'middle', 'none']).default('middle'),
});

export const ToolProgress = z.discriminatedUnion('kind', [
  z.object({ kind: z.literal('progress'), message: z.string().optional(),
             data: z.unknown().optional() }),
  z.object({ kind: z.literal('result'),
             forModel: z.array(ResultBlock),
             display: DisplayHint.optional() }),
]);
```

**截断由运行时统一执行，不由工具自觉。** 工具返回全量，运行时按 `resultLimits` 截断、把全文写进 blob、在截断处插入可见标记：

```
[... 已省略 128,442 字节 / 3,102 行。完整内容: blob:sha256:ab3f… ，
     可用 result.expand 工具按行范围读取 ...]
```

三个设计点：

1. **标记对模型可见。** 让模型知道自己看到的是残缺的，它才会去取剩下的。悄悄截断是最坏的做法——模型会基于残缺内容自信地下结论。
2. **默认 `middle` 策略。** 头尾都保留：命令输出的头部有上下文、尾部有错误信息，中间往往是噪音。`head`/`tail` 留给明确知道信息分布的工具。
3. **`result.expand` 工具在 M2 补。** M0 只要契约里留好 blob 引用，模型暂时看不到全文可以接受。

## 6. 权限契约

```ts
// permission/capability.ts —— 闭集，新增能力必须改这里 + 写 ADR
export const Capability = z.enum([
  'fs.read', 'fs.write', 'fs.delete',
  'shell.exec', 'process.spawn',
  'net.fetch', 'net.listen',
  'git.write', 'git.push',
  'env.read', 'secrets.read',
  'gui.capture', 'gui.input',
  'browser.control',
  'package.install', 'system.settings',
  'plugin.install', 'self.modify',
]);
```

**闭集是刻意的。** 能力词表开放（任意字符串）意味着插件可以自造能力名绕过策略——策略规则匹配不到的能力如果默认放行就是后门，默认拒绝则插件全废。闭集 + 新增走 ADR，是唯一能让 PolicyEngine 的行为可穷举测试的做法。

```ts
// permission/request.ts
export const PermissionRequest = z.object({
  requestId: RequestId,
  sessionId: SessionId,
  callId: CallId.optional(),
  capability: Capability,
  target: z.string(),          // 路径 / host / 命令行，能力相关
  risk: RiskLevel,
  reason: z.string(),          // 给用户看：为什么要这个权限
  preview: DisplayHint.optional(),   // 高风险操作的预览（如将要执行的 diff）
  trustLevel: z.enum(['user', 'model', 'untrusted']),  // 见下
});
```

**`trustLevel` 是注入防御的接口。** 当本轮上下文里混入了不可信内容（网页、MCP 返回、子 Agent 结果），发起的权限请求标记为 `untrusted`，PolicyEngine 对不可撤销能力子集自动降级为 `ask`（ADR-0003）。这个字段现在就要在契约里，M1 只是先恒填 `model`——**留位置的成本是零，补位置的成本是改所有调用点**。

```ts
// permission/policy.ts
export const PolicyRule = z.object({
  id: z.string(),
  effect: z.enum(['allow', 'ask', 'deny']),
  capability: z.union([Capability, z.literal('*')]),
  match: z.object({
    target: z.string().optional(),      // glob
    executor: z.enum(['local','container','remote']).optional(),
    trustLevel: z.array(z.enum(['user','model','untrusted'])).optional(),
  }).optional(),
  reason: z.string(),
  immutable: z.boolean().default(false),  // 红线：任何档位/YOLO 都不可覆盖
});

export const PolicyVerdict = z.discriminatedUnion('effect', [
  z.object({ effect: z.literal('allow'), ruleId: z.string(), reason: z.string() }),
  z.object({ effect: z.literal('ask'),   ruleId: z.string(), reason: z.string(), risk: RiskLevel }),
  z.object({ effect: z.literal('deny'),  ruleId: z.string(), reason: z.string() }),
]);
```

**Verdict 必须带 `ruleId`。** 用户问"为什么拦我"，答案要能精确到规则。审计日志同理。没有 ruleId 的权限系统在出问题时无法排查。

规则求值顺序：`deny(immutable)` → `deny` → `ask` → `allow`，**同优先级内后定义者胜**（项目配置覆盖用户配置）。无匹配规则时的兜底由档位决定（平衡档：非 `safe` 风险一律 `ask`）。这个顺序写进 PolicyEngine 的单测表格，穷举覆盖。

## 7. 模型契约

```ts
// model/request.ts
export const SystemSegment = z.object({
  text: z.string(),
  cacheable: z.boolean().default(false),   // 缓存断点候选
});

export const ModelRequest = z.object({
  model: z.string(),
  system: z.array(SystemSegment),
  messages: z.array(Message),
  tools: z.array(ToolDescriptor).optional(),
  toolChoice: z.union([
    z.enum(['auto', 'none', 'required']),
    z.object({ name: z.string() }),
  ]).optional(),
  maxOutputTokens: z.number().int().positive(),
  temperature: z.number().min(0).max(2).optional(),
  thinking: z.object({
    enabled: z.boolean(),
    budgetTokens: z.number().int().optional(),
  }).optional(),
  stopSequences: z.array(z.string()).optional(),
  cacheBreakpointAfterMessage: z.number().int().optional(),  // 消息数组下标
});
```

**缓存断点是中立表达，不是 Anthropic 细节。** ContextBuilder 只声明"到这里为止是稳定的"，Anthropic 适配器翻译成 `cache_control`，OpenAI 适配器忽略（它自动缓存），Ollama 适配器忽略。如果让 ContextBuilder 直接写 `cache_control`，内核就绑死了一家的 wire format。

配合 ADR-0006 的派生约束：`Tool.available()` 的动态过滤结果不得进入稳定前缀。具体到这里就是——**`tools` 数组若逐轮变化，`system` 的 `cacheable` 段仍可缓存，但 `cacheBreakpointAfterMessage` 必须置于工具列表变化点之后**。这条写进 ContextBuilder 的注释与单测。

```ts
// model/chunk.ts
export const ModelChunk = z.discriminatedUnion('kind', [
  z.object({ kind: z.literal('text_delta'),      text: z.string() }),
  z.object({ kind: z.literal('thinking_delta'),  text: z.string() }),
  z.object({ kind: z.literal('thinking_signature'), signature: z.string() }),
  z.object({ kind: z.literal('tool_call_start'), id: CallId, name: z.string() }),
  z.object({ kind: z.literal('tool_call_delta'), id: CallId, argsJson: z.string() }),
  z.object({ kind: z.literal('tool_call_end'),   id: CallId }),
  z.object({ kind: z.literal('usage'),           usage: Usage }),
  z.object({ kind: z.literal('stop'),            reason: StopReason }),
]);

// model/usage.ts
export const Usage = z.object({
  inputTokens: z.number().int(),
  outputTokens: z.number().int(),
  cacheReadTokens: z.number().int().default(0),
  cacheWriteTokens: z.number().int().default(0),
  reasoningTokens: z.number().int().optional(),
});

export const StopReason = z.enum([
  'end_turn', 'tool_use', 'max_tokens', 'stop_sequence', 'aborted', 'error',
]);
```

**成本不在 Provider 里算。** `Usage` 只有 token 数，`costUsd` 由 CostAccountant 查价格表得出。价格会变、会有折扣、不同账户不同价——把它硬编码进适配器就等于每次调价都要改代码发版。价格表是配置。

**`tool_call_delta.argsJson` 是增量 JSON 字符串片段。** 不要试图在契约层解析——各家的分片边界不同，累积完整后再一次性 parse 是唯一稳妥做法。累积器放在 kernel，配套一个"JSON 不完整"的明确错误码。

## 8. 配置契约

```ts
// config/secret.ts
export const SecretRef = z.object({ $secret: z.string() });   // { $secret: "anthropic.apiKey" }
```

**配置里永远不出现明文密钥**，只出现 `SecretRef`，由 SecretStore 在使用点解析。这是对参考项目 2.6（API key 提交进 git）的直接回应。配套：

- `redact(value)`：递归把 `SecretRef` 解析后的值替换为 `***`，日志与审计**强制**经过它。
- 事件 payload 里禁止出现密钥——`shell.exec` 的命令行可能含密钥，所以 `tool.start.input` 在落库前走一遍启发式脱敏（正则匹配常见 key 形态）。这是尽力而为，不是保证。

**M0 最小配置树**（ADR-0011 ②，字段随 M1 扩展）：`model`（角色→模型引用）、`providers`（kind / baseUrl / apiKey:SecretRef / models）、`permission`（tier + rules）、`tools`（disabled）、`logging`（level + redact）。

`ConfigPatch` 定义为 `Record<string, unknown>` 而**不是** `Config.deepPartial()`——补丁里要能出现 `null` 表示删除，而 `null` 不是 `Config` 的合法取值。合并后整体按 `Config` 校验。

配置分层与合并：

```
内置默认 < 用户级 ~/.xiaoming/config.json < 项目级 .xiaoming/config.json < 会话覆盖 < 环境变量
```

**合并语义必须写死并测试**：对象深合并，**数组整体替换**（不是拼接），`null` 表示删除该键。数组语义是最容易含糊的地方——"项目配置里的工具白名单"到底是覆盖还是追加，含糊一次就会有安全事故。选替换，因为它是可预测的；需要追加时用显式的 `extends` 字段。

## 9. 跨进程边界的校验策略

全量 Zod parse 有成本。token 级事件如果每条都 parse，开销可观。所以按**信任边界**区分，而不是一刀切：

| 边界 | 生产者可信度 | 策略 |
|---|---|---|
| 模型 → 工具入参 | 不可信 | **始终**全量 strict parse |
| 渲染层 → 主进程（命令） | 不可信（可能被 XSS 劫持） | **始终**全量 parse |
| 插件宿主 ↔ 主进程 | 不可信 | **双向**全量 parse |
| MCP server → 主进程 | 不可信 | **始终**全量 parse |
| 主进程 → 渲染层（事件推送） | 可信 | dev/test 全量 parse；生产仅信封校验 |
| 事件写库 | 可信 | 全量 parse（写入是低频的，且格式错误会永久污染） |
| 事件读库 | 需演进 | upcaster → 全量 parse |

**"生产环境跳过校验"只允许出现在唯一一处**（主→渲染的事件推送），且必须由构建期常量控制、在 CI 的 dev 模式下全量开启。任何其它地方想跳过校验，需要 ADR。

## 10. 契约包自身的版本策略

`@xm/contracts` 的版本号是**协议版本**，不只是包版本：

- 插件清单声明 `contractsRange: "^1.0.0"`，插件宿主启动时做兼容性检查，不兼容直接拒绝加载并给出明确原因（而不是运行到一半崩）。
- 主/渲染进程握手时交换版本，不一致时提示重启（自动更新后旧渲染层可能还活着）。
- 破坏性变更（改事件 payload 语义、删能力词条）走 major，且必须同时提供 upcaster。

## 11. 工具链现状（2026-08-04 实测）

详见 [ADR-0010](./adr/0010-TypeScript双编译器工具链.md)。对契约包的开发者，只需记住三件事：

1. **`npx tsc` 是 TS 7.0.2 原生二进制；`require('typescript')` 是 TS 6.0.x 的 JS API。** 别名双装，`tsc --build` / `--watch` / 项目引用在 pnpm workspace 下均已实测通过。
2. **typed lint 走 TS 6 检查器**，是 CI 里最慢的一环（16k 行约 26s / 1.4GB）。写契约时保持类型简单，收益直接体现在 CI 时间上。
3. **CI 脚本只判断退出码非零**——TS 7 与 TS 6 对同样的错误分别退出 `1` 和 `2`。

已验证可用、无需再怀疑的：`strict` 全开 + `exactOptionalPropertyTypes` + `noUncheckedIndexedAccess`、`never` 穷尽性检查、d.ts 中品牌类型保真、zod 4 的 `brand()` / `discriminatedUnion` / `looseObject` / `toJSONSchema`。
