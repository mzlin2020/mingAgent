# 03 · 技术选型

> 状态：**建议方案，待拍板**。对应 [ADR-0001](./adr/0001-桌面技术栈选型.md)。

## 1. 核心矛盾

桌面 Agent 的技术栈选择被四个约束同时拉扯：

1. **自我迭代**要求技术栈对 Agent 友好——语言生态成熟、编译反馈快、测试易写、AI 训练语料多
2. **操作电脑**要求能拿到系统底层能力——PTY、屏幕捕获、输入注入、进程沙箱
3. **高性能**要求内存与启动可控——Electron 的天然弱项
4. **UI 要接近 Claude Code 桌面端**——意味着 Web 技术栈的排版能力

## 2. 三方案对比

| 维度 | A. Electron + TS | B. Tauri + Rust | C. Electron + Python sidecar |
|---|---|---|---|
| 语言数 | 1（TS） | 2（Rust + TS） | 2（TS + Python） |
| 内存基线 | ~150MB | ~40MB | ~250MB（双运行时） |
| 启动 | 中 | 快 | 慢（Python 冷启动） |
| Agent 自我迭代友好度 | ★★★★★ | ★★★☆☆（Rust 编译慢、借用检查对生成代码不友好） | ★★★★☆（但跨语言改动要同时改两边） |
| 打包分发 | 成熟（electron-builder，签名/公证/自动更新齐全） | 成熟但生态较新 | 痛苦（PyInstaller + 原生依赖 + 体积 200MB+） |
| MCP SDK | 官方 TS SDK 最完整 | 需自实现或绑定 | 官方 Python SDK 完整 |
| 终端能力 | node-pty（VS Code 同款，最成熟） | 需绑定或走 Rust crate | node-pty（在 Node 侧） |
| 模型 SDK | Anthropic/OpenAI/Google 官方 TS SDK 齐全 | 多需自封装 HTTP | Python SDK 齐全 |
| 复用 manusAgent 代码 | 不能直接复用（重写） | 不能 | 可复用约 40% |
| 长期演化天花板 | 高（热点可下沉 Rust） | 最高 | 中（双运行时的技术债会持续累积） |

## 3. 结论：方案 A（Electron + TypeScript 单语言 monorepo）

### 3.1 理由

1. **单语言是自我迭代的前提**。小明要读懂自己、改自己、测自己。跨语言边界会让每一次自我修改都变成需要同时理解两套类型系统、两套构建、两套测试的任务，L3/L4 级自我迭代的成本会指数上升。
2. **生态完全对齐**。MCP 官方 TS SDK、各家模型官方 TS SDK、node-pty、chokidar、tree-sitter WASM、ripgrep 二进制、Monaco/CodeMirror、xterm.js——Agent 需要的每一块都有第一梯队的 TS 实现。
3. **VS Code 已经证明了上限**。Electron 能承载一个高性能、深度插件化、需要 PTY 和文件监视的复杂桌面产品；它的扩展宿主进程模型正是小明插件体系的直接参考。
4. **UI 风格要求天然匹配**。要做出 Claude Code 桌面端那种排版与动效，Web 技术栈是最短路径。
5. **性能可以补救，架构不可以**。Electron 的性能短板可以通过 Rust sidecar（napi-rs）针对性解决；而错误的架构（双运行时、跨语言契约）无法事后补救。

### 3.2 明确接受的代价

| 代价 | 缓解措施 |
|---|---|
| 内存基线高于 Tauri | 严控渲染进程数量（单窗口多视图，不滥开 BrowserWindow）；索引与缓存放主进程并设上限；引入内存预算监控 |
| 打包体积 ~120MB | 可接受（Cursor/VS Code 同量级）；差量更新降低更新成本 |
| CPU 密集任务弱 | 下沉 Rust sidecar：代码索引、语义检索、大文件 diff、屏幕图像处理 |
| Node 的 CPU 单线程 | 重活走 `worker_threads` 或独立进程；Agent 循环本身是 I/O 密集，不受影响 |

### 3.3 为什么不选 B（Tauri）

不是性能不够好，是**自我迭代成本太高**。Rust 的编译时长（增量 10s+，全量分钟级）会直接拖垮"改一版 → 跑评测 → 再改"的自我改进闭环；借用检查对模型生成的代码是高频挫败源。**如果未来某天核心稳定、自我迭代主要发生在插件层，可重新评估把外壳换成 Tauri**——所以要求内核对 Electron 零依赖（原则一），保留这条退路。

### 3.4 为什么不选 C（Python sidecar）

唯一优势是能复用参考项目 40% 的代码，但那 40% 恰恰是[评审文档](./02-参考项目评审-manusAgent.md)里判定要推翻的部分（非流式模型层、僵化 Flow、重依赖持久化）。为了复用注定要重写的代码而背上双运行时的债，是明确的亏本买卖。

> **例外**：如果未来需要本地推理、向量计算、数据分析类能力，可以以**可选插件**形式引入 Python 运行时（插件宿主本就支持异构进程），而不是把它放进主链路。

### 4.1 TypeScript 7.0 的约束与风险

TS 7.0 是编译器的 Go 原生重写（`typescript-go` / tsgo），类型检查速度有数量级提升——对小明这种"改一版 → 跑类型检查 → 跑评测"的自我迭代闭环，编译反馈速度是**直接的生产力乘数**，值得从第一天就用。

**它不支持的配置**（绿地项目全部无痛，但要在 M0 就定死，避免后期返工）：

| 不支持 | 我们的做法 |
|---|---|
| `module: AMD / UMD / System` | 全线 ESM（`module: nodenext`） |
| `moduleResolution: node10 / classic` | `nodenext` / `bundler` |
| `baseUrl` | **禁止用 baseUrl 做路径别名**；跨包引用一律走 workspace 依赖 + package `exports`，包内用相对路径 |
| `outFile` | 打包交给 tsup / Vite，tsc 只做类型检查与 d.ts |
| `target: ES5` | `ES2023`+（Electron 内置 Node 22，无历史包袱） |
| `esModuleInterop: false`、`allowSyntheticDefaultImports: false`、`alwaysStrict: false` | 本来就是要开的 |

### 4.1.1 冒烟验证结果（2026-08-04 实测）→ [ADR-0010](./adr/0010-TypeScript双编译器工具链.md)

上述三项风险已实机验证，结论如下。**上表的"不支持配置"清单仍然全部有效，继续作为 M0 硬约束。**

| 风险项 | 实测结论 |
|---|---|
| ① 编译器 API 成熟度 | ❌ **风险兑现**。TS 7.0 **完全不提供 JS 编译器 API**——`require('typescript')` 只剩 `{version, versionMajorMinor}`。typescript-eslint 硬失败并显式报错。官方原文：*"TypeScript 7.0 does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API."* |
| ② watch / 增量 / monorepo | ✅ 正常。`tsc --build` 项目引用全量 0.25s、增量命中缓存 0.07s；`--watch` 增量与错误恢复正确；pnpm workspace 无问题 |
| ③ 语言服务 | ✅ 由双装带来的 TS 6 `tsserver` 提供，编辑器体验不受影响 |

**已采用的对策**：官方双装机制，`npx tsc` → TS 7 原生，`require('typescript')` → TS 6 JS API：

```json
{
  "devDependencies": {
    "@typescript/native": "npm:typescript@^7.0.2",
    "typescript": "npm:@typescript/typescript6@^6.0.2"
  }
}
```

**同时修正本节"数量级提升"的表述**：实测在 16k 行 zod 重类型推导负载下为 **2.1x**（8.6s vs 17.9s）。而且 CI 的类型相关耗时由 typed lint 主导（26.4s / 峰值 1.41GB，走 TS 6 检查器），总体收益约 **1.26x**。仍然值得采用——退路成本为零、且 7.1 后可去掉 TS 6——但不要按"数量级"去规划自我迭代闭环的时长。

> 两个编译器对同一份含错代码给出**完全一致**的错误码与数量，因此"lint 用 6、构建用 7"不会撕裂。唯一差异：退出码 TS 7 为 `1`、TS 6 为 `2`，**CI 脚本一律只判非零**。

### 4.2 平台分级与 PlatformPort

平台支持分级见 [ADR-0007](./adr/0007-平台支持分级.md)：

| 等级 | 平台 | 承诺 |
|---|---|---|
| Tier 1 | macOS、Windows | 完整功能 |
| Tier 2 | Linux（基线 Ubuntu LTS + GNOME） | 除计算机操作外全功能，正式发布产物 |
| Tier 3 | Linux 上的计算机操作 | 尽力而为，可能长期缺失（Wayland 设计性禁止输入注入） |

**强制的架构约束**：所有平台相关能力收敛到 `PlatformPort` 接口之后——密钥、屏幕、输入、窗口、通知、托盘、路径解析。**业务代码中禁止出现 `process.platform` 判断**，由 **ESLint `no-restricted-properties`** 在 CI 拦截（原写"dependency-cruiser"是错的——它做依赖图分析，看不见标识符，见 [ADR-0011 ⑥](./adr/0011-契约与内核实现期的偏离.md)）。依赖层面的约束（内核禁 `node:*`）仍由 dependency-cruiser 负责。

```ts
interface PlatformPort {
  readonly os: 'darwin' | 'win32' | 'linux';
  secrets:  SecretStore;          // 探测后端能力，退化时显式告知，绝不静默明文
  screen?:  ScreenCapture;        // 可选：Linux 上可能不可用
  input?:   InputInjection;       // 可选：Wayland 上可能不可用
  windows?: WindowEnumeration;
  notify:   Notifier;
  tray:     TrayHost;
  paths:    PathResolver;         // env-paths 封装，含大小写敏感性差异处理
}
```

可选成员为 `undefined` 时，对应的工具通过 `Tool.available()` 自动从模型视野中消失，UI 灰显并说明原因——**不做半吊子实现，也不让用户撞上"点了没反应"**。

### 计算机操作（Computer Use）的平台实现

| 能力 | macOS | Windows | Linux |
|---|---|---|---|
| 截屏 | ScreenCaptureKit（需屏幕录制权限） | Windows.Graphics.Capture / BitBlt | X11 直接可用；Wayland 需 xdg-desktop-portal + PipeWire |
| 鼠标键盘注入 | CGEvent（需辅助功能权限） | SendInput | X11 用 XTEST；**Wayland 设计性禁止**，只能走 portal/libei 且各合成器支持不一 |
| 窗口枚举 | Accessibility API | UI Automation | X11 API；Wayland 无统一 API |
| 权限申请 | 引导用户在系统设置授权 | UAC 提示 | portal 授权对话框 |

> 实现路径：优先找成熟 npm 原生模块；不满足再自研 napi-rs 模块。**M4 之前不动这块**，先用浏览器自动化覆盖大部分"操作电脑"的实际需求——它在三个平台上都完全可用。

## 5. 仓库形态

单 monorepo。理由：契约包需要被所有包引用，跨包重构频繁，Agent 自我迭代需要在一个工作区内看到全貌。

```
mingAgent/
├── docs/                  # 本目录
├── packages/              # 库（见 04-总体架构）
├── apps/
│   ├── desktop/           # Electron 应用
│   └── cli/               # xm 命令行
├── plugins/               # 一方插件（与三方插件同构）
├── evals/                 # 评测集与回放用例（见 07）
├── scripts/
└── .xiaoming/             # 小明改自己时的工作区配置
```
