# 04 · 总体架构

> **当前边界（2026-08-13，M2 已完成）**：执行器仍是主机范围本地执行，核心资源由能力网关和不可覆盖规则保护，**不是 OS 沙箱**。受控 PTY 仅运行逐次判权后的 argv，不暴露原始 stdin。详见 [ADR-0040](./adr/0040-M1.5自主安全边界与受控终端.md)。

> 本文描述**当前已实现的架构边界**及已留出的扩展位置。最后核对：2026-08-13，
> M2-a 至 M2-i 已全部完成并通过总验收。
>
> 契约字段、接口签名与事件全集以 [10-契约设计](./10-契约设计.md) 和源码为准；本文只解释
> 各层为什么存在、现在已经跑通什么、未来能力应当落在哪里。已采纳的决策以
> [ADR 索引](./adr/README.md) 为准。

## 1. 当前分层

```
┌──────────────────────────────────────────────────────────────────────┐
│ Surfaces 表现层                                                       │
│ apps/desktop：Electron main / preload / React renderer（已实现）      │
│ apps/cli、Headless Daemon（未来）                                    │
└────────────────────────────────┬─────────────────────────────────────┘
                                 │ 窄 IPC：命令下发 + 事件推送
┌────────────────────────────────┴─────────────────────────────────────┐
│ Runtime 装配层  @xm/runtime（已实现）                                 │
│ SessionRuntime · ContextBuilder · Turn 循环 · Checkpoint · 子 Agent  │
└────────────────────────────────┬─────────────────────────────────────┘
                                 │ Ports（纯接口，定义在 kernel）
┌────────────────────────────────┴─────────────────────────────────────┐
│ Kernel 纯逻辑内核  @xm/kernel                                         │
│ reduce(events) · PolicyEngine · ToolRegistry · 状态/目标规范化 · Ports │
└────────────────────────────────┬─────────────────────────────────────┘
                                 │ Adapters（实现 Ports）
┌────────────────────────────────┴─────────────────────────────────────┐
│ platform · storage · providers · tools-core                           │
│ Node 平台/配置 · SQLite/Blob · 模型传输 · 文件/命令/网络/PTY            │
└──────────────────────────────────────────────────────────────────────┘
```

依赖方向是唯一的硬约束：**Surfaces → Runtime → Kernel，Adapters 实现 Kernel 的 Ports**。
`@xm/kernel` 不知道任何适配器、Node API 或 Electron；`@xm/contracts` 是所有跨层数据的唯一来源，
除 Zod 外不依赖其它包。依赖图由 `dependency-cruiser` 强制检查。

### 1.1 M3 之后的形态（规划，尚未实现）

[M3 微内核化重构](./11-微内核与插件容器.md) 在上面这张图里只加一层、改一处，
**依赖方向的硬约束一字不改**：

```
┌──────────────────────────────────────────────────────────────────────┐
│ Surfaces  apps/desktop · apps/cli                                     │
└────────────────────────────────┬─────────────────────────────────────┘
┌────────────────────────────────┴─────────────────────────────────────┐
│ Compose 装配层  @xm/compose（新增）                                    │
│ profile 解析 · patch 合并 · 内建 profile · 装配期断言                  │
└────────────────────────────────┬─────────────────────────────────────┘
┌────────────────────────────────┴─────────────────────────────────────┐
│ Runtime  @xm/runtime   事件总线 · seq 单点分配 · Turn 驱动器 · 崩溃恢复 │
└────────────────────────────────┬─────────────────────────────────────┘
┌────────────────────────────────┴─────────────────────────────────────┐
│ Kernel  @xm/kernel   reduce · PolicyEngine · ToolRegistry             │
│                      **+ 插件容器（纯逻辑、零 I/O）** · 接缝定义        │
└────────────────────────────────┬─────────────────────────────────────┘
┌────────────────────────────────┴─────────────────────────────────────┐
│ platform · storage · providers · tools-core（接缝提供者）              │
└──────────────────────────────────────────────────────────────────────┘
```

变化只有三处：**① 容器进 kernel**（纯逻辑，零 I/O，能在浏览器跑——这条约束反过来保证
它不会长出文件读写）；**② 新增 `@xm/compose`**，包数 8 → 9，depcruise 加两条规则
（不得依赖 electron；除 `apps/**` 外无人可依赖它）；**③ `turn.ts` 从"焊死的流程"变成
"驱动器 + 命名扩展点"**（[ADR-0055](./adr/0055-Turn驱动器的扩展点契约.md)）。

**不为插件新建细粒度包**：插件住在现有包里。这不是偷懒——容器化会让一部分依赖关系从
import 图挪到运行时，削弱 depcruise 的静态护栏，保住包边界规则是这个真损失的首要对策
（[ADR-0052](./adr/0052-插件容器与效果模型.md) 后果段）。

**微内核不等于一切可替换**：seq 分配、`evaluate()`、路径网关、`SecretStore`、`redact()`、
落库顺序这六项是不可绕过的安全底座，由容器在装配收敛时断言在位
（[ADR-0053](./adr/0053-微内核的特权底座与扩展点边界.md)）。

当前已经有唯一 `ContextBuilder`、持久摘要与上下文预算、串行只读子 Agent，以及 checkpoint v2
浏览/恢复闭环。当前仍没有通用并行 `Scheduler`、插件宿主或 MCP 客户端；后三者不能在描述当前
系统时当作已存在的模块。

## 2. 进程与信任边界

```
┌──────────────────────────────────────────────────────────────┐
│ Electron Main Process                                         │
│ · services.ts 装配 Runtime、存储、Provider、工具和密钥后端    │
│ · IPC 参数校验、SQLite、策略判定、文件/命令/网络工具           │
│ · 进程内 EventBus 将已记录事件推给窗口                        │
└───────────────────────────┬──────────────────────────────────┘
                            │ preload 暴露的具名 IPC 方法
┌───────────────────────────┴──────────────────────────────────┐
│ Renderer（React + Zustand）                                   │
│ · 会话/Home/tabs、消息流、在途渲染、终端与错误状态             │
│ · 无 Node 权限；不保存可与事件流投影分叉的第二份会话状态       │
└──────────────────────────────────────────────────────────────┘

                        ┌─────────────────────┐
                        │ PTY / 命令子进程      │
                        │ 由 tools-core 管理   │
                        └─────────────────────┘
```

- `contextIsolation: true`、`nodeIntegration: false` 与 renderer sandbox 缺一不可。
- preload 只转发少量具名调用；不存在通用的 `invoke(channel, args)` 入口。
- IPC 两端都用 Zod 校验。错误以 `{ ok: false, code, message }` 返回，避免 Electron 序列化异常时
  丢失错误码。
- 插件进程、MCP server 与 CLI 都是未来扩展：前两者属于 M4，CLI 也要只依赖 Runtime，不能把
  Electron 带入核心运行路径。

为了方便跨过这条边界。

## 4. 核心模型

### 4.1 事件流与会话状态

会话的唯一事实来源是 append-only 事件流：

```
SessionState = reduce(persisted events)
```

`SessionRuntime.record()` 是全系统唯一的 `seq` 分配点。它先把持久事件追加并脱敏，再更新内存
投影并广播；因此 UI 不会看到一条最终没有落库的事件。`seq` 在会话内单调递增且无空洞，
`PRIMARY KEY(session_id, seq)` 是最终并发写检测。

事件分两类：

- **持久事件**：`turn.start/end`、`message.start/end`、`tool.start/end`、`usage.recorded`、
  `session.renamed` 等，构成可回放状态。
- **瞬态事件**：`message.delta`、`tool.progress`、终端输出等，只经 EventBus 推送并进入
  `LiveBuffer`；它们不推进 `seq`，且不得携带持久事件中没有的终态信息。

渲染层只维护 UI 壳状态和瞬态 `LiveBuffer`。完整会话状态由主进程序列化后提供，并随着已验证的
事件更新；一段流式文字不会同时存在于 live buffer 和持久 `messages` 中。

### 4.2 ModelProvider

`ModelProvider` 是 Kernel 定义的纯端口，统一提供模型能力说明、可选的 token 计数和
`stream(request, signal)`。当前适配器为 Anthropic 与 OpenAI-compatible；Provider 差异（例如
system/developer 角色、thinking 块、工具名编码、图片编码）留在适配器内，不上浮到 Runtime 或 UI。

流式取消是端口契约的一部分：Provider 收到取消后以 `stop: aborted` 正常结束迭代，不把
`AbortError` 交给调用方猜测。用量由 Provider 返回，成本由配置中的价格表计算；未知价格明确标记
为未计价，不伪造为零成本。

### 4.3 ToolRegistry 与能力网关

工具含函数，不能跨进程；跨层传输的是其可序列化 `ToolDescriptor`。注册时会验证：

- 输入 schema 必须属于可导出 JSON Schema 的严格子集；模型未知字段立即报错。
- 所有副作用必须声明闭集中的 `capabilities` 与风险等级。
- 具有路径、命令或网络能力的工具必须声明相应入参字段；不能定位真实目标就失败关闭。
- 工具可声明稳定的可用性与资源主张；资源调度契约已存在，但通用并行 Scheduler 尚未实现。

工具执行前的顺序固定为：**严格解析入参 → 能力网关解析/回写 → 生成权限主张 → 策略判定 → 执行**。
路径网关会展开相对路径、解析符号链接和 Windows 8.3 短名，并把结果回写到执行入参；网络网关只解析
一次 DNS，工具只能使用被判定过的固定 IP 建连。判定看到的对象必须就是工具最终操作的对象。

### 4.4 PolicyEngine

当前权限模型由 [ADR-0039](./adr/0039-放弃审批模式.md) 定案：结果只有 `allow` 与 `deny`，没有
`ask`、审批 UI、权限档位或会话授权。`evaluate()` 是纯函数，按以下顺序工作：

1. 规范化 target；无法规范化则拒绝。
2. 先检查所有层中不可覆盖的 immutable `deny` 红线。
3. 从项目层、用户层、内置层倒序找第一个命中层；层内 `deny` 胜 `allow`。
4. 没有规则命中时默认放行。

规则层顺序为内置 → 用户 → 项目，其中项目层只能收紧。红线、敏感读取、持久化路径写入、
SSRF 私网地址、危险命令拆解出的路径主张，以及不可信上下文下的关键操作，均由拒绝规则表示。
工具任一主张被拒，整次调用不执行，并记录策略拒绝事件供回放和说明原因。

### 4.5 存储、密钥与还原点

`@xm/storage` 的 SQLite 库当前包含 `events`、`sessions` 摘要投影、`write_leases` 与会话快照。
快照只是回放缓存，删除后可从事件流重建；Blob 是文件系统中的 SHA-256 内容寻址对象。工作区
FTS/符号索引也是可重建派生数据，损坏或未就绪时查询退回 `search.text`。当前没有将 `messages`、
用量或记忆另建为真相表，不能把路线图中的目标表结构误认为已实现。

密钥不进配置、日志、事件或模型上下文。桌面端使用 Electron `safeStorage` 接入系统钥匙串；系统
钥匙串不可用时明确拒绝存储，而不是退化为明文。写入/删除工具在执行前按整组目标创建 checkpoint
v2 manifest，覆盖文件、目录、不存在目标和大文件；桌面端已经提供列表、状态和一次性恢复入口。
Blob GC 仍未开放，在引用闭包证明完成前继续只增不删。

## 5. 当前一轮对话的执行链路

```
用户输入（文字 / 图片）
  → services.sendUserMessage()
  → SessionRuntime.record(turn.start，持久化用户输入)
  → runtime.runTurn()
  → ContextBuilder（稳定系统前缀 + token 预算 + 持久摘要 + 近期原文）
  → Provider.stream(ModelRequest + 当前可用工具描述符)
  → message.delta / message.end 与 tool_use 事件
  → 每个工具调用依次：parse → gateway → claims → policy → checkpoint → execute
  → tool.start/progress/end，结果回灌下一次 Provider 流式调用
  → turn.end
```

实现细节：

- 所有主模型请求都经唯一 `ContextBuilder`：按模型窗口预留输出预算，在 75% 阈值触发分层压缩，
  最近四轮与当前轮保留原文；摘要先写 Blob、再写 `context.compacted`，重启后直接复用。
- 当前没有长期记忆。持久摘要只压缩本会话历史，不能把它描述成跨会话记忆或 M6 召回系统。
- 当前同一批模型工具调用按顺序执行；资源声明只为未来调度器准备，不能假定已经并行。
- Provider 或工具失败会落结构化结果/错误事件，使模型有机会改用其它方法；用户中断则记录完整的
  `message.end` 后再记录 `message.interrupted`，保证流式显示与持久回放一致。
- 第一条用户消息可触发后台短标题生成；标题只基于那条用户输入，净化后才写入
  `session.renamed`，模型输出与工具返回不参与命名。
- 主 Agent 可调用 `agent.explore` 派生独立会话；M2 实现串行、有限轮数、只读白名单，父会话只接收
  结论，子会话末态的不可信标记经 `subagent.end` 粘性并回父会话。

## 6. 取消、并发与崩溃恢复

- 每个正在运行的会话持有一个 `AbortController`，从 UI 停止按钮贯穿 Provider、工具与子进程。
- 每个会话同时只有一个 Turn；同一会话的 `record()` 写入序列化，跨会话可独立运行。
- SQLite 写租约是友好错误与早期检测；真正防止错乱历史的是事件表主键。
- 启动时只读扫描事件流并识别未收尾的回合。用户可继续或放弃：两条路径都会先补写缺失的收尾事件，
  不会重放不具备幂等性的原始工具调用。
- PTY 由共享 `PtySessionManager` 管理并按小明会话分区。`shell.session.open` 判定 cwd；模型没有
  原始 stdin，后续只能用 `shell.session.run` 提交结构化 argv，每次重新经过命令主张、策略、
  checkpoint、超时和环境白名单。`status/resize/close` 不产生新的系统资源主张。

## 7. 已完成能力与后续位置

| 阶段 | 能力 | 正确落点 |
|---|---|---|
| M2（已完成） | 多文件编辑、diff、检索、Git、checkpoint 回滚、todo、上下文管理、串行只读子 Agent | 工具/适配器 + Runtime 编排；Kernel 的无 I/O 边界未改变 |
| M3（下一阶段） | 插件容器、回合扩展点、Agent Inbox、能力接缝与执行世界、渲染意图、Code Mode | 容器进 Kernel（纯逻辑）、装配进新增的 `@xm/compose`、扩展点长在 Runtime 的驱动器上；六项安全底座不可替换（见 §1.1） |
| M4 | 插件宿主、MCP、多 Provider 管理、Skills、CLI、配置中心 | 独立进程/适配器与 Surface；工具仍经同一注册与策略闸门。M3 之后其中大部分变成"写一个插件" |
| M5 | 浏览器、Computer Use、容器执行器、后台任务 | 专用工具包与 PlatformPort 能力探测；Linux 必须明确降级 |
| M6–M7 | Trace、评测、记忆、技能生成与自我改进 | 事件真相之外的可轮转取证/评测数据；判权与护栏代码仍受红线保护 |

新增功能不应提前建立这些空包，也不应为了复用把 Electron、Node I/O 或 Provider 特性渗入 Kernel。

## 8. 架构守护与变更纪律

| 规则 | 当前执行方式 |
|---|---|
| 契约单一来源 | `@xm/contracts` 的 Zod schema；跨 IPC/跨包两侧验证 |
| 依赖方向 | dependency-cruiser；Kernel 禁 Node/Electron，Renderer 禁 Node |
| 事件可回放 | `reduce()` 纯函数、持久/瞬态分层、存储端口一致性测试 |
| 工具安全 | schema 注册断言、能力闭集、能力网关与策略测试 |
| 规模与工具链 | 单文件规模检查、四次 TypeScript 检查、ESLint、包体积预算 |
| 安全护栏有效性 | 每次改护栏均需构造它应该拦截的反向演练 |

影响跨包接口、依赖方向、数据格式或安全策略的改动，必须同批更新文档并新增 ADR。实施前先读
`CLAUDE.md`、相关 ADR 和 [10-契约设计](./10-契约设计.md)；发现旧文档与 ADR-0039 冲突时，
不得恢复 `ask` 或审批路径。
