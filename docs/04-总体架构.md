# 04 · 总体架构

> 本文是架构讨论的主战场，给出分层、进程模型与核心抽象的**全景**。
>
> ⚠️ 本文中的接口签名是**讨论用草案**。契约的**实现级规格**已收敛到 [10-契约设计](./10-契约设计.md)——两处不一致时**以 10 为准**，本文只保留全景视角，不再逐字同步细节。

## 1. 分层视图

```
┌───────────────────────────────────────────────────────────────────────┐
│  Surfaces 表现层（可替换、互不感知）                                    │
│  Desktop UI (React)   │   CLI (xm)   │   Headless Daemon (未来)        │
└───────────────────────────────┬───────────────────────────────────────┘
                                │  Session API（事件流订阅 + 命令下发）
┌───────────────────────────────┴───────────────────────────────────────┐

└───────────────────────────────┬───────────────────────────────────────┘
                                │  Ports（纯接口，内核定义）
```

**依赖方向严格单向向下到 Ports 为止**：Surfaces → Runtime → Kernel ← Adapters。内核不知道任何适配器的存在。

## 2. 进程模型

```
┌──────────────────────────────────────────────────────────────┐
│ Electron Main Process                                        │
│  · Runtime + Kernel（Agent 循环在这里跑）                     │
│  · SQLite、钥匙串、文件监视、权限闸门                          │
│  · 窗口与托盘、自动更新                                        │
└───┬─────────────┬──────────────┬──────────────┬──────────────┘
    │ MessagePort │ child_process│ child_process│ child_process
┌───┴─────────┐ ┌─┴──────────┐ ┌─┴──────────┐ ┌─┴─────────────┐
│ Renderer    │ │ Plugin Host│ │ MCP Server │ │ PTY / 工具子进程│
│ React UI    │ │ (每插件一进程│ │ (每服务一进程)│ │                │
│ 无 Node 权限 │ │  能力受限)  │ │            │ │                │
└─────────────┘ └────────────┘ └────────────┘ └───────────────┘
```

关键决策：

- **Agent 循环在主进程**。渲染层崩溃/重载不影响运行中的任务；关窗到托盘任务继续跑。
- **插件进程外隔离**。插件崩溃不拖垮宿主；能力通过 IPC 受控暴露（详见 [05](./05-可插拔与扩展体系.md)）。
- **渲染层零 Node 权限**。`contextIsolation: true`、`nodeIntegration: false`，只通过 preload 暴露的窄接口通信。
- **重 CPU 任务出主进程**。索引、大 diff、图像处理走 worker 或 Rust sidecar，绝不阻塞 Agent 循环。

## 3. 包结构

```
packages/
├── contracts/        # ✅ 唯一契约来源：Zod schema + 推导类型（事件/工具/配置/插件清单）
│                     #   零依赖，被所有人引用
├── kernel/           # ✅ 纯内核：状态归约 / 权限判定 / 工具注册 / 全部端口定义
│                     #   依赖：contracts + zod。禁止 node:*
├── platform/         # ✅ PlatformPort 的 Node 实现：os / 路径 / 能力探测。禁 electron
├── storage/          # ✅ SQLite 事件存储 + 文件 blob。索引与钥匙串留待 M1/M2
├── runtime/          # ✅ 装配层：事件总线 + 唯一 seq 分配点 + Turn 循环
├── providers/        # M1 · 模型适配：anthropic / openai / google / ollama
├── tools-core/       # ✅ 基础工具集：fs 读写列举 + 路径能力网关 + 写前还原点
│                     #   （M1-d 再加 shell / web-fetch；edit / search 是 M2）
├── executors/        # M1+ · 执行后端：local / container / ssh
├── indexer/          # M2 · 代码/文件索引：ripgrep + tree-sitter + FTS5 + 向量
├── mcp/              # M3 · MCP 客户端宿主（stdio / sse / http）
├── plugin-host/      # M3 · 插件进程宿主、能力网关、清单校验
├── tools-browser/    # M4 · 浏览器自动化工具集（Playwright）
├── tools-computer/   # M4 · 计算机操作工具集（截屏 / 输入注入 / 窗口）
└── ui-kit/           # M1+ · 共享 React 组件与主题

apps/
├── desktop/          # ✅ Electron main + preload + renderer
└── cli/              # M3 · xm：无 GUI 跑同一个 runtime
```

> **未开工的包不建空目录。** 空包比不存在的包更容易掩盖分层问题——依赖图里多一个
> 谁都不引用的节点，depcruise 的规则就少一处能匹配的地方。本项目已经吃过两次亏：
> `runtime-不得依赖-electron` 这条规则指着一个不存在的目录，整整一个里程碑没匹配过任何模块。

> **验证扩展性的硬指标**：`apps/cli` 必须只依赖 `@xm/runtime`，不依赖 electron。如果 CLI 跑不起来，说明 runtime 泄漏了 Electron 依赖。

## 4. 核心抽象（草案）

### 4.1 模型提供商 ModelProvider（端口已落地 → `kernel/src/port/model-provider.ts`）

```ts
interface ModelProvider {
  readonly id: string;                       // "anthropic" | "openai" | ...
  listModels(): Promise<ModelInfo[]>;
  capabilities(model: string): ModelCapabilities;
  stream(req: ModelRequest, signal: AbortSignal): AsyncIterable<ModelChunk>;
  countTokens?(req: ModelRequest): Promise<number>;
}

interface ModelCapabilities {
  tools: boolean;
  parallelTools: boolean;
  vision: boolean;
  documents: boolean;
  thinking: boolean;          // 扩展思考 / reasoning
  promptCache: boolean;
  maxContext: number;
  maxOutput: number;
}

type ModelChunk =
  | { kind: 'text_delta';      text: string }
  | { kind: 'thinking_delta';  text: string }
  | { kind: 'tool_call_start'; id: string; name: string }
  | { kind: 'tool_call_delta'; id: string; argsJson: string }   // 增量 JSON
  | { kind: 'tool_call_end';   id: string }
  | { kind: 'usage';           usage: Usage }
  | { kind: 'stop';            reason: StopReason };
```

**要点**：只有流式接口；能力自描述（内核据此决定是否走并行工具、是否附图、是否插入缓存断点）；`ModelRequest` 是 Provider 无关的中立结构，各家的差异（Anthropic 的 `system` 独立、OpenAI 的 `developer` 角色、思考块的处理）全部在适配器里消化。

### 4.2 消息与内容块

```ts
type ContentBlock =
  | { type: 'text';        text: string }
  | { type: 'image';       source: BlobRef; mime: string }
  | { type: 'document';    source: BlobRef; mime: string }
  | { type: 'thinking';    text: string; signature?: string }
  | { type: 'tool_use';    id: string; name: string; input: unknown }
  | { type: 'tool_result'; toolUseId: string; content: ContentBlock[]; isError: boolean };
```

多模态从第一天就在类型里（参考项目最大的架构缺口）。大块二进制存 blob 表，消息里只放 `BlobRef`，避免事件流膨胀。

### 4.3 工具 Tool

```ts
interface Tool<I = unknown, O = unknown> {
  readonly name: string;                     // 全局唯一，如 "fs.read"
  readonly group: string;                    // 工具集，用于按组授权/开关
  readonly description: string;              // 给模型看的，是提示词的一部分
  readonly input: ZodType<I>;                // 严格校验 + 导出 JSON Schema
  readonly risk: RiskLevel;                  // 'safe' | 'low' | 'medium' | 'high'
  readonly capabilities: Capability[];       // 需要的能力，权限闸门据此判定
  readonly concurrency: 'parallel' | 'exclusive';
  readonly available?: (ctx: ToolContext) => boolean;   // 动态可用性（如无 git 仓库则不暴露 git 工具）

  /** 声明本次调用要触碰的资源，供调度器做冲突检测。声明不了就别声明——
   *  返回 undefined 等同于"我可能碰任何东西"，调度器按 exclusive 处理。见 ADR-0005 */
  resources?(input: I): ResourceClaim[];

  execute(input: I, ctx: ToolContext): AsyncIterable<ToolProgress<O>>;
}

type ResourceClaim =
  | { kind: 'path'; mode: 'read' | 'write'; glob: string }
  | { kind: 'pty';  sessionId: string }
  | { kind: 'net';  host: string }
  | { kind: 'global'; name: string };        // 兜底：具名互斥锁

interface ToolContext {
  sessionId: string;
  cwd: string;
  executor: Executor;          // 命令跑在哪（本地/容器/远程）由此决定
  signal: AbortSignal;
  requestPermission(req: PermissionRequest): Promise<PermissionDecision>;
  emit(event: ToolProgressEvent): void;      // 流式中间产物
  log: Logger;
}

type ToolProgress<O> =
  | { kind: 'progress'; message?: string; data?: unknown }
  | { kind: 'result';   output: O; display?: DisplayHint; forModel: ContentBlock[] };
```

**四个关键设计**：

1. `forModel` 与 `display` 分离——给模型看的（省 token、结构化）和给人看的（截图、diff、表格）不是同一份数据。参考项目把它们混在一起，导致编排层要为每种工具打补丁。
2. `capabilities` 声明式——权限判定不靠工具自觉，靠闸门统一拦截。
3. `concurrency` 声明式——调度器据此决定并行策略。
4. `execute` 返回异步迭代器——中间进度天然流式。

### 4.4 执行器 Executor

```ts
interface Executor {
  readonly kind: 'local' | 'container' | 'remote';
  readonly id: string;
  exec(cmd: ExecSpec, signal: AbortSignal): Promise<ExecResult>;      // 一次性命令
  session(spec: PtySpec): Promise<PtySession>;                        // 长会话 PTY
  fs: FileSystemPort;                                                 // 路径语义由执行器决定
  dispose(): Promise<void>;
}
```

同一套工具代码，通过换 Executor 决定作用于本机、容器还是远程主机。这是"帮我操作电脑"与"安全跑不信任代码"之间的开关。

### 4.5 事件流 EventStream

```ts
type XmEvent =
  // 会话
  | { type: 'session.created' }  | { type: 'session.renamed'; title: string }
  // 模型
  | { type: 'message.start'; role: Role } | { type: 'message.delta'; text: string }
  | { type: 'thinking.delta'; text: string } | { type: 'message.end'; message: Message }
  // 工具
  | { type: 'tool.start'; callId: string; name: string; input: unknown }
  | { type: 'tool.progress'; callId: string; data: unknown }
  | { type: 'tool.end'; callId: string; ok: boolean; display?: DisplayHint }
  // 权限
  | { type: 'permission.request'; req: PermissionRequest }
  | { type: 'permission.decision'; decision: PermissionDecision }
  // 任务与子 Agent
  | { type: 'todo.updated'; todos: Todo[] }
  | { type: 'subagent.start' | 'subagent.end'; agentId: string; ... }
  // 运维
  | { type: 'usage.recorded'; usage: Usage; costUsd: number }
  | { type: 'checkpoint.created'; id: string; label: string }
  | { type: 'error.raised'; error: XmError }
  | { type: 'turn.end'; reason: StopReason };
```

所有事件带 `id / seq / sessionId / ts`。**会话状态 = reduce(events)**；UI、CLI、持久化、评测回放全部消费同一条流。

### 4.6 事件存储 EventStore（端口，已定案 → [ADR-0013](./adr/0013-存储引擎选型与EventStore端口.md)）

```ts
interface EventStore {
  listSessions(): Promise<readonly SessionSummary[]>;              // 读投影，不回放
  read(id: SessionId, o?: ReadOptions): AsyncIterable<PersistedEvent>;  // 流式，不物化
  openForWrite(id: SessionId): Promise<SessionWriter>;             // 取会话级排他标记
  rebuildSummaries(): Promise<void>;
  close(): Promise<void>;
}

interface SessionWriter {                 // 持有它 = 持有排他标记
  readonly lastSeq: number;
  append(events: readonly SealedEvent[]): Promise<void>;  // 原子；只收已脱敏的持久化事件
  close(): Promise<void>;
}
```

与其它草案不同，这个端口**已经是实现级的**：接口在 `kernel/src/port/event-store.ts`，
七条不变量与 12 条一致性用例（`EVENT_STORE_CONTRACT`）随代码走，参考实现是 `MemoryEventStore`，
SQLite 实现在 `packages/storage`，契约在**内存库与文件库两个工厂**上各跑一遍。

### 4.7 权限判定 PolicyEngine（纯函数）

```ts
// 纯函数：相同输入必得相同输出，可穷举测试
function evaluate(rules: PolicyRuleSet, req: PermissionRequest): PolicyVerdict;

type PolicyVerdict =
  | { effect: 'allow'; reason: string }
  | { effect: 'ask';   reason: string; risk: RiskLevel }
  | { effect: 'deny';  reason: string };
```

## 5. 一次对话的完整链路

```
用户输入
  │
  ├─→ Runtime.createTurn(sessionId, input)
  │      · 追加 user 消息事件（append-only 落库）
  │      · 建立 checkpoint（工作区快照点）
  ▼
ContextBuilder.build()
  · system prompt（稳定前缀 → 命中 prompt cache）
  · 长期记忆检索（按当前意图检索，不全量塞入）
  · 中期摘要 + 近期原文（token 预算分配）
  · 工具 schema（按当前上下文过滤 available 的工具）
  ▼
AgentLoop（内核主循环，无 I/O，通过 Ports 调用）
  │
  ├─ provider.stream() ──→ 事件流：thinking.delta / message.delta / tool_call
  │                          （逐块转发到 UI，用户可随时 abort）
  │
  ├─ 收到 tool_calls → 对每个：
  │     1. Zod 严格校验（失败 → 结构化错误回传模型，不静默丢弃）
  │     2. PolicyEngine.evaluate() → allow / ask / deny
  │     3. ask → 发 permission.request 事件，等 UI 决策（可"本次/本会话/永久"）
  │     4. Scheduler 编排：parallel 组并发，exclusive 串行
  │     5. tool.execute() → 流式 progress → tool.end
  │     6. 结果分流：forModel 回上下文，display 给 UI
  │
  ├─ 结果回灌 → 下一轮 provider.stream()
  │
  └─ 无工具调用 或 达到停止条件 → turn.end
  ▼
持久化（每个事件即时 append）+ usage 聚合 + 记忆沉淀（异步）
```

对比参考项目：去掉了 `PLANNING → EXECUTING → UPDATING → SUMMARIZING` 的硬状态机。**规划是模型用 `todo` 工具做的事，不是流程的阶段**。简单任务一轮结束，复杂任务模型自己拆解，成本与灵活性双赢。

## 6. 持久化设计

```sql
-- 事件：append-only，永不 UPDATE
events(session_id, seq, type, payload_json, ts)  PRIMARY KEY(session_id, seq)

-- 消息：由事件物化，供上下文装配快速读取
messages(session_id, idx, role, blocks_json, tokens, ts)

-- 大对象：截图、附件、大文件内容，内容寻址
blobs(hash, mime, size, path, refcount)

-- 会话元信息
sessions(id, title, cwd, status, model_ref, created_at, updated_at)

-- 用量与成本
usage(session_id, turn, provider, model, input_tokens, output_tokens,
      cache_read, cache_write, cost_usd, ts)

-- 还原点
checkpoints(id, session_id, seq, kind, ref, label, ts)

-- 记忆
memories(id, scope, kind, content, embedding, source_session, ts)

-- 审计（安全相关，独立库文件，只增不删）
audit(id, ts, actor, action, target, verdict, reason, session_id)
```

原则：**events 是真相，其它都是可重建的派生数据**。任何时候可以 `DROP` 掉 messages 重新 reduce 出来。

`sessions` 表就是 `SessionSummary` 投影的落地形态——它必须与 `events` 在**同一个事务**里更新，
否则崩在中间会留下"事件在、会话列表里没有"的会话（[ADR-0013](./adr/0013-存储引擎选型与EventStore端口.md) 决策六）。
引擎选型（为什么不是 PostgreSQL）与端口契约同见该 ADR。

## 7. 并发与取消

- 每个 Turn 一个 `AbortController`，向下贯穿到模型请求、工具执行、子进程。用户点"停止"必须在 200ms 内真正停止（包括杀掉子进程）。
- 工具调度：只读并发（默认上限 8），写操作互斥。写工具持有的资源（路径、终端会话）参与冲突检测。
- 每个会话一个串行 Turn 队列；多会话可并行（受全局并发预算约束）。
- 后台任务（长命令、监视器）脱离 Turn 生命周期，有独立的进程注册表，进程重启时能识别并重连或清理。

## 8. 崩溃恢复

已于 2026-08-09 完成（M1-e，[ADR-0032](./adr/0032-地基复审三-M1收尾前的原则符合度审查.md)
延续下来的"状态不设第二个持久化源"这条原则在这里落地）。**不新增 `sessions.status`
列**：运行中 / 已中断 / 空闲这三态不持久化，由调用方在扫描/查询时对事件流现算：

1. 启动时**只读**扫描全部会话（`scanForOrphanedSessions`，不 `openForWrite()`，
   不会跟仍然真的活着的另一个进程抢锁）：读事件流重建状态，`detectOrphanedTurn()`
   （`@xm/kernel`）识别四种停法——模型正在流式输出、工具没跑完（含一批并行调用里
   "连 `tool.start` 都没轮到"的遗留调用）、卡在权限审批、停在迭代边界上。
2. 用户选择"继续"：`synthesizeInterruption()` 先补发缺失的收尾事件（比如
   `message.interrupted{reason:'crash'}`），再从崩溃发生的那个迭代边界续跑
   （不重连原生进程、不重放原始工具调用）。
3. 用户选择"放弃"：同样先补发收尾事件，再写 `turn.end(reason:'aborted')`——
   与停止按钮完全同一套语义。

**不允许出现"任务消失了但没人知道"的状态**（参考项目的现状）。

## 9. 架构守护（自动化）

| 规则 | 检查方式 |
|---|---|
| kernel 不依赖 node:*/electron | dependency-cruiser 规则，CI 阻断 |
| 适配器不被内核反向引用 | 同上 |
| 契约变更必须同步双方 | contracts 包版本变更触发全量类型检查 |
| 无 `any` | eslint error |
| 新工具必须有 Zod schema + 权限声明 + 测试 | 工具注册时运行时断言 + 单测模板 |

架构规则写成代码，而不是写在文档里靠自觉——这也是给未来的小明自己准备的护栏。
