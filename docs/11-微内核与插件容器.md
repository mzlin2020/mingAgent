# 11 · 微内核与插件容器

> 本页是新 M3「微内核化重构」的总纲：为什么要做、从参考实现拿什么、不拿什么、
> 边界画在哪。实现级契约以 [10-契约设计](./10-契约设计.md) 与
> [ADR-0052 ~ ADR-0068](./adr/README.md) 为准；阶段拆分见 [M3-阶段划分](./M3-阶段划分.md)。
>
> **状态（2026-08-14）**：M3-a～M3-e 已完成；容器、Turn 扩展点、Agent Inbox 与 local
> 执行世界已由 desktop/headless 的 profile 和运行入口消费。M3-f 至 M3-h 仍是目标形态。

## 1. 这不是一个新方向

[01-愿景与设计原则](./01-愿景与设计原则.md) 的**原则二**从 M0 就写着：

> **一切皆插件。** 模型、工具、MCP、执行器、技能、UI 面板——六类扩展点，全部走同一套
> 注册/发现/生命周期机制。
>
> **约束**：删掉 `packages/tools-core` 后，内核 + UI 必须仍能启动（只是没有工具可用）。
> 这是可以写成集成测试的。

M3-b 已把原来的 `services.ts` 手工装配迁到 profile 插件树，并固定了无业务行启动与空工具 UI；
M3-e 又完成执行世界接缝，并真实跑通物理删除 `tools-core` 后的 typecheck 与 headless smoke。

所以新 M3 不是引入一个新架构方向，是**兑现一条已经写下、但一直没有机制支撑的原则**。
参考实现的本机源码位于 `C:\Users\EDY\Desktop\code_mine\deepseek-harness`，提供的正是那套缺失的机制。
实现时可以借鉴其容器与扩展点源码，但必须按本文 §4 过滤掉与小明现有安全边界冲突的设计。

## 2. 现状诊断：缺的到底是什么

M2 收官时，小明的**安全底座**是这个项目最扎实的部分——红线跨层判定、路径能力网关、
seq 单点分配、`reduce(events)` 可回放，每一条背后都有一份 ADR 和一次真实事故。
而**组合能力**接近于零，具体是四个洞：

| # | 洞 | 证据 |
|---|---|---|
| 一 | **只有一条装配路径** | `services.ts` 1043 行手工接线；headless 冒烟是另一条独立脚本；`xm` CLI 不存在。同一套引擎从未被第二次装配过 |
| 二 | **主循环没有扩展点** | `turn.ts` 391 行把上下文组装、checkpoint、工具分发、结果截断焊死在流程里。加任何新行为只能改它 |
| 三 | **工具与 UI 没有解耦** | `DisplayHint` 契约在 contracts 里躺着，**零生产者、零消费者**；真实需求绕过它长出了 `edit-review.ts` 专用通道 |
| 四 | **只有一条输入路径** | `sendUserMessage → runTurn`，同步、一次性。后台任务、定时任务、文件变更、子 Agent 回传在结构上无处落地 |

第四个洞最要命。路线图 M5–M7 的一大半（后台任务、定时任务、记忆召回、目标持续推进、
失败聚类的自动发现）**都要先有"给一个正在运行的 Agent 递东西"这个概念**，
否则每一个都会自己发明一条私有路径塞进 `turn.ts`。
**"高自主性"缺的是这块骨架，不是缺功能。**

## 3. 从参考实现拿什么

deepseek-harness 是一个跑在 vendored Cordis 上的插件化 harness：整个产品——
包括模型适配器、工具注册表、会话日志、Agent 循环本身——都是挂在容器上的插件，
51 个包、约 20 个能力接缝。它的组合能力正是小明缺的。

| 拿的东西 | 小明怎么落 | 对应 ADR |
|---|---|---|
| 插件容器：服务按 key 注册、`inject` 声明依赖、`effect` 可撤销、四种派发模式 | **自研**约 600–800 行放 `@xm/kernel/src/container/`，纯逻辑零 I/O | [0052](./adr/0052-插件容器与效果模型.md) |
| 能力接缝 = 定义 / 提供者 / 消费者 三角色 | `port/` 正名，统一注册与注入形状；新增**执行世界**接缝 | [0054](./adr/0054-能力接缝三角色与执行世界.md) |
| 回合循环即扩展点集合 | `turn.ts` 拆成驱动器 + 五个回合级扩展点 + 工具执行十二步 | [0055](./adr/0055-Turn驱动器的扩展点契约.md) |
| Agent 句柄 + Inbox（`followup`/`steer`/`inject`） | 同形照搬，但 `inject` **必须落持久事件** | [0056](./adr/0056-Agent句柄与Inbox.md) |
| 工具自带渲染意图（纯函数投影 + 落库元数据） | 同形照搬，四种卡片，`DisplayHint` 升级 | [0058](./adr/0058-工具渲染意图与结果投影.md) |
| profile / patch 配置化组合 | 简化成两层，四个内建 profile | [0059](./adr/0059-组合配置profile与patch层.md) |
| 运行时不变量注册表 + 文档图谱生成 | 同形照搬 | [0060](./adr/0060-运行时不变量注册表与文档图谱生成.md) |
| Code Mode（`run_code`） | 照搬，但子调用**重入完整闸门链** | [0061](./adr/0061-CodeMode与工具SDK生成.md) |

## 4. 不拿什么，以及为什么

这一节比上一节更重要。**照着参考实现补代码的人，最容易把这里刻意删掉的东西补回来。**

### 4.1 不拿「没有特权内核」

参考实现的架构文档第一句就是：

> There is no privileged core to patch.

对它成立，对小明不成立。小明保留六项不可绕过的底座（seq 分配、`evaluate()`、路径网关、
`SecretStore`、`redact()`、落库顺序），由容器在装配收敛时断言在位，缺失即拒绝启动。
理由是三次真实事故：ADR-0017（红线挂错能力，一个普通写文件工具整体绕过）、
ADR-0018（Windows 8.3 短名绕过）、ADR-0039（三次体验问题都出在"判完再修正一次"的形状上）。
详见 [ADR-0053](./adr/0053-微内核的特权底座与扩展点边界.md)。

> **原则二的措辞需要修订。** 原文说"内置能力也必须用插件机制实现，**不允许内置能力走特权后门**"，
> 字面上禁止了 ADR-0053 的底座。这里的区分是：**底座不是一个能力，它是判定能力能否运行的东西**。
> 工具、Provider、执行器、技能、UI 面板——这些"能力"一律走插件机制，无一例外；
> 而权限判定、路径规范化、密钥读取、seq 分配不是能力，它们是能力的裁判。
> `docs/01` 已按此修订。

### 4.2 不拿 `ask` 与审批接缝

参考实现的 `PreToolDecision` 是 `allow | deny | ask`，`ask` 由 `ctx.approval` 应答，
没有应答者时降级为 deny。**照搬时必须删掉 `ask` 这一支。**
ADR-0039 已经把它从 `PolicyVerdict` 里删除，那是编译期护栏。
参考实现有这个选项，不构成把它加回来的理由。

### 4.3 不拿「三方插件全进程内」

参考实现的插件就是 npm 包，全部进程内、全部受信。`docs/05` 承诺过"一插件一进程 + 能力网关"。
**本次不定这个立场**，`docs/05` 的进程隔离承诺原样保留并标注为待新 M4 决议。
M3 只做进程内容器（一方插件与小明自己生成的插件），三方隔离与 MCP 一起在新 M4 定案。

### 4.4 不拿工程规模上的做法

- **vendor 框架源码**：一次性引入数千行非自有代码，与单文件 400 行的规模纪律正面冲突。
- **51 个包 / 一角色一包**：小明包数 8 → 10，只新增固定边界包 `@xm/compose` 与
  `@xm/tool-runtime`，不随插件数量增长。
  插件住在现有包里——这同时是保住 depcruise 包边界规则的前提（见 §7）。
- **per-file 100% 覆盖率闸门**：kernel 85% 行门槛不变。本仓库六次"规则存在但从未生效"
  没有一条是覆盖率不足造成的。
- **双语文档与 i18n 流水线**：中文优先不变。

## 5. 容器：五个概念

| 概念 | 语义 | 替代今天的什么 |
|---|---|---|
| **服务** | 一个稳定的 `ctx.<key>`。消费者按 key 取，不 import 具体实现 | `TurnDeps` 上的 12 个可选字段 |
| **插件** | `{ name, inject?, apply(ctx) }`。`inject` 声明依赖，容器据此排装配顺序 | `services.ts` 里的手工顺序 |
| **效果** | 一切注册经 `ctx.effect()` 并返回撤销函数 | 无对应物——注册了撤不掉 |
| **类型化事件** | 四种派发模式：`emit` / `waterfall` / `parallel` / `serial` | 无对应物 |
| **作用域** | `ctx.fork()` 的子上下文，卸载父即卸载子 | `subagent.ts` 里手工过滤 `source.kind === 'builtin'` |

`waterfall` 是环绕中间件：监听器签名 `(...args, next)`，**调用 `next()` 才交给下一个，
不调用即短路**。ADR-0055 的闸门顺序与 ADR-0053 的"只能收紧"都建立在这条语义上。

### 两套事件，不合并

| | 会话事件（`EVENT_SPECS` + `EventBus`） | 容器事件（扩展点） |
|---|---|---|
| 落库 | 持久或显式瞬态 | **从不落库** |
| seq | 有，单点分配 | 无 |
| 跨进程 | 是，两侧 Zod 校验 | 否 |
| 可回放 | 是 | 否 |
| 谁能加 | contracts，或 `ext.*` 通道（[ADR-0057](./adr/0057-扩展事件通道与未知事件语义.md)） | 任何插件 |

贯穿两者的一条硬规则，照搬自参考实现：

> **模型可见 ⟺ 已落库。** 任何进入模型请求的东西，必须能从会话事件流重建。

它与小明的第一不变量（状态 = `reduce(events)`）是同一件事的两种说法。
`inject` 必须落 `context.injected` 事件，就是这条规则的直接推论。

## 6. 扩展点全表

### 6.1 工具执行：十二步

```
① 工具查找（含 available() 过滤）
② parseInput —— strict 校验
③ 构造 ToolContext
④ 网关规范化 —— realpath.native / argv 分解 / DNS 解析，回写 input，失败关闭
⑤ 主张完备性断言 —— 声明的每个 capability 都必须有对应 claim
─────── ①~⑤ 是特权链段：不得插入、重排或改写 ───────
⑥ tool/pre-execute（waterfall）—— 插件可追加 deny，不可改 input，不可放宽
⑦ PolicyEngine evaluate() + guard —— 单调终局，27 条红线在此
─────── 判定完成，此后不可再放宽 ───────
⑧ tool/execute（waterfall，环绕）—— checkpoint、超时、重试、度量
⑨ 工具体执行（经 ctx.executor）
⑩ tool/post-execute（waterfall）—— 结果截断、内容替换、附加上下文
⑪ 渲染投影（presentationMeta）
⑫ tool/result（只读观察）—— 审计、指标
```

### 6.2 回合级

| 扩展点 | 模式 | 用途 |
|---|---|---|
| `turn/pre-step` | waterfall | 决定模型这一步看到什么；可整体拒绝这一步 |
| `turn/request` | waterfall | 请求成形前最后一次修改 |
| `llm/stream` | waterfall | 包住流式读取（重试、录制、度量） |
| `turn/step-error` | waterfall | 请求失败后决定重试还是保留错误 |
| `turn/stopping` | serial | 自然停止前的终局检查，可要求再走一步 |

### 6.3 特性 → 机制映射

新行为一律挂在上面的点上。**这张表里没有一行需要改主循环**——这是"微内核"这个说法
可被检验的形式。

| 想做的事 | 挂在哪 |
|---|---|
| 加一个模型 Provider | 注册 `ctx.llm` 提供者 |
| 加一个工具 | `ctx.tools.register()`，schema 自动进提示词，卡片自带 |
| 加一个执行世界（容器 / 远端） | 注册 `ctx.executor` 提供者，fs/shell/pty 整片跟着换 |
| 上下文压缩策略 | `turn/pre-step` + `turn/step-error` |
| 写前还原点 | `tool/execute` 环绕 |
| 结果截断 | `tool/post-execute` |
| hooks（用户级 / 项目级） | `turn/pre-step`、`tool/pre-execute`、`tool/post-execute`、`turn/stopping` |
| plan mode | 一条 `ext.*` 持久状态 + `tool/pre-execute` 收紧 + 提示词段 |
| MCP server | 一个 server 一个插件：发现工具 → `ctx.tools.register()` |
| Skill 技能 | 提示词段 + 一个工具；调用时 `inject()` 正文 |
| 记忆 | 提示词段 + 一个工具 + `inject()` 召回 |
| 后台任务完成通知 | `inject({ source: { kind: 'job' } })` |
| 定时任务 | 定时器 → 空闲时 `followup`（标明来源），忙时 `inject` |
| 文件变更通知 | 监听器 → `inject()` |
| 子 Agent 回传 | `inject({ source: { kind: 'subagent' } })`，粘性污点照旧 |
| 目标持续推进 | `turn/stopping` 决定是否再走一步 |
| 审计 / 指标 | `tool/result` 只读观察 |
| 新的 UI 卡片 | 注册渲染器；工具侧只写纯函数投影 |
| 插件自有持久状态 | `ext.persisted` 信封 + 自建投影 |

## 7. 包布局与依赖方向

**依赖方向的硬约束一字不改。** 变化有两处：新增 `@xm/compose` 与 `@xm/tool-runtime`。

```
Surfaces (apps/desktop, apps/cli)
   ↓
Compose   @xm/compose      profile 解析 · patch 合并 · 内建 profile · 装配期断言
   ↓
Runtime   @xm/runtime      事件总线 · seq 单点分配 · Turn 驱动器 · 崩溃恢复
   ↓ 接缝定义（全部在 kernel/src/port/）
Kernel    @xm/kernel       纯逻辑 · 零 I/O · 插件容器住在这里
   ↑ 提供者实现接缝
platform · storage · providers
@xm/tool-runtime   路径网关 · checkpoint · local 执行世界     ← 能力的裁判
@xm/tools-core     工具实现，仅此而已（可被整包 rm -rf）        ← 能力
```

depcruise 新增规则：`@xm/compose` 不得依赖 electron、除 `apps/**` 外无人可依赖它；
`@xm/tools-core` 整包禁止 import `node:*`（只有 `@xm/tool-runtime` 可以）；
`@xm/tools-core` 不得依赖 `@xm/tool-runtime`。其余 20 条一条不改。

**第二处变化是 2026-08-14 规划复审的结果**（[ADR-0063](./adr/0063-安全底座与工具实现的包边界.md)）。
初稿把基线行 `baseline.gateway` 指向 `@xm/tools-core`，于是"删掉 `packages/tools-core`
仍能启动"这条原则二的可检验约束在结构上不可能成立，M3 的 DoD 被悄悄换成了更弱的
"删掉全部**业务插件行**仍能启动"——**删行不等于删包**。
根因是包切错了：网关与 checkpoint 是**能力的裁判**，却和**能力**挤在同一个包里。
拆开之后原则二第一次可以真的跑，且"工具不得直接碰 `node:*`"从**包内文件名单**
升级成了**包边界规则**——名单会因为"新文件忘了进名单"而漏，边界不会。

**为什么不为插件新建细粒度包**：这是 [ADR-0052](./adr/0052-插件容器与效果模型.md) 的对策之一。
容器化会让一部分依赖关系从 import 图挪到运行时，削弱 depcruise 的静态护栏——
这是真损失。保住包边界规则是三条对策里最重要的一条：插件住在现有包里，
"kernel 不许 import electron"这类约束依然由 import 图强制。

## 8. 与七条原则的逐条对照

| 原则 | 这次重构的影响 | 净效果 |
|---|---|---|
| 一 · 内核最小且纯净 | 容器进 kernel，但它是纯逻辑零 I/O，且这条约束反过来保证容器不会长出文件读写 | 不变 |
| 二 · 一切皆插件 | **从未落实的约束第一次可执行**（`rm -rf packages/tools-core` 后应用仍启动，见 §7）；措辞按 §4.1 修订 | **显著兑现** |
| 三 · 契约优先 | `ext.*` 通道让插件事件也走 Zod；两套事件的分工写进文档 | 加强 |
| 四 · 默认不信任 | 扩展点只能收紧；子调用重入闸门；注入内容是新的污点入口并被覆盖 | 加强 |
| 五 · 流式优先 | `llm/stream` 成为扩展点；流式语义不变 | 不变 |
| 六 · 可观测可回放可回滚 | `inject` 落库；渲染投影必须是纯函数（实时与回放同结果）；checkpoint 成为环绕插件并进装配断言 | 加强 |
| 七 · 为自我迭代而设计 | **最大的一条**：自我改进从"改内核"降级为"加插件"——可审阅、可撤销、失败不拖垮主循环 | **显著加强** |

唯一需要修订措辞的是原则二，见 §4.1。其余六条一字不改。

## 9. 这次重构不解决什么

一次架构重构最容易犯的错，是把"用起来不顺手"误当成"结构不够优雅"。
下面这些**插件化解决不了**，如果它们是真实痛点，必须在 M3 之外单独排期：

- 上下文压缩之后模型忘掉关键信息（是压缩策略问题，不是扩展点问题）
- 多文件编辑的冲突处理与内容漂移体验
- 检索召回不准
- 终端交互体验（受控 argv 的固有限制，ADR-0040）
- 模型本身的能力边界

真实痛点清单待补，见 [M2 收官记录](./experience/m2/收官记录.md) §2。

## 10. 2026-08-14 规划复审

本文初版与最初十份 ADR 定稿当天做了一次独立复审，抓到八处问题，**全部属实**。
其中三处是真的设计漏洞，五份新 ADR（[0062](./adr/0062-扩展点的异步契约与执行收据.md) ~
[0066](./adr/0066-时钟与ID的注入.md)）为此而写：

| 问题 | 性质 | 落到哪 |
|---|---|---|
| 原则二的验收被换成更容易通过的一条 | **降低了门槛而没留痕** | ADR-0063 拆包，DoD 改回物理删除 |
| `waterfall` 标成"不 await"，与它要承载的工作矛盾 | 契约自相矛盾 | ADR-0062 |
| "跳过 `next()` 谎称执行过"写成"或…（优先做不到）" | **决策没做完就写了 Accepted** | ADR-0062 的执行收据 |
| Code Mode 承诺"程序拿不到 fs/net/进程" | 普通 Node worker 兑现不了 | ADR-0061 降级 🟡，机制待 H2 |
| Inbox 没定崩溃语义、`steer` 没定是否取消在飞调用 | 缺口 | ADR-0064 |
| 三件套只出不进，退役不掉 `edit-review` | 缺口 | ADR-0065 |
| "事件流逐条一致"照现有代码跑不出稳定结果 | 验收不可执行 | ADR-0066 |

**留下的做法**：前两类问题有一个共同形状——**用"或"、用更宽的措辞、用更容易通过的验收，
把一个没做完的决定写成已定案**。它比写错更难自查，因为文档读起来是自洽的。
判据：**改验收标准前先问它是不是在降低门槛**；一份 ADR 里出现"或""待定""优先"，
它就还不是 Accepted。
