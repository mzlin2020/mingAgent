> 同时**不削弱**M0–M2 攒下的安全底座。每个阶段结束时仓库都必须处于可运行、可单独验收的状态。

## 1. 拆分原则

1. **一次只实现一个阶段。** 当前阶段通过验收并更新文档后，才开始下一阶段。沿用 M2 的纪律。
2. **行为等价优先于结构优雅。** M3-b 与 M3-c 是搬家，不是重写：在确定性 profile 下，
   同一输入跑出的事件流要与迁移前**逐字节对齐**（[ADR-0066](./adr/0066-时钟与ID的注入.md)）。
   想顺手改进的，记下来放到迁移完成之后。
3. **安全底座只增不减。** 任何一段结束时，[ADR-0053](./adr/0053-微内核的特权底座与扩展点边界.md)
   的六项底座必须仍然不可绕过。做不到就停在这一段。
4. **每段可停。** M3-a 之后的任何一段都可以是终点。停在哪一段，仓库都是可发布的。
5. **不恢复第二套权限系统。** 沿用 ADR-0039 的 `allow | deny`。参考实现的 `ask`
   与审批接缝不得随插件化一并搬入。
6. **架构决定先写 ADR。** 已接受的相关 ADR 是当前边界；实施中若需偏离，先补 ADR 再改代码。

所有阶段共同的基础门槛（与 M2 一致）：

- 开始前记录当前 `pnpm verify` 基线；结束时再次全量通过。
- 新机制至少包含确定性单元测试、跨层集成测试，以及一个与实际使用入口一致的 smoke。
- **护栏类改动必须先做反向演练**，证明缺少护栏时测试确实会红。本里程碑的护栏改动密度
  高于以往，这条格外要紧。
- 真实失败进入 `evals/regression/`；阶段材料归档到 `docs/experience/m3/`。

## 3. 各阶段范围

### M3-a · 容器与效果

**实施状态（2026-08-14）**：✅ 已完成。容器、确定性服务与 platform local 提供者已落地，
但尚未接入 runtime / desktop；完整证据见 [M3-a 收官记录](./experience/m3/M3-a-收官记录.md)。

**做什么**

- 在 `@xm/kernel/src/container/` 实现五个概念：服务、插件、效果、类型化事件、作用域。
- 四种派发模式，`waterfall` 的 `next()` 语义与参考实现一字不差；
  异步契约按 [ADR-0062](./adr/0062-扩展点的异步契约与执行收据.md)——
  **`waterfall` 是 await 的**，错误即中止不吞、`AbortSignal` 显式传递、重入按独立派发处理。
- `inject` 依赖解析；装配收敛时若仍有插件在等待，**报错并列出等待链**。
- `ctx.clock` / `ctx.ids` 两个服务（[ADR-0066](./adr/0066-时钟与ID的注入.md)）：
  生产用 local 提供者，测试/`eval` 用确定性提供者。**M3-b 的快照验收依赖它，必须在这一段落地。**
- **`ctx.fork()` 采用两级扁平解析 + 生命周期级联**（[ADR-0067](./adr/0067-子Agent作用域的两级扁平语义.md)）。
- 插件显式声明 `provide`，装配收敛时区分缺失提供者、等待链与依赖环
  （[ADR-0068](./adr/0068-插件服务声明与装配收敛.md)）。
- 前置：补齐 M2 验收留痕（见 [M2 收官记录](./experience/m2/收官记录.md)）。

**不做什么**

- 不接任何现有代码。本段结束时容器是一个没有消费者的纯逻辑模块。
- 不做 HMR、不做 `!!js` 配置表达式、不做完整 fiber 生命周期。

**验收**：容器用例全绿；`pnpm verify` 全绿；文件全部在 400 行以内（拆分而非豁免）。

**反向演练**

1. 插件卸载后其注册的工具 / 监听器 / 提示词段**必须**全部消失——漏撤销一处就要红。
2. 一个插件 `inject` 一个永不出现的服务 → 装配期报错并指名，**不许静默挂起**。
3. 构造依赖环 → 报错并打印环路。
4. `waterfall` 监听器不调 `next()` → 后续监听器确实不执行。
5. `waterfall` 监听器 `await` 一个永不 resolve 的 Promise + 触发 `AbortSignal`
   → 链条必须能被取消，不能挂死。
6. `parallel` 的一个观察者抛出 → 其余观察者仍执行完毕（`docs/05` 红线三：扩展失败不中断主循环）。
7. 在 `packages/runtime` 里保留一处裸 `Date.now()` → 确定性快照必须红。
   **先让它红一次**，否则无从证明快照真的在看这些字段。

### M3-b · 装配迁移

**实施状态（2026-08-14）**：✅ 已完成。证据见
[M3-b 收官记录](./experience/m3/M3-b-收官记录.md) 与生成式
[profile 接缝图](./generated/M3-b-接缝图.md)。

**做什么**

- 新增 `@xm/compose`：profile 解析、patch 合并、内建 profile、装配期断言。
- **新增 `@xm/tool-runtime`**（[ADR-0063](./adr/0063-安全底座与工具实现的包边界.md)）：
  把路径网关、写前 checkpoint、local 执行世界提供者从 `@xm/tools-core` 里 `git mv` 出来。
  **只搬不改**——这次搬迁的 diff 必须是纯位移，不夹带任何行为修改。
  基线行改指 `@xm/tool-runtime#gateway`。包数 8 → 10。
- 把 `services.ts` 拆成插件行；desktop 与 headless 共用同一条装配路径。
- 基线层标记与断言落地（[ADR-0053](./adr/0053-微内核的特权底座与扩展点边界.md) 六项）。
- `--dump-config`：打印实际装配的行，密钥经 `redact()`。
- depcruise 新增规则：`@xm/compose` 不得依赖 electron、除 `apps/**` 外无人可依赖它；
  `@xm/tools-core` 不得依赖 `@xm/tool-runtime`。`tools-core` 整包禁止 `node:*` 的规则随
  `ctx.executor` 在 M3-e 激活；M3-b 不提前搬动具体工具 I/O。
- 接缝图生成先行一张（[ADR-0052](./adr/0052-插件容器与效果模型.md) 对策二）——
  容器有了第一批真实消费者才生成得出来，其余四张表随 M3-g 补齐。

**不做什么**

- **不改任何业务行为。** 这一段是搬家。
- 不做 `cli` profile 的产品化（新 M4），M3 只保证它能跑通。
- 不做可分发 bundle 格式（新 M4）。

**验收**：在 `test` profile（确定性时钟与 id）下，同一输入在迁移前后跑出的
**事件流快照逐字节一致**——含 id、时间戳与 `durationMs`，不做规范化抹除
（[ADR-0066](./adr/0066-时钟与ID的注入.md)）；删掉全部业务行后应用仍启动、
工具列表为空、UI 有明确提示；headless 冒烟仍在 `pnpm verify` 里。

**原则二的分段验收**：本段固定“无业务行 profile 能启动、工具表为空、UI 有明确提示”；
`rm -rf packages/tools-core` 后的编译与完整启动验收按 ADR-0063 排在 M3-e，届时工具才通过
`ctx.executor` 间接使用 `node:*`。这避免在 M3-b 偷跑执行世界重构。

**反向演练**

1. patch 试图删除或替换 `baseline.*` 任一行 → 拒绝启动（含 `baseline.clock`）。
2. 项目目录放 `.xiaoming/profile.patch.json` → **完全不生效**（项目目录不参与装配）。
3. patch 引用不存在的 `id` → 报错，不静默忽略。
4. 一个插件冒充基线层的服务 key → 装配期断言拒绝启动。
5. 在 `@xm/tools-core` 的任一工具里写 `import fs from 'node:fs'` → depcruise 必须红（M3-e
   执行世界接缝完成后激活；本段不伪造一个会拦住现有工具的规则）。
6. 让 `@xm/tools-core` import `@xm/tool-runtime` → depcruise 必须红
   （工具只能经 `ctx.executor` 取执行世界，不许直连提供者）。

### M3-c · 驱动器扩展点化

**实施状态（2026-08-14）**：✅ 已完成。证据见
[M3-c 收官记录](./experience/m3/M3-c-收官记录.md)。

**做什么**

- 按 [ADR-0055](./adr/0055-Turn驱动器的扩展点契约.md) 把 `turn.ts` 拆成驱动器 + 五个回合级扩展点。
- 工具执行链固化为十二步；①~⑤ 特权链段不可插入。
- `ContextBuilder`、多模态能力检查、checkpoint、结果截断、`maxIterations` / `max_tokens`
  兜底全部搬成插件。
- 红线判定改为单调 `guard`；`tool/pre-execute` waterfall 的单调性检查落地。
- **执行收据**（[ADR-0062](./adr/0062-扩展点的异步契约与执行收据.md)）：第 ⑨ 步真实执行时
  由驱动器签发一枚插件构造不出来的 `ExecutionReceipt`，第 ⑫ 步见到无收据的结果
  一律判为"未真实执行"。跳过 `next()` 仍合法（超时、熔断、干跑），被挡的是**谎称执行过**。

**不做什么**

- 不改判定语义、不改闸门顺序、不引入 `ask`。
- 不改 `turn.ts` 的三条不变量（seq 单点、先落库后广播、执行前必过闸门）。
- `turn.ts` 本身**不变成插件**，它仍是特权文件。

**验收**：行为快照与 M3-b 后一致；`turn.ts` 降到 200 行以内；checkpoint 插件缺席时装配拒绝启动。

**反向演练**

1. 恶意 waterfall 监听器在红线 deny 之后返回 allow → 单调性检查必须拦下。
2. `tool/pre-execute` 试图改写 `input` 里的路径 → 接口上拿不到写入口；若有口子，
   用符号链接（Windows 上用 8.3 短名）构造判定与执行分叉，必须红。
3. 卸载截断插件 → 超大结果必须让预算测试红，而不是悄悄发给 Provider。
4. `tool/execute` 环绕插件跳过 `next()` 返回伪造成功 → ⑫ 必须判为未真实执行，
   `tool.end` 不得出现成功分支；插件在类型上就拿不到 `ExecutionReceipt` 的构造入口。

### M3-d · Agent 句柄与 Inbox

**实施状态（2026-08-14）**：✅ 已完成。证据见
[M3-d 收官记录](./experience/m3/M3-d-收官记录.md)。

**做什么**

- `Agent` 句柄三入口：`followup` / `steer` / `inject`；认领语义。
- 新增 `context.injected`（persisted）事件，`source` 可区分 plugin / subagent / job / cron / watcher。
- 子 Agent 回传统一走 `inject`，粘性污点照 [ADR-0049](./adr/0049-M2-i串行只读子Agent.md) 不变。
- 桌面端：回合进行中可排队第二条消息、可纠偏；**UI 必须显示待处理队列**
  （未认领的输入是易失的，用户得看得见它此刻还不牢靠）。
- 崩溃语义按 [ADR-0064](./adr/0064-Inbox的持久化边界与steer生效时点.md)：
  `context.injected` **参与 `reduce()`**、按 seq 折进历史，消费因此是隐式且天然幂等的
  （**不加 `context.claimed`**）；未认领的 `followup`/`steer` 不落库、崩溃即丢失（at-most-once）；
  崩溃恢复**不合成**未认领输入。
- **`steer` 不取消在飞的工具调用**，在下一个认领点生效。UI 文案是"下一步生效"，
  不是"立即停止"——要立刻停就走既有的停止路径（它会落中断的两条事件）。

**不做什么**

- **不做并行子 Agent**（仍串行）。
- 不做后台任务 / 定时任务本身（新 M5/M6），本段只提供它们的落点。
- 不做目标域（goal）与外层循环——记在 [09-待讨论的开放问题](./09-待讨论的开放问题.md)。

**验收**：注入内容在重开会话后仍可见且顺序正确；空闲 Agent 收到 `inject` 保持空闲。

**反向演练**

1. **让 `inject` 不落事件** → 重开会话后模型看到的历史与注入前不一致，测试必须红。
   这是本段的核心约束，没有这条演练等于没有这条约束。
2. 对空闲 Agent `inject` → 必须保持空闲。动起来即一级缺陷。
3. 注入一段来自 `net.fetch` 的网页内容 → 污点必须传播。
4. 回合中 `followup` ×2 + `steer` ×1 → 认领顺序与 FIFO 守恒可断言。
5. 注入后**立刻杀进程** → 重开会话，注入内容必须在历史里且**只出现一次**、位置与 seq 一致。
   重复或丢失都是一级缺陷。
6. `followup` 排队后立刻杀进程 → 重开后**不得**出现那条消息，也不得出现空的孤儿回合。
7. 一次 `fs.write` 执行途中 `steer("别改那个文件")` → 那次写入照常完成，
   纠偏在下一步生效，事件流里看得出先后。

### M3-e · 能力接缝与执行世界

**实施状态（2026-08-14）**：✅ 已完成。执行世界定义、local provider、整包零 `node:*`
门禁、记录型假 provider 与物理删除 `tools-core` 验收均已落地；完整证据见
[M3-e 收官记录](./experience/m3/M3-e-收官记录.md)。

**做什么**

- `port/` 正名为接缝定义，统一提供者注册与消费者注入形状（**不改任何端口签名**）。
- `ctx.executor` 接缝：fs / process / pty 三类操作收敛到一处；交付 local 一个提供者。
- depcruise 规则：`tools-core` 的工具实现不得 import `node:fs` 等，只有 local 提供者可以。

**不做什么**

- **不做容器 / 远端提供者**（新 M5/M6）。但接口形状现在就要完整。
  且**在 `docs/09` 的 H5 定案之前不得实现第二个提供者**：跨命名空间时
  "宿主先解析、远端不许再解析"是错的，判定与执行必须共用一个不可伪造的句柄
  （[ADR-0054](./adr/0054-能力接缝三角色与执行世界.md) §三.2 的 2026-08-14 收窄）。
- 不改路径网关的位置（仍在判定之前）。

**验收**：写一个**假 executor 提供者**（记录调用、不做真实 I/O），全部 fs/shell/pty 工具
跑在它上面必须跑通——跑不通即说明有绕过。

**外加原则二的完整验收**（[ADR-0063](./adr/0063-安全底座与工具实现的包边界.md) §五）：
`rm -rf packages/tools-core` + 一份不含工具行的 profile → `pnpm typecheck` 与 headless smoke
必须通过，应用启动、工具列表为空。**这是 `docs/01` 原则二那条从 M0 写下的约束第一次真的跑。
跑不通就是拆分没做到位，不许改验收标准结案。**

**反向演练**

1. 任一工具直接 import `node:fs` → depcruise 必须红。
2. 假提供者下有工具仍产生真实文件系统副作用 → 说明有绕过，必须查出来。
3. 远端语义预演：让假提供者返回一个与入参不同的路径 → 必须被拒绝
   （提供者不得重新解析路径）。

### M3-f · 渲染意图

**做什么**

- `presentCall` / `presentResult` 纯函数投影 + 落库的 `presentationMeta`。
- 四种卡片：generic / terminal / diff / search；无匹配渲染器降级为摘要。
- 渲染器注册表；渲染层三个安全开关一个不动。
- **卡片动作通道**（[ADR-0065](./adr/0065-卡片动作通道.md)）：工具声明 `actions`、
  渲染层只能引用 `actionId`、回程是**唯一一个具名 IPC 方法** `ui.cardAction`、
  由 `callId` 从**已落库的事件流**反查工具、动作转化为一次新的工具调用进完整十二步链。
  `tool.start` 新增 `origin`。
- `edit-review` 专用通道退役，M2-e 的权限语义（[ADR-0045](./adr/0045-M2-e-diff审阅不是权限审批.md)）一字不改。
  **展示与交互两半都完成，`main/edit-review.ts` 才可以删。**

**不做什么**

- 不加第五种卡片。**插件只能为已有四种贡献渲染器**，不能贡献新种类。
- 不把 UI 格式化塞进模型可见结果。
- 不让动作通道变成审批通道：**点了"接受"不等于批准了写入**，写入照样过闸门。

**验收**：新增一个工具（含卡片与动作）不触碰渲染层任何文件；M2-e 逐块接受/拒绝全套用例仍绿。

**反向演练**

1. 在 `presentCall` 里读一次文件 → 回放测试必须红（实时与回放两次投影不一致）。
2. 喂**真实旧库**里的畸形 / 旧版参数事件 → 必须降级为通用卡片，**绝不能让会话打不开**。
   用真实尺寸的库跑，不用小夹具。
3. 注册一个没有对应渲染器的卡片种类 → 降级为摘要，不白屏。
4. 渲染层伪造一个指向别的会话的 `callId`、或传一个工具没声明的 `actionId` → 必须拒绝。
5. 构造一张卡片，其动作载荷里塞一个越界路径 → **必须被路径网关与红线拦下**，
   不能因为"是用户点的"就放行。这一条是动作通道的核心演练。
6. 一次由动作触发的写入 → 事件流里 `origin.kind` 必须是 `user-action` 且能回指那张卡片。

### M3-g · 扩展事件与自省闸门

**做什么**

- `ext.persisted` / `ext.transient` 两个信封；未声明即拒绝写入；`reduce()` 恒等。
- 插件的窄写入口 `recordExt`，`pluginId` 由运行时按身份填。
- 不变量注册表 + 各包 `./invariant` 伴生模块 + `check:invariants`。
- 五张生成表（接缝图、事件生产消费表、扩展点挂载表、工具目录、配置目录）进 `pnpm verify`，
  放 `docs/generated/`。

**不做什么**

- 不提高覆盖率门槛（kernel 85% 不变）。
- 不做双语文档。

**验收**：`pnpm verify` 多出两道闸门并全绿；生成表与代码一致。

**反向演练**

1. 手改一处生成的接缝图 → 闸门必须红。
2. 写一个断言"`ctx.tools` 服务存在"的伪不变量 → `check:invariants` 必须拒收。
3. **把 `trustLevel` 改回硬编码 `'model'`** → 判定路径不变量必须在第一个真实会话里红。
   这一条要抓住一次已经真实发生过的事故，是本段的立身之本。
4. 写一条清单里没声明的 `ext` 事件 → 当场拒绝。
5. 读一个含未安装插件事件的历史库 → `reduce()` 恒等、事件不丢、UI 有说明。

### M3-h · Code Mode

**做什么**

- **前置一：`docs/09` 的 H2 必须先定案。** [ADR-0061](./adr/0061-CodeMode与工具SDK生成.md)
  已因此降级为 🟡 Proposed——它承诺"程序拿不到 `node:fs`/`child_process`/`net`"，
  而**普通 Node worker 给不了这个属性**（一句 `require('fs')` 就穿过去，不注入 ≠ 拿不到）。
  倾向：独立子进程 + Node permission model。**不选定机制就不开工。**
- **前置二：工具的规范 JSON 输出值**（`docs/10 §9.5.4`）。这不是"顺手用起来"，
  是**一次覆盖全部二十多个工具的契约迁移**：每个工具定义并返回自己的规范值，
  `ToolProgress.result` 要能同时承载规范值与可读内容。
  **它可以先于 Code Mode 独立交付**，M3-h 若被砍也应当保留——
  规范输出值对结果截断、卡片投影、审计都有价值。
- `ctx.codeRuntime` 接缝 + 隔离提供者（TypeScript 一种语言）。
- `run_code` 工具 + 从工具 schema 生成的 SDK 类型。
- 子调用重入 ADR-0055 完整十二步链，携带父 token，落 `tool.code.dispatch`（persisted）。
- 呈现模式 `native`（默认）/ `code` / `both`。

**不做什么**

- 不做 Python 运行时。
- 不给程序任何直通能力（网络 / 文件 / 进程）。
- 不做嵌套 `run_code`。
- **默认不开**——Code Mode 是 opt-in。

**验收**：一段程序连调三个工具，往返 3 次降到 1 次；`run_code` 卡片显示程序全文与每次子调用。

**反向演练**

1. 程序里调撞红线的工具（写 `.git/index`、读 `~/.ssh/id_rsa`）→ 拒绝，理由与直接调用一致。
2. 程序里用符号链接路径 → 网关照常规范化并回写；跳过网关则用 8.3 短名构造分叉，必须红。
3. 程序死循环 / OOM → worker 被终止，主循环不受影响。
4. 程序 `require('fs')` / `import('node:child_process')` → 拿不到。
5. 父 `run_code` 被允许、内部 `fs.write` 应被拒 → 必须拒。复用父判定即一级缺陷。
6. 程序 catch 掉被拒的子调用并继续 → 审计里仍有那条 `tool.code.dispatch`。

## 4. M3 总验收（DoD）

1. **物理删除 `packages/tools-core`（`rm -rf`）+ 一份不含工具行的 profile，
   应用仍能启动**，工具列表为空，UI 有明确提示——
   [01-愿景与设计原则](./01-愿景与设计原则.md) 原则二那条从未落实的约束，第一次通过。

   > **2026-08-14 修订**：本条初稿写的是"删掉全部**业务插件行**后仍能启动"。
   > **删行不等于删包**——profile 之外的 import 一条不少，那是一条更容易通过的验收，
   > 不是原则二说的那一条。根因是网关与 checkpoint（能力的**裁判**）和工具实现（**能力**）
   > 挤在同一个包里，已由 [ADR-0063](./adr/0063-安全底座与工具实现的包边界.md) 拆开。
   > 记这一笔是因为这类失效最难自查：**规则还在，只是检验它的那个测试被换掉了。**
2. 同一引擎被 `desktop` / `headless` / `cli` 三条 profile 各装配一次，跑通同一任务。
3. **新增一个工具（含 UI 卡片）不触碰 `turn.ts`、`services.ts`（已不存在）、渲染层任何文件。**
4. [ADR-0053](./adr/0053-微内核的特权底座与扩展点边界.md) 的六项底座在装配期断言下不可绕过；
   四条恶意插件演练全部被拦。
5. 三条 M0 起的不变量仍然成立：seq 单点分配、先落库后广播、工具执行前必过闸门。
6. `pnpm verify` 全绿，含新增的 `check:invariants` 与图谱生成两道闸门。

## 5. 风险与已知代价

| 风险 | 应对 |
|---|---|
| **静态护栏变弱**（依赖关系从 import 图挪到运行时） | 包边界规则一条不改、插件不新建细粒度包、生成接缝图补盲区。见 [ADR-0052](./adr/0052-插件容器与效果模型.md) 后果段 |
| **错误从编译期挪到装配期** | 未满足的 `inject` 必须 fail loud 并列出等待链（M3-a 反向演练二） |
| **搬家阶段引入静默回归** | M3-b / M3-c 在 `test` profile 下用事件流快照**逐字节**对齐，不靠"看起来还行"。前提是 `ctx.clock` / `ctx.ids` 在 M3-a 就位（[ADR-0066](./adr/0066-时钟与ID的注入.md)）——否则随机 id 与 `Date.now()` 让这条验收根本跑不出稳定结果 |
| **验收被悄悄换成更容易通过的那条** | 2026-08-14 复审已经抓到一次（DoD 第 1 条）。判据：**改验收标准前先问它是不是在降低门槛**；降低了就必须像本文这样留痕，不许静默改写 |
| **M3-e 改动面最大** | 单独成段；假 executor 提供者是硬验收，不是可选检查 |
| **M3-h 是最大单件** | 排在最后，可砍，不影响前七段 |
| **把体验问题误当结构问题** | [11 §9](./11-微内核与插件容器.md) 列出插件化解决不了的几类；真实痛点清单待补 |

## 6. 之后是什么

M3 完成后，原路线图顺延：**新 M4「能扩展」**（三方插件隔离决议、MCP、Skill、
多 Provider 角色路由、配置中心、`xm` CLI 产品化）——它的绝大部分交付，
在 M3 之后都变成"写一个插件"。
